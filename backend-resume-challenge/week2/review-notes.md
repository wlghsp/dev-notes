## 보완할 점 (다음 주차부터 적용)

### 1. k6 스크립트의 `cursor=`(빈 값)가 개선 전 조건과 완전히 동일한지 불명확

- 문제: `baseline.js`에서 개선 후 요청이 `${BASE}/api/studies?cursor=&size=20`처럼 `cursor`를 빈 문자열로 보내는데, 서버에서 `Long cursor`가 null로 파싱되는지 빈 문자열로 파싱 실패하는지가 코드만 봐서는 명확하지 않음
- 원인: 개선 전 `page=0`은 명시적 값이었는데, 개선 후엔 "생략"과 "빈 값"을 구분하지 않고 빈 값으로 처리함
- 다음 주차 적용: 쿼리 파라미터를 아예 생략하거나 값을 명시(`cursor=0`)해서 "이 요청이 정확히 무슨 조건을 재는지" 코드만 보고도 알 수 있게 작성. 재측정 스크립트를 작성할 때 개선 전/후 조건이 진짜 1:1로 대응하는지 한 번 더 점검

### 2. 병목 판단에서 "어느 쿼리가 원인인지"는 못 밝힘 (본인도 인정한 한계)

- 문제: CPU가 가장 먼저 반응했다는 결론은 지표로 뒷받침되지만, count 쿼리와 OFFSET 스캔 중 무엇이 CPU를 더 소비했는지는 특정하지 못함
- 원인: 이번 주차 도구(Prometheus/Grafana, k6)로는 자원 사용량 총합만 보이고 쿼리별 비용까지는 안 보임 — 애초에 이번 주차 범위 밖(3주차 EXPLAIN 영역)
- 다음 주차 적용: EXPLAIN이나 slow query log로 실제로 어느 쿼리가 비용을 쓰는지 직접 확인. 리뷰가 "다음 행동"으로 명시적으로 짚어준 부분이라 3주차에 우선순위로 다룰 것

### 3. "리뷰 반영" 섹션은 3주차 evidence에서 채운다

- 상태: 2주차 evidence의 "자동 리뷰 수신 전"은 PR 제출 시점엔 정상적인 문구였음(리뷰를 받기 전이니 반영할 내용이 없었던 게 맞음). 2주차는 이미 제출이 끝난 상태라 되돌려서 고치지 않고, "1주차 지적을 2주차에서 어떻게 반영했는가" + "2주차 지적(이 문서)을 3주차에서 어떻게 반영했는가"를 3주차 evidence의 "리뷰 반영"에 함께 기록한다
- 3주차에 적을 내용:
  - 1주차 지적 1(리뷰 반영 섹션 비워둠) → 2주차에서도 제출 시점엔 동일하게 비워둔 채 제출함(정상), 이 문서(review-notes.md)로 사후 분석은 남김
  - 1주차 지적 2(테스트가 검증하는 로직을 소스 코드로 같이 보여주기) → 2주차 evidence에서 `findByIdGreaterThanOrderByIdAsc` 메서드명은 언급했으나 실제 코드 스니펫은 인용 안 함 — 아직 미반영. 3주차부터는 신규 테스트 추가 시 검증 대상 로직을 코드 스니펫으로 함께 인용할 것
  - 1주차 지적 3(확인 불가 값을 실측값으로 교체) → resume.md 문장 1의 "한계"를 2주차 k6 실측값으로 교체 완료 — 반영됨
  - 2주차 지적(이 문서의 1, 2번) → 3주차 진행 시 반영 여부를 확인하고 기록
