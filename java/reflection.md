# Reflection

실행 중인 프로그램이 자기 자신의 구조(클래스, 필드, 메서드)를 코드로 조사하고 조작할 수 있게 해주는 자바 API다. 스프링과 Hibernate가 사용자 클래스를 다루는 방식의 근간이 되는 메커니즘이라 annotation-processing.md에서도 이미 등장한다.

## 평소 코드: 컴파일 시점에 모든 게 확정된다

```java
Member m = new Member();
m.setEmail("a@test.com");
```

이 코드를 컴파일할 때 컴파일러는 `Member` 클래스에 `setEmail`이라는 메서드가 실제로 존재하는지, 파라미터 타입이 `String`이 맞는지를 컴파일 시점에 전부 확인한다. 없는 메서드를 호출하면 컴파일 자체가 안 된다. "어떤 필드에 어떤 값을 넣을지"가 소스 코드 작성 시점에 이미 문자 그대로 박혀 있는 방식이다.

## Reflection: 실행 시점에 이름만으로 접근한다

Reflection은 이 접근 방식을 뒤집는다. 컴파일 시점엔 어떤 필드인지 몰라도, 실행 중에 "이름이 email인 필드를 찾아서 값을 넣어라"는 식으로 동작시킬 수 있다.

```java
Class<?> clazz = Class.forName("com.example.Member");
Object instance = clazz.getDeclaredConstructor().newInstance();

Field field = clazz.getDeclaredField("email");
field.setAccessible(true);
field.set(instance, "a@test.com");
```

여기엔 `Member`나 `email`이라는 이름이 소스 코드에 문자열로만 등장한다. 컴파일러는 이 문자열이 실제로 존재하는 클래스/필드인지 검증하지 않는다. 존재하지 않으면 컴파일은 성공하고 실행할 때 `NoSuchFieldException`이 터진다. "무엇을 다룰지"를 컴파일 시점이 아니라 런타임에 동적으로 결정한다는 게 핵심이다.

## 왜 프레임워크에 필요한가

스프링 컨테이너는 사용자가 만들 클래스가 뭔지, 그 안에 어떤 필드가 몇 개 있는지 컴파일 시점에 전혀 모른다. 스프링이라는 프레임워크는 사용자의 코드보다 먼저 컴파일되어 jar로 배포되기 때문이다. 그런데도 스프링은 실행 중에 사용자 클래스를 스캔해서 "이 필드에 `@Autowired`가 붙어 있으니 값을 채워 넣어야겠다"는 걸 해내야 한다.

이걸 가능하게 하는 게 Reflection이다. 스프링 입장에서 사용자 클래스는 실행 시점에야 `Class` 객체로 처음 마주치는 미지의 대상이고, Reflection API로 그 구조(필드 목록, 붙어 있는 어노테이션)를 읽어내고, 다시 Reflection API로 private 필드에도 값을 강제로 넣는다. annotation-processing.md에서 `AutowiredAnnotationBeanPostProcessor`가 하는 일이 정확히 이것이다.

## 대가: 타입 안전성과 성능을 잃는다

첫째, 타입 안전성이 사라진다. 평소 코드는 컴파일러가 오타나 잘못된 타입을 미리 잡아주지만, Reflection으로 `getDeclaredField("emial")`처럼 문자열 오타를 내면 컴파일은 통과하고 실행할 때야 예외가 터진다. 실수를 발견하는 시점이 컴파일 시점에서 런타임으로 밀린다.

둘째, 느리다. 일반 메서드 호출은 JVM이 컴파일 시점부터 알고 있는 고정된 주소로 바로 뛰어가지만, Reflection 호출은 이름으로 메서드를 찾고 접근 권한을 확인하고 파라미터 타입을 맞춰보는 과정을 거친 뒤에야 실행된다. 그래서 스프링은 이 비용을 감당하기 위해 애플리케이션 시작 시점에 한 번만 리플렉션으로 스캔한 결과를 캐싱해두고, 이후엔 캐싱된 정보를 재사용하는 식으로 비용을 최소화한다.

## 요약

Reflection은 "컴파일 시점에 이름과 타입을 다 알고 코드를 짜는" 자바의 기본 방식과 반대로, "실행 중에 이름만 갖고 클래스/필드/메서드를 찾아서 다루는" 능력이다. 프레임워크가 사용자 코드를 미리 알지 못한 채로도 그 구조를 들여다보고 조작해야 하는 상황(의존성 주입, ORM 매핑, 어노테이션 처리)에서 이게 필수인 이유는, 프레임워크 입장에선 사용자 클래스가 항상 컴파일 시점엔 존재조차 몰랐던 대상이기 때문이다.
