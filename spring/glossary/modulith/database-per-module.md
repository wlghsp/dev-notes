# 모듈별 데이터베이스 분리 (Database per Module)

모듈러 모놀리스에서 각 모듈이 자신만의 데이터베이스 스키마(또는 별도 데이터베이스)를 갖게 하는 설계 원칙이다.

## 왜 필요한가

여러 모듈이 하나의 공유 데이터베이스를 쓰면, 애플리케이션 코드 수준에서는 모듈 경계를 아무리 엄격하게 그어도 데이터베이스 계층에서 경계가 무너진다.
`order` 모듈이 `inventory` 모듈의 테이블을 직접 조인하거나 조회하는 SQL을 짜면, 코드에는 모듈 경계가 있는 것처럼 보여도 실질적으로는 데이터가 뒤엉킨 하나의 덩어리다.
이렇게 되면 나중에 특정 모듈만 별도 서비스로 분리하려 할 때, 어디까지가 그 모듈의 데이터인지 구분하는 작업부터 다시 해야 한다.

## 적용 방식

가장 느슨한 형태는 하나의 물리적 데이터베이스 안에서 모듈별로 스키마(User schema, Catalog schema, Order schema 등)를 나누는 것이다.
테이블은 물리적으로 같은 데이터베이스 인스턴스에 있지만, 스키마 경계를 넘어서는 조인이나 참조를 하지 않기로 규약을 정한다.
더 엄격한 형태는 모듈마다 물리적으로 별도의 데이터베이스 인스턴스를 두는 것인데, 이러면 애초에 다른 모듈의 테이블에 SQL로 접근하는 것 자체가 불가능해진다.

## 모듈러 모놀리스와 MSA의 중간 지점

모듈별로 스키마를 나누는 것은 모듈러 모놀리스가 MSA의 이점을 일부 미리 가져오는 방법이다.
애플리케이션은 여전히 하나의 배포 단위(단일 프로세스)로 묶여 있지만, 데이터 소유권만큼은 이미 모듈별로 명확히 분리돼 있는 상태가 된다.
그래서 나중에 특정 모듈을 실제로 별도 서비스로 떼어낼 때, 데이터베이스 분리 작업은 이미 끝나 있고 애플리케이션 프로세스만 나누면 되는 상황이 만들어진다.

## 실무적 트레이드오프

모듈별로 데이터베이스를 나누면 모듈 간에 트랜잭션을 하나로 묶기가 어려워진다.
예를 들어 주문 생성과 재고 차감을 하나의 데이터베이스 트랜잭션으로 묶던 것을, 스키마가 분리되면 더 이상 단순한 로컬 트랜잭션으로 처리할 수 없게 될 수 있다.
그래서 이 원칙을 어디까지 엄격하게 적용할지는 모듈 간에 강한 트랜잭션 일관성이 실제로 필요한지 여부에 따라 판단해야 한다.
이 판단 기준은 event-driven-suitability.md에서 다루는 즉시성·트랜잭션 일관성 기준과 같은 맥락에 있다.
