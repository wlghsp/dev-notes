# cdc-idempotent-consumer

**"CDC가 At-Least-Once로 중복 발행한 이벤트를, 소비자가 여러 번 받아도 결과가 같도록 처리하는 설계 패턴"**

cdc.md에서 CDC는 기본적으로 At-Least-Once이고 중복 처리 방법이 두 가지(멱등 설계, 중복 제거)라고 정리했다. 여기서는 그중 멱등 설계를 실제로 어떻게 구현하는지를 다룬다.

---

## 왜 필요한가

debezium-offset-recovery.md에서 본 것처럼, offset 커밋 전에 Task가 죽으면 이미 발행된 이벤트가 재시작 후 다시 발행된다. 소비자가 이 중복 이벤트를 그대로 처리하면 부작용이 생긴다.

```
정상 케이스: INSERT 이벤트 1번 처리 → 재고 -1
중복 케이스: 같은 INSERT 이벤트 2번 처리 → 재고 -2 (잘못됨)
```

멱등 소비자는 같은 이벤트가 여러 번 들어와도 결과가 한 번 처리한 것과 같아지도록 만든다.

---

## 패턴 1 — Upsert로 치환

CDC 이벤트를 "변화량 적용"이 아니라 "최종 상태 반영"으로 처리하면 중복 자체가 문제되지 않는다.

```
INSERT 이벤트 (id=1, amount=100)
  → "id=1의 amount를 100으로 UPSERT"
  → 같은 이벤트가 두 번 와도 결과는 amount=100으로 동일
```

재고 차감처럼 "이전 값 - 1"이 아니라, 이벤트의 `after` 상태를 그대로 목적 테이블에 UPSERT하는 방식이다. Elasticsearch 색인이나 캐시 갱신처럼 최종 상태만 중요한 경우에 잘 맞는다. 반대로 "차감/증가" 같은 변화량 자체가 의미 있는 경우(예: 이벤트 기반 카운터 증분)에는 이 패턴을 그대로 쓸 수 없다.

---

## 패턴 2 — 이벤트 ID 기반 중복 제거

이벤트마다 고유 식별자를 부여하고, 소비자가 처리한 ID를 별도로 기록해서 재처리 여부를 판단한다.

Debezium 이벤트는 binlog 파일명+position, 또는 GTID를 이벤트 메타데이터에 포함한다. 이를 멱등 키로 쓸 수 있다.

```
이벤트 수신 (offset: mysql-bin.000123:5000)
  → 이미 처리한 offset 목록에 있는가?
     있음 → 스킵
     없음 → 처리 후 offset을 처리 완료 목록에 기록
```

이 방식은 "처리"와 "처리 완료 기록"이 원자적이어야 한다. 둘이 분리되면 그 사이에 죽었을 때 또 다른 중복/유실 창구가 생긴다. 그래서 보통 같은 트랜잭션 안에서 대상 테이블 갱신과 처리 완료 offset 기록을 함께 커밋한다.

---

## 패턴 3 — DB 유니크 제약으로 자연스럽게 멱등화

목적 테이블에 이벤트의 고유 키(PK 또는 이벤트 ID) 기준 유니크 제약을 걸어두면, 중복 INSERT는 DB가 거부하거나(에러 처리 후 무시) `INSERT ... ON DUPLICATE KEY UPDATE`로 흡수된다.

패턴 1(Upsert)과 함께 쓰이는 경우가 많다. UPSERT 자체가 유니크 키 충돌을 전제로 동작하기 때문이다.

---

## 어떤 패턴을 고를지 가르는 기준

핵심 변수는 이벤트가 "최종 상태 반영"으로 충분한가, 아니면 "변화량 자체"가 의미를 가지는가다. 전자면 패턴 1(Upsert)이 구현이 가장 단순하고 별도 상태 저장이 필요 없다. 후자라면 패턴 2(이벤트 ID 기반 중복 제거)가 필요하고, 처리와 offset 기록의 원자성 확보가 설계의 핵심이 된다.

---

## 한 줄 요약

> 멱등 소비자는 CDC의 At-Least-Once 중복을 이벤트 자체(Upsert)나 이벤트 ID 추적으로 흡수해서, 같은 이벤트를 여러 번 받아도 한 번 처리한 것과 동일한 결과를 만든다.
