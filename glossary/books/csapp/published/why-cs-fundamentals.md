# 왜 컴퓨터 구조, OS, Database인가

## 셋은 하나로 묶여있다

- **컴퓨터 구조** — 하드웨어가 어떻게 생겼는가. CPU, 레지스터, 캐시, MMU, 버스
- **OS** — 그 하드웨어를 어떻게 추상화하는가. 프로세스, 가상 메모리, 파일
- **Database** — 그 추상화 위에서 데이터를 어떻게 안전하고 빠르게 다루는가. 트랜잭션, B-Tree, WAL

각각 따로 공부하면 "이게 왜 이래?" 하는 순간이 계속 나온다. 셋을 같이 알면 연결이 된다.

MMU가 없으면 가상 메모리가 없고, 가상 메모리가 없으면 프로세스 격리가 없고, 프로세스 격리가 없으면 안전한 멀티태스킹이 없다. Database의 buffer pool이 빠른 이유도 결국 메모리 계층 구조(CPU 캐시 → RAM → 디스크)를 이해해야 납득된다.

밑바닥부터 쌓아야 위가 흔들리지 않는다.

## 수십 년간 검증된 답이다

이 셋은 수십 년간 수천 명의 엔지니어가 가장 어려운 문제들과 싸워온 결과물이다.

- 느린 하드웨어를 어떻게 빠르게 쓸 것인가
- 여러 사람이 동시에 접근할 때 어떻게 일관성을 유지할 것인가
- 시스템이 죽어도 데이터를 어떻게 잃지 않을 것인가
- 복잡한 것을 어떻게 단순하게 보이게 할 것인가

그냥 동작하는 코드가 아니라, 수많은 실패와 트레이드오프를 거쳐서 살아남은 설계들이다.

## 모든 현대 시스템은 여기서 나왔다

Kafka, Redis, JVM, Kubernetes, PostgreSQL — 현대의 거의 모든 인프라와 미들웨어는 이 셋이 수십 년간 다뤄온 문제를 다시 푸는 것이다.

- Kafka가 왜 디스크에 순차 쓰기를 하는가 → OS의 page cache와 I/O 원리
- Redis가 왜 싱글 스레드인가 → 동시성 문제와 락 비용
- JVM GC가 왜 그렇게 복잡한가 → 메모리 관리와 단편화
- Kubernetes가 왜 swap을 끄는가 → 가상 메모리와 OOM
- PostgreSQL MVCC가 왜 그렇게 동작하는가 → 트랜잭션 격리와 동시성 제어

새로운 기술을 배울 때 "어떻게 쓰는가"만 아는 사람과 "왜 이렇게 설계됐는가"를 아는 사람은 다르다. 후자는 문서를 안 봐도 동작을 예측할 수 있고, 장애가 났을 때 원인을 찾는 속도가 다르다.

## 반복되는 핵심 주제들

이 셋이 수십 년간 씨름해온 문제들이 있다.

**캐싱** — 느린 것(디스크, 네트워크)을 빠른 것(메모리, CPU 캐시) 앞에 두는 것. CPU의 TLB, OS의 page cache, Database의 buffer pool — 전부 같은 원리다.

**동시성** — 여러 주체가 같은 자원에 동시에 접근할 때 어떻게 올바름을 보장할 것인가. OS의 스케줄러, Database의 트랜잭션 격리, JVM의 synchronized — 전부 같은 문제다.

**내구성** — 시스템이 죽어도 데이터를 잃지 않는 것. Database의 WAL(Write-Ahead Log), OS의 fsync — 같은 원리다.

**추상화** — 복잡한 것을 감추고 단순한 인터페이스를 제공하는 것. 프로세스, 가상 메모리, 파일, 트랜잭션 — 전부 추상화다.

이 주제들을 제대로 이해하면, 어떤 새로운 시스템을 만나도 "이건 결국 캐싱 문제네", "이건 동시성 문제네" 하고 빠르게 본질을 파악할 수 있다.

## 뛰어난 엔지니어와 그냥 엔지니어의 차이

기능을 구현하는 엔지니어는 많다. 프레임워크 쓰는 법, API 호출하는 법은 문서 보면 누구나 할 수 있다.

차이는 시스템이 왜 그렇게 동작하는지를 아는 것에서 난다.

- 왜 이 쿼리가 느린가
- 왜 이 서버가 갑자기 응답을 못 하는가
- 왜 이 설계가 스케일이 안 되는가
- 이 트레이드오프에서 무엇을 선택해야 하는가

이 질문들에 답할 수 있는 사람은 컴퓨터 구조, OS, Database를 깊이 이해한 사람이다. 새로운 기술을 빠르게 배우는 사람이 아니라, 어떤 문제든 원리부터 파고드는 사람.
