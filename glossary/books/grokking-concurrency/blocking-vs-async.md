# blocking-vs-async

스레드가 I/O를 기다리는 방식의 두 가지 모델. 스레드 풀이 언제 한계에 부딪히는지 이해하는 데 필요한 개념이다.

## 블로킹(blocking)이란

스레드가 어떤 작업의 결과를 기다리는 동안 아무것도 못 하는 상태. 실처럼 생각하면 된다. 실 하나가 DB 응답을 기다리는 동안은 그 실이 묶여 있다. 다른 일을 시킬 수 없다.

```
스레드 A: [요청 전송] ---30초 대기--- [응답 수신] [처리]
                          ↑
                     이 구간 동안 스레드 A는 아무것도 못 함
```

## 스레드 풀에서 블로킹이 문제가 되는 이유

스레드 풀은 스레드 수가 고정되어 있다. 예를 들어 10개.

상황:
- 외부 API 응답이 평균 30초 걸린다
- 요청이 동시에 10개 들어온다

결과:
- 스레드 10개 모두 30초 동안 대기 상태에 묶인다
- 11번째 요청이 오면 큐에서 대기한다 — 스레드가 풀릴 때까지
- 스레드 풀이 사실상 마비된 것과 같다

핵심은 스레드가 대기하는 동안에도 OS 자원(메모리, 컨텍스트)을 점유한다는 것이다. 일은 안 하면서 자리만 차지하는 상황이다.

## 비동기(async)란

스레드가 작업을 요청만 해두고, 결과가 나올 때 알림을 받는 방식. 기다리는 동안 스레드를 놓아준다.

```
스레드 A: [요청 전송] [다른 일 처리] ... [응답 도착 알림] [처리]
                        ↑
                   이 구간 동안 스레드 A는 다른 태스크를 처리할 수 있음
```

스레드 10개가 있어도 수백 개의 I/O 대기를 동시에 처리할 수 있는 이유가 이것이다. 스레드가 블로킹되지 않고 계속 다른 일을 하기 때문이다.

## 언제 어떤 모델이 맞는가

블로킹 + 스레드 풀이 잘 맞는 경우:
- 태스크가 CPU를 실제로 쓰는 경우 (계산, 압축, 암호화)
- 각 태스크가 빠르게 끝나는 경우
- 블로킹 대기 시간이 짧은 경우

비동기 모델이 더 맞는 경우:
- 외부 API, DB, 파일 I/O처럼 대기 시간이 긴 작업이 많은 경우
- 동시 연결 수가 스레드 수보다 훨씬 많아야 하는 경우 (예: 수천 개의 웹소켓)

Java에서는 CompletableFuture, Spring WebFlux, 코틀린 코루틴이 비동기 모델을 쓴다. Node.js는 처음부터 비동기 이벤트 루프 기반이다.

## 순차 연산과 블로킹은 다른 이야기다

"순차 연산 → 스레드 풀 불리"라고 생각하기 쉬운데, 이 둘은 별개다.

- 순차 연산이라도 각 태스크가 빠르게 끝나면 스레드 풀이 잘 동작한다
- 스레드 풀이 힘든 건 "대기 시간이 길다"는 것이지, "태스크 내부가 순차적이다"는 게 아니다

태스크 내부가 순차인 것은 문제가 없다. 그 순차 연산이 스레드를 오래 잡고 있는지가 문제다.
