# character-encoding

문자 인코딩은 문자 집합(character set)의 각 문자를 숫자 코드에 대응시키는 규칙이다. 컴퓨터는 비트만 저장할 수 있기 때문에, 텍스트를 다루려면 반드시 이 규칙이 필요하다.

## 왜 여러 표준이 존재하는가

ASCII는 7비트 코드다. 영어권에서는 충분했지만 두 가지 문제가 있었다.

**첫 번째: 영어 이외의 문자**
ASCII에는 영국 파운드 기호(£)도, 프랑스어 악센트(é, à)도, 그리스 문자도 없다. 한국어, 중국어, 일본어 한자는 수만 가지에 달해서 7비트는 물론 8비트로도 모자란다.

**두 번째: 8비트 확장의 혼란**
ASCII는 7비트지만 실제로는 8비트 바이트에 저장된다. 남는 상위 1비트를 활용해서 128개를 추가하면 256개의 코드를 쓸 수 있다. 문제는 이 확장 영역(80h~FFh)을 각 나라, 각 회사가 제각각 다르게 정의했다는 것이다. 같은 코드 값이 서로 다른 문자를 가리키게 됐다. EBCDIC(IBM이 자체 개발한 인코딩)은 ASCII와 완전히 다른 배치를 썼다.

## 인코딩 방식의 진화

**Baudot (5비트, 1874)**
전신 시대의 코드. 5비트로 32가지만 표현할 수 있어서 shift 코드(Figure Shift / Letter Shift)를 사용해 같은 코드가 문자 모드냐 숫자 모드냐에 따라 다른 의미를 가졌다. 대소문자 구분 없음. 상태에 따라 해석이 달라지므로 중간에 신호가 끊기면 이후 전체가 오독된다.

**ASCII (7비트, 1967)**
Baudot의 shift 문제를 해결한다. 대문자와 소문자에 각각 고유한 코드를 부여했다. 256개 이하의 문자를 쓰는 언어에는 8비트 확장으로 대응했다.

**Unicode (16비트, 1988~)**
전 세계 언어를 하나의 코드 체계로 통합하려는 시도다. 처음 128개 코드(0000h~007Fh)는 ASCII와 동일하다. 65,536가지를 표현할 수 있어서 세계 대부분의 언어를 수용한다.

Unicode의 실질적인 문제는 하나의 문자가 항상 2바이트라는 점이다. ASCII로 저장하면 1MB인 문서가 Unicode로 저장하면 2MB가 된다. 또 1문자 = 1바이트라는 기존 코드와의 호환성이 깨진다.

## 핵심 개념: shift code의 문제

Baudot처럼 상태에 의존하는 인코딩은 맥락이 바뀌면 이후 전체 해석이 틀어진다. ASCII가 각 문자에 고유 코드를 준 이유가 여기 있다. 상태를 추적할 필요 없이 각 바이트를 독립적으로 해석할 수 있다.

점자(Braille)도 같은 문제를 가졌다. 대문자 표시자나 숫자 표시자 코드 다음에 오는 코드는 그 앞의 shift 코드에 따라 의미가 달라진다. 참고: braille-binary.md, code-reuse.md
