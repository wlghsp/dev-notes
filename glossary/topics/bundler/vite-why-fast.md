# Vite는 왜 빠른가

Vite가 빠르다고 할 때는 두 가지를 구분해야 한다: **개발 서버 구동/HMR 속도**와 **프로덕션 빌드 속도**. 각각 이유가 다르다.

## 개발 서버가 빠른 이유 — 번들링을 생략한다

Webpack 같은 기존 번들러는 개발 서버를 켤 때도 앱 전체를 미리 번들링한다. 파일이 1000개면 1000개를 다 묶은 후에야 서버가 뜬다. 앱이 커질수록 이 초기 구동 시간이 선형적으로 늘어난다.

Vite는 이 과정을 생략한다. 대신 **브라우저의 native ES Module 로딩**을 그대로 활용한다 (참고: esm.md).

```
Webpack 방식:
  전체 소스 → [번들링] → 하나의 큰 bundle.js → 브라우저 로드
  (번들링 단계가 요청 이전에 끝나야 함 → 느린 초기 구동)

Vite 방식:
  브라우저가 <script type="module">로 진입점을 요청
    → import 문을 만나면 그 파일만 개별 요청
      → 그 파일의 import를 만나면 또 개별 요청
        → 필요한 파일만, 필요한 시점에 로드
```

즉 Vite의 개발 서버는 "전체를 미리 묶어서 주는" 게 아니라 "브라우저가 요청하는 모듈을 그때그때 변환해서 던져주는" 구조다. 앱 전체 크기와 무관하게, **현재 화면에 필요한 모듈만** 처리하면 되므로 앱이 아무리 커도 초기 구동 속도가 거의 일정하다.

## 의존성(node_modules)은 예외 — esbuild로 미리 번들링

`node_modules`의 패키지들(예: lodash, react)은 파일 수가 매우 많고 CJS로 작성된 것도 섞여 있다. 이걸 매번 개별 요청하면 오히려 느려진다.

그래서 Vite는 서버 시작 시 **의존성만** `esbuild`로 미리 번들링해서 캐싱해둔다. esbuild는 Go로 작성되어 JS 기반 번들러(Webpack, Rollup)보다 수십~수백 배 빠르다.

```
앱 소스 코드      → 번들링 없이 native ESM으로 그대로 서빙
node_modules 의존성 → esbuild로 사전 번들링 (한 번만, 이후 캐시 재사용)
```

## HMR(Hot Module Replacement)이 빠른 이유

파일 하나를 수정했을 때, Webpack은 그 파일이 포함된 번들 전체를 다시 계산해야 할 수 있다. Vite는 **수정된 모듈 하나만** 무효화하고 브라우저에 그 모듈만 다시 요청하게 만든다. 모듈 그래프에서 변경된 노드 하나만 교체하는 것이므로 앱 크기와 무관하게 갱신 속도가 일정하다.

## 프로덕션 빌드가 빠른(빨라진) 이유

개발 중에는 번들링을 생략하지만, 실제 배포용 빌드에서는 번들링이 필요하다 (수백 개의 개별 파일을 그대로 배포하면 실제 네트워크 요청이 너무 많아짐). 이 단계에서 Vite는 **Rollup**을 사용한다.

- Rollup은 ESM 기반 정적 분석에 강해서 tree shaking 품질이 좋다 (참고: esm.md)
- Vite 5+ 버전대에서는 빌드 단계에도 esbuild를 일부 활용해 트랜스파일 속도를 높인다

즉 "개발 = native ESM 서빙", "빌드 = Rollup 번들링"으로 단계를 분리한 것이 Vite의 핵심 설계다. 개발 중에는 번들링 자체가 필요 없다는 점을 이용해 그 비용을 아예 없앤 것이 속도의 근원이다.

## 요약

| 단계 | Webpack | Vite |
|---|---|---|
| 개발 서버 구동 | 전체 사전 번들링 필요 | 번들링 생략, native ESM 서빙 |
| 의존성 처리 | 번들 포함 | esbuild로 사전 번들링 (캐시) |
| HMR | 관련 번들 재계산 | 변경 모듈만 교체 |
| 프로덕션 빌드 | Webpack 자체 번들링 | Rollup 번들링 |

참고: esm.md, cjs.md, bundler.md
