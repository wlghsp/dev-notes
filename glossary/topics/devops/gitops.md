# GitOps

## 한 줄 요약

인프라나 애플리케이션의 원하는 상태를 Git 저장소에 선언해두면, 시스템이 그 상태를 실제 환경에 맞추는 운영 방식.

---

## Git이 유일한 진실이라는 말의 의미

전통적인 배포는 사람이나 CI 파이프라인이 `kubectl apply` 같은 명령을 직접 실행해서 클러스터를 바꾼다.
이 방식에서는 "지금 클러스터 상태가 왜 이런가"를 알려면 배포 로그, CI 히스토리, 누군가 수동으로 손댄 기록을 뒤져야 한다.

GitOps는 이 순서를 뒤집는다.
사람은 클러스터를 직접 건드리지 않고, Git 저장소에 "원하는 상태"만 커밋한다.
클러스터의 실제 상태는 이 Git 저장소 내용과 항상 같아야 하고, 다르면 그게 틀린 것으로 간주되어 교정된다.
그래서 Git 저장소를 보면 지금 클러스터가 어떤 상태여야 하는지, 그리고 과거에 어떤 상태였는지가 커밋 히스토리로 그대로 남는다.

---

## merge가 배포, revert가 롤백

GitOps에서 배포는 더 이상 별도의 "배포 명령"이 아니다.
원하는 상태를 적은 YAML을 브랜치에 올리고 merge하면, 그 merge 자체가 배포 행위가 된다.
문제가 생기면 그 커밋을 revert하면 되고, 이게 곧 롤백이다.

이 덕분에 배포 기록과 Git 히스토리가 같은 것이 된다.
"언제 무엇이 배포됐는가"를 추적하는 별도 시스템이 필요 없다 — `git log`가 곧 배포 로그다.

---

## push 방식과의 차이

GitOps를 실제로 동작시키려면 Git의 원하는 상태를 클러스터에 반영하는 주체가 필요하다.
CI가 빌드 후 클러스터에 직접 `kubectl apply`를 실행하는 방식(push)도 가능은 하지만, 이 경우 CI가 클러스터에 접근할 자격 증명을 들고 있어야 한다.

GitOps는 보통 반대 방향으로 동작한다(pull).
클러스터 안에 있는 에이전트가 주기적으로 Git 저장소를 확인하고, 차이가 있으면 스스로 끌어와 반영한다.
이 방식이 argocd.md에서 다루는 Argo CD 같은 도구가 하는 일이다.
클러스터 바깥에 있는 CI가 클러스터 자격 증명을 들고 있을 필요가 없어진다는 게 pull 방식의 핵심 이점이다.
