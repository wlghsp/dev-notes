## 2. TPS와 부하 테스트 개념

- 강의 2주차가 정의하는 "TPS"는 정확히 무엇을 세는 지표인가? (초당 처리 가능한 트랜잭션/요청 수)
  - 초당 처리 가능한 트랜잭션 수(Transactions Per Second)를 세는 지표입니다.
- k6의 `stages`(`k6-scripts/baseline.js`의 `{ duration, target }` 배열)는 무엇을 의미하는가? "target"이 뜻하는 게 요청 수인가, 동시 가상 사용자 수(VU)인가?
  - stages 배열은 시간이 지남에 따라 부하를 어떻게 변화시킬지 정의하는 단계별 설정입니다.
  - duration: 해당 단계가 지속되는 시간입니다.
  - target: 해당 단계의 끝에 도달해야 하는 목표 동시 가상 사용자수 (VU)입니다.
- `baseline.js`가 30초 동안 목표를 10에서 시작해 30까지 올리는 구조인데, 이게 "부하를 단계적으로 올린다"는 것과 어떻게 연결되는가?
  - 30초 동안 목표 부하를 10에서 30으로 서서히 올리는 방식은 서버에 갑작스러운 충격을 주지 않고 요청량을 점진적으로 증가(Ramp-up) 시키는 부하 테스트의 핵심 원리입니다. 
  - 부하를 단계적으로 올리는 이유와 연결되는 과정
  1. 급격한 충격 방지(Ramp-up)
    - 처음부터 30개의 요청을 한 번에 보내지 않고 10개부터 시작합니다.
    - 서버가 갑작스러운 트래픽 폭탄을 맞아 다운되는 허위 실패 현상을 막아줍니다.
  2. 서버의 안정화 시간 확보
    - 부하가 서서히 늘어나면서 서버가 커넥션 풀을 늘리거나 캐시를 준비할 여유를 가집니다.
  3. 성능 변화 추적 용이
    - 10에서 30으로 올라가는 동안 응답 속도나 오류율이 어느 시점부터 나빠지는지 명확하게 확인할 수 있습니다.

- `thresholds`의 `http_req_failed: ['rate<0.05']`는 왜 "실패시키지 않고 관측만 한다"는 주석이 붙어 있는가? (기준선을 잡는 단계와 실패 기준을 정하는 단계의 차이)
  - 기준선을 잡는 단계이므로 부하를 주면서 우리 시스템이 평소에 어느 정도 에러를 내는지 현황을 파악합니다
- k6 실행 결과에서 확인해야 할 지표는 무엇인가? (`http_req_duration`의 평균/p95/p99, `http_reqs`로 계산되는 TPS)
  - 응답시간 지표인 `http_req_duration`의 평균/p95/p99,처리량 지표인 `http_reqs`로 계산되는 TPS

## 3. 병목 자원 판단

- 1주차에 예측한 병목(count 쿼리 풀스캔, OFFSET 페이징)이 실제 부하 상황에서 어떤 자원 지표로 드러나는가? (CPU, 커넥션 풀, DB 응답 시간)
  - 1. DB 응답시간
  - 급격한 응답시간 증가: 대량의 데이터를 풀스캔하고 디스크I/O가 발생하면서 단일 쿼리의 수행시간이 밀리초단위에서 초 단위로 급증합니다.
  - 페이지 뒤로 갈수록 악화: OFFSET 페이징 특성상 뒤쪽 페이지를 조회할수록(예: 100000) 읽어야 하는 데이터양이 늘어나 응답 시간이 선형적으로 또는 기하급수적으로 증가합니다.
  - 2. CPU 사용률 (CPU Usage)
  - DB 서버 CPU 100% 도달: 대규모 테이블의 데이터 행을 조건에 맞는지 하나씩 비교·연산(Full Scan)하고, OFFSET 위치까지의 수많은 레코드를 메모리에 올려 정렬 및 폐기하는 과정에서 DB 서버의 CPU 연산 자원이 고갈됩니다.
  - 자원 고갈로 인한 도미노 현상: 특정 count나 페이징 쿼리가 CPU를 독점하면서, 정상적이던 다른 가벼운 쿼리들까지 처리가 지연되는 병목현상이 발생합니다.
  - 3. 커넥션 풀 (Connection Pool)
  - 커넥션 고갈 (Connection Pool Hell): DB 응답 시간이 길어지면 애플리케이션(WAS)이 DB 커넥션을 반환하지 못하고 웅덩이처럼 쥐고 있게 됩니다
  - 스레드 차단 및 요청 유실: 후속 요청들이 커넥션을 얻기 위해 대기(Wait)하다가 설정된 타임아웃(Connection Timeout)을 초과하게 되며, 결국 사용자 요청이 실패(500 에러 등)로 이어집니다.

- Grafana/Prometheus에서 확인 가능한 지표 중 이번 주차에 봐야 할 것은 무엇인가? (CPU 사용률, 메모리, HTTP 요청 처리 시간 등 — actuator가 노출하는 기본 지표 확인)
  - CPU 사용률
    - system_cpu_usage: 시스템 전체의 CPU 사용률입니다.
    - process_cpu_usage: JVM 프로세스가 사용하는 CPU 사용률입니다. 이 수치가 지속적으로 높다면 연산 부하가 높거나 무한 루프 등을 의심해야 합니다.
  - 메모리 및 GC (Memory & Garbage Collection)
    - jvm_memory_used_bytes: 현재 사용 중인 JVM 메모리 양입니다. jvm_memory_max_bytes와 비교하여 Heap 영역이 가득 차고 있는지 확인합니다.
    - jvm_gc_pause_seconds_count / sum: GC 발생 횟수와 소요 시간입니다. GC가 너무 자주 발생하거나 멈춤 시간이 길어지면 시스템 응답 속도가 떨어집니다.
  - HTTP 요청 성능 (HTTP Requests)
    - http_server_requests_seconds_sum / http_server_requests_seconds_count: HTTP 요청당 평균 처리 시간을 나타냅니다. 특정 API의 응답 속도가 느려졌는지 파악할 수 있습니다.
    - http_server_requests_seconds_count (status="5xx"): 500번대 에러 발생 비녿를 모니터링하여 서버 내부 오류를 즉시 감지합니다.
  - 애플리케이션 가동 상태 (Availability)
    - process_uptime_seconds: 애플리케이션이 실행된 총 시간입니다. 갑작스러운 재시작(Crash) 여부를 판단할 때 유용합니다.
- "어느 자원이 먼저 한계에 닿는지"를 판단하려면 부하를 걸기 전/후 지표를 어떻게 비교해야 하는가?
  - CPU 사용률
    - 전/후 비교: 부하 전 평상시 사용률과 부하 후 90% 이상 지속 여부를 비교합니다.
    - 판단 기준: iostat이나 top에서 us(사용자) 또는 sy(시스템) 비율이 100%에 근접하고 대기열(load average)이 급증하면 CPU가 첫 번째 한계입니다.
  - 메모리 사용량
    - 전/후 비교: 가용 메모리(Free/Available)잔여량과 스왑(Swap)영역 사용 추이를 비교합니다.
    - 판단 기준: 사용 가능한 메모리가 거의 남지 않고 스왑 인/아웃(Swap-in/out)이 빈번하게 발생하면 메모리가 한계입니다.
  - 디스크 I/O
    - 전/후 비교: 디스크 응답 시간(await)과 대기 큐 길이(avgqu-sz)의 변화를 비교합니다.
    - 판단 기준: 응답 시간이 수십 밀리초이상으로 치솟고 util%(사용률)가 100 가까이 유지되면 디스크 병목입니다.
  - 네트워크 대역폭
    - 전/후 비교: 인터페이스의 최대 전송 대역폭 대비 사용량 비율과 패킷 손실률(Dropped / Error)을 비교합니다.
    - 판단 기준: 대역폭 한계에 도달하거나 패킷 드롭이 발생하면 네트워크가 한계입니다.
- MySQL 자체의 커넥션 풀 상태(HikariCP 등)는 어디서 확인할 수 있는가?
  - 애플리케이션 계층 : Spring Boot Actuator, 모니터링 툴(Prometheus & Grafana), 로그 설정
  - 데이터베이스 계층
    - 현재 연결된 스레드(커넥션)수 확인 : SHOW STATUS LIKE 'Threads_connected';
    - 서버가 켜진 이후 가장 많이 동시 연결된 수 확인 : SHOW STATUS LIKE 'Max_used_connections';
    - MYSQL이 허용하는 최대 연결 제한 설정 확인 : SHOW STATUS LIKE 'max_connections';
