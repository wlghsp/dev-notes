# thread-pool

스레드를 미리 생성해두고 재사용하는 동시성 패턴.

스레드 생성과 소멸에는 비용이 있다. 요청마다 스레드를 새로 만들고 버리면 오버헤드가 누적된다. 스레드 풀은 프로그램 시작 시 N개의 워커 스레드를 만들어두고, 작업을 큐에서 꺼내 실행한 뒤 다시 대기 상태로 돌아오게 한다. 개발자가 스레드를 직접 생성하거나 관리할 필요가 없다.

## 내부 구조

스레드 풀 내부에서 메인 스레드와 워커 스레드 사이의 통신은 message queue로 이루어진다. 큐가 태스크 목록을 FIFO로 보관하고, 유휴 워커 스레드가 큐에서 꺼내 처리한다.

> 📷 Figure 5-x (책 p.85) — PROGRAM → TASKS QUEUE → THREAD #1/#2/#3 → TASK COMPLETED 흐름 다이어그램

1. 프로그램이 태스크를 풀에 제출한다 → 큐에 추가된다
2. 유휴 워커 스레드가 큐에서 태스크를 꺼낸다
3. 태스크를 실행하고, 완료되면 다음 태스크를 기다린다
4. 예외가 발생해도 워커 스레드 자체는 종료되지 않고 계속 동작한다

## 스레드 풀을 쓰지 말아야 할 때

책은 대부분의 동시성 애플리케이션에 스레드 풀이 좋은 기본 선택이라고 하면서도, 직접 스레드를 관리하는 게 나은 경우 4가지를 명시한다.

1. 스레드 우선순위를 직접 제어해야 할 때
2. 오래 블로킹되는 태스크가 많을 때 — 블로킹된 스레드가 풀을 가득 채우면 다른 태스크가 시작을 못한다
3. 스레드에 정적 식별자가 필요할 때
4. 하나의 스레드를 특정 태스크 전용으로 써야 할 때

## 스레드 풀의 핵심 이점

새 태스크가 도착하면 유휴 스레드가 깨어나 실행하고 다시 Ready 상태로 돌아간다. 스레드 생성/종료 비용을 없애고, 스레드 관리를 라이브러리나 OS에 위임한다. 태스크 하나가 예외로 실패해도 워커 스레드에는 영향이 없다.
