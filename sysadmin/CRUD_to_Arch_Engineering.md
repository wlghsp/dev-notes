# CRUD에서 복잡한 아키텍처로: AI 시대의 서버 엔지니어링 의사결정

복잡한 구조는 문제의 흔적이다.

단순 CRUD 구조 -> 완성된 아키텍처 구조

```
Client -> Signup API -> Database
```

## 문제 1. 요청 안에서 일이 너무 많아진다

응답 시간이 길어진다.

- 선택의 갈림길: 동기 유지 vs 비동기 분리
- 결정: 지연 가능한 후처리를 분리한다. 이벤트 스트리밍으로 큐나 이벤트 버스를 이용함

**검증**: 실제로 요청이 빨라졌는가

**부작용**
- 작업이 지연된다
- 메시지가 중복 처리된다
- 처리 결과를 (추적하기 어려워진다)

## 문제 2. 실패를 어떻게 다룰 것인가

- 선택의 갈림길: Retry, DLQ, 멱등 처리
  - 선택지: 실패 기록 후 무시, 즉시 재시도, DLQ 적재
- 결정: 실패를 운영 가능한 형태로 만든다. DLQ -> 수동 복구 도구

**검증**: Retry가 얼마나 발생하는가, DLQ가 얼마나 쌓이는가

**부작용**: 분석 쿼리가 DB 부하를 만든다.

## 문제 3. 조회와 분석 요구가 충돌한다

- 선택의 갈림길: DB 유지, Cache, Data Warehouse
  - 선택지: 기존 DB 유지, 인덱스/쿼리 최적화, Cache, DW
- 결정: 조회와 분석 경로를 나눈다.

**검증**: 서비스 DB 부하가 줄었는가. Slow Query가 줄었는가. 분석 쿼리 시간이 개선되었는가.

---

## 그러면 처음부터 다 넣으면 되지 않나

복잡도 또한 비용이다.

넣고 싶어지는 것과 아직 모르는 것은 별개로 존재한다.

### 복잡한 아키텍처가 만드는 문제
- 운영 대상 증가
- 장애 지점 증가

> Complexity = Cost

### 기술을 붙이기 전에 봐야 할 것
- 문제가 실제로 존재하는가
- 병목은 어디인가?
- 실패하면 어떻게 되는가?
- 무엇으로 성공을 판단할 것인가?
- 누가 운영할 것인가?
- 더 단순한 선택지는 없는가?
- 이 선택의 대가는 무엇인가?

### 구조를 바꿨다. 그런데 정말 좋아졌을까?

- 도입 전: 문제가 실제로 있는가? (테스트로 검증)
- 도입 중: 실패했을 때 되돌릴 수 있는가? (모니터링으로 확인)
- 도입 후: 병목이 실제로 해소됐는가? (프로파일링으로 확인)

### AI는 어디서 도움이 되는가

AI는 결정을 대신하지 않고, 질문을 넓혀준다.
