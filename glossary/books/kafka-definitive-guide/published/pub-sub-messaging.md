# Publish/Subscribe Messaging

송신자가 데이터를 특정 수신자에게 직접 보내지 않고, 데이터를 분류만 해서 내보내는 통신 패턴.

수신자는 자신이 관심 있는 분류를 구독(subscribe)해서 받는다. 송신자는 누가 구독하고 있는지, 몇 명이 구독하고 있는지 알 필요가 없다.

## 왜 직접 연결이 문제가 되는가

시스템 하나가 다른 시스템 하나에 필요한 데이터를 보낸다면 직접 연결로 충분하다. 하지만 데이터를 보내는 쪽과 받는 쪽이 각각 늘어나면 연결의 수가 참여자 수의 곱만큼 늘어난다.

이 상태에서는 데이터를 보내는 쪽 하나가 자신의 데이터를 어떤 시스템들이 받고 있는지 일일이 알아야 하고, 받는 시스템이 하나 늘어날 때마다 보내는 쪽 코드를 고쳐야 한다. 연결이 늘어날수록 전체 구조를 추적하기도 어려워진다.

## Pub/Sub이 이 문제를 어떻게 푸는가

송신자와 수신자 사이에 브로커(broker)를 둔다. 송신자는 브로커에만 데이터를 보내고, 수신자는 브로커를 구독해서 받는다.

이렇게 하면 송신자는 자신의 데이터를 누가 쓰는지 몰라도 되고, 수신자가 늘어나거나 줄어도 송신자 쪽 코드를 바꿀 필요가 없다. 데이터를 보내는 일과 받는 일이 서로 분리(decouple)된다.

## Kafka와의 관계

Kafka는 pub/sub 메시징 시스템으로 설계됐다. 다만 메시지를 그때그때 전달만 하고 버리는 다른 pub/sub 시스템과 달리, Kafka는 메시지를 디스크에 내구성 있게 저장해둔다는 점이 다르다(참고: kafka-retention.md).
