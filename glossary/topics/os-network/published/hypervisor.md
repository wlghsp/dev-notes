# Hypervisor (하이퍼바이저)

물리 서버 하나 위에서 여러 개의 가상 머신(VM)을 실행할 수 있게 해주는 소프트웨어다. 각 VM은 자기만의 OS와 커널을 가지고, 물리 하드웨어를 독립적으로 쓰는 것처럼 동작한다.

## 왜 필요한가

물리 서버를 하나씩 사면 비싸고, 대부분의 시간에 CPU/메모리를 다 쓰지도 않는다. 하이퍼바이저로 하나의 물리 서버를 여러 VM으로 쪼개면 자원을 효율적으로 쓸 수 있다. AWS EC2, GCP Compute Engine 같은 클라우드 인스턴스가 이 방식으로 동작한다.

## Type 1 vs Type 2

**Type 1 (베어메탈 하이퍼바이저)**
하드웨어 위에 하이퍼바이저가 직접 올라간다. OS 없이 하이퍼바이저가 하드웨어를 직접 제어한다.

```
하드웨어
└── 하이퍼바이저 (Type 1)
    ├── VM1 (OS + 앱)
    ├── VM2 (OS + 앱)
    └── VM3 (OS + 앱)
```

성능이 좋다. 서버 가상화에 쓰인다. VMware ESXi, Microsoft Hyper-V, KVM이 여기 속한다.

**Type 2 (호스트형 하이퍼바이저)**
기존 OS 위에서 하이퍼바이저가 애플리케이션처럼 실행된다.

```
하드웨어
└── 호스트 OS
    └── 하이퍼바이저 (Type 2)
        ├── VM1 (OS + 앱)
        └── VM2 (OS + 앱)
```

설치가 쉽다. 개발 환경에 쓰인다. VirtualBox, VMware Workstation, macOS의 Parallels가 여기 속한다.

## VM vs 컨테이너

하이퍼바이저 기반 VM과 Docker 같은 컨테이너는 다르다.

VM은 OS와 커널을 통째로 들고 다닌다. 완전히 격리되어 있고 무겁다.

컨테이너는 호스트 OS의 커널을 공유한다. 격리는 하되 OS를 따로 띄우지 않아서 가볍고 빠르다.

```
VM:         [앱 | OS | 커널]  ← 커널까지 각자
컨테이너:   [앱]              ← 호스트 커널 공유
```

## 언제 뭘 쓸까

**VM이 필요한 이유**

클라우드(AWS EC2, GCP, Azure)는 물리 서버 하나를 수백 명의 고객에게 나눠준다. 컨테이너는 같은 호스트 커널을 공유하기 때문에 완전한 멀티테넌트 격리가 불가능하다. 각 고객의 커널 버그가 다른 고객의 데이터를 볼 수 있다. 그래서 VM처럼 독립 커널을 갖춰야 한다.

또 컨테이너는 호스트 커널을 공유하기 때문에, Linux 호스트에서 Windows 컨테이너를 실행하거나 그 반대는 불가능하다. macOS에서 Docker가 동작하는 건 Docker Desktop이 내부적으로 Linux VM을 띄워서 그 위에서 컨테이너를 돌리기 때문이다. VM은 각각 다른 OS를 게스트로 띄울 수 있다.

**컨테이너가 좋은 이유**

VM은 부팅에 분 단위가 걸린다. 컨테이너는 초 단위다. 개발할 때 코드 바꾸고 다시 띄워야 하는데, VM은 너무 느리다. 그래서 개발-배포 파이프라인이 완전히 바뀌었다.

또 한 머신에 수백 개 컨테이너를 띄울 수 있지만, VM은 그럴 수 없다. 자원 효율이 훨씬 좋다.

**혼재하는 현실**

쿠버네티스 노드 자체는 VM 위에서 도는 경우가 많다. 컨테이너가 VM을 완전히 대체한 게 아니라, 각자 쓰임새가 다르다. 프로덕션 멀티테넌트 환경(클라우드)은 여전히 VM 기반이고, 개발/배포 자동화는 컨테이너 기반이다.
