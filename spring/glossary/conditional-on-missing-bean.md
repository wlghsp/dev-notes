# @ConditionalOnMissingBean과 자동 구성 충돌

## 정의

`@ConditionalOnMissingBean`은 "해당 타입의 빈이 컨텍스트에 아직 없을 때만 이 빈을 등록한다"는 조건이다. 스프링 부트의 자동 구성 클래스들이 내부에 이 조건을 붙여둔다 — 우리가 직접 쓰는 애노테이션이 아니라, 스프링 부트가 미리 깔아둔 규칙이다.

이 조건은 원래 "사용자가 같은 타입의 빈을 직접 만들어뒀으면 그걸 존중한다"는 배려로 설계됐다.

## 어떻게 충돌이 생기는가

문제는 사용자가 의도적으로 만든 적 없는 빈이 다른 기능의 부산물로 같은 타입 등록될 때다.

웹소켓 기능(`@EnableWebSocket`)이 자기 용도로 스케줄러 타입 빈을 하나 자동 등록하면, 타입만 같아서 스프링 부트는 "사용자가 이미 정의했다"고 오판하고 원래 만들어줬어야 할 기본 스케줄러 빈을 스킵해버린다.

## 왜 알아채기 어려운가

이 빈을 실제로 쓰는 코드(`@Scheduled` 처리기)는 못 찾으면 에러를 던지는 대신 이름 없는 임시 대체 구현을 만들어 계속 동작한다.

앱은 안 멈추고 로그도 안 남지만, 원래 기대한 설정(스레드 풀 크기 등)은 조용히 무시된 채 성능만 떨어진다.

## 해결이 "구현 누락 보완"은 아니다

해결은 그 타입의 빈을 직접 명시적으로 등록해주는 것이다.

다만 이건 원래 우리가 구현했어야 할 걸 빠뜨렸던 게 아니다 — 정상 상황이면 스프링 부트가 알아서 만들어줬을 빈이라, 다른 기능이 우연히 막아버린 자동 구성을 되돌리는 우회 조치일 뿐이다.

## 교훈

이런 문제는 로그로는 안 보인다. 실제로 어떤 빈이 등록됐는지 직접 조회해서 확인해야 한다.
