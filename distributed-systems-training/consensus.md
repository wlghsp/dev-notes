# Consensus (합의)

여러 노드가 네트워크 단절, 지연, 노드 장애 같은 불확실한 상황 속에서도 하나의 값에 대해 동일한 결론에 도달하는 문제, 그리고 그걸 보장하는 알고리즘들을 통칭하는 개념.

etcd, Kafka(KRaft), CockroachDB, ZooKeeper 같은 분산 시스템의 핵심에 자리한다.

## 왜 서버 한 대로는 안 되는가

서버 한 대는 합의 문제 자체가 없다 — 그 서버가 곧 진실이다. 하지만 그 한 대가 죽으면 서비스 전체가 멈춘다.

여러 대로 복제하면 가용성은 올라가지만 새로운 문제가 생긴다. 네트워크 단절로 노드들이 서로 다른 변경을 받아들이면, 나중에 다시 연결됐을 때 "누구 말이 맞는가"를 정해야 한다. 이걸 사람이 매번 수동으로 정할 수 없으니, 알고리즘으로 자동화한 것이 consensus 알고리즘이다.

## 합의가 풀어야 하는 두 가지

**리더 선출**
누가 결정을 내릴 권한을 가질지 정하는 문제. 리더가 없으면 여러 노드가 동시에 서로 다른 결정을 내릴 수 있다. 리더가 죽으면 새 리더를 다시 뽑아야 한다.

**상태 복제**
리더가 내린 결정을 나머지 노드에 전파하고, 그 결정이 "확정됐다"고 부를 수 있는 시점을 정하는 문제. 여기서 quorum.md의 과반수 개념이 등장한다 — 과반수가 받아들인 시점을 확정(commit)으로 본다.

## 대표 알고리즘

**Paxos**
최초로 이 문제를 정식으로 풀어낸 알고리즘. 정확성은 증명되어 있지만 이해하고 구현하기 어렵기로 유명하다.

**Raft(raft.md)**
Paxos와 동등한 보장을 하면서 이해하기 쉽게 설계된 알고리즘. 리더 선출, 로그 복제, 안전성을 명확히 분리된 단계로 나눠서 설명한다. 현재 실무에서 가장 널리 쓰인다.

## 합의가 있는 시스템과 없는 시스템

합의는 "정확히 하나의 진실"이 필요할 때만 쓰는 무거운 도구다. 예를 들어 리더가 누구인지, 설정값이 무엇인지처럼 애매하면 안 되는 값에는 합의가 필요하다.

반대로 CRDT(crdt.md)처럼 애초에 "여러 복제본이 서로 다른 순서로 값을 받아도 결국 같은 결과로 수렴하면 그만"인 문제라면, 굳이 무거운 합의 알고리즘을 쓸 필요가 없다. 합의는 정확한 순서와 하나의 확정된 값이 필요할 때, CRDT는 최종적으로만 같아지면 될 때 쓰는 서로 다른 도구다.

## 정리

Consensus = "이 클러스터의 진실은 무엇인가"에 대해 노드 장애/네트워크 단절 속에서도 하나의 답을 얻는 문제.
Quorum(quorum.md) = 그 답을 확정 짓는 기준(과반수).
Raft(raft.md) = 이 문제를 실제로 푸는 구현체 중 하나.

참고: raft.md, quorum.md, crdt.md
