# 과부하와 장애 방어 패턴 — 느려지면 왜 다 같이 죽고, 어떻게 막나

traffic-basics.md 6장(포화 방어 패턴)을 깊게 푼 문서.
출처: Release It! 2nd Edition (Nygard) 4~5장, Google SRE 북 21~22장. 쪽수는 책 본문 기준이고 내용은 요약이다.

---

## 1. 왜 필요했나

서버가 "죽는" 건 오히려 단순하다. 진짜 무서운 건 **죽지 않고 느려지는 것**이다.

- 느린 응답은 호출한 쪽의 스레드를 붙잡는다 → 호출한 쪽도 느려진다 → 위로 번진다
- Release It!은 느린 응답이 에러보다 나쁘다고 말한다. 에러는 빨리 끝나서 호출자가 다음 일을 하지만, 느린 응답은 양쪽 자원을 모두 묶어 둔다 (Slow Responses, p.84)
- 외부에서 보면 "아주 많이 느림"과 "다운"은 구분이 안 된다 (Shed Load, p.119)

앞 문서의 Little's Law(동시 처리 수 = TPS × 응답시간)가 이 현상의 수학적 뼈대다. 응답시간이 늘면 같은 TPS에서 동시 처리 수가 늘고, 스레드 풀이 꽉 차면 끝이다.

## 2. 장애가 번지는 경로

### 연쇄 장애 (Cascading Failure, Release It! p.49~)
하위 계층의 균열이 상위 계층의 균열을 일으키는 것. 하위가 DB든 외부 API든, **호출하는 쪽이 이를 어떻게 처리하느냐**가 갈린다. 잘못 처리하면 호출자도 같이 무너진다.

번지는 통로는 대체로 두 가지다.
- **블로킹된 스레드** (Blocked Threads, p.62): 스레드가 응답 없는 호출에서 풀려나지 못한다. 프로세스는 살아 있고 포트도 열려 있지만 일은 하나도 못 한다. "죽었다"가 아니라 "멈췄다".
- **과하게 공격적인 호출자**: 에러를 받자마자 재시도해서 하위 계층을 더 때린다.

### 양성 피드백 (SRE 북 22장, p.259)
연쇄 장애를 "시간이 갈수록 커지는 실패, 양성 피드백의 결과"라고 정의한다. 예시:

- 복제본 A, B가 각각 1000 QPS를 받다가 B가 죽으면 A에 몰려 부하가 늘어난다 (책 예시는 1200 QPS)
- A가 못 버티고 죽으면 남은 쪽은 더 큰 부하를 받는다
- 한 번 시작하면 몇 분 안에 서비스 전체로 번질 수 있다

그리고 중요한 관찰: 과부하가 걸린 서버는 **처리량이 오히려 줄어든다.** 자원을 다 써서 정상 요청도 못 끝내기 때문이다. 부하가 한계를 넘으면 "조금 느려짐"이 아니라 "일을 못 함"으로 꺾인다.

## 3. 방어 패턴

### 3-1. 타임아웃 (Timeouts, Release It! p.91)
**기다림에 상한을 둔다.** 모든 외부 호출과 풀 대기에 필요하다.

- 풀에서 자원을 빌릴 때도 타임아웃이 필요하다. 없으면 스레드가 영원히 대기한다 (책의 강조점)
- 라이브러리가 타임아웃을 숨기고 있는지 확인한다. 소켓을 감춘 클라이언트 라이브러리는 타임아웃 설정이 안 되는 경우가 많다
- 타임아웃은 장애를 막는 게 아니라 **내 장애가 되는 걸 막는다.** 남의 문제가 내 스레드를 묶지 않게 한다

### 3-2. 서킷 브레이커 (Circuit Breaker, p.95)
**아픈 곳은 부르지 않는다.**

| 상태 | 동작 |
|---|---|
| Closed | 평소처럼 호출. 실패를 센다 |
| Open | 임계치를 넘으면 호출 자체를 하지 않고 즉시 실패시킨다 |
| Half-Open | 일정 시간 뒤 한 건만 시험 호출. 성공하면 Closed, 실패하면 다시 Open |

- 재시도는 "다시 해 본다", 서킷 브레이커는 "하지 않는다"로 목적이 반대다 (p.95)
- "실패 횟수"보다 **실패 밀도**가 중요하다. 5시간에 5번과 30초에 5번은 다르다 (Leaky Bucket 카운터 제안)
- Open 시 대응(폴백)은 **비즈니스 결정**이다. 재고 확인이 안 될 때 주문을 받을까? 개발자 혼자 정할 일이 아니다 (p.97)
- 상태 변화는 반드시 로그와 지표로 남긴다. 책은 "서킷이 열리는 빈도는 다른 곳 문제의 선행 지표"라고 한다
- 책 권장: 서킷 브레이커 상태는 프로세스 단위로 둔다 (공유하면 그 자체가 새 장애 지점이 됨)

### 3-3. 벌크헤드 (Bulkheads, p.98)
**한 구획이 침수돼도 배 전체가 가라앉지 않게 칸막이를 친다.**

- 서버/인스턴스 분리가 가장 흔한 형태 (물리적 중복)
- 두 시스템이 공용 서비스 하나를 같이 쓰면, 한쪽 폭주가 다른 쪽 장애가 된다. 서비스를 풀 1, 풀 2로 나눠 **중요 고객 몫을 따로 확보**한다 (책의 Foo/Bar/Baz 예)
- 스레드 풀, 커넥션 풀을 호출 대상별로 분리하는 것도 같은 아이디어다
- 어디에 칸막이를 칠지는 "무엇을 잃어도 되는가"를 비즈니스 관점에서 따져 정한다

### 3-4. 부하 차단 (Shed Load, p.119)
**감당 못 할 요청은 처음부터 거절한다.**

- 세상은 내가 감당할 수 있는 것보다 더 많은 부하를 만들 수 있다 ("You can't out-scale the world")
- 기준: 서비스가 **자기 SLA 대비 응답시간**을 보고 판단한다. SLA보다 느려지면 일부를 거절한다
- 대안: 동시 요청 수를 세마포어로 제한
- 로드밸런서 뒤에서는 헬스체크에 503을 반환해 잠시 빠지겠다고 알릴 수 있다

SRE 북도 같은 방향이다 (22장 p.267): 큐 길이나 처리 중 요청 수가 임계를 넘으면 503을 반환한다.

### 3-5. 백프레셔 (Create Back Pressure, p.120)
**소비자가 못 따라가면 생산자를 늦춘다.**

- 모든 성능 문제는 어딘가에서 큐가 쌓이는 것에서 시작한다
- **큐가 무한이면 응답시간도 무한으로 간다** (Little's Law). 큐는 반드시 유한해야 한다
- 큐가 찼을 때 선택지는 넷뿐이다: 받은 척하고 버리기 / 다른 걸 버리고 받기 / 거절 / 생산자를 막기
- 시스템 **내부**(경계 안쪽)에서는 백프레셔, **경계(외부 사용자)** 에서는 부하 차단과 비동기를 쓴다. 외부 사용자는 막을 수 없기 때문이다

### 3-6. 큐 길이 설정 (SRE 북 22장, p.266)
스레드 풀 앞의 큐를 길게 잡으면 안전해 보이지만 실제로는 지연만 늘린다.

- 책의 예: 큐가 스레드 수의 10배, 처리 시간 100ms면, 큐가 꽉 찬 상태에서 들어온 요청은 약 **1.1초** 걸린다. 거의 전부 큐에서 기다리는 시간이다
- 트래픽이 꾸준한 서비스는 큐를 스레드 풀 대비 작게(예: 50% 이하) 두고 **빨리 거절** 하는 편이 낫다
- 이미 사용자가 포기했을 요청을 처리하는 건 낭비다. 큐가 오래된 요청을 버리는 방식(LIFO, CoDel)과 데드라인 전파가 이를 줄인다

### 3-7. 거버너 (Governor, p.123)
**자동화는 판단력이 없다.** 위험한 방향의 행동(인스턴스 종료, 데이터 삭제, IP 차단)은 속도 제한을 건다. 사람이 개입할 시간을 번다. 예: 오토스케일러가 한 번에 전체의 일정 비율 이상은 줄이지 못하게 한다 (Reddit 장애 사례).

## 4. 재시도 — 가장 흔한 자해

### 문제
서버가 느려지면 클라이언트가 재시도하고, 그 재시도가 서버를 더 느리게 만든다.

**계층마다 재시도하면 곱해진다** (SRE 북 p.270):
프론트, 백엔드, JS 세 계층이 각각 3회 재시도(총 4번 시도)하면, 사용자 행동 하나가 DB에 **4×4×4 = 64번** 시도로 번질 수 있다.

### 막는 법 (SRE 북 21장 p.254, 22장 p.269~270)

| 규칙 | 내용 |
|---|---|
| 요청당 재시도 상한 | 책의 예: 최대 3회까지만 |
| 클라이언트별 재시도 예산 | 전체 요청 중 재시도 비율이 **10%** 를 넘으면 재시도하지 않음. 최악의 경우 부하 증폭이 약 3배에서 **1.1배** 로 줄어든다 |
| 지수 백오프 + 지터 | 간격을 점점 늘리고 **무작위를 섞는다.** 안 섞으면 작은 흔들림에도 재시도가 같은 시각에 몰려 서로 증폭한다 |
| 한 계층에서만 재시도 | 여러 계층이 동시에 재시도하지 않도록 정한다 |
| 재시도 가능/불가 구분 | 영구 오류나 잘못된 요청은 재시도해도 소용없다. 과부하일 때는 "재시도 말 것"을 명시적으로 알린다 |

Release It!도 비슷한 조언이다 (p.93). 데이터센터 안에서의 실패는 대개 상대편 문제라서 오래 가고, **즉시 재시도는 같은 실패를 반복할 가능성이 높다.** 차라리 큐에 넣고 나중에 다시 처리하는 편이 낫다.

### 클라이언트 측 스로틀링 (SRE 북 p.249~250)
서버가 거절하는 데에도 자원이 든다. 거절이 많아지면 서버가 거절만 하다 죽을 수 있다. 그래서 클라이언트가 **최근 2분간의 요청 수와 수락 수**를 기록하고, 요청 수가 수락 수의 K배(기본 2)를 넘으면 스스로 일부를 서버에 보내지 않고 막는다. 판단이 로컬 정보만으로 이뤄져 추가 의존성이 없다.

### 지표로 알아보기
재시도율 그래프가 같이 오르면 원인이 재시도 폭주일 수 있다. 다만 책은 "증상으로 착각하기 쉽다"고 경고한다. 재시도가 장애를 키우는 원인인지, 장애의 결과인지 함께 봐야 한다.

## 5. 우선순위를 둔 차단 — Criticality (SRE 북 p.251)

모든 요청이 똑같이 중요하지 않다. 구글은 요청에 4단계 중요도를 붙인다.

| 단계 | 의미 |
|---|---|
| CRITICAL_PLUS | 실패하면 사용자에게 심각한 영향 |
| CRITICAL | 기본값. 사용자 영향 있음 |
| SHEDDABLE_PLUS | 부분적 불가용성이 예상되는 트래픽 (배치 등) |
| SHEDDABLE | 자주 안 돼도 되는 트래픽 |

- 과부하일 때는 **낮은 중요도부터 먼저 거절** 한다
- 중요도는 호출 체인을 따라 자동 전파한다

우리 환경에 가져오면: 사용자 화면용 API와 배치/백필 호출을 같은 풀에서 받지 말고, 과부하 시 배치를 먼저 막는 구조가 같은 사고방식이다.

## 6. 용량을 QPS로 재지 말 것 (SRE 북 p.248)

요청마다 비용이 다르다. 같은 QPS라도 요청 종류나 시간대에 따라 자원 소모가 크게 달라진다. 구글은 QPS 대신 **CPU 소모량** 으로 용량을 모델링하고, 대부분의 경우 CPU가 충분한 신호라고 한다 (GC 언어에서는 메모리 압박도 CPU로 나타나기 때문).

앞 문서의 "파드 1대 처리량을 TPS로 재라"는 말의 보완이다. TPS는 요청 구성이 바뀌면 달라지므로, **부하 테스트 때의 요청 비율과 실제 운영 비율이 같은지** 확인해야 한다.

## 7. 우리 환경에 대응시키기

아래는 책이 아니라 제 정리다. 실제 적용 전에 사용 중인 버전과 설정 방식을 확인할 것.

| 개념 | Spring 쪽에서 보는 곳 |
|---|---|
| 타임아웃 | RestTemplate/WebClient 타임아웃, JDBC 쿼리 타임아웃, HikariCP `connectionTimeout` |
| 서킷 브레이커, 벌크헤드, 레이트 리밋, 재시도 | Resilience4j |
| 부하 차단 | 톰캣 `maxThreads`/`acceptCount`, 게이트웨이 레이트 리밋, 헬스체크 503 |
| 벌크헤드(풀 분리) | 호출 대상별 별도 스레드 풀·커넥션 풀 |

관측: 서킷 상태 변화 횟수, 재시도 비율, 거절된 요청 수(5xx 중 503), 풀 대기 시간·대기 스레드 수를 지표로 둔다. 앞 문서의 RED(p95/p99, 에러율, TPS)와 USE(포화 = 풀 대기)에 이 지표들이 붙는다.

## 8. 대화에서 쓰는 말

| 이렇게 말하면 | 뜻 |
|---|---|
| "연쇄 장애 났어요" | 하위 장애가 호출 계층을 타고 위로 번짐 |
| "스레드가 블로킹돼서 멈췄어요" | 프로세스는 살아 있으나 모든 스레드가 응답 대기 중 |
| "타임아웃이 없어서 번졌어요" | 외부 호출 대기에 상한이 없었음 |
| "서킷 열렸어요" | 하위 호출을 의도적으로 차단 중 |
| "벌크헤드로 분리해야 해요" | 풀/인스턴스를 나눠서 폭주 영향 범위를 제한 |
| "load shedding 걸어야 해요" | 한계 넘는 요청은 일찍 거절 |
| "retry storm 같아요" | 재시도가 부하를 키우는 중 |
| "재시도 예산을 두죠" | 재시도 비율에 상한 |
| "큐가 길어서 지연만 늘어요" | 큐를 줄이고 빨리 거절하는 게 낫다는 뜻 |

### 스스로 점검

1. 느린 응답이 에러보다 나쁜 이유는?
2. 타임아웃과 서킷 브레이커는 어떻게 다르고, 왜 같이 쓰나?
3. 스레드 풀 앞의 큐를 길게 잡으면 왜 위험한가? (책의 1.1초 예시로 설명)
4. 세 계층이 각각 4번씩 시도하면 최악에 몇 번인가? 어떻게 막나?
5. 백프레셔와 부하 차단은 각각 시스템의 어디에 쓰나?
6. 재시도 간격에 지터를 섞는 이유는?

## Recap

장애의 핵심 위험은 죽음이 아니라 **느려짐**이다. 느린 응답은 호출자의 스레드를 묶고, 풀이 차면 호출자도 느려지며, 이렇게 위로 번지는 게 연쇄 장애다. 한계를 넘으면 처리량이 도리어 줄어드는 양성 피드백이 생긴다. 막는 방법은 층층이 있다. **타임아웃**은 기다림에 상한을 두고, **서킷 브레이커**는 아픈 곳 호출을 멈추며, **벌크헤드**는 풀을 나눠 영향 범위를 가두고, **부하 차단**은 감당 못 할 요청을 일찍 거절하고, **백프레셔**는 내부에서 생산자를 늦추며, **거버너**는 위험한 자동화를 천천히 만든다. 큐는 유한해야 하고, 길수록 지연만 늘어난다. 재시도는 가장 흔한 자해로, 계층마다 곱해지고(4×4×4=64), 요청당 상한, 클라이언트 재시도 예산(약 10%), 지수 백오프+지터, 한 계층에서만 재시도로 막는다. 모든 요청이 똑같이 중요하진 않으므로 낮은 중요도부터 차단하고, 용량은 QPS보다 CPU 같은 자원으로 가늠한다.
