# C/C++로 DB를 만드는 이유 — 속도 말고

MySQL, PostgreSQL, SQLite 같은 DB가 C/C++로 만들어진 이유는 단순히 "빠르기 때문"이 아니다. **제어권** 때문이다. DB는 메모리, I/O, 동시성을 언제 어떻게 처리할지 스스로 결정해야 하는데, 런타임이 끼면 그 결정권이 넘어간다.

## 메모리 직접 관리

메모리 해제 시점을 직접 통제하고 싶어서 C/C++를 선택한 것이고, 그 결과로 `malloc`/`free`를 직접 쓰게 된다. Java나 Go처럼 GC가 있는 언어는 해제 시점을 런타임이 결정한다. DB 입장에서 이건 치명적이다.

redo log를 flush하는 critical section 도중에 GC가 끼어들면, 그 순간 동안 다른 트랜잭션들의 커밋이 줄줄이 막힌다. 하나의 GC pause가 lock contention으로 번지면서 지연이 전파된다.

MySQL이 `mysys/`에 자체 메모리 할당 API(`my_malloc`, `my_free`)를 만든 것도 이 이유다. OS의 `malloc`을 직접 쓰지 않고 한 번 감싸서 추적, 통계, 풀링을 DB 레벨에서 관리한다.

## 메모리 레이아웃 직접 설계

Buffer Pool 같은 구조는 데이터를 메모리에 어떤 형태로 올릴지 바이트 단위로 설계한다. 구조체 필드 순서, 패딩, 정렬까지 신경 써서 CPU 캐시 히트율을 높인다.

멀티스레드 환경에서는 false sharing 문제도 있다. 서로 다른 스레드가 같은 캐시 라인에 올라간 다른 변수를 건드리면, 실제로 같은 데이터를 공유하지 않아도 캐시 무효화가 발생한다. InnoDB의 page descriptor나 mutex 구조체들이 캐시 라인 크기(64바이트)에 맞춰 정렬되는 것도 이 때문이다. 패딩을 일부러 넣어서 false sharing을 막는 것은 단순 성능 최적화가 아니라 동시성 정확성과도 연결된다.

Java나 Python은 객체 레이아웃을 런타임이 결정한다. 어디에 어떻게 올라갈지 코드 레벨에서 보장할 수 없다.

## 시스템 콜 직접 호출

`fsync()`, `mmap()`, `pread()`/`pwrite()` 같은 OS 레벨 I/O를 직접 쓴다. 파일을 언제 디스크에 flush할지를 DB가 직접 결정해야 내구성(Durability)을 보장할 수 있다.

여기서 핵심 변수는 OS page cache를 거치느냐 마느냐다. 일반적인 write는 OS page cache에 먼저 쌓이고, 실제 디스크에 내려가는 시점은 OS가 결정한다. DB는 이걸 믿을 수 없다. `O_DIRECT` 플래그로 OS page cache를 우회하면 write가 곧바로 디스크로 간다. "지금 이 시점에 실제로 디스크에 썼는가"를 OS에 맡기지 않고 DB가 직접 통제하는 방식이다.

## 락과 동시성 직접 구현

뮤텍스, 스핀락, 원자적 연산(atomic operation)을 직접 구현한다. 어떤 상황에서 스핀할지, 몇 회 후에 sleep으로 전환할지, 우선순위 기반으로 큐잉할지를 DB가 직접 정책으로 짠다.

언어 런타임의 스케줄러는 범용 목적으로 설계되어 있다. DB가 원하는 세밀한 정책을 강제할 수 없다. 범용 스케줄러 자체가 나쁜 게 아니라, DB 특화 정책과 범용 정책은 목적이 다르다.

## 결국 "제어권"이 핵심

C/C++가 정답이라는 얘기가 아니다. TiKV, SurrealDB처럼 Rust로 짠 DB들도 늘고 있다. Rust도 GC 없이 컴파일 타임에 메모리 해제 시점을 결정하기 때문에 같은 철학 선상에 있다. 글의 핵심은 "제어권이 필요하고, C/C++는 그걸 얻는 한 가지 방법"이라는 것이다.
