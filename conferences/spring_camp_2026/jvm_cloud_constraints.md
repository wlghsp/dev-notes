# JVM의 클라우드 환경 제약

## 배경

JVM은 원래 **오래 켜두고 쓰는** 환경을 전제로 설계됐다. 서버 하나를 며칠~몇 달씩 운영하면서 점점 최적화되는 구조.

그런데 클라우드/컨테이너 환경은 정반대다. Pod를 수시로 띄우고 죽이고, 트래픽에 따라 수십 개로 늘리고 줄인다. JVM의 설계 전제와 클라우드의 운영 방식이 충돌한다.

크게 두 가지 문제로 나뉜다.

---

## 문제 1: 잦은 Migration vs 긴 기동시간 + 반복적 JIT

### 클라우드에서 Pod는 자주 죽고 다시 태어난다

Kubernetes 환경에서 Pod는 여러 이유로 재시작된다.
- 배포할 때마다 기존 Pod를 죽이고 새 Pod를 띄움
- 트래픽이 늘면 Pod를 새로 생성 (Scale Out)
- 노드 장애 시 다른 노드로 Pod를 이동 (Migration)
- 메모리 부족 시 OOMKilled로 강제 종료

즉 **Pod의 생명주기가 짧고, 재시작이 잦다.**

### JVM은 켜자마자 바로 빠르지 않다

JVM은 처음엔 코드를 인터프리터로 실행한다. 실행되는 코드를 관찰하면서 "이 부분이 자주 실행되네" 싶으면 **JIT(Just-In-Time) 컴파일러**가 해당 코드를 기계어로 최적화한다.

```
앱 시작
  → 인터프리터로 실행 (느림)
  → JIT가 Hot Path 감지
  → JIT 컴파일 (CPU 집중, 시간 소요)
  → 최적화된 기계어로 실행 (빠름)  ← 여기까지 수십 초~수 분
```

이 과정을 **워밍업(Warmup)** 이라고 한다. Spring Boot 앱 기준으로 기동에 4~8초, JIT가 충분히 최적화되기까지 수 분이 걸린다.

### 충돌 지점

Pod가 자주 재시작될수록 JIT 워밍업을 반복해야 한다. 어렵게 최적화해둔 기계어 코드는 Pod가 죽으면 사라진다. 다음 Pod는 처음부터 다시 워밍업.

```
[배포]
  → 새 Pod 기동 (4~8초)
  → JIT 워밍업 (수 분간 성능 불안정)
  → 겨우 최적 성능 도달
  → [다음 배포] → 처음부터 반복
```

자주 배포하는 팀일수록, 트래픽 변동이 큰 서비스일수록 이 비용이 커진다.

## 문제 2: Memory Footprint vs Noisy Neighbor

### JVM은 생각보다 메모리를 많이 쓴다

JVM 프로세스가 사용하는 메모리는 `-Xmx`(최대 힙)이 전부가 아니다.

```
JVM 전체 메모리 사용량
  = Heap (비즈니스 객체)
  + Metaspace (클래스 메타데이터)
  + CodeCache (JIT 컴파일된 기계어)
  + Thread Stack (스레드마다 고정 할당)
  + Direct Buffer (NIO, 네이티브 메모리)
  + JVM 자체 오버헤드
```

실제로는 `-Xmx 512MB` 설정해도 컨테이너 전체 메모리 사용량은 700~800MB를 넘기기 쉽다. Kubernetes Pod의 메모리 리밋을 `-Xmx`와 같게 설정하면 OOMKilled가 터진다.

### Noisy Neighbor 문제

Kubernetes 노드(물리 서버) 하나에 여러 Pod가 함께 올라간다. JVM 프로세스 하나의 메모리 Footprint가 크면 같은 노드의 다른 Pod들이 쓸 메모리가 줄어든다.

```
[노드: 16GB RAM]
  ├── JVM Pod A: 힙 1GB + 오버헤드 500MB = 1.5GB
  ├── JVM Pod B: 힙 1GB + 오버헤드 500MB = 1.5GB
  ├── JVM Pod C: 힙 1GB + 오버헤드 500MB = 1.5GB
  └── 나머지 Pod들이 쓸 수 있는 메모리가 줄어듦
```

JVM Pod 하나가 예상보다 메모리를 많이 쓰기 시작하면(메모리 누수, 트래픽 급증 등), 같은 노드의 **아무 관계 없는 다른 Pod가 OOMKilled** 당할 수 있다. 내 잘못이 아닌데 피해를 입는 구조 — 이걸 **Noisy Neighbor** 문제라고 한다.

---

## 두 문제의 공통점

JVM이 나쁜 기술이라서가 아니다. JVM은 **장기 실행, 고성능 최적화** 목적으로 설계됐고, 그 목적에는 매우 잘 맞는다.

문제는 클라우드/컨테이너 환경이 요구하는 게 다르다는 것이다.
- **빠른 기동** (Pod는 자주 죽고 살아남)
- **작은 메모리** (노드 하나에 많은 Pod를 올려야 함)
- **즉각적인 피크 성능** (워밍업 시간 없이 바로 최적 성능)

이 요구사항과 JVM의 설계가 맞지 않는다.

## 대응 방향들

이 문제를 해결하려는 시도들이 나오고 있다.

**GraalVM Native Image**
JIT 대신 빌드 타임에 AOT(Ahead-Of-Time) 컴파일. 기동 시간 수십 ms, 메모리 사용량 대폭 감소. 단, 빌드 시간이 길고 JVM의 동적 기능(Reflection 등) 제약이 있음.

**CRaC (Coordinated Restore at Checkpoint)**
JVM이 워밍업된 상태를 스냅샷으로 저장. 재시작 시 스냅샷에서 복원 → 워밍업 없이 최적 성능에서 바로 시작. Spring Boot 3.2+에서 지원.

**Project Leyden**
JVM 안에서 AOT 방식으로 클래스 로딩과 JIT 캐시를 미리 준비하는 OpenJDK 프로젝트. GraalVM처럼 완전 Native가 아니라 JVM을 유지하면서 기동 시간을 단축하는 방향.

---

## 요약

- JVM은 오래 켜둘수록 빨라지는 구조 — 클라우드의 잦은 재시작과 충돌
- 기동마다 JIT 워밍업 반복 → 배포/스케일아웃 시 성능 불안정 구간 발생
- JVM 메모리는 힙 외에도 숨겨진 오버헤드가 많아 실제 사용량이 설정값보다 큼
- Footprint가 크면 같은 노드의 다른 Pod에 영향 (Noisy Neighbor)
- 대응: GraalVM Native, CRaC, Project Leyden 등 기동 시간/메모리 최적화 방향으로 진화 중
