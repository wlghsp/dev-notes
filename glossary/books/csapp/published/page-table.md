# page table (페이지 테이블)

가상 주소와 물리 주소의 매핑 정보를 담은 자료구조. OS가 프로세스마다 하나씩 만들어서 커널 영역 메모리에 저장한다.

주소록이라고 생각하면 된다. "가상 페이지 N번은 물리 프레임 M번에 있다"는 정보를 담고 있다.

## 구조

가상 주소를 두 부분으로 나눈다.

- 페이지 번호 — 페이지 테이블에서 항목을 찾는 인덱스
- 오프셋 — 페이지 안에서의 위치 (페이지 크기가 4KB면 하위 12비트)

```
가상 주소: [페이지 번호 | 오프셋]
                ↓
          페이지 테이블 조회
                ↓
물리 주소: [프레임 번호 | 오프셋]
```

오프셋은 변환 없이 그대로 쓰고, 페이지 번호만 프레임 번호로 바꾼다.

## 페이지 테이블 항목에 담긴 정보

단순히 물리 주소만 담는 게 아니다.

- 물리 프레임 번호
- 유효 비트 — 해당 페이지가 현재 메모리에 있는지 여부
- 권한 비트 — 읽기/쓰기/실행 가능 여부
- dirty 비트 — 페이지가 수정됐는지 여부 (스왑 시 디스크에 써야 하는지 판단)

유효 비트가 0이면 해당 페이지가 디스크에 있다는 뜻이다. 접근하면 page fault가 발생하고 OS가 디스크에서 메모리로 가져온다.

## 프로세스마다 별도로 존재

프로세스A와 프로세스B는 각자 페이지 테이블을 가진다. 그래서 둘 다 가상 주소 0x1000을 써도 서로 다른 물리 주소를 가리킨다. 이게 프로세스 격리의 근거다.

PCB 안에 "이 프로세스의 페이지 테이블이 메모리 어디 있는지" 포인터가 저장되어 있다. 컨텍스트 스위치 시 OS가 MMU한테 새 프로세스의 페이지 테이블 위치를 알려준다.

## 다단계 페이지 테이블

64비트 주소 공간을 페이지 테이블 하나로 만들면 테이블 자체가 너무 커진다. 가상 주소가 2^64이고 페이지 크기가 4KB(2^12)면 페이지 테이블 항목이 2^52개 필요하다. 프로세스마다 이 크기의 테이블을 메모리에 올려두는 건 불가능하다.

그래서 페이지 테이블을 계층적으로 나눈다. Linux x86-64는 4단계 페이지 테이블을 쓴다. 실제로 쓰는 주소에 해당하는 테이블만 메모리에 올려두고 나머지는 비워둘 수 있어서 메모리를 아낀다.

## TLB와의 관계

페이지 테이블이 메모리에 있기 때문에 조회할 때마다 메모리 접근이 발생한다. 모든 메모리 접근에 페이지 테이블 조회가 추가되면 2배로 느려진다.

TLB가 최근 변환 결과를 캐싱해서 이 문제를 해결한다. TLB 히트면 페이지 테이블 조회 없이 바로 물리 주소를 얻는다. 참고: tlb.md

## 오늘 나온 개념들의 연결

```
PCB → 페이지 테이블 포인터
페이지 테이블 → 가상/물리 주소 매핑
MMU → 페이지 테이블 읽어서 변환 실행
TLB → 페이지 테이블 조회 결과 캐싱
```

참고: virtual-memory.md, tlb.md, mmu.md
