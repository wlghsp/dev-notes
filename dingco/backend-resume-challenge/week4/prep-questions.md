## 1. 경합 지점 이해

- `EnrollmentService.enroll()`은 어떤 순서로 동작하는가? (스터디 조회 → `study.enroll()` 호출 → Enrollment 저장 → 집계 갱신)

: 스터디 조회 → 회원 조회 → study.enroll() 호출 → Enrollment 저장 → 집계 갱신

- `Study.enroll()`은 정원을 어떻게 확인하고 채우는가? (`isFull()`로 `enrolledCount >= capacity` 확인 → `enrolledCount + 1`)

: isFull() 로 enrollment >= capacity 확인 → enrolledCount + 1

- 이 코드에 "check-then-act"라는 경합 패턴이 있다고 할 때, check는 어디이고 act는 어디인가?

: 정원 확인이 check, 수강 수 증가가 act

- 여러 스레드가 동시에 같은 `studyId`로 `enroll()`을 호출하면, 왜 정원을 넘겨 신청이 받아질 수 있는가? (같은 `enrolledCount` 값을 여러 트랜잭션이 동시에 읽고, 각자 +1한 값을 따로 커밋하는 상황을 구체적으로 그려본다)

: 여러 스레드가 들어와 동시에 check를 하고 act를 해버림
A 스레드 B스레드가 동시에 들어와 같은 데이터인 9를 읽고 10 미만이므로 check를 통과하고 1 + 9 = 10을 실행하여 10을 2번쓰게 되므로써 
11이어야할 데이터가 10이 되어버림
원인: 
1. 같은 데이터 공유
스레드 A와 스레드 B는 격리 수준에 따라 서로 커밋되지 않거나 기존에 커밋된 데이터를 동시에 동일하게 읽어갑니다. 
두 스레드 모두 아직 9명이니까 1자리 남았네 신청 가능해 라고 판단하게 됩니다.
2. 갱신 분실과 정원 초과
두 스레드는 각각 독립적으로 9 + 1 = 10 이라는 계산을 수행합니다. 스레드 A가 먼저 반영되어 10이 되었더라도 뒤이어 스레드 B가 계산한 10을 다시 데이터베이스에 덮어씁니다. 결과적으로 DB상의 숫자는 정원인 10이지만 실제로는 스레드 A와 스레드 B를 통한 신청서 2장이 모두 정상 처리(성공)되어 정원을 넘기게 됩니다. 

## 2. 격리 수준만으로 안 막히는 이유

- MySQL(InnoDB) 기본 격리 수준(REPEATABLE READ)에서, 두 트랜잭션이 같은 `Study` 행을 동시에 읽고 각자 업데이트하면 무슨 일이 일어나는가?

: 지금 코드(`study.enroll()`의 dirty checking → 평범한 `UPDATE study SET enrolled_count = ? WHERE id = ?`)처럼 조회 시점에 아무 락도 걸지 않는 경우, REPEATABLE READ는 두 트랜잭션이 대기하게 만들지 않는다. 두 트랜잭션 모두 자신이 읽은 스냅샷(예: enrolledCount=9) 기준으로 각자 +1을 계산하고, 그대로 각자 커밋에 성공한다. 나중에 커밋하는 트랜잭션이 앞선 트랜잭션의 최신 값을 보고 대기하거나 그 값을 기준으로 다시 계산하지 않는다 — 그래서 두 트랜잭션 다 성공하지만 결과는 +1 한 번만 반영된 것처럼 남는다(Lost Update).

(참고: `SELECT ... FOR UPDATE`처럼 조회 시점에 배타 락을 거는 경우라면 얘기가 다르다. 그때는 나중 트랜잭션이 락 대기 상태가 되고, 앞선 트랜잭션이 커밋한 뒤에야 최신 값을 다시 읽고 계산한다. 이건 비관적 락의 동작이지, 지금 코드가 겪는 문제의 원인은 아니다.)

REPEATABLE READ : 한 트랜잭션 안에서 같은 데이터를 여러 번 조회할 때 항상 동일한 결과를 보여준느 데이터베이스 격리 수준
1. 일관성 보장: 트랜잭션이 시작되기 전에 커밋된 데이터만 바라보며, 트랜잭션 동중 다른 트랜잭션이 값을 수정해도 이전 데이터를 유지합니다.
2. MVCC 활용: Multi Version Concurrency Control와 Undo Log를 사용해 트랜잭션별 스냅샷을 만들어 데이터를 관리합니다.
3. 방지하는 문제: 다른 트랜잭션의 수정 때문에 조회값이 달라지는 Non-Repeatalbe Read(반복 조회 불가능)현상을 방지합니다.

Lost Update: 두 개 이상의 트랜잭션이 동일한 데이터를 동시에 읽고 수정할 때, 한 트랜잭션의 변경사항이 다른 트랜잭션의 덮어쓰기에 의해 무효화되는 동시성 데이터 문제 
정의: 먼저 처리된 트랜잭션의 결과가 나중에 커밋되는 트랜잭션에 의해 지워져 반영되지 않는 현상입니다.

- `@Transactional`이 이미 붙어 있는데도 왜 정원 초과가 막히지 않는가? 트랜잭션의 원자성(commit 단위)과 "동시에 여러 트랜잭션이 같은 초기 상태를 본다"는 문제는 왜 다른 것인가?

: @Transactional은 단순히 트랜잭션의 범위를 지정함. 데이터베이스 레벨의 다른 트랜잭션의 접근을 막는 락을 걸지 않음

원자성
- 트랜잭션 내부의 작업들이 하나의 덩어리로 처리되는지 뜻합니다.
- 중간에 에러가 나면 전부 취소하고 성공하면 전부 반영합니다. 
동시성 문제
- 여러 트랜잭션이 같은 시간에 실행되면서 서로의 연산을 덮어쓰는 논리적 문제입니다.
- 각 트랜잭션은 원자적으로 잘 끝났지만, 먼저 처리된 변경사항을 나중에 처리된 트랜잭션이 보지 못하고 이전 데이터를 기준으로 연산했기 때문에 발생

## 3. 재현 방법

- 정원 초과를 실제로 재현하려면 무엇이 필요한가? (단일 스레드 테스트로는 왜 드러나지 않는지, 여러 스레드가 동시에 같은 `studyId`에 `enroll()`을 호출하게 만들려면 무엇이 필요한지 — `ExecutorService`, `CountDownLatch` 등)


: 단일 스레드 환경에서는 코드가 순차적으로 실행되어 데이터 정합성이 개지 않아 경합 상황의 문제가 발생하지 않습니다. 

동시성 테스트를 위해 필요한 도구와 역할
1. ExecutorService(스레드 풀)
- 역할: 비동기로 실행될 스레드를 만들고 관리합니다. 
- 필요한 이유: 수십~수백 개의 스레드를 직접 생성(new Thread())하고 제어하는 것은 리소스 소모가 크고 비효율적입니다.
Executors.newFixedThreadpPool(스레드_개수)를 사용하면 지정된 개수만큼의 스레드 풀을 만들어 작업을 효율적으로 병렬 처리할 수 있습니다.

2. CountDownLatch(동기화 장치)
- 역할: 다른 스레드들이 수행 중인 작업이 완료될 때까지 대기하거나, 여러 스레드를 도잇에 출발시키는 '총잡이' 역할을 합니다.
- 필요한 이유: ExecutorService에 작업을 제출하면 스레드들이 제각각 순차적으로 실행될 수 있습니다. 우리가 원하는 것은 "동시(Simultaneous)"공격입니다. CountDownLatch(1)을 선언하고 모든 스레드가 latch.await() 대기하게 만든 뒤, 메인 스레드에서 latch.countDown()을 외치는 순간 모든 스레드가 동시에 enroll()을 호출하게 만듭니다. 

- 재현 테스트에서 "정원이 초과됐다"는 것을 어떻게 판정할 것인가? (성공한 신청 수 vs capacity, 또는 최종 `enrolledCount` vs capacity)

: 
1. 1차 판정 (로직 오류 검사): API 응답 기준으로 성공 처리된 총 인원이 정원을 넘었는가? (넘었다면 동시성 제어 실패)
2. 2차 판정 (데이터 무결성 검사): 테스트 종료 후 DB의 실제 enrolledCount가 capacity와 정확히 일치하는가? (초과했다면 치명적 버그)

- 재현 테스트는 왜 매번 같은 결과가 나오지 않을 수 있는가? (스레드 스케줄링에 따라 경합이 매번 똑같이 발생하지 않을 수 있음 — 재현율을 어떻게 보여줄 것인가)

: 스레드 스케줄링의 비결정성(Nondeterminism)때문입니다. 
- 스레드 스케줄링의 무작위성: 운영체제의 스케줄러는 CPU 자원, 다른 프로세스의 작업량, 인터럽트 등 수많은 외적 요인에 따라 스레드의 실행 순서와 타이밍을 결정합니다. 이로 인해 코드의 실행 수넛가 매번 미세하게 달라집니다.
- 레이스 컨디션: 여러 스레드가 공유 자원에 동시에 접근할 때, 타이밍이 운 좋게 맞으면 정상 작동하고 찰나의 타이밍으로 어긋나면 버그(데이터 오염, 데드락 등)가 발생합니다. 
- 자원 경합(Contention)의 가변성: CPU 코어의 개수, 메모리 대역폭, 캐시 히트율에 따라 경합이 일어나는 지점과 빈도가 매번 달라집니다.

## 4. 락 전략 선택

- 비관적 락(Pessimistic Lock)은 이 문제를 어떻게 막는가? (`SELECT ... FOR UPDATE`로 행을 잠그고 다른 트랜잭션이 대기하게 만드는 방식)

: 비관적 락은 데이터를 읽는 순간부터 락을 걸어 다른 트랜잭션의 접근을 물리적으로 차단하여 동시성 문제를 해결합니다.

비관적 락의 동작원리
1. 선점 잠금: 트랜잭션이 시작되고 데이터를 조회할 때 SELECT ... FOR UPDATE 구문을 사용해 대상 행에 배타 락을 겁니다. 
2. 대기 상태 전화: 락이 걸린 행에 다른 트랜잭션이 접근하려고 하면, 선행 트랜잭션이 끝날 때까지 대기 상태가 됩니다.
3. 락 해제: 선행 트랜잭션이 작업을 마치고 커밋이나 롤백을 수행하면 락이 풀리고, 대기 중이던 다음 트랜잭션이 실행됩니다.

배타 락: Exclusive Lock, X-Lock 데이터베이스나 운영체제에서 특정 데이터에 대해 하나의 작업(트랜잭션)만 독점적인 접근 권한을 갖도록 제한하는 잠금 장치. 읽기/수정 불가능. 
공유 락: 여러 명이 동시에 읽기 가능함. 읽기 가능/ 수정 불가능

- 낙관적 락(Optimistic Lock)은 이 문제를 어떻게 막는가? (버전 컬럼을 확인해 변경됐으면 커밋을 실패시키고 재시도하게 만드는 방식)

: 데이터베이스의 물리적인 락을 사용하지 않고, 애플리케이션 수준에서 버전 번호를 관리하여 동시성 문제를 방지합니다.

- 두 전략의 트레이드오프는 무엇인가? (비관적 락: 대기 시간·데드락 가능성 vs 낙관적 락: 재시도 로직 필요·충돌이 잦으면 재시도 비용 증가)

:
### 비관적 락
데이터 충돌이 자주 발생할 것으로 가정하고, 조회 시점에 먼저 락을 겁니다.
- 장점: 데이터 무결성을 강력하게 보장하며 충돌을 원천 차단합니다.
- 트레이드오프
  - 대기 시간 발생으로 인한 동시 처리 성능(Throughpu)저하
  - 락 대기 중 교착 상태인 데드락 발생 가능성
### 낙관적 락
데이터 충돌이 거의 없을 것으로 가정하고, 버전을 이용해 최종 수정 시점에 충돌을 감지합니다.
- 장점: 락을 직접 걸지 않아 충돌이 없을 때 성능이 매우 뛰어납니다.
- 트레이드오프
  - 충돌 발생 시 애플리케이션 레벨에서 재시도 로직 구현 필요
  - 동시 충돌이 잦으면 잦은 실패로 재시도 비용 및 오버헤드 급증

- 이 프로젝트의 상황(짧은 트랜잭션, 인기 스터디에 순간적으로 몰리는 요청)에서 어떤 락이 더 적합할 것 같은가? 그 판단의 근거는 무엇인가?

: 인기 스터디에 순간적으로 많은 요청이 몰리는 선착순 모집(수정 요청) 상황과 짧은 트랜잭션이라는 조건에서 비관적 락이 더 적합
1. 충돌 발생 빈도 : 순간적으로 동시에 신청 버튼을 누르는 경우 데이터 충돌(동시 수정) 발생 확률이 매우 높습니다.
2. 짧은 트랜잭션: 비관적 락의 단점이 다른 트랜잭션이 대기하는 것이 있으나, 트랜잭션이 짧다면 비관적 락이 적합합니다.

향후 서버를 여러 대 두는 분산환경으로 확장할 계획이라면 분산 락(Redis활용 Redisson)
- DB 부하 감소: DB레베렝서 락을 잡고 대기하는 것이 아니라, Redis 레이어에서 락 획득 가능 여부를 먼저 판단하기 때문에 DB 커넥션을 효율적으로 쓸 수 있습니다. 
- 스핀 락 방지: Redisson의 경우 Pub/Sub 기반으로 작동하여, 락이 해제되면 대기하던 요청에게 알림을 주는 방식이므로 서버 자원을 크게 아낄 수 있습니다. 
스핀 락: 락을 얻을 때까지 스레드가 무한 루프를 돌며 확인하는 동기화 메커니즘


- JPA에서 비관적 락은 어떻게 거는가? (`@Lock(LockModeType.PESSIMISTIC_WRITE)`를 리포지토리 메서드에 붙이는 방식)

: @Lock(LockModeType.PESSIMISTIC_WRITE)`를 리포지토리 메서드에 붙이는 방식. 
트랜잭션 필수이므로 이 메서드를 호출하는 서비스 계층에는 @Transactional 어노테이션 필수 

- JPA에서 낙관적 락은 어떻게 거는가? (엔티티에 `@Version` 컬럼 추가, 충돌 시 `OptimisticLockException` 처리와 재시도 로직 필요)

: 엔티티에 `@Version` 컬럼 추가, 충돌 시 `OptimisticLockException` 처리와 재시도 로직 필요
 
## 5. 트랜잭션 범위 점검

- `EnrollmentService.enroll()` 안에서 외부 호출(이메일 발송, 알림 등)처럼 트랜잭션 밖으로 빼도 되는 작업이 있는가? 지금 코드에는 그런 게 있는가, 없는가?

: 없다

- 트랜잭션 범위를 줄이는 것과 락 전략을 바꾸는 것은 왜 별개의 문제인가? (트랜잭션이 길수록 락을 오래 잡고 있어 대기·데드락 가능성이 커진다는 연결 고리)

: 둘은 서로 다른 문제를 해결한다.
- 락 전략(비관적/낙관적 선택)은 "정원 초과를 막을 것인가, 어떻게 막을 것인가"라는 정합성 문제를 해결한다. 락 전략이 없으면 아예 정원이 넘는다.
- 트랜잭션 범위 축소는 락 전략을 이미 정한 뒤, "그 락을 얼마나 오래 잡고 있을 것인가"라는 성능 문제를 해결한다.

둘이 연결되는 지점은 비관적 락을 선택했을 때다. 비관적 락은 락을 잡은 트랜잭션이 끝날 때까지 다른 트랜잭션을 대기시키므로, 트랜잭션 범위가 길어지면 그만큼 대기 시간도 길어지고 여러 자원에 락을 거는 순서가 꼬이면 데드락 가능성도 커진다. 그래서 락 전략을 비관적 락으로 정했다면, 트랜잭션 범위를 최대한 좁혀(락과 무관한 작업을 락 획득 전/후로 빼서) 대기 시간을 줄이는 작업이 따라와야 한다. 반대로 트랜잭션 범위를 아무리 줄여도, 애초에 락 전략 자체가 없으면(현재 코드처럼) 정합성 문제는 그대로 남는다 — 그래서 둘은 순서가 다른 별개의 조치다.
