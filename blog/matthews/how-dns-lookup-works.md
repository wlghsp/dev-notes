# 도메인 Lookup의 이해

## 도메인이 필요한 이유

인터넷에서 도메인이 없다면 `14.169.188.13` 같은 IP 주소를 그대로 외워야 한다. 대신 사람이 이해하기 쉬운 이름, 즉 도메인(예: `imweb.me`)을 쓴다. 그렇다면 도메인으로 IP 주소를 찾는 방법이 필요하다.

## DNS: 도메인의 IP를 찾아주는 서비스

DNS(Domain Name Server)는 도메인의 IP 주소를 찾아주는, 일종의 전화번호부다. 누구나 DNS 서버를 만들거나 운영할 수 있고, 이렇게 만들어진 DNS 서버는 Root DNS와 최신 정보를 주고받으며 동기화를 유지한다. 다만 요즘은 대부분 AWS Route53이나 Cloudflare 같은 서비스를 이용한다.

그렇다면 DNS 서버 하나가 모든 도메인의 정보를 가지고 있어야 할까? 그렇지 않다.

## 도메인 레지스트리

도메인에는 TLD(Top-Level Domain)라는 영역이 있다. `.com`은 국제 범용 TLD(gTLD), `.us`는 미국, `.kr`/`.co.kr`은 한국의 TLD다. TLD별로 각각의 DB가 있고, 이를 관장하는 국가나 단체가 관리하는데 이것이 도메인 레지스트리다.

도메인을 등록할 때 입력하는 정보는 크게 두 가지다.

- 소유자명, 주소, 이메일 등 소유권 정보
- NameServer(NS) 정보 1~4번 등

이 메타데이터는 DNS 서버가 아니라 도메인 레지스트리 DB에 저장된다. `whois`로 도메인 정보를 조회하면, 먼저 도메인 레지스트리에게 해당 도메인의 NS 서버 정보를 물어보고, 받아온 NS 서버에 다시 IP를 물어보는 방식으로 최종 IP를 얻는다.

레지스트리 DB가 물리적으로 먼 곳에 있으면 지역에 따라 응답이 느려질 수 있어서, 전 세계 엣지(edge) 서버에 복사되어 관리된다. 도메인의 NS 정보를 변경하면 반영에 하루 정도 걸리는 이유도, 레지스트리 DB 자체는 바로 업데이트되지만 전 세계 엣지 서버로 동기화되는 데 시간이 걸리기 때문이다.

## 브라우저에서 imweb.me를 찾아가는 과정

1. 브라우저에 `imweb.me`를 요청한다.
2. 내 PC의 `/etc/hosts`(윈도우는 `C:\Windows\System32\drivers\etc\hosts`) 파일에 해당 도메인의 IP가 있는지 확인한다. 있으면 바로 그 IP를 반환하고 끝난다.
3. 없으면 DNS에 인터넷으로 요청한다. 이때 `/etc/resolv.conf`에 정의된 nameserver IP를 가져와서, 그 주소로 `imweb.me`의 IP를 요청한다.
4. 이 DNS 서버가 `imweb.me`의 IP를 모를 수도 있다. 이 경우:
   - `imweb.me`에서 TLD(`.me`)를 꺼낸다.
   - `.me`를 관리하는 레지스트리에게 `imweb.me`의 NS 서버 정보(도메인 등록 시 입력한 NS 1~4번)를 요청한다.
   - 받아온 NS 서버 중 하나에 `imweb.me`의 IP를 요청한다. 이 NS 서버가 실제 IP를 갖고 있으며, 일반적으로 AWS Route53 같은 서비스가 이 역할을 한다.
   - 이 결과를 내부에 캐시하고 유저에게 IP를 반환한다.
5. IP를 받아온 브라우저는 그 주소로 데이터를 전송한다.

이 모든 과정은 대부분 0.5초 안에 끝난다.

## 여기저기 쓰이는 캐시

캐시는 첫 응답을 보관해두고, 두 번째 요청부터는 보관한 데이터를 바로 꺼내 쓰는 개념이다. IP를 찾는 과정도 두 번째 요청부터는 여러 지점에서 캐시된 데이터가 쓰인다. 그렇지 않으면 매번 전체 조회 과정을 거쳐야 해서 인터넷이 크게 느려질 것이다.

캐시가 발생하는 지점은 여러 곳이다.

- 크롬 자체가 한 번 조회한 도메인을 내부에 캐시한다. 크롬을 완전히 껐다 켜야 초기화된다.
- OS도 한 번 요청한 도메인을 로컬에 캐시한다. OS별로 DNS 캐시를 초기화하는 명령어가 있다.
- 가까운 DNS 서버가 어디인지도 캐시된다.
- DNS 서버 내부의 캐시는 사용자가 직접 지울 수 없지만, 문제가 있으면 다른 DNS 서버로 바꿔 사용하면 된다.

이렇게 여러 지점에서 각자 캐시하기 때문에 DNS 조회 결과가 모호해질 수 있다. 어디서 캐시됐는지 알아야 그에 맞게 대처할 수 있기 때문에, DNS 룩업 과정을 이해하는 것이 중요하다.
