# Andrej Karpathy의 CLAUDE.md — 한국어 해설

원문: andrej_kapathy_cladue_md.md  
출처: Andrej Karpathy가 공유한 LLM 코딩 실수 줄이기 행동 지침

---

## 이 문서가 뭔가

CLAUDE.md는 Claude(또는 다른 LLM)가 코딩 작업을 할 때 따라야 할 행동 규칙을 담은 지침 파일이다.  
프로젝트 루트에 놓으면 Claude가 대화 시작 시 자동으로 읽고 해당 규칙을 적용한다.

핵심 트레이드오프: **속도보다 신중함**. 사소한 작업에는 판단해서 적용한다.

---

## 1. Think Before Coding — 코딩 전에 먼저 생각하라

**Don't assume. Don't hide confusion. Surface tradeoffs.**  
→ 가정하지 마라. 혼란을 숨기지 마라. 트레이드오프를 드러내라.

구현 전에 해야 할 것들:

- 가정을 명시적으로 말한다. 불확실하면 묻는다.
- 해석이 여러 가지라면 그걸 제시한다. 조용히 하나를 고르지 않는다.
- 더 단순한 방법이 있으면 말한다. 필요하면 반박한다.
- 뭔가 불분명하면 멈춘다. 뭐가 헷갈리는지 이름 붙인다. 묻는다.

**왜 중요한가:**  
LLM은 불확실한 상황에서도 확신 있게 답하는 경향이 있다.  
이 규칙은 그 경향을 억제하고, 실수가 구현된 후에야 발견되는 상황을 막기 위한 것이다.

---

## 2. Simplicity First — 단순함을 먼저

**Minimum code that solves the problem. Nothing speculative.**  
→ 문제를 푸는 최소한의 코드. 추측성 코드는 없다.

- 요청 이상의 기능을 추가하지 않는다.
- 한 번만 쓰는 코드에 추상화를 만들지 않는다.
- 요청하지 않은 "유연성"이나 "설정 가능성"을 넣지 않는다.
- 불가능한 시나리오에 대한 에러 처리를 넣지 않는다.
- 200줄을 50줄로 쓸 수 있다면, 다시 작성한다.

스스로 물어볼 것: "시니어 엔지니어가 이걸 보면 너무 복잡하다고 할까?"  
그렇다면 단순화한다.

**왜 중요한가:**  
LLM은 유용해 보이려고 요청보다 많은 걸 만드는 경향이 있다.  
추측성 코드는 나중에 관리 부담이 되고, 실제로는 쓰이지 않는 경우가 많다.

---

## 3. Surgical Changes — 수술적 변경

**Touch only what you must. Clean up only your own mess.**  
→ 반드시 건드려야 하는 것만 건드린다. 자기가 만든 것만 정리한다.

기존 코드를 편집할 때:
- 옆에 있는 코드, 주석, 포맷팅을 "개선"하지 않는다.
- 망가지지 않은 것을 리팩터링하지 않는다.
- 다르게 하고 싶어도, 기존 스타일에 맞춘다.
- 관련 없는 데드 코드를 발견하면 언급만 한다 — 삭제하지 않는다.

자기 변경이 고아(orphan)를 만들 때:
- 자신의 변경이 사용하지 않게 만든 import/변수/함수는 제거한다.
- 기존에 있던 데드 코드는 요청받지 않는 한 건드리지 않는다.

판단 기준: **변경된 모든 줄이 사용자의 요청으로 직접 연결되어야 한다.**

**왜 중요한가:**  
LLM은 주변 코드를 "청소"하면서 의도치 않은 동작 변경을 만들곤 한다.  
이 규칙은 diff를 최소화하고 리뷰 부담을 줄이기 위한 것이다.

---

## 4. Goal-Driven Execution — 목표 중심 실행

**Define success criteria. Loop until verified.**  
→ 성공 기준을 정의한다. 검증될 때까지 반복한다.

작업을 검증 가능한 목표로 변환한다:
- "유효성 검사 추가" → "잘못된 입력에 대한 테스트를 작성하고, 통과시킨다"
- "버그 수정" → "재현하는 테스트를 작성하고, 통과시킨다"
- "X 리팩터링" → "전후로 테스트가 통과하는지 확인한다"

다단계 작업에는 간략한 계획을 먼저 제시한다:

```
1. [단계] → 검증: [확인 방법]
2. [단계] → 검증: [확인 방법]
3. [단계] → 검증: [확인 방법]
```

**왜 중요한가:**  
"작동하게 만들어" 같은 약한 기준은 계속 사람이 개입해야 한다.  
강한 성공 기준이 있어야 LLM이 독립적으로 루프를 돌면서 스스로 검증할 수 있다.

---

## 전체 요약

이 지침이 잘 작동하고 있다면:
- diff에 불필요한 변경이 줄어든다
- 과도한 복잡함 때문에 다시 작성하는 일이 줄어든다
- 구현 실수가 난 후가 아니라, 구현 전에 명확하게 하는 질문이 나온다

---

## 어디에 쓰는가

`CLAUDE.md` 파일은 프로젝트 루트나 `~/.claude/` 에 놓으면  
Claude가 새 대화를 시작할 때 자동으로 읽고 지침으로 적용한다.  
팀 공유 지침이나 개인 워크플로 맞춤 설정 모두 이 방식으로 관리할 수 있다.
