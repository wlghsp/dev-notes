# [강의 노트] 4강: 싱글 스레드의 한계를 넘다: 콜 스택, libuv, 이벤트 큐, 그리고 이벤트 루프 6단계 심층 해부 (2/2)

앞선 내용(콜 스택, libuv, 이벤트 큐)은 04-callstack-libuv-queue.md에서 다뤘습니다. 이어서 이벤트 루프 내부의 6단계 페이즈와 VIP 대기열의 우선순위 정책, 그리고 실전 사고 실험을 다룹니다.

## 1. 심층 해부: 이벤트 루프의 6단계 페이즈(Phases)

이벤트 루프(순찰 반장)는 하나의 대기함만 보는 것이 아니라, 특정 작업의 독점을 막기 위해 총 6개의 분리된 정거장을 순서대로 도는 순환 버스를 타고 현장을 관리합니다.

1. **Timer (타이머 정거장)**: setTimeout, setInterval 등 약속된 시간이 지난 알람 콜백들을 처리합니다. (💡 강사 팁: setTimeout(0)이라고 적어도 운영체제 타이머의 물리적 한계로 인해 정확히 0ms 만에 실행됨을 보장하지는 않습니다. 보통 최소 1ms 이상의 지연이 발생합니다.)
2. **Pending Callbacks (대기 정거장)**: TCP 오류 등 운영체제 레벨의 긴급한 에러를 처리합니다.
3. **Idle, Prepare (유휴 정거장)**: 내부 정비 시간 (개발자 코드 실행 안 됨).
4. **Poll (폴 / 핵심 대기 정거장)**: 가장 중요하고 바쁜 정거장. 파일 읽기, 데이터베이스 응답 등 대부분의 I/O 콜백이 이곳에 모입니다. 당장 처리할 일이 없으면 버스 시동을 켜둔 채 새 일거리가 올 때까지 여기서 대기합니다.
5. **Check (체크 정거장)**: setImmediate() 전용 창구입니다.
6. **Close Callbacks (종료 정거장)**: 소켓 연결 종료 등 메모리 누수를 막기 위한 뒷정리를 담당합니다.

> 💡 **[CS 실무 Point: setTimeout(0) vs setImmediate()]**
> 파일 읽기(Poll 정거장) 내부에서 이 둘을 동시에 호출하면, 순환 버스는 Poll에서 출발하여 항상 다음 정거장인 Check(5번) 정거장에 먼저 도착하므로 무조건 setImmediate()가 setTimeout(0)(1번 정거장)보다 먼저 실행됨을 보장받을 수 있습니다.

## 2. [매우 중요] 절대 권력의 VIP 대기열과 소름 돋는 새치기 현장

6단계 정거장의 룰을 완벽하게 박살 내고 새치기하는 절대 권력의 대기열이 있습니다. 이를 마이크로태스크 큐(Microtask Queue)라고 부릅니다.

**👑 엄격한 VIP 우선순위 체계 (외워두세요!)**

1. **0순위 (VVIP - 넥스트틱 큐)**: process.nextTick()의 콜백. 현장에서 가장 급한 재난 알림.
2. **1순위 (VIP - 마이크로태스크 큐)**: Promise (.then, async/await)의 콜백.
3. **2순위 (일반 시민)**: 1~6번 정거장 서류들 (setTimeout, fs.readFile 등)

**🚌 [상황극] 정거장 이동 중, VIP는 어떻게 새치기를 하는가?**

이벤트 루프 버스는 1번(Timer) 정거장에서 일을 마치고 2번(Pending) 정거장으로 그냥 쿨하게 넘어가지 않습니다. 정거장과 정거장 사이를 이동할 때마다 무조건 급브레이크를 밟고 VIP 결재함(Microtask Queue)을 쳐다봅니다. 어떤 타이머 콜백 안에서 갑자기 Promise가 생성된 상황을 상상해 보십시오.

1. 버스가 1번 정거장(Timer)에 도착하여 대기 중이던 알람 서류를 소장님께 올립니다.
2. 그런데 소장님이 알람 서류를 처리하다 보니, 그 안에 "긴급 VIP 서류(Promise) 제출 요망!"이라는 코드가 있었습니다. 즉시 VIP 결재함에 서류가 하나 꽂힙니다.
3. 1번 정거장의 서류가 다 끝났습니다. 버스는 이제 2번 정거장(Pending)으로 출발하려고 엑셀을 밟습니다.
4. [새치기 발생!] 엑셀을 밟으려던 찰나, 버스는 급브레이크를 밟습니다! 방금 전 접수된 VIP 결재함에 불이 들어왔기 때문입니다.
5. 버스는 2번 정거장으로 가는 것을 멈추고, 즉시 VIP 결재함부터 열어서 방금 접수된 Promise 서류를 소장님께 올립니다.
6. VIP 결재함이 완전히 텅텅 빈 것을 확인한 후에야, 비로소 버스는 2번 정거장으로 출발합니다.

> 💡 **[CS 실무 Point: 최신 Node.js의 극한의 VIP 우대]**
> Node.js 11 버전 이후부터는 우선순위가 더욱 깐깐해졌습니다. 정거장을 이동할 때뿐만 아니라, 정거장 안에서 일반 서류를 딱 1장 처리할 때마다 매번 VIP 결재함을 쳐다봅니다. 1번 정거장에 서류가 10장 있어도, 1장 처리 후 VIP 서류가 생기면 나머지 9장을 버려두고 VIP부터 처리하는 극한의 새치기가 발생합니다.

**[시각화] 정거장 이동 중 VIP 새치기 발생의 순간**

```javascript
setTimeout(() => {
    console.log('1. 알람 처리 중...');
    Promise.resolve().then(() => console.log('2. [새치기] 긴급 프로미스 생성!'));
}, 0);
```

```
[ 일반 1번 정거장 (Timer) 처리 완료 직후의 순간 ]
--------------------------------------------------
[ Call Stack ] : (알람 처리 완료로 텅 빔)

[ VIP 결재함 (Promise) ] : [ '2. [새치기] 긴급 프로미스 생성!' ] <-- 방금 접수됨!

[ 일반 2번 정거장 (Pending) ] : (여기로 넘어가야 하지만...)

▶ 이벤트 루프의 행동:
"잠깐! 2번 정거장으로 가기 전에 VIP 함에 서류가 있네? 무조건 저것부터 콜 스택으로 올려!"
결과적으로 2번 정거장으로 가기 전, Promise가 중간에 가로채어 실행됩니다.
```

> 💡 **[CS 실무 Point: 기아 현상 (Starvation) 발생]**
> 만약 개발자가 process.nextTick이나 Promise를 재귀적으로 끝없이 호출하면 어떻게 될까요? 이벤트 루프는 VVIP 서류만 쳐내느라 1번(Timer) 정거장이나 4번(Poll) 정거장으로 영원히 버스를 출발시키지 못합니다. 데이터베이스 응답이나 유저 접속 요청이 평생 대기상태에 빠져 굶어 죽는 기아 현상(Starvation)이 발생합니다.

## 3. [실전 훈련] 사고 실험: 상태 누적 시각화 추적하기

이제 코드가 한 줄씩 실행될 때마다 소장님 책상과 대기함에 서류가 어떻게 쌓이고 빠지는지 눈으로 직접 추적해 보겠습니다. (면접 단골 질문입니다.)

```javascript
console.log("A: 현장 출근 (동기)");
setTimeout(() => console.log("B: 알람 (Timer 정거장)"), 0);
Promise.resolve().then(() => console.log("C: VIP 결재 (Promise)"));
console.log("D: 현장 퇴근 (동기)");
```

**[Step 1] 동기 코드 즉시 실행**
```
▶ 출력: "A: 현장 출근"
[ Call Stack ] : console.log("A") 실행 후 즉시 비워짐.
[ VIP 결재함 ] : (비어 있음)
[ 일반 1번 정거장 ] : (비어 있음)
```

**[Step 2] setTimeout과 Promise 등록**
```
* 소장님이 지시만 내리고 책상을 즉시 치웁니다.
[ Call Stack ] : (비어 있음)
[ VIP 결재함 ] : [ "C: VIP 결재" ] <-- 우선순위 높은 Promise 대기
[ 일반 1번 정거장 ] : [ "B: 알람" ] <-- 0초 뒤 실행 예약 대기
```

**[Step 3] 마지막 동기 코드 실행 및 콜 스택 비워짐**
```
▶ 출력: "D: 현장 퇴근"
[ Call Stack ] : console.log("D") 실행 후 완전히 텅 빔!
* 소장님 책상이 텅 빈 이 순간, 이벤트 루프(순찰 반장)가 움직입니다.
```

**[Step 4] 이벤트 루프의 개입 (무조건 VIP 먼저!)**
```
* 이벤트 루프는 일반 정거장에 일이 있어도, 무조건 VIP 결재함부터 열어서 올립니다.
▶ 출력: "C: VIP 결재"
[ Call Stack ] : (VIP 서류 처리 후 비워짐)
[ VIP 결재함 ] : (완전히 텅 빔!)
[ 일반 1번 정거장 ] : [ "B: 알람" ] <-- 여전히 대기 중
```

**[Step 5] 일반 정거장 처리 (마무리)**
```
* VIP 결재함이 비워진 것을 확인하고 나서야 일반 1번 정거장으로 버스가 향합니다.
▶ 출력: "B: 알람"
[ Call Stack ] : (일반 서류 처리 완료)
[ VIP 결재함 ] : (비어 있음)
[ 일반 1번 정거장 ] : (비어 있음)
```

**최종 출력 순서: A -> D -> C -> B**

이 시각화의 흐름이 머릿속에 자리 잡으셨다면, 단일 스레드의 한계를 비동기 콜백 큐와 스레드 풀 위임으로 돌파하는 하이브리드 아키텍처를 완벽하게 통찰하신 것입니다. 앞으로 마주할 어떠한 복잡한 백엔드 병목 문제도 이 뼈대를 바탕으로 진단할 수 있습니다.
