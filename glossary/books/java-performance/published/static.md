# static
참고: Java Performance: The Definitive Guide Ch.7 (GC Root 관련 서술 일부). 그 외 내용은 일반 Java 지식

---

static 키워드는 필드나 메서드를 인스턴스가 아니라 클래스 자체에 귀속시킨다. static이 나쁜 것은 아니다. 다만 남발하면 문제가 생기는 이유가 있다.

---

## 인스턴스 필드와 다른 점

인스턴스 필드는 객체마다 힙에 따로 존재한다. 그 객체가 더 이상 참조되지 않으면 GC가 회수한다. 참고: stack-vs-heap.md

static 필드는 클래스당 하나만 존재한다. 클래스 메타데이터가 Method Area(Metaspace)에 로드되어 있는 한 계속 살아있고, 개별 인스턴스의 생존 여부와 무관하다. 참고: jvm-memory-areas.md

---

## 남발하면 안 되는 이유

### 상태 공유로 인한 동시성 문제

모든 인스턴스, 모든 스레드가 같은 static 필드를 공유한다. 한 스레드가 값을 바꾸면 다른 스레드도 그 변경을 그대로 본다. 별도 동기화 없이 static 변수를 여러 스레드에서 수정하면 race condition이 생긴다.

### 메모리 누수 (GC Root 문제)

static 필드는 GC Root의 한 종류다. static 변수가 참조를 들고 있으면, 그 참조 사슬 끝에 있는 객체는 아무도 안 쓰더라도 GC가 회수하지 못한다. 클래스가 언로드되기 전까지 static 변수 자체가 계속 살아있기 때문이다. static List에 계속 add만 하고 remove를 안 하면 대표적인 누수 패턴이 된다.

### 테스트와 설계 결합도

static 메서드나 static 상태에 의존하는 코드는 목(mock)으로 교체하기 어렵다. 인스턴스 기반 설계라면 인터페이스로 갈아끼울 수 있는 지점이, static 호출로 박히면 그 유연성이 사라진다.

---

## static이 적절한 경우

- 상수: `static final`
- 상태가 전혀 없는 순수 유틸리티 메서드: `Math.max` 같은 경우
- 클래스 전체에서 진짜로 하나만 있어야 하는 값

기준은 "이 필드/메서드가 인스턴스별로 달라야 하는가, 아니면 진짜로 전역이어야 하는가"다. 후자가 아니라면 인스턴스 필드로 두는 편이 안전하다.
