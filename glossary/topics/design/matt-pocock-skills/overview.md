## 이 레포가 뭔가

Matt Pocock이 실제 엔지니어링 작업에서 매일 쓰는 Claude Code 슬래시 커맨드 모음.
"바이브 코딩"이 아니라 실제 소프트웨어 엔지니어링 원칙을 AI 에이전트에 적용하기 위해 만들었다.

핵심 주장: GSD, BMAD, Spec-Kit 같은 프레임워크는 프로세스 전체를 AI가 소유하게 만들어
제어를 빼앗기고 버그가 숨는다. 이 skills는 작고, 적응하기 쉽고, 조합 가능하다.

---

## 왜 이게 필요한가 — 4가지 문제

### 문제 1: 에이전트가 원하는 걸 안 만든다

사람도, AI도 요구사항 전달이 잘 안 된다. 커뮤니케이션 갭이 항상 존재한다.
해결책: 만들기 전에 에이전트가 사용자를 철저하게 인터뷰하는 "grilling session".

### 문제 2: 에이전트가 너무 장황하다

에이전트가 프로젝트 전문 용어를 모르면 20단어로 설명할 것을 1단어로 못 한다.
해결책: 프로젝트 공용 언어(ubiquitous language)를 CONTEXT.md에 정의해서 공유.

### 문제 3: 코드가 동작을 안 한다

피드백 루프 없이 에이전트는 눈감고 코딩한다.
해결책: 테스트 주도 개발. 실패 테스트 먼저, 코드 나중. 빨간 것 → 초록 것 → 리팩토링.

### 문제 4: 엉망진창 코드베이스가 된다

AI로 코딩하면 소프트웨어 엔트로피가 전례 없는 속도로 가속된다.
해결책: 코드 설계에 투자하는 습관. 깊은 모듈(작은 인터페이스, 많은 구현) 지향.

## 핵심 개념들

### User-invoked vs Model-invoked

스킬에는 두 종류가 있다.

User-invoked: 사람이 `/명령어`로 직접 호출. SKILL.md에 `disable-model-invocation: true` 표시.
오케스트레이션 역할을 한다. 다른 user-invoked 스킬은 절대 호출하지 않는다.

Model-invoked: 에이전트가 상황에 맞게 자동 호출하거나 사람도 호출 가능.
재사용 가능한 규율(discipline)을 담는다.
user-invoked 스킬이 model-invoked 스킬을 호출하는 건 정상.

### Deep Module 설계 철학

codebase-design 스킬에서 정의하는 핵심 어휘:

모듈: 인터페이스와 구현을 가진 모든 것. 함수, 클래스, 패키지. "서비스"나 "컴포넌트"라 부르지 않는다.

인터페이스: 호출자가 모듈을 올바르게 사용하기 위해 알아야 할 모든 것.
타입 시그니처뿐 아니라 불변식, 순서 제약, 에러 모드, 성능 특성까지 포함.

깊이(Depth): 인터페이스 대비 동작의 양. 작은 인터페이스 뒤에 많은 구현이 있으면 깊다.

이음새(Seam): 그 위치를 수정하지 않고 동작을 바꿀 수 있는 지점.
참고: loose-coupling.md, cohesion.md

깊은 모듈 = 작은 인터페이스 + 많은 구현. 이게 목표.
얕은 모듈 = 큰 인터페이스 + 적은 구현. 이걸 피한다.

삭제 테스트: 이 모듈을 지우면 어떻게 되나? 복잡도가 한 곳에 모이면 가치 있는 모듈.
복잡도가 여러 호출자로 흩어지면 얕은 모듈.

### TDD 수직 슬라이스

tdd 스킬의 핵심 반패턴 경고:

수평 슬라이스(하면 안 됨):
- RED 단계에서 테스트 전체를 쓴다
- GREEN 단계에서 구현 전체를 쓴다
- 결과: 상상된 동작을 테스트하게 됨. 실제 동작을 테스트 못함.

수직 슬라이스(올바른 방법):
- 테스트 하나 → 구현 하나 → 반복
- 각 테스트는 이전 사이클에서 배운 것을 반영

좋은 테스트의 기준:
- 공개 인터페이스로만 동작을 검증한다
- 내부 구현이 바뀌어도 테스트는 안 깨진다
- "user can checkout with valid cart" 같이 동작을 서술한다

나쁜 테스트의 기준:
- 내부 협력자를 모킹한다
- private 메서드를 테스트한다
- 리팩토링하면 깨진다

### 버그 진단 6단계

diagnosing-bugs 스킬의 핵심:

1단계: 피드백 루프 구축. 이게 전부다. 빨간 신호를 줄 수 있는 명령어 하나 없으면 다음 단계 없음.

피드백 루프 구축 수단 (이 순서로 시도):
1. 실패하는 테스트
2. curl/HTTP 스크립트
3. CLI 호출 + 스냅샷 비교
4. 헤드리스 브라우저 스크립트
5. 캡처된 트레이스 재생
6. 일회용 하네스
7. 속성/퍼즈 루프
8. 이분 탐색 하네스
9. 차분 루프
10. HITL bash 스크립트 (최후 수단)

피드백 루프 완료 기준: 이미 한 번 실행해봤고, 이 특정 버그를 잡을 수 있고, 결정론적이고, 빠르고, 에이전트가 혼자 실행 가능.

2단계: 재현 + 최소화. 재현 후 더 작게 만든다. 모든 요소가 필수적일 때까지.

3단계: 3-5개 가설 생성 및 순위 결정. 가설 하나만 있으면 첫 번째에 고착된다.
각 가설은 반증 가능해야 한다. "X가 원인이면, Y를 바꾸면 버그가 사라진다"는 형식.

4단계: 계측. 가설당 프로브 하나. 한 번에 변수 하나.
디버그 로그는 고유 접두사 [DEBUG-a4f2] 붙이기. 나중에 grep으로 일괄 삭제.

5단계: 수정 + 회귀 테스트. 올바른 이음새가 있으면 수정 전에 테스트 먼저.

6단계: 정리 + 사후 분석. 모든 디버그 로그 제거. 이 버그를 예방했을 설계 변화가 있으면 /improve-codebase-architecture에 넘긴다.

### CONTEXT.md와 도메인 공용 언어

도메인 모델을 CONTEXT.md 파일에 기록한다.

CONTEXT.md는 오직 용어집. 구현 세부사항, 스크래치패드, 스펙 용도로 쓰지 않는다.

ADR(Architecture Decision Record)을 만드는 기준 3가지를 모두 만족해야:
1. 되돌리기 어렵다
2. 맥락 없이 보면 이상해 보인다
3. 실제 트레이드오프가 있었다

하나라도 빠지면 ADR 만들지 않는다.

### teach 스킬의 학습 구조

/teach는 단순 설명이 아니라 여러 세션에 걸친 학습 워크스페이스를 구축한다.

파일 구조:
- MISSION.md: 이걸 왜 배우는지. 모든 레슨의 근거.
- reference/*.html: 빠른 참조용 압축 지식
- RESOURCES.md: 신뢰할 수 있는 외부 자료 목록
- learning-records/*.md: ADR처럼 핵심 인사이트 기록
- lessons/*.html: 하나씩 완결되는 레슨 파일

유창성(fluency) vs 저장 강도(storage strength) 구분:
유창성은 지금 당장 떠올리는 능력. 저장 강도는 장기 기억.
유창성이 높아도 저장 강도가 낮으면 착각. 실제 학습은 저장 강도를 키워야 한다.

저장 강도를 키우는 방법:
- 인출 연습(recall from memory)
- 간격 반복(spacing)
- 교차 연습(interleaving) — 스킬 연습에만 해당

## 바로 적용 가능한 원칙

첫째, 코드 작성 전 grilling. 무엇을 만들지 명확히 하지 않고 시작하면 항상 다시 한다.

둘째, TDD 수직 슬라이스. 테스트 전체를 먼저 쓰는 습관이 있다면 지금 당장 고쳐야 한다.

셋째, 버그 진단 시 피드백 루프 먼저. 코드를 읽고 가설을 세우기 전에 재현 명령어부터.

넷째, 깊은 모듈 지향. 인터페이스가 단순한가? 호출자가 알아야 할 게 최소인가?

다섯째, CONTEXT.md. 프로젝트에 용어집 파일 하나. 에이전트와 사람 모두 같은 언어를 쓴다.
