# 구글 검색창에 검색하면 무슨 일이 일어나는가

면접에서 자주 나오는 빅픽처 질문. 네트워크, DNS, TCP, TLS, HTTP를 한 흐름으로 꿰뚫어야 한다.

---

## 전체 흐름 요약

1. DNS 조회 — 도메인을 IP로 변환
2. TCP 연결 — 3-way handshake
3. TLS 핸드셰이크 — 암호화 채널 수립
4. HTTP 요청 전송 — 실제 검색 요청
5. 서버 처리 — 구글 서버가 응답 생성
6. HTTP 응답 수신 — HTML 받기
7. 브라우저 렌더링 — 화면에 결과 표시

---

## 1단계: DNS 조회

브라우저 주소창에 `google.com`을 입력하면 브라우저는 IP 주소를 모른다. DNS가 이걸 해결한다.

조회 순서:
1. 브라우저 캐시 확인
2. OS 캐시 확인 (`/etc/hosts` 포함)
3. 로컬 DNS 리졸버(보통 공유기 or ISP)에 질의
4. 로컬 리졸버가 캐시 없으면 루트 네임서버 → `.com` 네임서버 → `google.com` 네임서버 순으로 재귀 조회
5. 최종적으로 `142.250.x.x` 같은 IP 주소 반환

DNS 조회 자체도 UDP 53번 포트를 쓰는 네트워크 통신이다. 응답이 크면 TCP로 전환된다.

---

## 2단계: TCP 3-way Handshake

IP를 알았으니 이제 연결을 맺는다. TCP는 데이터 전송 전에 반드시 연결을 먼저 수립한다.

```
클라이언트 → 서버: SYN (연결 요청)
서버 → 클라이언트: SYN-ACK (수락 + 확인)
클라이언트 → 서버: ACK (확인 완료)
```

이 3번의 패킷 교환이 끝나야 연결이 성립된다. HTTPS니까 이 위에 TLS가 또 올라온다.

---

## 3단계: TLS 핸드셰이크

TCP 연결 위에서 암호화 채널을 수립한다. HTTPS = HTTP + TLS.

핵심 흐름 (TLS 1.3 기준):
1. 클라이언트가 지원하는 암호화 방식 목록 전송 (ClientHello)
2. 서버가 인증서와 선택한 암호화 방식 전송 (ServerHello)
3. 클라이언트가 인증서 검증 (CA 체인 확인)
4. 세션 키 교환 (공개키 암호화 방식으로)
5. 이후 통신은 세션 키로 대칭 암호화

TLS 핸드셰이크까지 마치면 실제 HTTP 요청을 보낼 수 있는 상태가 된다.

참고: tls.md

---

## 4단계: HTTP 요청 전송

TLS 채널 위에서 HTTP 요청을 보낸다.

```
GET /search?q=검색어 HTTP/2
Host: www.google.com
User-Agent: Chrome/...
Accept: text/html
```

이 요청이 암호화된 채로 구글 서버에 도달한다.

---

## 5단계: 서버 처리

구글 서버는 요청을 받아서:
- 검색 쿼리 파싱
- 인덱스 조회 및 랭킹 계산
- HTML 응답 생성

이 과정은 구글 내부 시스템 (수천 대의 서버, 분산 인덱스 등) 이야기라 면접에서는 "서버에서 처리 후 응답 반환"으로 요약하면 충분하다.

---

## 6단계: HTTP 응답 수신

서버가 응답을 보낸다.

```
HTTP/2 200 OK
Content-Type: text/html
...

<html>...</html>
```

TCP는 이 데이터를 여러 세그먼트로 나눠서 전송한다. 순서 보장과 재전송은 TCP가 처리한다.

---

## 7단계: 브라우저 렌더링

HTML을 받은 브라우저는:
1. HTML 파싱 → DOM 트리 생성
2. CSS 파싱 → CSSOM 생성
3. DOM + CSSOM → 렌더 트리
4. 레이아웃 계산 → 화면에 페인팅

HTML 안에 CSS, JS, 이미지 링크가 있으면 각각에 대해 추가 HTTP 요청이 발생한다. 이미 TCP 연결이 맺어져 있으니 재사용한다 (HTTP/2는 같은 연결에서 병렬 요청 가능).

---

## 면접에서 포인트

이 질문의 의도는 "얼마나 깊이 아는가"를 계층별로 확인하는 것이다. 단순 나열이 아니라 각 단계에서 왜 그게 필요한지를 설명할 수 있어야 한다.

자주 파고드는 포인트:
- DNS가 왜 필요한가 (IP를 직접 쓰면 되지 않나)
- TCP 3-way handshake가 왜 3번인가 (2번으로는 왜 안 되나)
- TLS에서 인증서를 왜 검증하는가 (중간자 공격 방지)
- HTTP/1.1과 HTTP/2의 차이 (멀티플렉싱)
- 캐시는 어디서 작동하는가 (DNS 캐시, 브라우저 캐시, CDN)

참고: osi-communication-flow.md, tls.md
