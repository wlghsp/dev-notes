# Handshake

두 시스템이 통신을 시작하기 전에 서로의 상태와 조건을 맞추는 과정. 데이터를 주고받기 전에 "준비됐어?" 를 확인하는 절차다.

---

## TCP 3-way Handshake

TCP 연결을 맺을 때 발생한다. 신뢰성 있는 연결을 수립하기 위해 3번의 패킷을 교환한다.

```
클라이언트 → 서버: SYN       (연결 요청, 임의의 시퀀스 번호 n 전송)
서버 → 클라이언트: SYN-ACK   (수락, 서버 시퀀스 번호 m + ACK n+1)
클라이언트 → 서버: ACK       (확인, ACK m+1)
```

왜 3번인가: 2번으로는 서버가 클라이언트의 수신 능력을 확인할 수 없다. 3번째 ACK를 통해 양방향 통신이 모두 가능함을 확인한다.

시퀀스 번호를 임의의 난수로 시작하는 이유: 이전 연결의 패킷과 현재 연결의 패킷이 섞이는 것을 방지하기 위해서다.

---

## TCP 4-way Handshake

TCP 연결을 끊을 때 발생한다. 연결 수립보다 한 단계 더 많은 이유는 양쪽이 각각 독립적으로 종료 의사를 표현해야 하기 때문이다.

```
클라이언트 → 서버: FIN       (연결 종료 요청)
서버 → 클라이언트: ACK       (확인, 서버는 아직 데이터 보낼 수 있음)
서버 → 클라이언트: FIN       (서버도 종료 준비 완료)
클라이언트 → 서버: ACK       (최종 확인)
```

마지막 ACK 이후 클라이언트는 바로 연결을 끊지 않고 일정 시간(TIME_WAIT) 대기한다. 마지막 ACK가 유실됐을 때 서버가 FIN을 재전송하면 받을 수 있어야 하기 때문이다.

## TLS Handshake

TCP 연결 위에서 암호화 채널을 수립할 때 발생한다. SSL Handshake라고도 부르는데, SSL이 TLS의 전신이라 관습적으로 혼용된다. 정확한 명칭은 TLS Handshake다.

TLS 1.3 기준 흐름:

```
클라이언트 → 서버: ClientHello  (지원하는 암호화 방식 목록, 클라이언트 난수)
서버 → 클라이언트: ServerHello  (선택한 암호화 방식, 서버 인증서, 서버 난수)
클라이언트: 인증서 검증           (CA 체인 확인, 서버가 진짜인지 검증)
클라이언트 → 서버: 키 교환       (세션 키 생성에 필요한 정보 전달)
이후 통신: 세션 키로 대칭 암호화
```

인증서를 검증하는 이유: 중간자 공격(MITM)을 막기 위해서다. 내가 연결한 서버가 진짜 google.com인지 확인하지 않으면, 공격자가 중간에서 트래픽을 가로챌 수 있다.

공개키 암호화와 대칭키 암호화를 함께 쓰는 이유: 공개키 암호화는 안전하지만 느리다. 세션 키를 공유할 때만 공개키 암호화를 쓰고, 실제 데이터 통신은 빠른 대칭키 암호화로 처리한다.

## 핸드셰이크가 일어나는 순서

HTTPS 통신 기준으로 세 가지가 순서대로 발생한다.

```
TCP 3-way Handshake → TLS Handshake → HTTP 요청/응답
```

TCP가 연결을 만들고, 그 위에서 TLS가 암호화 채널을 수립하고, 그 다음에야 실제 데이터가 오간다.

---

## HTTP/3에서의 변화

HTTP/3는 TCP 대신 UDP 기반의 QUIC 프로토콜을 사용한다. QUIC은 TCP 연결 수립과 TLS 핸드셰이크를 한 번에 처리해서 연결 지연을 줄인다. TCP 3-way Handshake가 없어지는 것이 핵심 개선점이다.
