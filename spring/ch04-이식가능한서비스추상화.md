# 제2편 4장, 이식 가능한 서비스 추상화

이 챕터에서 생성된 키워드 파일: service-abstraction.md

원본: 스프링 프로그래밍 배우기 (springrunner.dev)

---

## 이 장에서 다루는 것

2, 3장이 IoC 컨테이너와 빈이라는 스프링의 기본 골격을 다뤘다면, 이 장은 그 위에서 스프링이 엔터프라이즈 기술(트랜잭션, 데이터 접근, 리소스 접근 등)을 어떻게 일관되게 다룰 수 있게 해주는지를 다룬다.

## 이식 가능한 서비스 추상화란

환경과 구현 기술이 바뀌어도 일관된 방식으로 그 기술을 다룰 수 있게 하는 원리다.
2장에서 본 전략 패턴 구조와 본질적으로 같다. 비즈니스 오브젝트(POJO)는 추상화된 인터페이스에만 의존하고, 실제 구현 기술은 갈아 끼울 수 있다.

이 장의 예시는 XmlMovieReader다.
XmlMovieReader가 자바 객체와 XML 데이터를 주고받을 때 Object-XML 매퍼(Marshaller and Unmarshaller)라는 추상화를 사용한다.
그 추상화 뒤에서 JAXB, JiBX, XStream 중 어떤 라이브러리가 실제 변환을 수행하는지는 XmlMovieReader가 알 필요가 없다.
구현 기술이 바뀌어도 비즈니스 오브젝트의 코드는 그대로 유지된다.

트랜잭션(transaction), 캐시(cache), 메일(mail), 메시징(messaging), Object/XML Mapping(OXM)이 대표적으로 서비스 추상화가 제공되는 영역이다.

## 저수준 리소스 접근을 위한 Resource 인터페이스

파일, 클래스패스, HTTP 등 저수준 리소스에 접근하는 방법은 원래 제각각이다.
자바 표준 `java.net.URL`과 그 접두사 체계만으로는 이 다양한 소스를 다루기에 부족하다.
스프링은 `Resource` 인터페이스로 이 문제를 해결했다. `ClassPathResource`, `FileSystemResource`, `UrlResource`, `ServletContextResource` 등 접두사에 따라 알맞은 구현체를 반환한다.

```java
Resource resource = applicationContext.getResource("classpath:template.tml");
Resource resource = applicationContext.getResource("file:./files/template.tml");
```

애플리케이션 컨텍스트는 `ResourceLoader` 인터페이스를 확장하고 있어서, 컨테이너 자체가 리소스 로더 역할을 겸한다.
접두사를 지정하지 않으면 컨텍스트 타입에 맞는 기본 방식으로 자원을 찾는다. 자세한 내용은 service-abstraction.md에 정리했다.

## 구체적인 데이터베이스 기술을 숨기는 서비스 추상화

JDBC API를 직접 쓰면 커넥션 획득부터 SQL 실행, 예외 처리, 자원 반환, 트랜잭션 제어까지 반복 코드가 상당히 길어진다.
스프링의 데이터 접근 서비스 추상화(`JdbcTemplate`, 트랜잭션 매니저)를 쓰면 이 반복 코드와 구현 기술에 종속적인 코드를 걷어낼 수 있다.

일관된 프로그래밍 모델로 트랜잭션을 제어할 수 있다는 점, 그리고 데이터베이스마다 다른 예외를 스프링이 정의한 일관된 예외 계층으로 다룰 수 있다는 점이 핵심이다.

## 정리

이 장의 핵심은 "구체적인 기술을 비즈니스 오브젝트로부터 숨긴다"는 한 문장으로 요약된다.
2장의 IoC/DI가 객체 사이의 의존관계를 인터페이스 경계로 옮겼다면, 서비스 추상화는 엔터프라이즈 기술 자체를 인터페이스 경계로 옮긴 것이다.
다음 장(관점지향 프로그래밍)은 이 두 축(핵심 로직, 엔터프라이즈 기술)과는 또 다른 세 번째 축, 즉 로깅이나 트랜잭션 관리처럼 애플리케이션 전반에 걸쳐 필요한 부가기능을 어떻게 다루는지를 다룬다.
