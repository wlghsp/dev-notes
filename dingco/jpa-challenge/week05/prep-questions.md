## A-1. 근거형 질문 직결 개념

정답은 안 적는다. 각 질문에서 무엇을 코드로 직접 확인해야 답이 나오는지만 짚는다.

- N+1은 LAZY와 EAGER 중 어느 쪽에서 발생하며 본질적인 원인은 무엇인가?
  - 확인할 것: Todo 목록을 조회한 뒤 각 Todo의 `user`에 접근했을 때, LAZY일 때와 EAGER일 때 각각 SQL이 몇 번 발생하는지. "지연 로딩이 원인"이라고 단정하기 전에 EAGER로도 N+1이 재현되는지 직접 실험해봐야 한다(week3의 "LAZY로 선언해도 N+1이 발생할 수 있는 이유"와 이어지는 지점).

양쪽 모두에서 발생할 수 있음. 
본질적인 원인
1. JPQL과 SQL의 패러다임 불일치
JPA의 JPQL은 연관 관계 테이블을 자동으로 조인해서 가져오지 않습니다. 오직 대상 엔티티 자체만을 타겟으로 SQL 쿼리를 빌드합니다. 
2. 객체 그래프 탐색의 한계
데이터베이스는 조인을 통해 한 번에 묶어서 데이터를 가져오는 것이 효율적입니다. 반면 JPA는 객체 간의 연관 관계를 맺고 있기 때문에 연관 데이터를 
가져올 때 '조인 쿼리'가 아니라 연관 엔티티 ID를 조건으로 하는 개별 SELECT 쿼리를 추가로 던지게 설계되어 있습니다. 이로 인해 최초 쿼리 1개 외에 데이터 수만큼의 추가 쿼리가 발생하는 것입니다. 

- 선택한 조회 최적화 방식(fetch join 또는 DTO projection)이 다른 대안보다 현재 요구에 맞는 이유는 무엇인가?
  - 확인할 것: fetch join 적용 시 실제 SQL이 어떻게 바뀌는지(조인 1개로 줄어드는지), DTO projection 적용 시 SELECT 컬럼이 필요한 것만 남는지. 두 방식을 각각 시도해보고 쿼리 수·응답 데이터 형태·엔티티 영속 여부(fetch join은 영속 엔티티, DTO projection은 비영속 DTO)가 어떻게 다른지 비교해야 "왜 이걸 골랐는지" 방어할 수 있다.

화면에 정확히 필요한 데이터만 필터링하여 네트워크 성능을 최적화하고 불필요한 메모리 낭비를 줄일 수 있기 때문입니다. 


- QueryDSL 조건 조합에서 null·빈 값 경계를 어떤 규칙과 테스트로 고정했는가?
  - 확인할 것: 조건 DTO의 필드가 null일 때 QueryDSL의 `BooleanExpression`이 어떻게 동작하는지(where절에서 자동으로 빠지는지, 아니면 명시적으로 null 체크를 해야 하는지). 빈 문자열("")과 null을 같은 값으로 취급할지 다르게 취급할지도 결정하고 테스트로 고정해야 한다.

QueryDSL은 BooleanExpression이 null을 반환하면 where 절에서 해당 조건을 자동으로 무시합니다. 이를 안전하게 활용하기 위해 다음 세 가지 규칙을 적용합니다. 

1. Null-Safe Wrapper 활용: Optional 또는 자체 유틸리티 메서드를 구현하여 입력값이 null 이거나 공백 문자열일때 null을 반환하도록 설계합니다. 
2. String 단위의 빈값 검증: 단순 null 체크만으로는 "" 또는 " " 같은 빈 값을 거를 수 없습니다. StringUtils.hasText()를 반드시 조합합니다. 
3. Collection의 isEmpty 검증: List 등 컬렉션 파라미터는 null 뿐만 아니라 isEmpty() 상태일 때 동적 쿼리에서 제외되도록 명시적인 방어 코드를 작성합니다. 

- 1차 캐시와 fixture INSERT가 쿼리 수 측정을 오염하지 않도록 어떤 순서로 통제했는가?
  - 확인할 것: fixture로 넣은 Todo/User가 영속성 컨텍스트에 그대로 남아있으면 측정 대상 조회 시 1차 캐시 때문에 SELECT가 안 나갈 수 있다. `em.flush()` + `em.clear()`로 1차 캐시를 비운 뒤 `observation.reset()`을 호출하는 순서가 맞는지, week4까지 이 순서를 어떻게 지켰는지 되짚어봐야 한다.

테스트 환경에서 정확한 쿼리 수를 측정하기 위해서는 1차 캐시(영속성 컨텍스트)를 비우는 작업(clear)과 fixture INSERT 의 실행 시점을 엄격하게 통제해야 합니다. 이를 통제하지 않으면 실제 비즈니스 로직 외에 테스트 데이터 삽입 쿼리나 1차 캐시에 남은 엔티티 조회로 인해 결과가 왜곡됩니다. 

## A-2. 실험 설계 전에 확정해야 하는 것

- 동적 조회 조건은 무엇 2개 이상을 조합할 것인가? (예: Todo의 title 부분 일치 + User의 username 일치, 또는 title + 특정 user 소유 여부)

Todo 서비스 기준 추천 조합
가장 직관적이며 실제 관리자나 사용자가 많이 사용하는 조건입니다.
- 조합: Todo 제목 부분 일치(Like) + 담당자(Username) 일치
  - 설명: 특정 사용자가 담당하고 있는 할 일 중, 특정 키워드가 포함된 할 일을 찾을 때 사용합니다.
- 조합: Todo 완료 여부(Status) + 특정 유저 소유 여부(User ID)
  - 설명: "내가 작성한 할 일 중 아직 완료되지 않은 것만 보기"와 같은 필터링 기능에 필수적입니다.
- 조합: 생성일 범위(Date Range) + 카테고리/태그(Category)
  - 설명: "이번 주에 생성된 할 일 중 '업무' 태그가 붙은 것만 조회"할 때 사용합니다.

- 조건 DTO를 어떻게 설계할 것인가? 모든 필드가 optional(null 허용)이어야 하는 이유는 무엇인가?

조건 DTO 설계
1. 하나의 객체로 묶기
2. 불변 객체 지향
3. 타입 안정성 확보

모든 필드가 optional(null 허용) 이어야 하는 이유
1. 클라이언트 선택적 필터링
2. 원치 않는 기본값 방지
3. 유연한 동적 쿼리 구현


- N+1을 재현하려면 Todo가 최소 몇 건, 서로 다른 User가 몇 명 필요한가? (Todo 1건, User 1명으로는 N+1이 드러나지 않는다 — N이 최소 2 이상이어야 "1+N"이 의미 있는 숫자로 보인다)

User 2명, Todo 2건 
전체 User를 가져오는 쿼리 + 첫 번째 User의 Todo를 가져오는 쿼리 + 두 번째 User의 Todo를 가져오는 쿼리
1 + 2 = 3 번의 쿼리 발생으로 데이터 갯수(N = 2)만큼 추가 쿼리 반복

- fetch join과 DTO projection 중 어느 쪽을 선택할 것인가? 이번 도메인(Todo-User, ManyToOne 단일 연관)에서 각각의 장단점은 무엇인가?

ManyToOne 구조에서 장단점
### Fetch Join
장점
- N + 1 문제 완벽 해결 : 하나의 Query롤 Todo와 연관된 User를 한 번에 가져옵니다. 
- 안전한 페이징: 일대다와 달리 다대일 연관관계는 데이터 뻥튀기가 발생하지 않으므로 DB내 페이징이 안전하게 동작합니다. 
- 엔티티 기능 활용: 조회한 엔티티로 비즈니스 로직을 수행하거나 데이터를 수정할 수 있습니다.
단점
- 사용하지 않는 컬럼까지 Select 절에 포함되어 데이터 전송량이 약간 더 많아집니다. 

### DTO projection
장점
- 최적의 select 절: 딱 화면에 필요한 필드만 조회하므로 DB 및 네트워크 부하를 줄입니다. 
- 영속성 컨텍스트 오버헤드 감소: 엔티티로 관리되지 않으므로 대량의 데이터를 단순 조회만 할 때 메모리 효율이 좋습니다. 
단점
- 수정 불가: 변경 감지를 통한 데이터 업데이트를 할 수 없습니다. 
- 유지보수 복잡도 증가: Repository 코드가 특정 DTO 구조에 의존하게 되어 화면 요구사항이 바뀔 때마다 Repository 코드나 쿼리를 수정해야 합니다. 


## A-3. 실험 중 부딪힐 것들

- fetch join을 페이징(`OFFSET`/`LIMIT`)과 같이 쓸 때, 이번 Todo-User(`@ManyToOne`) 관계에서는 문제가 없는 이유는 무엇인가? (컬렉션(`@OneToMany`) fetch join과 페이징을 같이 쓸 때 생기는 메모리 페이징 문제와 비교해서 설명할 수 있어야 한다)

@ManyToOne(대다일) 관계에서 fetch join과 페이징을 함께 사용해도 문제가 없는 이유는 데이터의 수(Row 수)가 변경되지 않는 단일 엔티티 조회이기 때문입니다. 반면, @OneToMany(일대다) 컬렉션 fetch join은 데이터가 뻥튀기되는 '카테시안 곱(Cartesian Product)' 현상이 발생하여 메모리 페이징 문제가 발생합니다.

- DTO projection을 선택했다면, `Projections.constructor`와 `Projections.fields`/`@QueryProjection` 중 무엇을 쓸지, 그 차이(생성자 시그니처 의존 여부, 컴파일 타임 안전성)를 알아야 한다.

안전성을 최우선으로 하며, DTO가 Querydsl에 의존해도 상관없다면: ➡️ @QueryProjection을 사용하는 것이 가장 좋습니다. 오타나 구조 변경으로 인한 장애를 컴파일 시점에 철저히 막아줍니다.아키텍처 구조상 DTO를 순수하게 유지(Querydsl 의존성 제거)해야 한다면: ➡️ Projections.constructor를 권장합니다. 필드명 변경보다 타입 변경이 더 직관적으로 에러를 잡기 쉽기 때문입니다. 단, 이때는 잘못된 바인딩을 방지하기 위한 테스트 코드 작성이 필수적입니다.


- 개선 전후 쿼리 수를 비교하는 테스트에서, "개선 전" 테스트와 "개선 후" 테스트가 같은 fixture와 같은 조회 조건을 쓰는지 확인해야 한다 — 조건이 다르면 쿼리 수 차이가 최적화 때문인지 조건 차이 때문인지 구분이 안 된다.

- 정합성 회귀 테스트에서 "정합성"이 구체적으로 무엇을 의미하는지 정해야 한다 (개선 전후 결과 개수가 같은가, 각 필드 값이 같은가, 순서까지 같아야 하는가).

## A-4. 선택 과제(컬렉션 fetch join + 페이징, 또는 벌크 연산 후 영속성 컨텍스트 정합성)를 고를지 판단

- 컬렉션 fetch join + 페이징 실험은 무엇을 검증하는 것인가? (User 기준으로 `todos` 컬렉션을 fetch join하면서 페이징을 걸었을 때 Hibernate가 실제로 어떻게 동작하는지 — 경고 로그가 뜨는지, 메모리에서 페이징이 일어나는지)

1. 하이버네이트의 메모리 페이징(In-Memory Paging) 동작 검증
- 핵심 의문: DB 레벨에서 LIMIT, OFFSET 쿼리가 나가는가, 아니면 애플리네이션 메모리로 데이터를 다 긁어와서 페이징 하는가?
- 검증 내용: 일대다 조인을 하면 데이터 결과 가로 행(Row)의 수가 다(N) 측의 개수만큼 뻥튀기(중복)됩니다. DB 레이어에서는 정확한 User 기준의 페이징 데이터 개수를 산출할 수 없기 때문에, Hibernate는 DB에서 중복된 전체 데이터를 메모리로 모두(Full Scan) 가져온 뒤 JVM 메모리 내에서 페이징 연산을 수행합니다. 실험을 통해 실제 실행되는 SQL에 limit 구문이 빠진 채 전체 조인 쿼리가 나가는지 확인합니다.
2. OOM(Out Of Memory) 위험성 경고 로그 확인
- 핵심 의문: Hibernate가 위험한 메모리 페이징을 수행할 때 경고를 주는가?
- 검증 내용: Hibernate는 일대다 컬렉션 fetch join + 페이징 대상 데이터가 존재할 때 콘솔에 명확한 경고(Warn) 로그를 남깁니다. 실험을 통해 아래와 같은 유명한 경고 메시지가 콘솔에 출력되는지 눈으로 확인합니다.
- HH000104: firstResult/maxResults specified with collection fetch; applying in memory!
3. 데이터 정합성 및 성능 영향도 측정
- 데이터가 수만~수십만 건일 때 실제로 애플리케이션 서버가 일시적으로 멈추거나 뻗는 현상(OOM 위험)을 체감합니다.
- User 엔티티 기준의 페이지 사이즈(예: size=10)와 실제 메모리에 로드되는 데이터 양의 차이를 분석합니다.


- 벌크 연산(`update`/`delete` 쿼리) 뒤 영속성 컨텍스트 정합성 실험은 무엇을 검증하는 것인가? (벌크 연산은 영속성 컨텍스트를 거치지 않고 DB에 직접 반영되므로, 이미 조회해서 영속 상태로 갖고 있던 엔티티와 DB 값이 어긋날 수 있다는 문제)

벌크 연산(update/delete 쿼리) 뒤 영속성 컨텍스트 정합성 실험은 벌크 연산 수행으로 인해 데이터베이스(DB)의 실제 데이터와 1차 캐시(영속성 컨텍스트)에 남아있는 엔티티 객체의 상태가 서로 달라지는 데이터 불일치 현상(정합성 깨짐)을 확인하고, 이를 어떻게 동기화하여 해결할 수 있는지 검증하는 것입니다.

- 이번 주차도 필수 항목(동적 조회 + N+1 재현/개선 + 정합성 테스트)만으로 분량이 크다. 선택 과제는 필수를 먼저 끝낸 뒤 판단한다.
