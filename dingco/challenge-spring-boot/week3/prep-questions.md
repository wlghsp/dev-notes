## 필수 1 — User/Todo 리포지토리 + 조율 서비스

- schema.sql에 `challenge_user` 테이블(`id`, `name`)이 이미 있다. `User` 도메인 클래스는 어떤 필드를 가질 것인가? Week 1의 `Todo` 클래스처럼 생성 시점 검증(예: name 공백 체크)을 넣을 것인가?

> User 도메인 클래스는 id, name 을 가질 수 있다. name 공백 체크를 넣을 것이다. 

- `UserRepository`를 `TodoRepository`와 같은 패턴(인터페이스 + `JdbcUserRepository`)으로 만들 것인가, 아니면 이번 주는 인터페이스 없이 바로 구현체 하나로 갈 것인가? Week 2에서 두 구현체 패턴을 이미 다뤘으니 반복할 필요가 있는지 판단해볼 것.

> 일관성 있게 구현하기 위해서는 구현체를 갈아낄 수 있게 인터페이스 + 구현체 패턴으로 갑니다. 

- "두 변경을 조율하는 서비스 유스케이스"란 정확히 무엇을 의미하는가? User를 먼저 저장하고 그 User에 딸린 Todo를 저장하는 흐름인가? `todo` 테이블의 `user_id` 컬럼(Week 1에서는 안 썼던 컬럼)을 이번 주에 처음 쓰게 되는가?

1. 두 변경을 조율하는 서비스 유스케이스의 의미
- 동시 처리와 일관성: 두 개 이상의 테이블을 수정할 때, 데이터가 어긋나지 않도록 함께 성공하거나 함께 취소(Rollback)되도록 조율합니다.
- 비즈니스 규칙 실행: 단순히 데이터를 저장하는 것을 넘어, "유저가 존재할 때만 Todo를 연결할 수 있다"같은 규칙을 서비스 계층에서 제어합니다.
2. User 저장 후 Todo 저장 흐름인지?
- 맞습니다. 데이터베이스 구조 상 User가 먼저 생성되어야 고유 식별자 (id 또는 user_id)가 만들어집니다. 
- 그 후 생성된 유저의 ID 값을 가져와서 Todo 데이터에 포함해 저장하는 순서로 흐름이 진행됩니다.
3. todo 테이블의 user_id 컬럼을 이번 주에 처음 쓰는지?
- 맞습니다.Week 1 단계에서는 연관 관계없이 Todo 단일 기능만 구현했기 때문에 user_id를 사용하지 않았을 가능성이 높습니다.
- 이번 주부터는 유저와 할 일을 연결하는 관계형 데이터베이스(RDB) 설계가 적용되면서 todo 테이블의 user_id 컬럼에 실제 값을 저장하고 조회하는 로직을 처음 사용하게 됩니다. 

## 필수 2 — 트랜잭션 없는 서비스의 부분 저장

- "User 저장 직후 예외를 던지게 호출"한다고 했다. 이 예외를 어디서 발생시킬 것인가? 실제 비즈니스 로직에 있는 예외를 재사용할 것인가, 테스트 전용으로 의도적으로 예외를 던지는 지점을 만들 것인가?

1. 예외 발생 위치 (Where)
- 서비스 레이어(Service Layer): userRepository.save(user) 호출 바로 다음 줄에 배치합니다.
- 이유: 데이터 저장 직후 발생하는 후속 로직(이벤트 발행, 외부 연동 등)이나 트랜잭션 롤백(@Transactional) 동작을 정확히 검증할 수 있는 위치이기 때문입니다.
2. 실제 비즈니스 예외 vs 테스트 전용 예외
- 테스트 전용 예외 생성 권장:
  - 기존 비즈니스 예외(DuplicatedUserException 등)를 재사용하면, 실제 상황이 아님에도 비즈니스 의미가 오해될 수 있습니다.
  - 테스트 목적으로만 쓰이는 TestRuntimeException 같은 전용 예외 클래스를 정의해 사용하는 것이 코드의 의도를 명확하게 만듭니다.
- 프로덕션 코드 수정 최소화:
  - 만약 단순히 트랜잭션 롤백 테스트가 목적이라면, 프로덕션 코드에 직접 throw 코드를 심기보다 Mockito의 doThrow() 같은 Spy/Mock 기능을 사용해 저장 직후 예외를 발생시키는 방법이 프로덕션 코드를 깨끗하게 유지하는 가장 좋은 방법입니다.

> **[정정]** doThrow()는 이 시나리오와 안 맞음. doThrow()를 쓰려면 UserRepository를 mock으로 대체해야 하는데, 이 테스트는 "User 1건·Todo 0건이 실제 DB에 남았는지"를 검증하는 것이 목적이라 UserRepository는 실제 JDBC 구현체로 살아있어야 실제 저장이 일어난다. 테스트 전용 예외를 실제 코드 흐름(User 저장 후, Todo 저장 전 지점)에서 던지는 방식으로 가야 함.

- "테스트 메서드에 `@Transactional`을 붙이지 않은 상태"라는 조건이 명시돼 있다. 왜 이 조건이 중요한가? `@Transactional`이 테스트에 붙으면 무슨 일이 달라지는지 알고 있는가? (힌트: 스프링 테스트의 `@Transactional`은 기본적으로 테스트가 끝나면 롤백한다 — 이게 이번 검증과 충돌하는 이유를 생각해볼 것)

> 테스트 메서드에 @Transactional을 붙이지 않은 상태가 중요한 이유는 테스트가 끝난 후 데이터베이스의 변경 사항을 자동 롤백(Rollback)하지 않고 그대로 유지하기 위해서입니다.

### @Transctional 이 테스트에 붙을 때 생기는 일
- 자동 롤백: 스프링 테스트(Spring Test)컨텍스트에서 @Transctional은 테스트 메서드가 끝난 후 트랜잭션을 강제로 롤백합니다. 
- 데이터 미저장: 테스트 안에서 데이터베이스에 데이터를 저장(save)하거나 수정해도, 테스트 종료 시점에 변경 사항이 취소되므로 실제 DB에는 데이터가 남지 않습니다.
- 격리성: 다른 테스트에 영향을 주지 않고 독립적인 상태를 유지할 수 있습니다.

### 이번 검증과 충돌하는 이유
- 만약 이번 검증에서 실제로 데이터베이스에 데이터가 반영(Commit)되는지, 혹은 다른 트랜잭션이나 별도의 커넥션에서 해당 데이터를 조회할 수 있는지를 확인해야 한다면 롤백 기능이 방해가 됩니다.
- @Transactional이 붙어 있으면 데이터가 커밋되지 않고 사라지기 때문에, 실제 영속성 상태나 DB 반영 여부를 정확하게 검증할 수 없습니다.


- "예외 뒤 User 1건·Todo 0건이 남는" 것을 어떻게 확인할 것인가? 서비스가 던진 예외를 잡은 뒤, 별도로 `UserRepository`/`TodoRepository`를 조회해서 실제 row 개수를 세는 방식이 필요한가?

> 서비스가 던진 예외를 캐치한 뒤, Repository를 통해 데이터베이스(DB)의 실제 데이터 개수를 조회하여 검증하는 방식이 가장 확실하고 올바른 방법입니다. 
> 특히 스프링의 @Transactional 환경에서는 예외가 발생했을 때 롤백(Rollback)이 의도대로 일어났는지 검증하기 위해 이 과정이 꼭 필요합니다.

## 필수 3 — @Transactional 프록시를 거친 롤백 검증

- 필수 2와 필수 3은 같은 실패 시나리오(User 저장 후 예외)를 트랜잭션 유무만 다르게 해서 대비시키는 구조로 보인다. 서비스 클래스를 하나로 두고 트랜잭션 있는/없는 메서드를 나눌 것인가, 아니면 클래스 자체를 두 개로 나눌 것인가?

>  하나의 서비스 클래스에 트랜잭션이 있는 메서드와 없는 메서드를 함께 두는 방식

테스트를 위해 클래스를 나누는 것은 오버엔지니어링임 

- "외부에서 Spring 프록시를 거쳐 호출"이라는 표현이 있다. Week 2에서 다뤘던 self-invocation 문제(프록시를 거치지 않으면 advice/트랜잭션이 안 걸림)가 여기서도 똑같이 적용되는가? 테스트에서 컨테이너 빈을 어떻게 받아야 "프록시를 거친 호출"이 보장되는가?

> 외부에서 Spring 프록시를 거쳐 호출하는 구조와 self-invocation 문제는 동일하게 적용됩니다.

- 스프링 테스트(예: @SpringBootTest)에서 컨테이너 빈을 받을 때 프록시 적용을 보장하려면 인터페이스나 구현체 타입으로 정상 주입받아야 하며, 테스트 내에서 this를 통한 내부 호출을 피하고 주입받은 빈(또는 AopTestUtils 등)을 통해 호출해야 합니다.
- 표준 주입 방식 (@Autowired): 필드나 생성자 주입을 통해 스프링 컨테이너가 관리하는 프록시 빈을 정상적으로 주입받습니다.- 주의할 점: 테스트 메서드 내에서 대상 빈을 new 키워드로 직접 생성하면 스프링 관리 대상이 아니므로 프록시가 적용되지 않습니다. 반드시 @Autowired나 @MockBean 등으로 컨테이너에 등록된 빈을 가져와야 합니다.

> **[정정]** AopTestUtils는 방향이 반대. 이건 프록시에서 원본 타겟 객체를 꺼내 프록시를 우회해서 검사하고 싶을 때 쓰는 유틸이다. 여기서 필요한 건 정확히 반대로 "프록시를 거친 호출"이므로, @Autowired로 받은 빈을 그대로 호출하면 충분하고 AopTestUtils는 불필요.

- 롤백 검증은 "예외 처리 뒤 별도 조회로 User 0건·Todo 0건"을 확인해야 한다. 이 조회 자체는 트랜잭션 안에서 하면 안 되는 이유가 있는가? (힌트: 아직 커밋 안 된 변경사항을 같은 트랜잭션 안에서 조회하면 실제로 반영이 롤백됐는지 판단하기 어려울 수 있다)

> 아직 커밋 안 된 변경사항을 같은 트랜잭션 안에서 조회하면 실제로 반영이 롤백됐는지 판단하기 어려울 수 있다

## 근거형 질문 사전 판단

미션 근거형 질문 1~4에 대해, 코드를 쓰기 전 시점의 최초 판단만 짧게 적어둔다.

1. 트랜잭션 경계를 컨트롤러나 리포지토리가 아니라 서비스에 둔 이유는?

> 트랜잭션 경계를 컨트롤러나 리포지토리가 아닌 서비스(Service) 계층에 두는 가장 핵심적인 이유는 비즈니스 로직의 원자성(Atomicity)을 보장하기 위해서입니다.
1. 하나의 비즈니스 로직은 여러 데이터 변경 작업을 포함함
2. 관심사의 분리 (Separation of Concerns)
3. 인프라 및 프레임워크 기술과의 독립성

2. 체크 예외와 언체크 예외에서 기본 롤백 동작 차이는? (힌트: 스프링 `@Transactional`의 기본 롤백 정책이 두 예외 종류를 다르게 취급한다)

언체크 예외
동작: 예외가 발생하면 트랜잭션이 자동으로 롤백됩니다. 

체크 예외
동작: 예외가 발생해도 트랜잭션이 롤백되지 않고 커밋됩니다. 

스프링이 이렇게 설계한 이유
- 언체크 예외: 시스템 오류 등 복구하기 어려운 예외로 간주하여 데이터를 안전하게 원래대로 돌리기 위해 롤백합니다. 
- 체크 예외: 잔액 부족이나 포인트 부족처럼 비즈니스적 의미가 담긴 예외로 보아 예외 발생 시에도 비즈니스 로직의 일부로 처리하거나 커밋할 수 있도록 기본 설정을 비워둔 것입니다. 

주의 및 해결방법
- 체크 예외 발생 시 강제로 롤백을 진행하고 싶다면 @Transactional(rollbackFor = Exception.class)와 같이 rollbackFor 속성을 직접 지정해야 합니다.
- 예외를 try-catch로 직접 잡아 처리하면 예외가 스프링 프록시로 전달되지 않아 두 예외 모두 롤백되지 않고 커밋되므로 주의가 필요합니다.

3. 같은 클래스 내부 호출이 트랜잭션 프록시를 우회할 수 있는 이유는? (Week 2 self-invocation 답변을 그대로 연결할 수 있는가?)

> 스프링이 프록시 방식의 AOP를 사용하며, 내부 메서드 호출은 this 를 통해 실제 대상 객체의 메서드를 직접 실행하기 때문입니다. 

4. 롤백 테스트가 데이터베이스 상태까지 확인해야 하는 이유는?

- 트랜잭션 격리 수준 및 Lock 검증: 트랜잭션이 실패했을 때 발생한 데이터베이스 락(Lock)이 올바르게 해제되었는지 파악하기 위함입니다. 롤백은 되었더라도 락이 풀리지 않아 시스템이 멈추는 데드락(Deadlock) 현상이 발생할 수 있습니다.
- DB 트리거 및 제약 조건 확인: 애플리케이션 코드가 롤백을 명령했더라도, DB 내부에 설정된 트랜잭션 외적인 요소(트리거, 외래키 제약 조건 등)로 인해 예기치 못한 데이터 변형이나 잔재가 남을 수 있습니다.
- 자동 증가(Auto-Increment) 값 검증: 일부 DB 엔진에서는 롤백이 수행되어도 PK(기본키)의 자동 증가 시퀀스 값은 롤백되지 않고 증가한 상태로 유지됩니다. 이러한 DB 고유의 특성이 비즈니스 로직에 영향을 주지 않는지 확인해야 합니다.
- 부분 롤백(Savepoint)의 정확성: 트랜잭션 전체가 아닌 특정 세이브포인트(Savepoint)까지만 롤백하는 경우, 개발자가 의도한 부분까지만 정확히 데이터가 되돌아갔는지 DB 상태를 직접 조회해야만 확신할 수 있습니다.
