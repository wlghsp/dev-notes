# Saga 패턴

여러 서비스에 걸친 작업을 로컬 트랜잭션의 연속으로 처리하고, 실패 시 보상 트랜잭션으로 되돌리는 패턴.

---

## 왜 필요한가

마이크로서비스에서 여러 서비스에 걸친 트랜잭션이 문제다.

```
주문 서비스 DB → 결제 서비스 DB → 재고 서비스 DB
```

각 서비스가 DB를 따로 가지고 있어서 전통적인 DB 트랜잭션(`BEGIN` / `COMMIT` / `ROLLBACK`)으로 묶을 수가 없다.

---

## 기존 해법: 2PC (2 Phase Commit)

분산 트랜잭션을 묶는 고전적인 방법. 모든 참여자가 준비됐을 때만 커밋.

```
[코디네이터]
  1단계 (Prepare): "다들 커밋 준비됐어?" → 주문/결제/재고 모두 "준비됐어"
  2단계 (Commit):  "그럼 다 같이 커밋해"
```

문제:
- 준비 상태에서 모든 서비스가 락을 잡고 기다림 → 성능 저하
- 코디네이터가 죽으면 전체가 멈춤 → 단일 장애점
- 서비스가 많아질수록 느려지고 복잡해짐

---

## Saga 패턴

2PC 대신 **각 서비스가 자신의 로컬 트랜잭션만 처리**하고, 실패하면 **보상 트랜잭션(Compensating Transaction)** 으로 되돌리는 방식.

```
주문 생성(로컬 TX) → 결제 처리(로컬 TX) → 재고 차감(로컬 TX)
```

재고 차감에서 실패하면:

```
재고 차감 실패
  → 결제 취소(보상) ← 새로운 트랜잭션으로 되돌림
  → 주문 취소(보상) ← 새로운 트랜잭션으로 되돌림
```

**중요: 보상 트랜잭션은 ROLLBACK이 아니다.** DB ROLLBACK처럼 없었던 일이 되는 게 아니라, 이미 커밋된 내용을 **새로운 트랜잭션으로 의미적으로 되돌리는 것**이다. 결제 취소 이력이 DB에 남는다.

---

## 두 가지 구현 방식

### Choreography (안무형)

중앙 관리자 없이 서비스끼리 이벤트로 소통. 각 서비스가 이벤트를 보고 알아서 반응한다.

```
주문 서비스: 주문 생성 → "OrderCreated" 이벤트 발행
결제 서비스: "OrderCreated" 수신 → 결제 처리 → "PaymentCompleted" 이벤트 발행
재고 서비스: "PaymentCompleted" 수신 → 재고 차감
```

실패 시:

```
재고 서비스: 재고 부족 → "StockFailed" 이벤트 발행
결제 서비스: "StockFailed" 수신 → 결제 취소 → "PaymentCancelled" 이벤트 발행
주문 서비스: "PaymentCancelled" 수신 → 주문 취소
```

장점: 서비스 간 결합도 낮음, 각자 독립적으로 배포 가능
단점: 전체 흐름이 어디에도 명시되지 않음. 장애 추적이 어렵고, 보상 흐름이 이벤트에 흩어져 있어 파악이 힘들다.

### Orchestration (지휘형)

중앙 오케스트레이터가 전체 흐름을 직접 지시한다.

```
[오케스트레이터]
  1. 주문 서비스에게: "주문 생성해"
  2. 결제 서비스에게: "결제 처리해"
  3. 재고 서비스에게: "재고 차감해"

실패 시:
  3. 재고 서비스: 실패 보고
  2. 결제 서비스에게: "결제 취소해" (보상)
  1. 주문 서비스에게: "주문 취소해" (보상)
```

장점: 전체 흐름이 한 곳에 명시됨. 추적과 디버깅이 쉽다.
단점: 오케스트레이터가 커지면 서비스들이 여기에 의존하게 됨.

**Temporal은 Orchestration 방식의 구현체다.** Workflow가 오케스트레이터 역할을 하고, Activity가 각 서비스 호출을 담당한다.

---

## Choreography vs Orchestration 선택 기준

서비스가 적고 흐름이 단순하면 Choreography가 가볍다. 서비스가 많고 흐름이 복잡하거나, 보상 로직이 중요하면 Orchestration이 추적과 관리가 쉽다.

---

## Saga의 한계

Saga는 2PC를 대체하지만 트레이드오프가 있다.

- **일시적 불일치 허용**: 모든 단계가 완료되기 전까지 시스템은 부분적으로 일관성 없는 상태다. "결제는 됐는데 재고는 아직" 같은 순간이 존재한다.
- **보상이 항상 가능하진 않음**: 이메일 발송, 외부 알림처럼 되돌릴 수 없는 작업이 있다. 이런 작업은 흐름의 가장 마지막에 배치하는 게 원칙이다.
- **멱등성 필수**: 재시도 시 같은 작업이 여러 번 실행될 수 있어서, Activity는 여러 번 호출돼도 결과가 같아야 한다.

---

## 요약

- 마이크로서비스에서 분산 트랜잭션을 2PC 없이 처리하는 패턴
- 각 단계는 로컬 트랜잭션, 실패 시 보상 트랜잭션으로 의미적으로 되돌림
- Choreography: 이벤트 기반, 분산, 추적 어려움
- Orchestration: 중앙 집중, 명시적 흐름, Temporal이 여기 해당
- 일시적 불일치를 허용하는 대신 락 없이 높은 가용성을 얻음
