# Kafka Topic

메시지를 분류하는 논리적 단위. 데이터베이스의 테이블에 비유하면 비슷하지만, 읽어도 삭제되지 않는다는 점이 다르다.

producer는 특정 토픽에 메시지를 발행하고, consumer는 특정 토픽을 구독해서 읽는다. 토픽 이름으로 어떤 종류의 이벤트인지 구분한다. `orders`, `payments`, `user-events` 같은 식이다.

## 토픽과 파티션의 관계

토픽은 논리적 개념이고, 파티션이 실제 저장 단위다. 토픽 하나는 하나 이상의 파티션으로 구성된다. 물리적으로는 파티션 단위로 디스크에 저장되고 브로커에 분산된다.

```
토픽: payments (파티션 3개)
  partition-0 → broker-1에 저장
  partition-1 → broker-2에 저장
  partition-2 → broker-3에 저장
```

토픽에 메시지를 발행하면 Kafka가 어떤 파티션에 넣을지 결정한다. key가 있으면 key를 해싱해서 파티션을 고른다. key가 없으면 라운드 로빈으로 분산한다.

## Retention

토픽은 메시지를 일정 기간 또는 일정 용량까지 보존한다. 기본은 7일이다. 기간이 지나거나 용량을 초과하면 오래된 메시지부터 삭제된다.

consumer가 읽었다고 삭제되지 않는다. retention 기간 안에 있으면 몇 번이든 다시 읽을 수 있다. 이 특성 때문에 새로운 consumer가 과거 데이터를 처음부터 읽어오는 것도 가능하다.

## 토픽을 여러 개 쓰는 이유

관심사를 분리하기 위해서다. 주문 이벤트와 결제 이벤트를 같은 토픽에 섞으면 consumer마다 필요한 메시지를 골라내는 로직이 필요하다. 토픽을 분리하면 각 서비스가 자신이 관심 있는 토픽만 구독하면 된다.

retention, 파티션 수, 복제 설정도 토픽별로 다르게 줄 수 있다. 중요도가 높은 결제 토픽은 retention을 길게, 로그 토픽은 짧게 가져가는 식이다.
