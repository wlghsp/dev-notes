# /codebase-design — 깊은 모듈 설계 어휘

## 한 줄 요약

작은 인터페이스 뒤에 많은 구현을 숨기는 것. 이게 좋은 코드의 핵심이고, 이 어휘가 기준이다.

## 언제 쓰나

- "어디서 테스트할지" 결정해야 할 때
- 코드 리뷰 중 설계 피드백을 줄 때

## 핵심 어휘 (이 단어들만 쓴다)

모듈: 인터페이스와 구현을 가진 모든 것. 함수, 클래스, 패키지 모두 해당.
"서비스", "컴포넌트"라고 부르지 않는다.

인터페이스: 호출자가 모듈을 올바르게 쓰기 위해 알아야 할 모든 것.
타입 시그니처만이 아니다. 불변식, 순서 제약, 에러 모드, 성능 특성도 포함.

깊이(Depth): 인터페이스 대비 동작의 양.
작은 인터페이스 뒤에 많은 구현 = 깊다 = 좋다.
큰 인터페이스에 적은 구현 = 얕다 = 피한다.

이음새(Seam): 그 위치를 수정하지 않고 동작을 바꿀 수 있는 지점.
"경계(boundary)"라고 부르지 않는다. DDD의 bounded context와 혼동된다.

어댑터(Adapter): 이음새에서 인터페이스를 만족시키는 구체적인 구현.
역할을 설명하는 단어다. 내부가 뭔지는 설명하지 않는다.

레버리지(Leverage): 호출자가 깊이에서 얻는 것. 인터페이스를 배우는 단위당 더 많은 기능.

로컬리티(Locality): 유지보수자가 깊이에서 얻는 것. 변경/버그/지식이 한 곳에 모인다.

## 깊은 모듈 vs 얕은 모듈

깊은 모듈 (이게 목표):
```
┌─────────────────────┐
│   작은 인터페이스    │  ← 메서드 적음, 파라미터 단순
├─────────────────────┤
│                     │
│  많은 구현           │  ← 복잡한 로직 숨겨짐
│                     │
└─────────────────────┘
```

얕은 모듈 (이걸 피한다):
```
┌─────────────────────────────────┐
│       큰 인터페이스              │  ← 메서드 많음, 파라미터 복잡
├─────────────────────────────────┤
│  얇은 구현                       │  ← 그냥 통과만 함
└─────────────────────────────────┘
```

---

## 삭제 테스트

이 모듈을 삭제하면 어떻게 되나?

복잡도가 한 곳에 모인다 → 가치 있는 모듈. 지우지 마라.
복잡도가 N개 호출자로 흩어진다 → 얕은 모듈. 이 모듈이 뭔가를 숨기고 있었나 의심한다.

---

## 테스트 가능한 설계 3원칙

1. 의존성은 받아들인다. 내부에서 만들지 않는다.
```java
// 테스트 가능
void processOrder(Order order, PaymentGateway gateway) {}

// 테스트하기 어려움
void processOrder(Order order) {
    PaymentGateway gateway = new StripeGateway(); // 내부에서 생성
}
```

2. 결과를 반환한다. 사이드이펙트를 남기지 않는다.
```java
// 테스트 가능
Discount calculateDiscount(Cart cart) {}

// 테스트하기 어려움
void applyDiscount(Cart cart) {
    cart.total -= discount; // 외부 상태 변경
}
```

3. 인터페이스를 작게 유지한다. 메서드가 적을수록 테스트가 적어도 된다.

---

## 이음새 결정 원칙

어댑터가 하나면 가상의 이음새다. 실제로 뭔가가 변하는 게 아니다.
어댑터가 둘이면 진짜 이음새다. 그때 인터페이스를 만든다.

인터페이스를 너무 일찍 만들면 과도한 추상화다.

---

## 테스트와의 관계

"인터페이스가 테스트 표면이다."
테스트도 호출자고, 호출자와 테스트는 같은 이음새를 쓴다.
인터페이스를 넘어 테스트하고 싶다면 모듈 형태가 잘못된 것이다.
