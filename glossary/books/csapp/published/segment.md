# segment

프로세스 메모리를 역할별로 나눈 덩어리.

하나의 프로세스가 올라가면 OS는 그 메모리를 통째로 관리하지 않고, 용도가 같은 영역끼리 묶어서 각각에 다른 속성(권한, 크기 정책 등)을 적용한다. 이 묶음 하나하나를 세그먼트라고 부른다.

## 세그먼트 종류

**코드 세그먼트 (text segment)**
- 컴파일된 기계어 명령어들이 위치하는 영역
- 읽기 + 실행 권한만 있고, 쓰기는 불가
- 프로그램 실행 중 내용이 바뀌지 않는다

**데이터 세그먼트 (data segment)**
- 초기값이 있는 전역 변수, 정적 변수가 위치
- 읽기 + 쓰기 권한
- 예: `int x = 5;` 같은 전역 변수

**BSS 세그먼트**
- 초기값이 없는(0으로 초기화되는) 전역 변수, 정적 변수
- 실행 파일에 실제 값을 저장하지 않고 "이 크기만큼 0으로 채워라"라는 정보만 담는다
- BSS = Block Started by Symbol (역사적 이름)

**힙 (heap)**
- 런타임에 동적으로 할당되는 영역 (`malloc`, `new`)
- 낮은 주소에서 높은 주소 방향으로 자란다
- 프로그래머가 직접 관리하거나 GC가 관리

**스택 (stack)**
- 함수 호출 시 지역 변수, 리턴 주소, 인자가 쌓이는 영역
- 높은 주소에서 낮은 주소 방향으로 자란다
- 함수가 리턴되면 자동으로 해제

## 권한 제어가 핵심인 이유

세그먼트를 나누는 가장 중요한 이유는 영역마다 다른 권한을 적용하기 위해서다.

코드 세그먼트에 쓰기 권한이 있으면 실행 중인 코드를 덮어써서 임의 코드를 실행시킬 수 있다. 이게 고전적인 버퍼 오버플로우 공격의 원리다. 세그먼트를 분리하고 코드 영역을 읽기 전용으로 만들면 이런 공격을 원천 차단한다.

현대 OS는 여기서 더 나아가 NX bit(No-Execute)를 통해 스택이나 힙에서 코드를 실행하는 것 자체를 하드웨어 수준에서 막는다.

## 세그멘테이션 vs 페이징

x86 아키텍처 초기에는 **세그멘테이션**이 메모리 보호의 주된 방법이었다. 세그먼트 레지스터(CS, DS, SS 등)가 각 세그먼트의 시작 주소와 크기를 가리키고, CPU가 접근할 때마다 범위와 권한을 확인했다.

문제는 세그먼트 크기가 제각각이라 메모리 단편화가 심하다는 점이었다. 세그먼트들을 물리 메모리에 배치하다 보면 중간에 쓰지 못하는 빈 공간이 생긴다.

**페이징**은 메모리를 고정 크기(보통 4KB)로 잘라서 관리한다. 크기가 균일하니 단편화 문제가 훨씬 줄고, 물리 메모리와 가상 메모리를 유연하게 매핑할 수 있다.

현대 OS(Linux, Windows)는 페이징을 기본으로 쓰고 세그멘테이션은 거의 형식적으로만 남아 있다. 그래도 "코드/데이터/스택 세그먼트"라는 이름은 그대로 쓰인다.
