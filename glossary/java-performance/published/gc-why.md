# gc-why
참고: Java Performance: The Definitive Guide Ch.5

---

GC(Garbage Collection)는 프로그래머가 명시적으로 메모리를 해제하지 않아도, JVM이 더 이상 사용되지 않는 객체를 자동으로 찾아 회수하는 메커니즘이다.

---

## C/C++와의 차이

C에서는 `malloc()`으로 할당한 메모리를 반드시 `free()`로 해제해야 한다. 해제를 안 하면 메모리 누수, 이미 해제된 메모리를 다시 해제하면 double-free, 해제된 메모리를 참조하면 use-after-free. 이런 오류들이 가장 찾기 어려운 버그 중 하나다.

Java는 이 부담을 GC가 대신한다. 프로그래머는 객체를 생성하기만 하고, 언제 해제할지 신경 쓰지 않아도 된다.

---

## GC가 해결하는 문제

GC의 핵심 질문은 하나다. "이 객체가 앞으로 다시 사용될 것인가?"

사실 이 질문에 정확히 답하는 것은 불가능하다(Halting Problem과 동일한 이유로). 그래서 GC는 보수적인 판단을 한다. "현재 도달 가능한(reachable) 객체는 살아있다. 도달 불가능한 객체는 죽었다."

도달 가능하다는 것은: GC Root(스택의 로컬 변수, static 필드, JNI 참조 등)에서 참조를 따라가다 보면 만날 수 있다는 뜻이다.

---

## GC의 비용

공짜가 아니다. GC는 두 가지 비용을 유발한다.

1. CPU 시간 — GC 알고리즘이 살아있는 객체를 찾고 죽은 객체를 회수하는 데 CPU를 쓴다
2. Stop-The-World — GC 실행 중 일부 또는 전체 단계에서 애플리케이션 스레드를 멈춰야 한다

이 비용이 JVM 성능 튜닝의 대부분을 차지한다. GC가 얼마나 자주, 얼마나 오래 멈추는가를 이해하고 조절하는 것이 Java Performance 책 전체의 주제다.

---

## Java에도 메모리 누수가 있다

GC가 있어도 메모리 누수는 발생한다. C의 누수와 원인이 다를 뿐이다.

Java의 메모리 누수 = 더 이상 필요 없는 객체인데, 어딘가에서 참조를 붙들고 있어서 GC가 회수하지 못하는 상황.

static 컬렉션에 계속 추가만 하고 삭제하지 않거나, 리스너 등록 후 해제를 안 하거나, 캐시가 계속 커지는 경우가 대표적이다.
