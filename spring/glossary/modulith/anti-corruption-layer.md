# 손상 방지 계층 (Anti-Corruption Layer, ACL)

한 모듈(또는 바운디드 컨텍스트)이 다른 모듈과 통합할 때, 그 모듈의 내부 모델이 상대 모듈의 모델에 오염되지 않도록 중간에 두는 변환 계층이다.
도메인 주도 설계(DDD)에서 나온 패턴으로, 여러 바운디드 컨텍스트를 통합하는 상황(컨텍스트 매핑) 전반에 적용된다.

## 왜 필요한가

모듈 A가 모듈 B의 인터페이스나 타입을 도메인 계층에서 직접 참조하기 시작하면, 모듈 A의 도메인 모델이 모듈 B의 설계 방식에 종속된다.
예를 들어 `order` 모듈의 핵심 비즈니스 로직 안에서 `catalog` 모듈의 `Catalogs` 인터페이스를 직접 호출하면, `catalog`의 인터페이스가 바뀔 때마다 `order`의 도메인 로직까지 같이 흔들린다.
이런 강결합은 모듈 독립성을 해치는 대표적인 원인이다.

## 동작 방식

손상 방지 계층은 이 직접 참조를 모듈 도메인 계층에서 걷어내고, 별도의 어댑터 계층으로 옮긴다.
예를 들어 `order` 모듈 안에 `integrate`라는 별도 패키지를 두고, 그 안의 `OrderPlacementAdapter` 같은 클래스가 `catalog` 모듈이나 `user` 모듈의 인터페이스를 대신 호출한다.
`order`의 도메인 계층(`OrderPlacementProcessor` 등)은 이 어댑터가 제공하는, `order` 모듈 자신의 언어로 정의된 인터페이스(`OrdererVerification`, `OrderItemFactory` 등)만 바라본다.
결과적으로 다른 모듈의 구현 세부사항이나 API 변경이 이 어댑터 계층에서 흡수되고, 도메인 계층까지 전파되지 않는다.

## 명명 규칙에서 드러나는 설계 의도

어댑터가 구현하는 인터페이스 이름을 상대 모듈의 용어가 아니라 자기 모듈의 용어로 짓는 것이 이 패턴의 핵심이다.
`catalog` 모듈을 그대로 참조하는 대신 `order` 모듈 입장에서 필요한 개념인 `OrderItemFactory`(주문 항목을 만드는 팩토리)라는 이름을 쓰면, `order` 모듈의 도메인 언어가 다른 모듈의 언어에 오염되지 않는다.
이것이 "손상 방지"라는 이름이 뜻하는 바다 — 다른 컨텍스트의 모델이 내 컨텍스트의 도메인 언어를 침범하지 못하게 막는다.

## Named Interface와의 차이

named-interface.md에서 다룬 `@NamedInterface`가 "내 모듈의 어떤 부분을 밖으로 공개할지"를 정하는 것이라면, 손상 방지 계층은 "다른 모듈의 것을 내 모듈 안으로 들여올 때 어떻게 변환해서 받아들일지"를 다루는 반대 방향의 문제다.
두 패턴은 서로 다른 방향의 결합을 막는 것이라 함께 쓰이는 경우가 많다.
