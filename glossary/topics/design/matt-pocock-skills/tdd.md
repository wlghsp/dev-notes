# /tdd — 테스트 주도 개발 수직 슬라이스

## 한 줄 요약

테스트 하나 쓰고 → 코드 쓰고 → 반복. 테스트를 먼저 전부 쓰는 수평 슬라이스는 쓰레기를 만든다.

---

## 언제 쓰나

- 새 기능을 버그 없이 만들고 싶을 때
- "red-green-refactor" 루프를 쓰고 싶을 때
- 통합 테스트를 제대로 작성하고 싶을 때
- 에이전트가 코드를 만들었는데 검증 방법이 없을 때

---

## 핵심 반패턴: 수평 슬라이스

절대 하면 안 되는 방식:

```
잘못된 방식:
  RED:   test1, test2, test3, test4, test5  ← 전부 먼저 씀
  GREEN: impl1, impl2, impl3, impl4, impl5  ← 전부 나중에 씀
```

왜 나쁜가:
- 테스트를 쓸 때 실제 코드가 없으니 상상으로 쓴다
- 상상한 동작 = 실제 동작이 아닐 수 있다
- 리팩토링하면 깨지는 테스트가 된다
- 내부 구현을 테스트하게 된다

---

## 올바른 방식: 수직 슬라이스

```
올바른 방식:
  RED→GREEN: test1 → impl1
  RED→GREEN: test2 → impl2
  RED→GREEN: test3 → impl3
  ...
```

각 테스트는 직전 사이클에서 배운 것을 반영해서 쓴다.
코드를 방금 썼으니 어떤 동작이 중요한지 정확히 안다.

---

## 좋은 테스트 기준

- 공개 인터페이스(public API)로만 검증한다
- 내부 구현이 바뀌어도 안 깨진다
- "user can checkout with valid cart"처럼 동작을 서술한다

나쁜 테스트 기준:
- 내부 협력자를 목킹한다
- private 메서드를 직접 테스트한다
- 리팩토링하면 깨진다

---

## 워크플로우

1. 계획 단계
   - 어떤 공개 인터페이스가 필요한지 확인
   - 어떤 동작을 테스트할지 우선순위 결정
   - 깊은 모듈 기회 파악 (작은 인터페이스, 많은 구현)

2. 트레이서 불릿 (첫 번째 사이클)
   - 시스템에 대해 한 가지를 확인하는 테스트 하나
   - RED: 테스트 작성 → 실패 확인
   - GREEN: 통과시키는 최소한의 코드 작성

3. 증분 루프
   - 남은 동작마다 RED → GREEN 반복
   - 한 번에 테스트 하나
   - 미래 테스트 예측해서 미리 쓰지 않는다

4. 리팩토링
   - 모든 테스트가 GREEN일 때만
   - 중복 제거, 모듈 깊게 만들기
   - 리팩토링 중에 테스트 깨지면 잘못된 것

---

## 실제 활용 팁

테스트 이름이 스펙이다. "should return null when..." 같은 구현 투영 이름 말고
"user can checkout with empty cart and gets error" 같이 동작을 서술한다.

목킹은 최소화한다. 내부를 목킹하면 인터페이스가 아니라 구현을 테스트하는 것이다.
