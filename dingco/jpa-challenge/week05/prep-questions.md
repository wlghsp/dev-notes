## A-1. 근거형 질문 직결 개념

정답은 안 적는다. 각 질문에서 무엇을 코드로 직접 확인해야 답이 나오는지만 짚는다.

- N+1은 LAZY와 EAGER 중 어느 쪽에서 발생하며 본질적인 원인은 무엇인가?
  - 확인할 것: Todo 목록을 조회한 뒤 각 Todo의 `user`에 접근했을 때, LAZY일 때와 EAGER일 때 각각 SQL이 몇 번 발생하는지. "지연 로딩이 원인"이라고 단정하기 전에 EAGER로도 N+1이 재현되는지 직접 실험해봐야 한다(week3의 "LAZY로 선언해도 N+1이 발생할 수 있는 이유"와 이어지는 지점).

- 선택한 조회 최적화 방식(fetch join 또는 DTO projection)이 다른 대안보다 현재 요구에 맞는 이유는 무엇인가?
  - 확인할 것: fetch join 적용 시 실제 SQL이 어떻게 바뀌는지(조인 1개로 줄어드는지), DTO projection 적용 시 SELECT 컬럼이 필요한 것만 남는지. 두 방식을 각각 시도해보고 쿼리 수·응답 데이터 형태·엔티티 영속 여부(fetch join은 영속 엔티티, DTO projection은 비영속 DTO)가 어떻게 다른지 비교해야 "왜 이걸 골랐는지" 방어할 수 있다.

- QueryDSL 조건 조합에서 null·빈 값 경계를 어떤 규칙과 테스트로 고정했는가?
  - 확인할 것: 조건 DTO의 필드가 null일 때 QueryDSL의 `BooleanExpression`이 어떻게 동작하는지(where절에서 자동으로 빠지는지, 아니면 명시적으로 null 체크를 해야 하는지). 빈 문자열("")과 null을 같은 값으로 취급할지 다르게 취급할지도 결정하고 테스트로 고정해야 한다.

- 1차 캐시와 fixture INSERT가 쿼리 수 측정을 오염하지 않도록 어떤 순서로 통제했는가?
  - 확인할 것: fixture로 넣은 Todo/User가 영속성 컨텍스트에 그대로 남아있으면 측정 대상 조회 시 1차 캐시 때문에 SELECT가 안 나갈 수 있다. `em.flush()` + `em.clear()`로 1차 캐시를 비운 뒤 `observation.reset()`을 호출하는 순서가 맞는지, week4까지 이 순서를 어떻게 지켰는지 되짚어봐야 한다.

## A-2. 실험 설계 전에 확정해야 하는 것

- 동적 조회 조건은 무엇 2개 이상을 조합할 것인가? (예: Todo의 title 부분 일치 + User의 username 일치, 또는 title + 특정 user 소유 여부)

- 조건 DTO를 어떻게 설계할 것인가? 모든 필드가 optional(null 허용)이어야 하는 이유는 무엇인가?

- N+1을 재현하려면 Todo가 최소 몇 건, 서로 다른 User가 몇 명 필요한가? (Todo 1건, User 1명으로는 N+1이 드러나지 않는다 — N이 최소 2 이상이어야 "1+N"이 의미 있는 숫자로 보인다)

- fetch join과 DTO projection 중 어느 쪽을 선택할 것인가? 이번 도메인(Todo-User, ManyToOne 단일 연관)에서 각각의 장단점은 무엇인가?

## A-3. 실험 중 부딪힐 것들

- fetch join을 페이징(`OFFSET`/`LIMIT`)과 같이 쓸 때, 이번 Todo-User(`@ManyToOne`) 관계에서는 문제가 없는 이유는 무엇인가? (컬렉션(`@OneToMany`) fetch join과 페이징을 같이 쓸 때 생기는 메모리 페이징 문제와 비교해서 설명할 수 있어야 한다)

- DTO projection을 선택했다면, `Projections.constructor`와 `Projections.fields`/`@QueryProjection` 중 무엇을 쓸지, 그 차이(생성자 시그니처 의존 여부, 컴파일 타임 안전성)를 알아야 한다.

- 개선 전후 쿼리 수를 비교하는 테스트에서, "개선 전" 테스트와 "개선 후" 테스트가 같은 fixture와 같은 조회 조건을 쓰는지 확인해야 한다 — 조건이 다르면 쿼리 수 차이가 최적화 때문인지 조건 차이 때문인지 구분이 안 된다.

- 정합성 회귀 테스트에서 "정합성"이 구체적으로 무엇을 의미하는지 정해야 한다 (개선 전후 결과 개수가 같은가, 각 필드 값이 같은가, 순서까지 같아야 하는가).

## A-4. 선택 과제(컬렉션 fetch join + 페이징, 또는 벌크 연산 후 영속성 컨텍스트 정합성)를 고를지 판단

- 컬렉션 fetch join + 페이징 실험은 무엇을 검증하는 것인가? (User 기준으로 `todos` 컬렉션을 fetch join하면서 페이징을 걸었을 때 Hibernate가 실제로 어떻게 동작하는지 — 경고 로그가 뜨는지, 메모리에서 페이징이 일어나는지)

- 벌크 연산(`update`/`delete` 쿼리) 뒤 영속성 컨텍스트 정합성 실험은 무엇을 검증하는 것인가? (벌크 연산은 영속성 컨텍스트를 거치지 않고 DB에 직접 반영되므로, 이미 조회해서 영속 상태로 갖고 있던 엔티티와 DB 값이 어긋날 수 있다는 문제)

- 이번 주차도 필수 항목(동적 조회 + N+1 재현/개선 + 정합성 테스트)만으로 분량이 크다. 선택 과제는 필수를 먼저 끝낸 뒤 판단한다.

## A-6. 실험 설계 순서 제안 (확정 아님)

1. 조건 DTO + QueryDSL 조회 메서드(조건 2개 이상 조합) 작성 → 컴파일 확인
2. fixture(Todo 여러 건, User 여러 명)를 넣고 목록 조회 후 각 Todo의 User에 접근 → N+1이 실제로 몇 개의 쿼리로 재현되는지 로그로 확인
3. fetch join 또는 DTO projection 적용 → 같은 조회에서 쿼리 수가 줄어드는지 같은 방식으로 확인
4. 개선 전후 결과 정합성 회귀 테스트 작성
5. evidence 문서화 (Week4와 같은 형식: 변경/검증/선택근거/근거형질문/리뷰반영)
