# DLQ (Dead Letter Queue)

처리에 실패한 메시지가 쌓이는 별도의 큐다. 실패한 메시지를 버리지 않고 따로 보관해서 나중에 원인을 분석하거나 재처리할 수 있게 한다.

## 왜 필요한가

consumer가 메시지를 처리하다 실패하면 보통 재시도를 한다. 그런데 메시지 자체가 잘못된 경우 — 파싱 불가능한 포맷, 존재하지 않는 ID 참조, 비즈니스 로직 위반 — 몇 번을 재시도해도 계속 실패한다. 이런 메시지를 poison message라고 한다.

poison message를 재시도 루프에 그냥 두면 정상 메시지 처리까지 막힌다. DLQ로 빼내면 문제 메시지를 격리하고 나머지는 계속 처리할 수 있다.

## 동작 방식

재시도 횟수 한도를 설정한다. 그 횟수를 넘기면 해당 메시지를 원래 큐에서 꺼내 DLQ로 이동시킨다. 이후 원래 큐는 다음 메시지를 정상적으로 처리한다.

```
원래 큐 → consumer 처리 실패 → 재시도 3회 → DLQ로 이동
DLQ      → 개발자가 원인 분석 → 수정 후 재처리 or 폐기
```

DLQ 자체도 큐이기 때문에 DLQ를 구독하는 별도 consumer를 붙일 수 있다. 알림을 보내거나, 로그를 남기거나, 자동 재처리 로직을 붙이는 식이다.

## RabbitMQ에서의 DLQ

AMQP에서는 큐에 `x-dead-letter-exchange` 속성을 설정하면 된다. 메시지가 거부되거나(nack), TTL이 만료되거나, 큐가 꽉 차면 지정한 Exchange로 메시지를 보낸다. 그 Exchange에 DLQ를 바인딩해두면 자동으로 쌓인다.

## Kafka에서의 DLQ

Kafka는 DLQ를 기본 제공하지 않는다. 별도 토픽을 만들어서 직접 구현한다. consumer가 처리에 실패하면 해당 메시지를 `orders.dlq` 같은 토픽에 발행하는 코드를 직접 작성한다.

Kafka Connect나 Spring Kafka 같은 프레임워크는 DLQ 토픽 설정을 지원한다. 실패한 메시지를 자동으로 지정한 토픽으로 보내주는 기능이 내장돼 있다.

## DLQ 운영 시 주의할 점

DLQ는 쌓아두는 것만으로는 의미가 없다. 모니터링을 붙여서 메시지가 쌓이면 알림이 오게 해야 한다. DLQ가 조용히 쌓이고 있으면 실제로 처리 실패가 계속 일어나고 있다는 신호다.

재처리할 때는 원인을 먼저 수정한 뒤에 DLQ 메시지를 원래 큐로 되돌려야 한다. 원인 수정 없이 재처리하면 다시 DLQ로 돌아온다.
