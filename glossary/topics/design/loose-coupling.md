# Loose Coupling (느슨한 결합)

**한 줄 정의**: 서로 직접 의존하지 않아서, 한쪽이 바뀌어도 다른 쪽에 영향이 없는 관계.

---

## Tight Coupling과의 차이

**Tight Coupling**은 A가 B를 직접 알고 있는 상태다. A가 B를 직접 호출하고, B의 주소(URL, 메서드 시그니처 등)를 하드코딩으로 들고 있다. B가 바뀌면 A도 바꿔야 한다.

**Loose Coupling**은 A가 B를 모르는 상태다. A는 이벤트를 던지거나 인터페이스에만 의존하고, 실제로 누가 받아서 처리하는지 관여하지 않는다.

```
Tight Coupling:
  주문 서비스 → 결제 서비스 직접 호출
  주문 서비스 → 알림 서비스 직접 호출
  주문 서비스 → 정산 서비스 직접 호출
  (서비스가 늘수록 주문 서비스 코드가 비대해짐)

Loose Coupling:
  주문 서비스 → "주문 생성됨" 이벤트 발행
  결제 서비스 ← 이벤트 구독해서 처리
  알림 서비스 ← 이벤트 구독해서 처리
  정산 서비스 ← 이벤트 구독해서 처리
  (주문 서비스는 나머지 서비스의 존재를 모름)
```

---

## 왜 중요한가

Tight Coupling에서는 의존 관계가 사방으로 퍼진다. 서비스 하나를 수정하면 그것을 직접 호출하는 모든 곳을 확인해야 한다. 시스템이 커질수록 변경 비용이 기하급수적으로 늘어난다.

Loose Coupling에서는 변경이 격리된다. 알림 서비스를 새로 만들어도 주문 서비스는 건드릴 필요가 없다. 이벤트를 구독하기만 하면 된다.

---

## 코드 수준에서의 Loose Coupling

서비스 간 뿐만 아니라 코드 수준에서도 같은 개념이 적용된다.

구체 클래스에 직접 의존하면 Tight Coupling이다. 인터페이스에 의존하면 Loose Coupling이다. 구현체가 바뀌어도 인터페이스가 그대로면 호출하는 쪽은 수정할 필요가 없다.

```java
// Tight: 구체 클래스에 직접 의존
EmailNotifier notifier = new EmailNotifier();

// Loose: 인터페이스에 의존
Notifier notifier = new EmailNotifier();  // 나중에 SlackNotifier로 교체 가능
```

Spring의 DI(의존성 주입)가 Loose Coupling을 달성하는 대표적인 수단이다.

---

## 트레이드오프

Loose Coupling이 항상 좋은 건 아니다. 추적이 어려워진다. 이벤트가 어디서 어디로 흘렀는지, 어떤 서비스가 처리했는지 따라가기 어렵다. 결합이 느슨할수록 흐름을 머릿속에서 재구성하는 비용이 높아진다.

단순한 시스템에서 억지로 Loose Coupling을 만들면 오히려 복잡해진다. 결합도를 낮추는 게 목적이 아니라, 변경 비용을 낮추는 게 목적이다. 변경이 잦은 곳, 서비스 경계가 명확한 곳에 적용할 때 가치가 있다.
