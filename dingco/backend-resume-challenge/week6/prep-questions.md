## 1. 캐싱 대상 선정

- `GET /api/studies/popular`는 왜 캐싱 대상 후보로 지목됐는가? (`StudyController.popular()`와 `StudyRepository.findTop10ByStatusOrderByEnrolledCountDesc`의 주석이 무엇을 가리키는가 — 호출마다 다시 계산된다는 것이 왜 문제인가)

매번 호출될 때마다 데이터베이스에서 복잡한 집계 및 정렬 연산을 처웁터 다시 계산하기 때문입니다. 
1. 주석이 가리키는 핵심 문제점
- 호출마다 발생하는 재계산(Re-calculation on Every Request): 인기 스터디를 조회하기 위해서는 모든 ㅣ스터디 데이터의 상태를 확인하고, 신청자 수를 기준으로 내림차순 정렬하여 상위 10개를 뽑아내야 합니다. 
모든 HTTP 요청이 들어올 때마다 DB가 동일한 대량의 데이터를 다시 읽고 정렬하는 비효율적인 연산을 반복하고 있다는 점을 지적합니다. 
2. 호출마다 다시 계산하는 것이 왜 문제인가? 
- 데이터베이스 부하(DB Bottleneck): 스터디 데이터와 신청자 수가 많아질수록 정렬(Order by)연산에 드는 비용이 기하급수적으로 증가합니다. 인덱스가 있더라도 매 요청마다 전체 데이터나 인덱스를 스캔하는 것은 DB CPU에 큰 부담을 줍니다. 
- 응답 시간(Latency) 저하: 메인 화면 드에서 자주 호출되는 API인데, DB 연산이 끝날 때까지 사용자가 대기해야 하므로 전반적인 사용자 경험(UX)이 나빠집니다. 
- 자원 낭비: 인기 스터디 목록은 실시간(초 단위)으로 정홗하게 바뀔 필요가 없는 경우가 많습니다. (예: 10분 전 데이터나 지금 데이터나 큰 차이가 없음). 변하지 안흔ㄴ 데이터를 위해 계속 같은 연산을 수행하는 것은 컴퓨팅 자원의 심각한 낭비입니다. 

- 이 쿼리가 다시 계산하는 비용은 무엇인가? (`status = 'OPEN'` 조건으로 전체 스터디를 스캔하고 `enrolledCount` 기준 정렬 후 상위 10건만 취하는 과정을 구체적으로 그려본다)

1단계: 디스크 I/O 및 풀스캔 비용 (Full Table Scan)
- 모든 데이터 읽기: DB는 status='OPEN'인 데이터를 찾기 위해 테이블의 모든 데이터 페이지(블록)를 디스크에서 메모리(Buffer Pool)로 올립니다. 
- 비효율적인 핕터링: 10만개의 스터디 중 9만개가 'OPEN' 상태라면, 9만 개의 레코드를 하나씩 확인하면 메모리로 가져오는 과정에서 막대한 디스크 Read(I/O) 비용이 발생합니다. DB 성능 저하의 가장 큰 원인은 이 디스크 I/O 입니다. 

2단계: 메모리 오버헤드 및 정렬 비용 (File Sort)
- 메모리(Sort Buffer) 공간 낭비: 필터링된 9만 개의 데이터 전체를 정렬하기 위해 DB 내부의 정렬용 메모리 공간(Sort Buffer)에 할당합니다. 
- CPU 집약적인 정렬 연산: 9만 개의 enrolledCount를 비교하며 내림차순(DESC)으로 정렬하는 CPU 연산이 수행됩니다. (보통 O(NlogN)의 시간 복잡도를 가집니다)
- 임시 디스크 파일 사용 (Disk Swap): 만약 정렬해야 할 데이터 양이 설정된 Sort Buffer 크기보다 크다면 DB는 디스크에 임시 파일을 만들어 정렬을 수행(정렬 병합 알고리즘 등)하므로 디스크 I/O가 추가로 폭발합니다. 

3단계: 무의미한 버려짐 Top-N 절단
- 99.9%의 데이터 폐기: 정렬된 9만 개의 데이터 중 필요한 것은 단 10개뿐입니다. 나머지 89,990개의 데이터를 읽고, 메모리에 올리고, 정렬하기 위해 쓴 모든 CPU와 메모리, 디스크 자원이 이 순간 전부 허공으로 날아가고 버려집니다.


만약 인덱스(status, enrolledCount)가 있다면?
- 그나마 인덱슥다 걸려있다면 풀 스캔과 정렬과정은 생략되고 인덱스 트리를 통해 상위 10개만 바로 읽어 오므로 비용이 줄어듭니다. 하지만 인기 스터디 API 특성상 메인 페이지 등에서 초당 수백~수천 번 호출될 수 있으며, 인덱스가 있더라도 매번 B-Tree를 탐색하는 비용과 DB 커넥션을 차지하는 비용 자체가 누적되면 결국 데이터베이스 전체의 병복 현상으로 이어지게 됩니다. 


- 캐싱 대상으로 적합한 데이터의 조건은 무엇인가? (자주 읽히지만 자주 바뀌지 않는 데이터, 계산 비용이 큰 데이터 — `popular` 결과가 이 조건에 맞는지 판단해본다)

1. 자주 읽히는 데이터인가? (Hig Read Frequency)
- 조건: 애플리케이션의 서비스 메인 화면, 탐색 페이지 등 유저가 접속하자마자 가장 먼저 보게 되는 화면에서 호출되는 데이터여야 캐시 효율(Hit Rate)이 극대화됩니다.
- popular 판단: 적합. '인기 스터디' 목록은 일반적으로 웹 서비스의 메인 페이지나 대시보드 상단에 위치합니다. 서비스의 모든 사용자가 유입될 
때마다 한 번씩 무조건 호출하므로 트래픽이 가장 몰리는 핵심 API입니다.

2. 자주 바뀌지 않는 데이터인가? (Low Write Frequency)
- 조건: 데이터의 실시간 정합성(Real-time Consistency) 요구도가 낮아야 합ㄴ미다. 1초, 5초 전에 바뀐 내용이 즉시 반영되지 않더라도 유저 경험이나 비즈니스 로직에 큰 문제가 없는 데이터가 좋습니다. 
- popular 판단: 적합. 인기 순위 목록은 실시간 점수가 수 밀리초(ms) 단위로 엄격하게 일치할 필요가 없습니다. 10분 전의 인기 목록이나 지금의 인기 목록이 조금 다르더라도 사용자는 인지하기 어렵고 서비스 장애나 결제 오류 같은 크리티컬한 문제를 일으키지
않습니다. 즉, 일정 시간(예: 10분~1시간)동안 데이터가 유지되어도 무방한 성격을 가집니다.

3. 계산 비용이 큰 데이터인가 (High Computation Cost)
- 조건: 한 번 조회하기 위해 DB 여러 개를 조인(Join)해야 하거나, 대량의 행을 정렬(Order By)해야하거나, 외부 API를 호출해야 하는 등 서버나 DB 자원을 많이 소모하는 연산이어야 캐싱의 이점이 큽니다. 
- popular 판단: 적합. 앞서 살펴본 것처럼 전체 스터디 테이블을 스캔하고 status='OPEN' 수만 건의 대상을 메모리나 디스크에서 정렬(enrolledCount DESC)한 뒤 10건만 남기는 Top-N 쿼리 연산입니다. 호출할 때마다 
DB CPU와 디스크 I/O를 갉아먹는 대표적인 무거운 연산입니다. 

- `RedisTemplate`와 `@Cacheable` 중 어느 쪽으로 적용할 것인가? 그 판단 기준은 무엇인가? (선언적 어노테이션 방식과 직접 키·TTL을 제어하는 방식의 차이)

: @Cacheable 방식 채택
- 선택 이유: 단순 리스트 조회 기능이므로 Redis 특화 자료구조가 불필요하면 캐시 추상화 기술만으로 충분함
- 도입 장점: 비즈니스 로직에 Redis 전용코드가침범하지 않아 가독성이 높고 깔끔한 아키텍처(AOP 기반 분리)유지가 가능함      

## 2. 캐시 적용 전후 측정

- 캐시 적용 전 `GET /api/studies/popular` 호출 시 DB 조회는 몇 번 나가는가? (5주차에서 만든 `QueryCountProbe`를 그대로 재사용할 수 있는가)

: 호출 당 1회 


- 같은 요청을 반복 호출했을 때, 캐시 적용 후에는 DB 조회가 어떻게 달라져야 하는가? (첫 호출은 캐시 미스라 DB를 타고, 이후 호출은 캐시 히트라 DB를 안 타야 한다)

: 5번을 호출하면 1회 조회만 일어나야 함

- 캐시 히트·미스를 실제로 관측하려면 무엇을 확인해야 하는가? (Redis 로그, `redis-cli MONITOR`, 애플리케이션 로그에 히트/미스 표시를 남기는 방법 중 무엇을 쓸 것인가)

: SQL 로그

- 응답 시간은 캐시 적용 전/후 어떤 차이를 보일 것으로 예상하는가? (DB 왕복이 없어지므로 캐시 히트 시 응답 시간이 크게 줄 것 — 5주차처럼 같은 조건으로 재측정해야 근거가 된다)

: 캐시를 적용하면 DB 왕복(Round Trip)과정이 생략되므로, 캐시 히트(Cache Hit)시 응답 시간이 극적으로 단축됩니다.
지표: 
1. 평균 응답 시간 : 대략 수십 ~ 수백 ms 쿼리 복잡도에 비례 -> Memory Read로 수 ms 이내
2. 처리량 : DB 커넥션 및 CPU 한계로 인해 조기 포화 -> 초당 처리 건수(TPS)가 대폭 상승
3. DB 부하 : 요청이 밀릴수록 DB부하급증, 병목 발생 -> DB부하가 최소화되어 안정적으로 유지

## 3. TTL과 무효화 전략

- `popular` 결과가 실제로 바뀌는 시점은 언제인가? (`EnrollmentService.enroll()`이 `study.enroll()`을 호출해 `enrolledCount`를 갱신하는 순간 — 이 갱신이 정렬 순위에 영향을 줄 수 있다)

: `EnrollmentService.enroll()`이 최종적으로 커밋되는 순간입니다.


- TTL(만료 시간)만으로 충분한가, 능동적 무효화(신청 발생 시 캐시 삭제/갱신)도 필요한가? 그 판단 기준은 무엇인가? (TTL이 짧으면 캐시 효과가 줄고, 길면 신청이 몰리는 인기 스터디 순위가 실제와 오래 어긋날 수 있다)

TTL에 더불어 능동적 무효화도 필요합니다. 

능동적 무효화 도입 여부 판단 기준
1. 데이터의 비대칭적 가치 (인기 데이터 집중 현상): 모든 스터디가 아닌 '인기 스터디 순위'처럼 사용자가 메인 화면 등에서 가장 먼저, 많이 보는 데이터인가?
2. 사용자 경험(UX)의 민감도: 사용자가 스터디를 '신청'한 직후에 순위나 마감 여부가 바로 반영되지 않았을 때 복수 신청, 중복 신청 등으로 인한 불만이나 시스템 오류(과신청 등)가 발생할 확률이 높은가?
3. 예측 불가능한 트래픽 튀어오름(Traffic Spike): 특정 핫한 스터디가 오픈되는 순간 신청이 폭주할 때, TTL 만료 직후 수많은 요청이 한 번에 DB로 몰리는 캐시 쇄도(Cache Stampede) 현상을 방지해야 하는가?

- TTL을 정한다면 몇 초/분으로 정할 것이며, 그 근거는 무엇인가? (인기 스터디 목록이 몇 초 단위로 갱신돼야 사용자가 이상함을 못 느끈다고 판단하는가)

: 하이브리드 전략(TTL + 능동적 무효화)을 전제로 TTL은 60초로 잡는다. 60초는 출발값이며 4단계 실측 후 바꿀 수 있다.
- 근거: 신청 시 능동적 무효화가 순위를 바로 갱신해 주므로 TTL은 "무효화 코드에 버그가 났을 때 오래된 데이터가 보이는 최대 시간"을 막는 안전망 역할만 하면 된다. 그 상한이 60초면 사용자가 순위 어긋남을 느끼기 전에 스스로 복구된다.
- 5~10분은 안전망 상한이 너무 길어서(무효화 실패 시 최대 5~10분 어긋남) 쓰지 않는다.

> ✏️ 가이드(implementation-guide.md) 결정 사항에 맞게 수정함 (원래 답: 5~10분)


- 능동적 무효화를 택한다면, `EnrollmentService.enroll()`의 어느 지점에서 캐시를 지워야 하는가? (트랜잭션 커밋 전에 지우면 롤백 시 문제가 될 수 있다는 점을 고려한다)

: 커밋 후에 지운다. `enroll()` 안에서 곧바로 지우면 커밋 전에 지우게 된다. 지운 직후 커밋 전에 다른 요청이 들어오면 아직 옛 값인 DB를 읽어 옛 값을 캐시에 다시 채운다. 롤백되면 지운 게 무의미하고, 커밋돼도 이미 늦다.
- 구현: `enroll()` 끝에서 `ApplicationEventPublisher`로 이벤트를 발행하고, 별도 리스너에 `@TransactionalEventListener(phase = AFTER_COMMIT)`로 `CacheManager.getCache("popularStudies").evict("top10-open")`을 호출한다.
- 남는 한계: "리더가 커밋 전 옛 값을 읽고 → 커밋·무효화 → 리더가 옛 값을 캐시에 씀" 순서의 경합은 이론상 남는다. 이 틈은 TTL(60초)이 막아 준다.

> ✏️ 가이드(implementation-guide.md) 5단계에 맞게 작성함 (원래 비어 있었음)

## 4. 캐시 문제 사례 방지

- cache penetration(존재하지 않는 키를 계속 조회해 캐시를 우회하고 DB를 계속 때리는 것)이 `popular` API에서 발생할 여지가 있는가? (고정된 키 하나만 쓰는 캐시라면 이 문제와 무관할 수 있다 — 왜 그런지 설명해본다)

: popular API가 '고정된 키 하나'만 사용하는 구조라면 캐시 관통(Cache Penetration) 문제는 발생하지 않습니다.

- cache avalanche(대량의 캐시가 동시에 만료되며 DB에 요청이 몰리는 것)는 이 API에서 발생할 수 있는가? (캐시 키가 하나뿐이라면 "동시 만료"라는 말이 이 상황에 어떻게 적용되는가 — TTL에 jitter를 주는 이유가 무엇인가)

:  캐시 키가 단 하나뿐이더라도 다수의 트래픽이 몰리는 API라면 캐시가 만료되는 순간 수많은 요청이 동시에 DB로 향하는 캐시 스탬피드(Cache Stampede) 현상이 발생할 수 있습니다.

- Hot Key(특정 키에 요청이 몰려 그 키를 처리하는 Redis 노드나 애플리케이션 스레드가 병목이 되는 것)는 `popular`처럼 캐시 키가 하나뿐인 경우 왜 특히 취약한가?

: popular처럼 캐시 키가 하나뿐인 Hot Key는 모든 요청이 단 하나의 해시 슬롯(Hash Slot)과 특정 Redis 마스터 노드(또는 단일 스레드)로만 집중되기 때문에 특히 취약합니다

- 셋 중 이 프로젝트 상황(단일 Redis 인스턴스, 단일 캐시 키)에 가장 해당하는 것은 무엇이고, 어떤 방지 장치를 적용할 것인가?

: 가장 해당하는 것은 Hot Key(만료 순간의 stampede)다.
- penetration: 키가 고정 하나라 입력으로 키를 바꿀 수 없어 해당 없음.
- avalanche: 여러 키가 동시에 만료되는 문제인데 키가 하나라 해당 없음. TTL jitter는 키들의 만료 시점 분산이 목적이라 키 하나에서는 의미가 없다. (제외 근거)
- Hot Key: 모든 `popular` 요청이 정의상 이 키 하나에 몰린다. 특히 위험한 순간은 TTL 만료 또는 무효화 직후다. 키가 비는 순간 동시에 들어온 N개 요청이 전부 미스가 되어 같은 쿼리를 N번 DB로 보낸다.

방지 장치: `@Cacheable(sync = true)`. 같은 키에 동시 미스가 여러 개 와도 한 스레드만 DB를 조회하고 나머지는 그 결과를 기다려 받는다.

동작 확인: 캐시를 비운 상태에서 동시 30건을 `CountDownLatch`로 출발시키고 `QueryCountProbe`로 `from study` 조회 수를 센다. `sync` 끈 상태(방지 전)와 켠 상태(방지 후)를 같은 조건으로 비교한다. 예측은 켠 상태 1건, 끈 상태 여러 건이다.

한계:
- `sync = true`의 잠금은 JVM 하나 안에서만 유효하다. 앱이 인스턴스 여러 개로 늘면 인스턴스당 1건씩은 DB로 간다. (✏️ 보완: 이 문장은 인메모리 `ConcurrentMapCache` 기준이다. 실제 Redis 캐시에서는 4-1의 6번 보완처럼 Boot 기본 설정에서 락이 없을 수 있어 확인이 필요하다.)
- `sync = true`는 만료 순간의 동시 미스를 막는 것이지, 읽기가 한 키에 몰려 Redis 한 노드에 부하가 쏠리는 구조적 Hot Key까지 해결하지는 않는다. 로컬 캐시(L1) 도입은 그쪽의 해법이지만 이번 미션에서는 다루지 않는다.

> ✏️ 가이드(implementation-guide.md) 6단계에 맞게 수정함 (원래 답: 로컬 캐시 L1 + Redis L2 도입)

### 4-1. `@Cacheable(sync = true)`와 고정 키의 메커니즘 (학습용, 직접 작성)

```java
// 키가 하나뿐이라는 사실이 코드에 보이도록 고정 문자열로 준다.
@Cacheable(cacheNames = CACHE_NAME, key = "'" + CACHE_KEY + "'", sync = true)
```

> ✏️ Claude 보완 (2026-10-06): 아래 답변을 검토해 보완했다. 지호님이 쓴 본문은 그대로 두고, 보완한 곳마다 `✏️ 보완` 표시를 붙였다. 근거는 프로젝트가 실제로 쓰는 버전의 소스 jar(spring-context 6.2.8, spring-data-redis 3.5.1, spring-boot-autoconfigure 3.5.3)를 직접 읽은 것이다. 가장 큰 보완은 `sync = true`가 실제 Redis 캐시에서는 JVM 락이 아닐 수 있다는 점이다(6번 보완 참고).

- `sync = true`가 없을 때, 동시 30개 요청이 캐시가 빈 순간에 들어오면 호출 하나가 "조회 → 미스 → 메서드 실행 → 저장"을 거치는 동안 무엇이 문제인가? (이 네 단계가 하나로 묶여 있는가, 아니면 각각 따로 실행되는가 — 방지 전에 조회가 30번 나온 이유와 연결해서 생각해본다)

sync=true가 없을 때, 캐시가 비어 있는 상태에서 동시 30개의 요청이 들어오면 캐시 스탬피드 현상이 발생합니다. 

조회가 30번 동시에 일어나는 근본적인 이유는 조회, 미스판정, 메서드 실행, 저장 단계가 원자적(Atomic, 하나로 묶인 연산)으로 실행되지 않고 각각 따로 실행되기 때문입니다. 

네 단계의 분리 및 문제점 발생 과정
1. 조회 (30번 발생)
- 30개의 스레드가 거의 동시에 캐시 서버에 접근해 데이터를 조회합니다.
- 이때 캐시가 비어 있으므로, 30개 스레드 모두 캐시 미스 판정을 받습니다. 

2. 미스 판정 & 메서드 실행 (30번 중복 실행)
- sync=false(기본값) 환경에서는 캐시 미스가 난 이후의 무거운 작업(DB 조회 또는 비즈니스 로직 연산)에 대해 락을 걸어주지 않습니다. 
- 결과적으로 30개의 스레드 전부가 "아, 데이터가 없구나"라고 판단하고, 각자 DB를 찌른거나 복잡한 연산을 독립적으로 30번 실행하게 됩니다. 서버와 DB에 엄청난 부하가 걸립니다.

3. 저장 (30번 덮어쓰기)
- 30개의 스레드가 연산을 끝낸 순서대로 캐시에 결과를 덮어씁니다. 
- 결과적으로 같은 데이터가 30번 중복 연산되어 불필요한 자원이 낭비되고, 먼저 끝난 연산의 결과가 나중에 끝난 연산의 결과로 덮어써집니다(값이 같아도 저장이 30번 일어납니다).

> ✏️ 보완: 위 두 곳을 고쳤다. 173행의 끊긴 문장을 마무리했고, 169행의 "복잡한 3 동작"을 "복잡한 연산"으로 바로잡았다. 개념(조회, 미스 판정, 실행, 저장이 분리됨)은 맞다. Spring의 `@Cacheable`은 `sync`가 아닐 때 "캐시 조회 → 없으면 메서드 실행 → 결과 저장"을 별도 호출로 처리한다.

- `sync = true`를 켜면 같은 상황에서 스레드들은 각각 무엇을 하는가? (누가 DB를 조회하고, 나머지는 무엇을 기다리는가. 기다리던 스레드는 결과를 어디서 어떻게 받는가)

동일한 캐시 키에 대해 여러 요청이 동시에 들어올 때 하나의 스레드만 캐시 미스를 처리하고 나머지 스레드들은 대기하는 동기화 메커니즘이 작동합니다.

1. 스레드들의 역할 분담
- 첫 번째로 진입한 스레드(Lock 획득자): 데이터베이스를 직접 조회하는 역할을 맡습니다. 이 스레드가 연산을 수행하는 동안 해당 캐시 키에 대한 락을 쥡니다. 
- 나머지 후속 스레드들 (대기자): DB를 조회하지 않고, 첫 번째 스레드가 락을 해제하고 캐시에 값을 채워넣을 때까지 블로킹되어 기다립니다. 

2. 기다리던 스레드가 결과를 받는 방법
대기하던 스레드들은 첫 번째 스레드의 작업이 끝난 후, DB가 아닌 캐시 메모리(또는 캐시 저장소)에서 결과를 받습니다. 
- 어디서 받는가: 최초 스레드가 DB에서 조회해와서 저장해 둔 캐시(Cache Object)에서 결과를 가져 옵니다. 
- 어떻게 받는가:
  1. 첫 번째 스레드가 DB 조회를 마치고 캐시에 값을 저장한 뒤 락을 해제합니다.
  2. 대기하고 있던 스레드들이 차례대로 깨어나며 락을 획득합니다. 
  3. 이때 이미 캐시에 값이 존재(Cache Hit)하므로, DB를 호출하지 않고 캐시 엔진 내부 인터페이스를 통해 직접 값을 읽어서 반환받습니다.

> ✏️ 보완 (2번): 큰 흐름(한 스레드가 조회하고 나머지는 대기)은 맞다. 다만 "해당 캐시 키에 대한 락"이라는 표현은 구현에 따라 달라진다. 인메모리 `ConcurrentMapCache`는 `ConcurrentHashMap.computeIfAbsent(key, 로더)`를 쓰므로 같은 키(같은 해시 버킷)의 다른 스레드가 로더가 끝날 때까지 기다렸다가, 저장된 값을 그 호출의 결과로 바로 받는다(별도로 캐시를 다시 읽는 게 아니다). Redis 캐시에서는 6번 보완처럼 구조가 다르다.

- 이 잠금은 어디에 걸리는가? Redis인가, JVM인가? 그래서 애플리케이션 인스턴스가 2개 이상이면 어떻게 되는가? (6단계 한계 항목에 적은 "인스턴스당 1건"이 왜 그렇게 되는지 설명해본다)

JVM 레벨에 걸리는 로컬 락입니다. 
1. 잠금의 위치(JVM vs Redis)
- JVM 락: synchronized나 ReentrantLock처럼 단일 서버(프로세스)안의 메모리에서만 동작하니다. 
- Redis 락: 별도의 레디스 서버를 통해 여러 애플리케이션이 공통으로 바라보는 분산 락입니다. 
- 인스턴스 당 1건만 허용된다는 것은 각 서버의 JVM 메모리에서만 유효한다는 뜻이므로 JVM 락에 해당합니다. 

2. 인스턴스가 2개 이상일 때 발생하는 현상
- 애플리케이션 서버가 2대 이상(예: 서버 A, 서버 B)으로 확장되면 각각 독립된 JVM이 실행됩니다. 
- 서버 A의 JVM과 서버 B의 JVM은 서로의 락(Lock) 상태를 공유하지 않습니다. 
- 따라서, 서버 A에서 1건, 서버 B에서 1건이 동시에 처리될 수 있으며, 전체 시스템 기준으로 중복 실행을 막지 못합니다. 


> ✏️ 보완 (3번): "JVM 락이라서 인스턴스 2개면 인스턴스당 1건"이라는 결론은 **인메모리 `ConcurrentMapCache`에서만** 소스로 확인된다(`computeIfAbsent`는 JVM 안의 동기화). 실제 Redis 캐시(`RedisCache`)에서는 6번 보완처럼 Spring Boot 기본 설정에서 락이 아예 없을 가능성이 있다. 그 경우 인스턴스당 1건이 아니라 한 인스턴스 안에서도 여러 건이 DB로 갈 수 있다. 이 부분은 소스를 읽고 추론한 것이라 로컬 Redis에서 동시 호출로 직접 확인해야 한다(6번 보완의 "확인 방법").

- `key = "'top10-open'"`에서 작은따옴표는 왜 필요한가? 따옴표 없이 `key = "top10-open"`이라고 쓰면 어떻게 되는가? (SpEL 표현식과 문자열 리터럴의 차이)

작은따옴표는 해당 값이 변수나 연산식이 아닌 순수한 문자열(String Literal)임을 SpEL(Spring Expression Language)에 알려주기 위해 필요합니다.

따옴표 없이 key = top10-open이라고 쓰면 어떻게 되는가?
• 뺄셈 연산으로 인식: SpEL은 중간에 들어간 하이픈(-)을 문자열이 아니라 마이너스(뺄셈) 연산자로 해석합니다.
• 오류 발생: SpEL은 top10이라는 변수(또는 프로퍼티)에서 open이라는 변수의 값을 빼려고 시도합니다.
• 결과: 해당 변수들이 정의되어 있지 않거나 숫자가 아니라면 SpelEvaluationException (표현식 평가 오류)이 발생합니다.


- 인자가 없는 메서드에 `key`를 지정하지 않으면 기본 키는 무엇이 되고, 고정 키로 명시하면 무엇이 더 나은가? (Redis에서 보이는 키 이름, 무효화 코드가 같은 키를 지울 때의 일치 문제)

:인자가 없는 메서드에 key를 지정하지 않으면 Spring Cache(Redis)의 기본 키는 빈 스트링("")을 기반으로 한 SimpleKey.EMPTY 객체가 됩니다.

> ✏️ 보완 (5번): 답이 "기본 키는 `SimpleKey.EMPTY`"에서 멈춰 있어 이어서 채운다.
> - 기본 키: `SimpleKeyGenerator.generateKey(params)`는 `params.length == 0`이면 상수 `SimpleKey.EMPTY`를 반환한다(spring-context 6.2.8 소스 확인). `SimpleKey.EMPTY`는 "빈 문자열"이 아니라 매개변수 배열이 비어 있는 `SimpleKey` 객체다. Redis에 저장될 때의 실제 키 이름은 `key`를 지정하지 않고 한 번 띄워 `redis-cli KEYS '*'`로 보는 게 확실하다(이 부분은 확인하지 않았다).
> - 고정 키가 나은 점 세 가지: (1) 인자 없는 메서드는 모두 같은 상수 키를 쓰므로, 같은 캐시 이름 아래 인자 없는 메서드가 둘 이상이면 키가 충돌한다. (2) `popularStudies::top10-open`처럼 Redis에서 읽을 수 있는 이름이 된다. (3) 무효화 코드가 `evict("top10-open")`로 정확히 같은 키를 지울 수 있다. 기본 키였다면 `SimpleKey.EMPTY` 객체를 알아야 지울 수 있다.

- (조사) 테스트가 쓰는 인메모리 캐시(`ConcurrentMapCache`)와 실제 Redis 캐시에서 `sync = true`가 같은 방식으로 구현되어 있는가? 같다/다르다를 확인한 근거는 무엇인가? (Spring 소스나 공식 문서에서 찾아보고, 찾은 곳을 적는다)

1. ConcurrentMapCache (인메모리 캐시)
• 작동 방식: 애플리케이션(JVM) 내부의 로컬 락을 사용합니다.
• 구현 세부사항: ConcurrentMapCache 소스코드를 보면 get(Object key, Callable<T> valueLoader) 메서드 호출 시, 동기화를 위해 내부적으로 synchronized 블록 또는 ConcurrentHashMap 고유의 버킷 레벨 락(e.g. computeIfAbsent) 메커니즘을 사용합니다.
• 범위: 동일한 JVM 프로세스 내의 멀티스레드 간에만 동기화(Cache Stampede 방지)가 보장됩니다.
• 확인 근거 (Spring Framework 공식 문서 및 소스):
	• org.springframework.cache.concurrent.ConcurrentMapCache 클래스의 소스코드를 확인하면, sync=true 요청을 처리하기 위해 내부 store(기본값 ConcurrentHashMap) 객체 자체나 로컬 동기화 프리미티브를 활용해 스레드를 대기시킵니다.

  2. RedisCache (Spring Data Redis)
• 작동 방식: 별도의 분산 락(Distributed Lock)을 구현하지 않고, 단일 애플리케이션 내부에서 로컬 동기화를 수행하는 데 그칩니다.
• 구현 세부사항: RedisCache 클래스의 get(Object key, Callable<T> valueLoader) 메서드는 내부적으로 RedisCacheWriter를 호출합니다. 하지만 Spring Data Redis의 기본 구현체는 다중 서버(멀티 프로세스) 환경 전체를 묶는 글로벌 분산 락을 걸지 않습니다. 단지 해당 요청을 보낸 단일 WAS(JVM 인스턴스) 내부에서만 스레드가 락을 공유합니다.
• 범위: 다중 서버(분산 서버) 환경에서 여러 대의 WAS가 동시에 동일한 캐시 미스를 발생시키면, 서버 개수만큼 Redis로 데이터 조회 요청이 중복해서 들어갈 수 있습니다.
• 확인 근거 (Spring Data Redis 공식 이슈 및 문서):
	• Spring Data Redis의 관련 버그/기능 토론인 DATAREDIS-1100 (GitHub Issue #1670)에 따르면, *"sync flag는 단일 인스턴스의 로컬 캐시 동기화 역할만 할 뿐, 다중 컨테이너/서버 인스턴스 간의 글로벌 동기화나 락을 제공하지 않는다"*라고 명시하며 이를 Not a bug(의도된 설계)로 판단하고 종결했습니다.

> ✏️ 보완 (6번, 가장 중요): 위 답변의 근거 인용과 Redis 쪽 설명을 소스로 다시 확인해 고쳤다.
>
> 1. **`DATAREDIS-1100 (GitHub Issue #1670)` 인용은 근거로 쓰지 않는다.** 이 이슈와 인용문을 확인하지 못했다. 번호가 실재하는지, 그 내용인지 모른다. 대신 아래의 소스 확인을 근거로 한다.
> 2. **`ConcurrentMapCache`** (spring-context 6.2.8, `ConcurrentMapCache.get(Object key, Callable<T> valueLoader)`): `this.store.computeIfAbsent(key, k -> toStoreValue(valueLoader.call()))`를 호출한다. `synchronized` 블록이 아니라 `ConcurrentHashMap.computeIfAbsent`다. JVM 안에서만 유효한 동기화이고, 같은 키의 다른 스레드는 로더가 끝날 때까지 기다린다.
> 3. **`RedisCache`** (spring-data-redis 3.5.1, `RedisCache.get(Object key, Callable<T> valueLoader)`): 이 메서드는 `synchronized`가 아니다. 대신 `getCacheWriter().get(캐시이름, 키, 로더, ttl, ...)`로 위임한다. 즉 "단일 WAS 안에서 스레드가 락을 공유한다"는 기존 답은 이 버전에서는 맞지 않는다.
> 4. **`DefaultRedisCacheWriter.get(name, key, valueLoader, ttl, tti)`**: 락을 쓰는 라이터(locking)이면 `SET ... NX`로 Redis에 락 키를 걸고(캐시 이름 단위, 키 단위가 아님) 조회, 로더 실행, 저장, 락 해제(DEL)를 한다. 락을 안 쓰는 라이터(non-locking)이면 락 없이 `조회 → 없으면 로더 실행 → 저장`만 한다.
> 5. **Spring Boot 기본 설정은 non-locking이다.** `RedisCacheManager.builder(connectionFactory)`는 `RedisCacheWriter.nonLockingRedisCacheWriter(connectionFactory)`를 만들고, Boot 3.5.3의 `RedisCacheConfiguration.cacheManager`가 이 `builder`를 쓴다(소스 확인).
>
> **소스에서 이어지는 추론(실행하지 않음)**: Boot 기본 설정의 실제 Redis 캐시에서는 `@Cacheable(sync = true)`가 같은 JVM 안에서도 중복 로드를 막지 못할 수 있다. 6단계의 "30번 → 1번"은 **인메모리 `ConcurrentMapCache`로 테스트한 결과**이고, Redis 캐시에서는 확인된 적이 없다.
>
> **확인 방법**(로컬 Redis, 앱이 Redis 캐시를 쓰는 상태):
> ```bash
> docker compose exec redis redis-cli FLUSHDB
> curl -s localhost:8080/actuator/prometheus | grep hibernate_statements_total
> seq 30 | xargs -P 30 -I{} curl -s -o /dev/null http://localhost:8080/api/studies/popular
> curl -s localhost:8080/actuator/prometheus | grep hibernate_statements_total
> ```
> 호출 전후 `hibernate_statements_total`의 차이가 DB 조회 횟수다. 1이면 Redis에서도 막힌 것이고, 1보다 크면 막히지 않은 것이다.

## 5. 정합성 보장

- 캐시된 `popular` 데이터와 실제 DB 데이터가 잠깐 어긋나는 것을 허용할 수 있는가? (인기 스터디 목록처럼 실시간 정확도가 필수는 아닌 데이터인가, 아닌가)

네, 인기 스터디 목록과 같은 데이터는 실시간 정확도가 필수가 아니기 때문에, 캐시와 실제 DB 데이터가 잠깐 어긋나는 것(최종 일관성, Eventual Consistency)을 충분히 허용할 수 있습니다.

- 만약 캐시 무효화 코드에 버그가 있어 무효화가 안 된다면, 최악의 경우 얼마나 오래된 데이터가 보이는가? (TTL이 상한선 역할을 한다는 것을 코드로 어떻게 보장할 것인가)
1. 비즈니스적 관점: 실시간성이 중요하지 않음
2. 기술적 관점: 시스템의 안정성과 성능 극대화
3. 최악의 경우: 무효화가 실패해도 TTL 60초가 상한이라 최대 60초까지 오래된 데이터가 보인다. 상한은 코드에서 `RedisCacheConfiguration`의 `entryTtl(Duration.ofSeconds(60))`로 보장하고, 실제 TTL이 걸렸는지는 `redis-cli TTL`로 확인한다. (테스트는 인메모리 폴백 캐시라 TTL 자체는 검증하지 못한다.)

## 7. 근거형 질문 준비 (미션 질문 1~5)

정답은 안 적는다. 각 질문에서 무엇을 실측/조사해야 답이 나오는지만 짚는다.

- 캐싱 대상 데이터를 어떻게 선정했나요?
  - 확인할 것: `StudyController.popular()`·`StudyRepository` 주석, 이 쿼리의 계산 비용

- TTL(만료 시간) / 무효화 전략은 어떻게 설정했나요?
  - 확인할 것: `enrolledCount`가 바뀌는 시점(`EnrollmentService.enroll()`)과 TTL 값의 관계, 능동적 무효화 코드 위치

- 캐싱 적용 전후의 성능(응답 시간, DB 부하 등)은 어떻게 달라졌나요?
  - 확인할 것: 같은 조건(반복 호출)에서의 응답 시간, `QueryCountProbe`로 잰 DB 조회 수, 캐시 히트/미스 관측 기록

- Cache avalanche나 Hot Key 문제를 어떻게 방지할 수 있을까요?
  - 확인할 것: 이 프로젝트(단일 캐시 키) 상황에 실제로 해당하는 문제가 무엇인지, 적용한 방지 장치와 그 동작 확인 방법

- 캐시에 저장된 데이터가 변경되어도 문제가 없는지(정합성)는 어떻게 보장할까요?
  - 확인할 것: TTL 상한과 능동적 무효화 코드, 무효화가 실패했을 때의 최악 시나리오
