# /improve-codebase-architecture — 코드베이스 설계 개선

## 한 줄 요약

코드베이스를 스캔해서 얕은 모듈을 깊게 만들 기회를 HTML 보고서로 제시한다.
AI로 빠르게 코딩할수록 설계 엔트로피도 빠르게 쌓인다. 이걸 정기적으로 실행한다.

---

## 언제 쓰나

- 며칠 동안 기능을 빠르게 추가한 후 설계를 점검하고 싶을 때
- 코드베이스가 점점 이해하기 어려워질 때
- 버그 수정 후 "왜 테스트하기 어려웠지?"를 물었을 때
- 새 기능 추가 전에 현재 설계 상태 파악이 필요할 때

Matt Pocock이 "며칠에 한 번씩 실행하라"고 추천하는 스킬.

---

## 프로세스

### 1. 탐색

먼저 CONTEXT.md 읽기. 도메인 어휘를 기준으로 탐색한다.

탐색 중 찾는 것:
- 하나의 개념을 이해하려면 여러 작은 모듈을 오가야 하는 곳
- 얕은 모듈: 인터페이스가 구현만큼 복잡한 곳
- 테스트하기 어려운 공개 인터페이스
- 긴밀하게 결합된 모듈이 이음새를 넘어 흘러나오는 곳
- 테스트가 없거나 현재 인터페이스로 테스트하기 어려운 부분

각 후보에 삭제 테스트 적용:
이걸 지우면 복잡도가 한 곳에 모이나? → 가치 있는 모듈
이걸 지우면 복잡도가 여러 호출자로 흩어지나? → 얕은 모듈

---

### 2. HTML 보고서 생성

후보들을 HTML 파일로 작성해서 OS 임시 디렉토리에 저장하고 열어준다.
레포에는 아무것도 남기지 않는다.

각 후보 카드에 포함되는 것:
- 관련 파일/모듈
- 현재 설계가 마찰을 일으키는 이유
- 무엇이 바뀌어야 하는지 평이한 설명
- 로컬리티와 레버리지 측면의 개선 효과, 테스트 개선 방법
- Before/After 다이어그램 (시각적으로)
- 권장 강도: Strong / Worth exploring / Speculative

보고서 마지막에 "가장 먼저 해야 할 것" 섹션 포함.

---

### 3. 그릴링 루프

후보를 하나 선택하면 /grilling을 실행해서 설계 트리를 함께 내려간다.
제약, 의존성, 깊어진 모듈의 형태, 이음새 뒤에 뭐가 들어가는지, 어떤 테스트가 살아남는지.

결정이 확정되는 순간 /domain-modeling 실행:
- 깊어진 모듈 이름이 CONTEXT.md에 없으면 추가
- 모호한 용어가 명확해지면 즉시 업데이트
- 후보를 거부하되 납득할 만한 이유가 있으면 ADR 제안

---

## 권장 강도 기준

Strong: 명확한 얕은 모듈, 테스트가 없거나 불가능함, 삭제 테스트 통과

Worth exploring: 마찰이 있지만 리팩토링 비용이 클 수 있음, 트레이드오프 있음

Speculative: 아키텍처적으로 흥미롭지만 현재 실질적 문제가 없음

---

## 주의사항

ADR이 있는 영역은 그 결정을 다시 꺼내지 않는다.
마찰이 ADR을 재논의할 만큼 실질적일 때만, 명확한 경고와 함께 제시한다.

용어는 항상 codebase-design 스킬 어휘를 쓴다:
모듈, 인터페이스, 깊이, 이음새, 어댑터, 레버리지, 로컬리티.
"서비스", "컴포넌트", "API", "경계"는 쓰지 않는다.
