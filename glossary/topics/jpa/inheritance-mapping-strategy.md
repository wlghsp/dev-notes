# 상속 매핑 전략 (Inheritance Mapping Strategy)

자바의 클래스 상속과 관계형 DB의 테이블 구조는 자연스럽게 맞아떨어지지 않는다. 자바는 부모 클래스를 두고 여러 자식 클래스가 상속받는 계층 구조를 만들 수 있지만, 테이블은 컬럼들의 평평한(flat) 집합일 뿐이라 "상속"이라는 개념 자체가 없다.

그래서 이 자바 클래스 계층을 테이블로 어떻게 옮길지 JPA가 규칙을 정해줘야 하는데, 이 규칙이 상속 매핑 전략이다. `@Inheritance` 애노테이션으로 선언하며, 항상 최상위 부모 클래스에만 붙인다. 자식 클래스에는 따로 붙이지 않는다 — 전략은 상속 계층 전체에 한 번 적용되는 설정이기 때문이다.

## SINGLE_TABLE

부모와 모든 자식의 컬럼을 테이블 하나에 전부 몰아넣는 방식이다. 부모 공통 컬럼과 각 자식의 전용 컬럼이 테이블 하나에 함께 들어간다.

이 구조에서는 어떤 자식 타입의 row든, 자신과 관련 없는 다른 자식의 전용 컬럼은 NULL로 남는다. 테이블이 하나뿐이라 그 컬럼 자체는 존재하지만, 그 row와는 실제로 관련이 없는 값이기 때문이다. 이게 SINGLE_TABLE이 "정규화를 위반한다"고 불리는 이유다 — 각 컬럼이 그 row와 실제로 관련 있는 값만 가져야 한다는 정규화 원칙이 깨진다.

그 결과, 서브타입 고유 컬럼에는 NOT NULL 제약을 걸 수 없다. 특정 컬럼에 NOT NULL을 걸면, 같은 테이블에 저장되는 다른 서브타입의 row가 항상 이 제약을 위반해서 INSERT가 실패한다. "이 서브타입일 때만 필수"라는 조건부 제약은 테이블 레벨에서 표현할 방법이 없기 때문에, 그 검증 책임은 DB가 아니라 애플리케이션 코드가 떠안아야 한다.

대신 조회는 항상 테이블 하나만 보면 되므로 조인이 필요 없다. 다형성 조회(부모 타입으로 전체 조회)도 discriminator column(참고: discriminator-column.md)으로 구분만 할 뿐 조인 없는 단일 SELECT로 끝난다.

## JOINED

부모 테이블과 자식 테이블을 각각 따로 만든다. 부모 컬럼은 부모 테이블에, 자식 전용 컬럼은 해당 자식 테이블에만 들어간다. 자식 테이블의 PK는 부모 테이블의 PK 값을 그대로 공유하며, 동시에 부모를 가리키는 FK 역할도 한다 — 이래야 "부모의 공통 정보 row"와 "자식의 전용 정보 row"가 같은 엔티티임을 연결할 수 있다.

이 구조는 정규화가 지켜진다. 각 테이블에는 실제로 필요한 컬럼만 존재하고, 서브타입 전용 컬럼에 NOT NULL 제약을 자유롭게 걸 수 있다.

```mermaid
erDiagram
    parent ||--o| child_a : "PK = FK"
    parent ||--o| child_b : "PK = FK"
    parent {
        bigint id PK
        string common_field
    }
    child_a {
        bigint id PK_FK
        string field_a
    }
    child_b {
        bigint id PK_FK
        string field_b
    }
```

대신 특정 서브타입 하나를 온전히 조회하려면 부모 테이블과 자식 테이블을 JOIN해야 한다. 다형성 조회를 하면 Hibernate가 부모 테이블에 모든 서브타입 테이블을 LEFT OUTER JOIN으로 붙여서 한 번에 가져오고, 조회된 row에서 어느 서브타입 컬럼이 NULL이 아닌지로 실제 타입을 판별한다. 서브타입이 많아질수록 조인 개수도 그만큼 늘어난다 — 상속 깊이가 깊거나 조회가 빈번한 도메인에서는 이 조인 비용이 구조적으로 예정되어 있다.

## 두 전략을 비교할 때 실측이 필요한 부분과 그렇지 않은 부분

"SINGLE_TABLE이 더 빠르다/느리다"는 방향성 자체는 구조만 봐도 논리적으로 도출된다 — 조인이 없으니 빠르고, 조인이 있으니 그만큼 손해를 본다는 건 SQL 구조의 문제라 어떤 DB 엔진에서든 동일하게 성립한다.

하지만 그 차이가 실제로 몇 ms인지, 운영에서 감내할 만한 수준인지는 실측 없이는 답할 수 없다. 특히 H2 같은 인메모리 DB에서 측정한 실행 시간은 옵티마이저와 인덱스 동작이 다른 MySQL 등 실제 운영 DB로 그대로 일반화할 수 없다. 일반화 가능한 것은 SQL의 구조(조인 유무, 조인 개수)이고, 일반화 불가능한 것은 그 SQL의 실행 비용(절대적인 ms 수치)이다.

## 선택 기준

SINGLE_TABLE이 유리한 경우
- 조회 성능이 최우선이고 조인 비용을 감내하기 어려울 때
- 서브클래스 전용 컬럼 수가 적어서 nullable 컬럼 낭비가 크지 않을 때
- 다형성 조회가 매우 빈번한 반면 서브타입별 데이터 삽입/수정은 상대적으로 드물 때

JOINED가 유리한 경우
- 서브클래스마다 컬럼이 많고 서로 겹치지 않아서 nullable 컬럼이 과도하게 늘어날 때
- 서브타입 하나만 단독으로 자주 조회/수정하는 패턴이 많을 때
- 정규화와 데이터 무결성이 중요해서 NOT NULL 제약을 서브클래스별로 강제하고 싶을 때

참고: discriminator-column.md
