# VFF(Value-for-Fable) 플러그인 검증

## 개요

`https://github.com/itsinseong/value-for-fable` — Claude Code 플러그인. Sonnet 세션에 output-style/skill로 "단서 우선 진단, 결론 먼저, 검증 후 완료선언" 같은 운영 패턴을 주입해서, Opus 수준 품질을 Sonnet 단가로 얻으려는 시도.

저자 벤치(`bench/RESULTS.md`) 핵심 주장:
- v2(권장 버전)가 중립 재채점에서 Opus 대비 약 95~101% (노이즈 범위 내 동률)
- 단, 기본 진단·정량 글쓰기에서만 그렇고, 아키텍처 결정·복잡 성능진단 같은 **깊은 추론에서는 Opus가 5~7점 앞섬**을 저자가 직접 인정
- "프롬프트로 상위 모델을 복제하는 게 아니라(distillation 아님), Sonnet이 평소 덜 쓰는 능력을 끌어내는 것(elicitation)" — **Sonnet의 천장 자체는 넘지 않는다**고 명시

레포 코드(hook 스크립트, plugin.json) 검토 결과 안전성 문제 없음. `/plugin marketplace add` + `/plugin install`로 설치 완료.

## 실행 방식

- **세션 트리거**: 대화에 `VFF` 입력 시 발동, `VFF 꺼`로 해제. 해당 세션에만 적용.
- **상시 모드**: `/config` → Output style → VFF. 모든 세션에 자동 적용.
- 현재는 세션 트리거로만 사용 중 (2026-07-12 기준).

## 테스트 1 — 확정 지식 설명형 (쉬운 난이도)

질문: "MySQL InnoDB에서 트랜잭션 커밋 시점에 REDO 로그를 먼저 디스크에 쓰고 데이터 페이지를 나중에 쓰는 이유는? 데이터 페이지를 바로 쓰면 안 되나?"

**결과**: 정보량 차이 거의 없음. VFF ON은 산문 위주로 논리 흐름이 이어지고 첫 문장이 결론("핵심은 순서다")으로 시작. VFF OFF는 헤더+불릿 나열형이지만 같은 내용을 다 담음.

**해석**: 이 질문은 원인 후보가 하나(WAL 원칙)로 확정된 지식 설명이라 VFF의 핵심 강점(단서 기반 가설 좁히기, 확신도 표현)이 발휘될 여지가 애초에 없었음. 차이는 문체(산문 vs 불릿)에 그침.

## 테스트 2 — 진단형, 원인 불확실 (어려운 난이도)

질문: "운영 중인 Spring Boot 서비스에서 매일 오후 2~3시에만 API 응답 지연이 튀는데, CPU/메모리 사용률은 평소와 큰 차이 없다. 원인이 뭘까?" (의도적으로 정보 불완전, 원인 후보 다수 — GC/배치/DB락/커넥션풀/외부API/캐시)

**VFF ON**:
- 첫 문장에서 단서(CPU 정상 + 시간 규칙성)로 결론 방향(대기 계열 원인) 제시
- 후보에 우선순위 부여 — 단서를 설명 못하는 후보(외부 API: "매일 정확히 같은 시간"과 안 맞음)는 순위 하향
- "가장 싼 확인부터" 순서 명시(GC 로그 → 스케줄러 → 커넥션 풀)와 그 근거 포함

**VFF OFF**:
- 결론 없이 바로 "가능한 원인은 다음과 같습니다"로 리스트 시작
- 6개 후보를 동급 나열, 우선순위 구분 없음
- 확인 항목만 나열, 어떤 순서로 확인해야 할지는 사용자에게 위임

**해석**: 이번엔 차이가 뚜렷함. VFF OFF는 지식 자체는 갖고 있지만 후보를 좁히거나 순위 매기는 일을 하지 않음(카탈로그). VFF ON은 같은 지식 위에서 관찰된 단서와 각 가설의 정합성을 판단해서 순위를 매김(진단적 사고). 다만 이는 Sonnet이 이미 아는 지식을 정리하는 능력 차이지, 새 지식이 생긴 게 아님 — 후보 목록 자체가 처음부터 틀렸다면(예: 낯선 벤더 특이 버그) VFF를 켜도 채워지지 않음.

## 결론 (2026-07-12 기준)

- 확정 지식 설명형: VFF 효과 미미, 문체 차이만
- 원인 불확실 진단형: VFF 효과 뚜렷 — 우선순위 있는 액션 플랜 vs 체크리스트의 차이
- 저자 벤치 결론(쉬운 과제=동급, 깊은 추론=Opus 우위)과 방향이 일치하는 것으로 관찰됨
- 현재 결정: 세션 트리거(`VFF`)로만 사용, 상시 모드 전환은 보류. 진단·트러블슈팅류 질문에 트리거해서 쓰는 걸로 우선 적용.

## 표본 한계

- 각 난이도별 1회 비교. 저자 벤치 대비도 표본 극소.
- 코딩/리팩토링 등 실무 코드 작업에서의 효과는 아직 테스트 안 함 — 저자도 벤치 범위 밖이라 인정한 영역.
- 추가로 테스트해볼 만한 것: dev-internals/jvm-training 문서 작성 시 VFF ON/OFF 비교, 실제 코드 리뷰·버그 진단 상황에서의 비교.
