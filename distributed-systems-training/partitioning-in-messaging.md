# 메시징 시스템에서의 파티셔닝

하나의 토픽/큐를 여러 개의 독립된 단위로 쪼개서, 병렬로 쓰고 읽을 수 있게 만드는 방식. Kafka는 이걸 파티션(partition)이라 부르고, SQS FIFO는 메시지 그룹(message group)이라 부른다 — 이름은 다르지만 푸는 문제는 같다.

## 왜 쪼개는가

메시지를 하나의 스트림으로만 다루면, 순서를 지키기 위해 반드시 한 번에 하나씩만 처리해야 한다. consumer가 여러 대 있어도 동시에 하나만 일하게 되니 처리량이 늘지 않는다.

반대로 순서를 아예 신경 쓰지 않으면 여러 consumer가 마음대로 병렬 처리할 수 있지만, 이번엔 "사용자 A의 이벤트가 발생 순서대로 처리된다"는 보장이 깨진다.

파티셔닝은 이 둘을 절충한다. 전체 스트림의 순서는 포기하는 대신, **같은 키를 가진 메시지끼리는 항상 같은 파티션으로 보내서 그 안에서만 순서를 지킨다.** 서로 다른 키의 메시지는 다른 파티션에서 병렬로 처리된다.

```
키 없음 (순서 없음, 최대 병렬)
   → 여러 consumer가 아무 메시지나 가져감

파티션 없음 (순서 보장, 병렬 없음)
   → consumer 1대만 순서대로 처리

파티션 있음 (키 내부만 순서 보장, 파티션 수만큼 병렬)
   → 키 A의 메시지는 항상 파티션 0
   → 키 B의 메시지는 항상 파티션 1
   → 파티션 0, 1은 동시에 처리됨
```

## 키를 어떻게 고르는가

파티션 키는 보통 "그 안에서 순서가 지켜져야 하는 단위"로 고른다.

- 채팅 시스템 — 대화방 ID를 키로. 같은 대화방의 메시지 순서는 지켜야 하지만, 서로 다른 대화방끼리는 순서가 섞여도 상관없다
- 주문 시스템 — 사용자 ID나 주문 ID를 키로. 한 사용자의 주문 상태 변경은 순서대로 처리돼야 한다
- 로그 수집 — 서비스명이나 서버 ID를 키로. 같은 서버의 로그는 시간 순서가 의미 있다

키를 잘못 고르면 특정 파티션에만 메시지가 몰리는 hot partition 문제가 생긴다. 예를 들어 대화방 ID를 키로 썼는데 특정 대화방 하나가 유독 활발하면, 그 파티션을 처리하는 consumer만 부하를 받고 나머지는 노는 상황이 된다.

## Kafka와 SQS FIFO의 차이

Kafka는 파티션 수를 토픽 생성 시 미리 정해두고, 이후 늘릴 수는 있어도 줄이기는 어렵다. 파티션 수가 곧 최대 병렬 consumer 수의 상한이 된다 (파티션 10개면 동시에 일할 수 있는 consumer는 최대 10대).

SQS FIFO는 메시지 그룹이라는 논리적 단위를 쓰고, 그룹 수에 물리적 상한을 미리 정하지 않는다 (내부적으로는 알아서 스케일링한다). 대신 Standard 큐 대비 처리량 자체가 낮다는 제약이 있다.

## 정리

파티셔닝은 "전체 순서 보장"과 "병렬 처리"라는 상충하는 두 요구를, 순서가 필요한 범위를 키로 좁혀서 절충하는 방식이다. 이 절충 지점을 어디서 잡을지가 메시징 시스템 설계의 핵심 결정이고, 파티션 키 선택이 곧 그 결정을 코드로 표현한 것이다.
