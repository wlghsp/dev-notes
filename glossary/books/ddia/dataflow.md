# dataflow (데이터 흐름)

참고: encoding.md, backward-forward-compatibility.md

---

같은 메모리를 공유하지 않는 다른 프로세스로 데이터를 보내려면 반드시 encoding.md 과정을 거쳐야 한다. 이 인코딩된 데이터가 실제로 어떤 경로를 통해 한 프로세스에서 다른 프로세스로 흘러가는지 정리한 것이 dataflow다. 누가 인코딩하고 누가 디코딩하느냐에 따라 필요한 호환성 방향(backward-forward-compatibility.md)이 달라진다.

## DB를 통한 흐름

DB에 쓰는 프로세스가 인코딩하고, 읽는 프로세스가 디코딩한다. 프로세스가 하나뿐이면 "미래의 나 자신에게 메시지를 보내는 것"과 같다. 여러 프로세스가 동시에 같은 DB에 접근하는 경우가 흔하고, 그중 일부는 신버전, 일부는 구버전 코드를 돌리고 있을 수 있다(rolling upgrade 도중 등). 따라서 backward/forward compatibility가 모두 필요하다.

또한 "데이터가 코드보다 오래 산다(data outlives code)"는 특성 때문에, 한 DB 안에 여러 세대의 스키마로 인코딩된 레코드가 공존할 수 있다. 자세한 내용은 schema-evolution.md 참고.

백업이나 데이터 웨어하우스 적재를 위해 스냅샷을 뜨는 archival storage의 경우, 이 시점에는 최신 스키마로 일괄 인코딩하는 게 자연스럽다. 이후로는 불변(immutable)이기 때문에 Avro object container file 같은 포맷이나 컬럼 지향 포맷(Parquet)과 잘 맞는다. 참고: column-oriented-storage.md, data-warehouse.md

## 서비스 호출을 통한 흐름 — REST와 RPC

클라이언트가 서버에 네트워크로 요청을 보내는 방식이다. 서버가 노출하는 API를 서비스라고 부른다.

- REST는 프로토콜이 아니라 HTTP의 원칙을 그대로 활용하는 설계 철학이다. URL로 리소스를 식별하고, 캐시/인증/컨텐츠 협상에 HTTP 기능을 그대로 쓴다.
- SOAP은 XML 기반 프로토콜로, WS-*라는 복잡한 표준 묶음과 WSDL(코드 생성용 인터페이스 정의 언어)에 의존한다. 상호운용성 문제가 잦아 최근에는 잘 안 쓰인다.
- RPC(원격 프로시저 호출)는 네트워크 요청을 마치 로컬 함수 호출처럼 보이게 하려는 오래된 아이디어다. 하지만 네트워크 요청은 로컬 호출과 근본적으로 다르다 — 실패할 수 있고, 타임아웃으로 결과를 알 수 없는 경우가 있고, 재시도가 중복 실행으로 이어질 수 있고, 레이턴시가 예측 불가능하고, 포인터를 그대로 못 넘긴다. 그래서 "원격 호출을 로컬 호출처럼 숨기려는" 접근 자체가 문제로 지적된다.
- 서비스 호출에서는 서버가 먼저 배포되고 클라이언트가 나중에 배포된다고 가정할 수 있어서, 요청은 backward compatibility만, 응답은 forward compatibility만 있으면 충분하다.

## 비동기 메시지 전달을 통한 흐름

RPC와 DB의 중간쯤에 있는 방식이다. RPC처럼 저지연으로 메시지가 전달되지만, 직접 네트워크 연결이 아니라 메시지 브로커(메시지 큐)라는 중개자를 거쳐 메시지를 임시로 저장한다는 점은 DB와 비슷하다.

메시지 브로커를 쓰면 수신자가 다운되어 있어도 버퍼 역할을 하고, 크래시된 프로세스에 메시지를 재전달할 수 있고, 발신자가 수신자의 주소를 몰라도 되고, 하나의 메시지를 여러 수신자에게 보낼 수 있다. 다만 RPC와 달리 보통 단방향이라서 발신자가 응답을 기다리지 않는다(비동기).

메시지 브로커는 특정 데이터 모델을 강제하지 않는다. 메시지는 그냥 메타데이터가 붙은 바이트 시퀀스이므로 어떤 인코딩 포맷이든 쓸 수 있다. 인코딩이 양방향 호환되면 publisher와 consumer를 독립적으로, 어떤 순서로든 배포할 수 있는 유연성을 얻는다.

분산 액터 프레임워크(Akka, Orleans 등)는 액터 모델(단일 프로세스 동시성 모델)을 여러 노드로 확장한 것으로, 메시지 브로커와 액터 프로그래밍 모델을 하나로 통합한 형태다. 다만 rolling upgrade를 하려면 여전히 메시지 인코딩의 backward/forward compatibility를 신경 써야 한다.
