## 1. 모니터링 구성 이해

- `docker-compose.yml`에서 Prometheus는 studypass 애플리케이션의 지표를 어디서 긁어오는가? (`monitoring/prometheus.yml`의 `scrape_configs`, `host.docker.internal:8080`)
- 왜 `localhost:8080`이 아니라 `host.docker.internal:8080`인가? (컨테이너 안에서 호스트에 떠 있는 애플리케이션에 접근하는 방법 — 1주차에 확인한 Grafana↔Prometheus 컨테이너 간 통신과 같은 원리를 반대 방향으로 적용)
  - 컨테이너 → 호스트 로의 접근 = docker는 컨테이너가 호스트 컴퓨터에 접근할 수 있도록 내부적으로 특별한 DNS도메인(host.docker.internal)을 제공합니다. 이 도메인을 사용하면 Docker가 호스트 컴퓨터의 내부 IP주소로 신호를 라우팅해 주기 때문에 호스트의 8080포트에 정상적으로 접근할 수 있습니다.
  - 컨테이너 간 통신은 Docker가 제공하는 내부 가상 네트워크(Bridge)를 통해 컨테이너 이름을 IP로 자동 변환해 줍니다. 
- `application.yml`의 `management.endpoints.web.exposure.include: health,info,prometheus,metrics`는 무슨 역할을 하는가?
  - Spring Boot Actuator가 제공하는 특정 엔트포인트를 웹을 통해 외부로 노출(공개)하도록 지정하는 역할을 합니다.
- `/actuator/prometheus` 엔드포인트에 직접 접속하면 무엇이 보이는가? (curl로 먼저 확인)
  - Prometheus 서버가 수집할 수 있는 형식(텍스트 포맷)의 애플리케이션 메트릭 데이터가 보입니다.
- Grafana에서 Prometheus data source를 다시 연결해야 하는가, 1주차에 연결한 게 유지되는가?
  - 한 번 설정하면 삭제하거나 수정하지 않는 한 그대로 유지됩니다.

## 2. TPS와 부하 테스트 개념

- 강의 2주차가 정의하는 "TPS"는 정확히 무엇을 세는 지표인가? (초당 처리 가능한 트랜잭션/요청 수)
  - 초당 처리 가능한 트랜잭션 수(Transactions Per Second)를 세는 지표입니다.
- k6의 `stages`(`k6-scripts/baseline.js`의 `{ duration, target }` 배열)는 무엇을 의미하는가? "target"이 뜻하는 게 요청 수인가, 동시 가상 사용자 수(VU)인가?
  - stages 배열은 시간이 지남에 따라 부하를 어떻게 변화시킬지 정의하는 단계별 설정입니다.
  - duration: 해당 단계가 지속되는 시간입니다.
  - target: 해당 단계의 끝에 도달해야 하는 목표 동시 가상 사용자수 (VU)입니다.
- `baseline.js`가 30초 동안 목표를 10에서 시작해 30까지 올리는 구조인데, 이게 "부하를 단계적으로 올린다"는 것과 어떻게 연결되는가?
  - 30초 동안 목표 부하를 10에서 30으로 서서히 올리는 방식은 서버에 갑작스러운 충격을 주지 않고 요청량을 점진적으로 증가(Ramp-up) 시키는 부하 테스트의 핵심 원리입니다. 
  - 부하를 단계적으로 올리는 이유와 연결되는 과정
  1. 급격한 충격 방지(Ramp-up)
    - 처음부터 30개의 요청을 한 번에 보내지 않고 10개부터 시작합니다.
    - 서버가 갑작스러운 트래픽 폭탄을 맞아 다운되는 허위 실패 현상을 막아줍니다.
  2. 서버의 안정화 시간 확보
    - 부하가 서서히 늘어나면서 서버가 커넥션 풀을 늘리거나 캐시를 준비할 여유를 가집니다.
  3. 성능 변화 추적 용이
    - 10에서 30으로 올라가는 동안 응답 속도나 오류율이 어느 시점부터 나빠지는지 명확하게 확인할 수 있습니다.

- `thresholds`의 `http_req_failed: ['rate<0.05']`는 왜 "실패시키지 않고 관측만 한다"는 주석이 붙어 있는가? (기준선을 잡는 단계와 실패 기준을 정하는 단계의 차이)
  - 기준선을 잡는 단계이므로 부하를 주면서 우리 시스템이 평소에 어느 정도 에러를 내는지 현황을 파악합니다
- k6 실행 결과에서 확인해야 할 지표는 무엇인가? (`http_req_duration`의 평균/p95/p99, `http_reqs`로 계산되는 TPS)
  - 응답시간 지표인 `http_req_duration`의 평균/p95/p99,처리량 지표인 `http_reqs`로 계산되는 TPS

## 3. 병목 자원 판단

- 1주차에 예측한 병목(count 쿼리 풀스캔, OFFSET 페이징)이 실제 부하 상황에서 어떤 자원 지표로 드러나는가? (CPU, 커넥션 풀, DB 응답 시간)
  - 1. DB 응답시간
  - 급격한 응답시간 증가: 대량의 데이터를 풀스캔하고 디스크I/O가 발생하면서 단일 쿼리의 수행시간이 밀리초단위에서 초 단위로 급증합니다.
  - 페이지 뒤로 갈수록 악화: OFFSET 페이징 특성상 뒤쪽 페이지를 조회할수록(예: 100000) 읽어야 하는 데이터양이 늘어나 응답 시간이 선형적으로 또는 기하급수적으로 증가합니다.
  - 2. CPU 사용률 (CPU Usage)
  - DB 서버 CPU 100% 도달: 대규모 테이블의 데이터 행을 조건에 맞는지

- Grafana/Prometheus에서 확인 가능한 지표 중 이번 주차에 봐야 할 것은 무엇인가? (CPU 사용률, 메모리, HTTP 요청 처리 시간 등 — actuator가 노출하는 기본 지표 확인)
