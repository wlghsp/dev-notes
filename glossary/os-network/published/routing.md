# routing (라우팅)

**"이 데이터를 어디로 보낼지 결정하는 행위"**

목적지가 있는 데이터(패킷, 요청)가 있을 때, 그게 어느 경로를 타고 누구에게 전달될지를 결정하는 과정 전체를 라우팅이라 한다.

---

## 왜 필요한가

인터넷에 연결된 기기는 수십억 개다. 내 컴퓨터에서 보낸 패킷이 어떻게 서울 데이터센터에 있는 서버를 찾아가는가? 중간에 수십 개의 라우터가 "이건 저쪽 방향으로 보내면 된다"는 판단을 연속으로 해서다. 그 판단 하나하나가 라우팅이다.

---

## 핵심 개념: 라우팅 테이블

라우터(혹은 라우팅을 하는 주체)는 **라우팅 테이블**을 갖고 있다. 목적지 IP 대역별로 "이쪽으로 보내라"는 규칙이 들어있다.

```
목적지 10.0.0.0/8   → eth0 (내부망)
목적지 192.168.0.0/16 → eth1 (사무실망)
목적지 0.0.0.0/0    → 게이트웨이 (기타 모든 것 → 인터넷으로)
```

패킷이 도착하면 목적지 IP를 보고 테이블에서 가장 구체적으로 매칭되는 규칙을 따른다.

---

## 맥락에 따라 다른 층에서 쓰인다

같은 단어지만 어느 층에서 쓰이느냐에 따라 의미가 달라진다.

**L3 (네트워크 계층) — 패킷 라우팅**

IP 패킷을 목적지까지 어느 경로로 보낼지 결정. 인터넷의 라우터들이 하는 일이 이것.

```
내 PC → ISP 라우터 → 백본 라우터 → ... → 목적지 서버
        (라우팅)       (라우팅)
```

**L7 (애플리케이션 계층) — HTTP 라우팅**

HTTP 요청의 URL, 헤더, 도메인을 보고 어느 서버/서비스로 보낼지 결정. Nginx, Ingress Controller가 하는 일.

```
GET /users → users-service
GET /orders → orders-service
```

이건 IP 패킷을 라우팅하는 게 아니라, 도착한 HTTP 요청을 라우팅하는 것.

**K8s Service / iptables — 클러스터 내 라우팅**

Service IP로 들어온 패킷을 실제 Pod IP로 바꿔 전달. kube-proxy가 iptables 규칙으로 한다.

```
10.96.0.10:80 (Service IP) → 10.244.0.5:8080 (Pod IP)
```

## 한 줄 요약

> 라우팅 = "이 데이터, 어디로 보낼지 결정"  
> 그 결정이 IP 수준이면 L3 라우팅, URL 수준이면 L7 라우팅.
