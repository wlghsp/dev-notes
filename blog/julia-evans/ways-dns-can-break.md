# DNS는 이렇게 깨질 수 있다

원문: "Some ways DNS can break" — Julia Evans (jvns.ca, 2022)

## Why

DNS 룩업 자체는 단순해 보이지만(참고: how-dns-lookup-works.md), 실제 인프라에서는 이 단순한 과정이 여러 지점에서 예상치 못하게 깨진다. 이 글은 실무에서 마주치는 DNS 장애 패턴을 모아 정리한다.

## 성능 문제

- **느린 요청**: DNS 리졸버 자체의 성능 저하(과부하, 메모리 누수 등)로 응답이 지연될 수 있다.
- **타임아웃**: 쿼리가 2초 혹은 30초 이상 걸려 타임아웃되는 경우, 요청 전체가 크게 지연된다. Kubernetes 환경에서 실제로 보고된 사례가 있다.
- **Kubernetes ndots:5**: `/etc/resolv.conf`에 `ndots:5`가 설정되면, `google.com`처럼 점이 5개 미만인 도메인을 조회할 때 먼저 4번의 도메인 검색 접미사 붙이기를 시도하다 실패하고 나서야 실제 조회를 한다. 즉 정상 도메인 하나 찾는 데 불필요한 조회가 여러 번 발생한다.

## 어떤 리졸버가 쓰였는지 특정하기 어려움

리눅스에서는 보통 `/etc/resolv.conf`를 보면 되지만, 브라우저는 DNS-over-HTTPS를 쓸 수도 있다. 일반 UDP DNS는 tcpdump로 추적 가능하지만, 암호화된 프로토콜은 어떤 리졸버가 응답했는지 숨겨버린다.

## 잘못된 NXDOMAIN 응답

서버가 "없음(no error, 레코드 없음)"을 반환해야 할 상황에서 "도메인 자체가 없음(NXDOMAIN)"을 반환하면, 조회가 조기에 중단된다. 예를 들어 도메인에 AAAA 레코드는 있는데 A 레코드가 없는 경우, NXDOMAIN 응답이 오면 정상적인 AAAA 조회까지 막힐 수 있다.

## 네거티브 캐싱

레코드가 "없다"는 사실 ㅅ자체도 캐시된다. 도메인에 아직 DNS 항목이 없던 시점에 조회하면, 그 "없음"이라는 결과가 SOA 레코드의 TTL만큼(길게는 몇 시간) 캐시되어, 나중에 레코드를 추가해도 한동안 여전히 없는 것으로 보인다.

## 애플리케이션 레벨의 영구 캐싱

- **nginx**: `proxy_pass https://some.domain.com` 설정은 시작 시점에 한 번만 도메인을 resolve하고 이후 갱신하지 않는다. 몇 달 뒤 대상 IP가 바뀌면 갑자기 서비스가 끊길 수 있다.
- **Java**: JVM도 DNS TTL을 무시하고, JVM을 재시작하기 전까지 캐시된 IP를 계속 쓰는 경우가 있다.

## /etc/hosts로 인한 혼란

로컬 `/etc/hosts`에 등록된 항목은 실제 DNS 조회 결과를 덮어쓰지만, `dig` 명령으로는 이 override가 보이지 않는다. 그래서 dig로는 정상인데 실제 브라우저/앱에서는 다른 결과가 나오는 혼란이 생긴다.

## 이메일 관련 문제

MX, SPF, DKIM 레코드가 모두 DNS에 의존하기 때문에, 겉으로는 "메일이 안 온다"는 문제도 근본 원인은 DNS인 경우가 많다.

## 국제화 도메인(IDN)

`💩.la` 같은 비-ASCII 도메인은 실제로는 퓨니코드(punycode)로 변환되어 `xn--ls8h.la` 형태로 처리된다. 소프트웨어마다 이 변환 지원이 일관되지 않아 호환성 문제가 생긴다.

## TCP DNS 포트 차단

방화벽이 UDP 53번 포트는 허용하면서 TCP 53번 포트는 막아두면, 응답 크기가 커서 TCP로 재시도해야 하는 상황에서 간헐적으로 실패한다.

## musl의 TCP DNS 미지원

Alpine Linux가 쓰는 musl libc는 응답이 너무 커서 TCP로 재시도해야 하는 상황을 제대로 처리하지 못한다. DNS 서버가 잘려진(truncated) 응답을 주며 TCP 재시도를 기대해도, musl은 조용히 실패한다.

## Round Robin DNS와 getaddrinfo

`getaddrinfo`는 반환된 IP 목록을 정렬하는데, 이 때문에 과거 `gethostbyname`(현재는 deprecated)으로 동작하던 라운드로빈 방식의 로드밸런싱이 깨질 수 있다. 라이브러리 업그레이드만으로 의도치 않게 이 문제가 발생하기도 한다.

## 서비스 시작 시 레이스 컨디션

컨테이너들이 동시에 시작되면, DNS 레코드가 전파되기도 전에 조회가 먼저 일어날 수 있다. 이때 실패한 조회 결과가 캐시되어 버리면, 이후 레코드가 정상적으로 생겨도 캐시 때문에 계속 실패 상태로 남는다.
