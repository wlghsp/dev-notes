# hash-index
참고: sstable.md, lsm-tree.md

---

가장 단순한 인덱스 구조다. 키와 해당 키가 저장된 파일 내 바이트 오프셋을 인메모리 해시맵으로 유지한다. 읽기 요청이 오면 해시맵에서 오프셋을 찾아 디스크의 정확한 위치로 점프한다.

## 동작 방식

Bitcask(Riak의 기본 스토리지 엔진)가 이 방식을 쓴다. 쓰기는 파일 끝에 항상 append한다. 삭제도 "삭제됐다"는 표시(tombstone)를 append하는 방식으로 처리한다. 데이터를 중간에 수정하지 않기 때문에 순차 쓰기만 발생한다.

세그먼트 파일이 일정 크기를 넘으면 새 파일로 전환하고, 백그라운드에서 이전 세그먼트들을 병합(compaction)해 공간을 회수한다. compaction이 끝나면 병합된 세그먼트의 오프셋으로 해시맵을 교체하고 이전 파일을 삭제한다.

## 조건: 키가 메모리에 들어와야 한다

해시맵을 RAM에 올려놓는 구조이므로, 키가 너무 많으면 메모리를 초과한다. 키 종류가 적고 각 키에 대한 쓰기가 매우 빈번한 경우(예: URL 클릭 수 누적)에 적합하다. 키가 너무 많거나 키 집합이 메모리에 올라오지 않으면 쓸 수 없다.

## 범위 쿼리에 취약하다

해시맵은 순서가 없다. "kitty00000에서 kitty99999 사이의 키를 모두 조회"하는 요청을 처리하려면 전체 해시맵을 스캔해야 한다. 범위 쿼리가 필요하다면 sstable.md 기반의 구조를 써야 한다.
