# 쿠버네티스와 OCP의 관계

쿠버네티스는 컨테이너 오케스트레이션을 위한 오픈소스 프로젝트 자체다. OCP는 그 쿠버네티스를 가져다 레드햇이 패키징하고 지원하는 배포판이다. "OCP는 쿠버네티스 배포판"이라는 말만으로는 정확히 뭘 더했고 뭐가 다른지 알기 어려운데, 그 내용을 여기서 정리한다.

## 배포판이라는 말의 의미

리눅스로 비유하면 이해가 빠르다. 리눅스 커널 자체는 오픈소스 프로젝트이고, 우분투나 RHEL은 그 커널에 패키지 관리자, 설치 도구, 기본 설정을 얹어 배포하는 배포판이다. 쿠버네티스와 OCP의 관계도 똑같다 — 쿠버네티스는 오픈소스 프로젝트이고, OCP는 그 위에 레드햇이 운영 도구와 엔터프라이즈 기능을 얹어 배포하는 제품이다.

## OCP가 순정 쿠버네티스에 더한 것

- 설치/업그레이드 도구 — 순정 쿠버네티스는 클러스터 구축 방법이 여러 갈래(kubeadm, kops 등)로 나뉘어 있고 사용자가 직접 조합해야 한다. OCP는 설치·업그레이드 과정을 자체 Installer로 통합해서 제공한다
- 인증/사용자 관리 — 순정 쿠버네티스는 인증 방식을 플러그인 형태로 열어만 두고 구현은 사용자 몫이다. OCP는 OAuth 기반 로그인, 역할 기반 접근 제어(RBAC) 설정을 기본으로 갖추고 있다
- 이미지 빌드 — 순정 쿠버네티스에는 이미지 빌드 기능이 없다. OCP는 소스 코드를 클러스터 안에서 바로 컨테이너 이미지로 빌드하는 기능(Source-to-Image)을 포함한다
- 웹 콘솔 — 순정 쿠버네티스의 대시보드는 별도로 설치해야 하는 부가 기능이지만, OCP는 웹 콘솔을 기본 제공한다
- `oc` CLI — `kubectl`을 그대로 쓸 수 있지만, OCP 고유 기능(빌드, 배포 등)까지 다루는 `oc` 명령어가 추가된다

## 오브젝트와 API는 그대로다

핵심은 Pod, Deployment, Service 같은 쿠버네티스 오브젝트와 API 자체는 OCP에서도 그대로라는 점이다. 참고: pod.md

OCP가 바꾸는 것은 "그 오브젝트들을 어떻게 설치·운영·접근하느냐"는 주변 계층이지, 오브젝트 모델 자체가 아니다. 그래서 순정 쿠버네티스에서 쓰던 YAML 매니페스트나 `kubectl` 명령은 OCP에서도 대부분 그대로 동작한다.

참고: ocp.md, rhov.md, rhoso.md, odf.md, ovn-kubernetes.md
