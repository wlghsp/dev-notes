# NTP (Network Time Protocol)

여러 서버(VM)의 시스템 시각을 하나의 기준 시각에 맞춰 동기화하는 프로토콜. 각 VM은 자체 하드웨어 클럭을 갖고 있는데, 이 클럭은 서버마다 미세하게 다른 속도로 흘러간다(clock drift). NTP는 이 오차를 주기적으로 보정해서 여러 서버가 "같은 시간"을 보게 만든다.

---

## 왜 클럭이 서버마다 달라지는가

하드웨어 클럭은 수정 발진자(crystal oscillator)의 진동을 세어 시간을 계산한다. 이 발진자의 진동 주파수는 온도·전압·제조 편차에 따라 미세하게 달라진다. 그래서 VM마다 시간이 조금씩 다른 속도로 흘러 서서히 어긋난다. 하이퍼바이저 위의 VM은 이 문제가 더 심하다. 호스트가 다른 프로세스에 CPU를 뺏기면 VM의 가상 클럭도 같이 멈췄다 가기 때문이다.

## 분산 시스템에서 NTP가 중요한 이유

여러 서버가 "이벤트 순서"나 "지금이 유효기간 안인지"를 시각에 의존해 판단할 때, 시각이 안 맞으면 이 판단이 틀어진다. k8s 클러스터와 데이터 파이프라인 모두 이 문제를 겪는다.

**k8s 클러스터** — 가장 흔한 문제는 인증서(TLS) 검증 실패다. kubelet ↔ API server, Istio mTLS 같은 컴포넌트 간 통신은 유효기간이 있는 TLS 인증서로 이뤄진다. VM 시계가 이 유효기간을 벗어나면 정상 인증서도 거부된다. etcd 리더 선출과 노드 생존 판단(heartbeat)도 시간 계산을 전제로 한다. 그래서 시각이 어긋나면 클러스터 운영 전반이 불안정해질 수 있다.

**데이터 파이프라인** — 노드마다 타임스탬프가 어긋나면 "실제 발생 순서"와 "기록된 순서"가 달라진다. 윈도우 집계(예: 5분 단위 집계)의 경계 판단이 틀어지고, late data인지 실제로 늦게 발생한 데이터인지 구분하기 어려워진다. 여러 소스를 타임스탬프 기준으로 병합(join)할 때는 시각 오차가 곧바로 데이터 정합성 오류로 이어진다.

해결 방향은 같다. 클러스터/파이프라인의 모든 노드가 같은 내부 NTP 서버 하나를 참조하도록 맞춰서 노드 간 시각차를 최소화한다.

## 실무에서는 chronyd로 맞춘다

리눅스에서는 보통 ntpd 대신 chronyd로 동기화한다. VM처럼 클럭이 자주 흔들리는 환경에서 더 빠르게 수렴하도록 설계됐기 때문이다. `chronyc tracking`으로 기준 서버와의 offset을, `chronyc sources`로 현재 참조 중인 NTP 서버를 확인할 수 있다.
