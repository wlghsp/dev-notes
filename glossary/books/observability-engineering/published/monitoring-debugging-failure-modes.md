# Monitoring 기반 디버깅의 실패 패턴

Monitoring/대시보드 기반 트러블슈팅에서 반복적으로 나타나는 네 가지 구조적 실패 패턴.

## Insufficient Correlation (불충분한 상관관계)

던지고 싶은 질문과, 대시보드가 실제로 답해줄 수 있는 질문 사이에 간극이 있는 문제. 예를 들어 인덱스를 추가한 뒤 "이 쿼리가 더 적은 row를 스캔하는가", "새 인덱스가 어떤 쿼리에서 얼마나 자주 선택되는가" 같은 걸 알고 싶지만, 가진 건 CPU/메모리/인덱스 카운터 같은 host 단위 집계 그래프뿐이다. user, query, destination 단위로 데이터를 쪼개볼 방법이 없어서, 결국 타임스탬프를 기준으로 뭉뚱그린 추측만 할 수 있다.

## Not Drilling Down (더 파고들 수 없음)

이상 징후를 발견했지만, 그게 전체에 영향을 주는지 일부에만 국한된 것인지 더 세밀하게 확인할 방법이 없는 문제. 예를 들어 특정 샤드의 디스크 사용량이 이상하게 보여도, 다른 샤드는 동시에 진행 중인 별도 작업(import 등) 때문에 정상처럼 보일 수 있다. 더 깊이 파고들 수단이 없으면, "이 샤드만의 문제"라는 성급하고 틀린 결론에 멈추게 된다.

## Tool-hopping (도구를 이리저리 옮겨다님)

에러 스파이크를 발견하고 여러 대시보드를 오가며 비슷한 시점의 다른 스파이크를 찾은 뒤, 원인과 결과를 구분하지 못한 채 로깅 도구로 넘어가 grep하고, request id를 찾으면 다시 tracing 도구로 복사-붙여넣기하며 옮겨다니는 패턴. 각 도구가 서로 다른 데이터, 다른 포맷, 다른 질의 방식을 갖고 있어서 매번 새로 적응해야 한다.

## Context Switching (맥락 전환)

앞의 세 패턴이 공통적으로 만들어내는 부담. 데이터가 여러 도구에 흩어져 있으면, "지금까지 뭘 확인했고 다음에 뭘 봐야 하는가"를 사람이 머릿속으로 계속 이어 붙여야 한다. 대시보드를 보다가 로그로, 로그를 보다가 trace로 넘어갈 때마다 이 맥락을 다시 불러오는 비용이 든다. 이 전환 자체가 에러를 유발하고 지치게 만들며, 서로 다른 데이터 소스 간의 상관관계를 사람이 정확히 그려내는 건 사실상 불가능에 가깝다.

## 네 패턴이 공통적으로 가리키는 것

네 가지 모두 같은 근본 원인에서 나온다. 데이터가 미리 집계되어 있고(사전에 무엇을 볼지 정의해야 함), 여러 도구에 쪼개져 저장되어 있다는 것. Observability 도구는 cardinality와 dimensionality가 높은 데이터를 한 곳에 모아두기 때문에, 이 네 가지 실패 패턴이 구조적으로 훨씬 덜 일어난다.

참고: cardinality-dimensionality.md, confirmation-bias-debugging.md, institutional-knowledge-debugging.md

## Recap

Insufficient correlation(질문과 데이터의 간극), Not drilling down(더 세밀하게 못 파고듦), Tool-hopping(도구를 옮겨다님), Context switching(맥락을 사람이 직접 이어붙임) 네 가지는 Monitoring 기반 디버깅에서 반복되는 실패 패턴이다. 모두 데이터가 미리 집계되고 여러 도구에 흩어져 있다는 같은 원인에서 나오며, cardinality/dimensionality가 높은 데이터를 한 곳에 모으는 Observability 도구가 이 문제를 구조적으로 줄인다.
