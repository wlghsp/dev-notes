# Shared Object와 동시 접근 문제

참고: The Art of Multiprocessor Programming — Herlihy & Shavit (Morgan Kaufmann, 2012), Ch.1

## Shared Object란

여러 스레드가 함께 접근하는 객체를 shared object(공유 객체)라고 한다. 멀티프로세서 프로그래밍은 결국 여러 스레드가 이 공유 객체를 조작하는 과정을 설계하는 일이다.

## 카운터 예시로 보는 문제

1부터 10^10 사이의 소수를 찾는 작업을 10개의 스레드에 나눠준다고 하자. 가장 단순한 방법은 각 스레드에게 동일한 크기의 구간을 미리 나눠주는 것이다. 하지만 이 방식은 실패한다. 소수는 균등하게 분포하지 않고(구간마다 밀도가 다르다), 큰 수일수록 소수 판별에 걸리는 시간도 길어지기 때문에, 구간을 똑같이 나눠도 작업량은 똑같이 나뉘지 않는다.

더 나은 방법은 공유 카운터(shared counter) 하나를 두고, 각 스레드가 작업이 끝날 때마다 카운터에서 다음 숫자를 하나씩 받아가는 것이다. 이렇게 하면 작업량이 스레드마다 동적으로 결정된다.

## 순진한 카운터 구현이 실패하는 이유

카운터를 다음처럼 단순하게 구현했다고 하자.

```java
public class Counter {
    private long value;
    public long getAndIncrement() {
        return value++;
    }
}
```

`value++`는 사실 한 번의 연산이 아니라 다음 세 단계를 줄인 표현이다.

```java
long temp = value;   // 읽기
value = temp + 1;    // 쓰기
return temp;
```

스레드 하나만 쓸 때는 문제가 없지만, 스레드 A와 B가 동시에 `getAndIncrement()`를 호출하면 문제가 생긴다. 둘 다 `value`에서 1을 읽고, 각자 로컬 변수에 1을 저장한 뒤, 둘 다 2를 써넣고 둘 다 1을 반환할 수 있다. 서로 다른 값을 반환해야 하는데 같은 값을 반환해버리는 것이다. 더 나쁜 경우, 한 스레드가 값을 읽은 뒤 오랫동안 실행이 밀리는 사이 다른 스레드들이 값을 여러 번 증가시켰다가, 원래 스레드가 뒤늦게 자신이 읽었던 오래된 값 기준으로 값을 다시 써버려 카운트가 거꾸로 줄어들 수도 있다.

## 문제의 본질

카운터 값을 증가시키는 작업이 "읽기"와 "쓰기"라는 두 개의 분리된 연산으로 이루어져 있다는 점이 문제의 핵심이다. 두 스레드가 각자 읽은 시점과 쓰는 시점이 서로 끼어들면서 결과가 꼬인다.

이는 복도에서 마주 오는 사람과 부딪히지 않으려고 피하는 상황과 비슷하다. 서로 상대방의 위치를 "읽고" 방향을 "쓰는" 두 단계로 행동하는데, 상대방이 그 사이에 어떻게 움직일지 알 수 없어서 결국 같은 방향으로 피하다 부딪히는 일이 생긴다.

## 해결의 실마리

현대 멀티프로세서 하드웨어는 읽기-수정-쓰기(read-modify-write)를 하나의 원자적(atomic, 더 이상 쪼갤 수 없는) 하드웨어 연산으로 처리하는 특수 명령어를 제공한다. 이런 명령어를 쓰면 카운터 증가를 원자적으로 처리할 수 있다. 소프트웨어만으로(읽기/쓰기 명령어만 사용해서) 한 번에 하나의 스레드만 특정 코드 블록을 실행하도록 보장하는 문제는 별도로 상호 배제(mutual exclusion) 문제라고 부른다.
