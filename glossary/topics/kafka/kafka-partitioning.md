# kafka-partitioning (파티션 분배)
참고: kafka-parallelism.md, kafka-replication.md

---

프로듀서가 메시지를 보낼 때 어느 파티션에 넣을지 결정하는 과정이다. 이 로직을 모르면 "특정 파티션만 몰린다", "순서가 안 지켜진다" 같은 문제를 디버깅하기 어렵다.

## 분배 방식

**키가 있는 경우 — 키 해싱**

메시지에 키를 지정하면 `hash(key) % 파티션 수`로 파티션이 결정된다. 같은 키는 항상 같은 파티션에 들어간다.

```
userId=A → hash(A) % 3 = 0 → 파티션 0
userId=B → hash(B) % 3 = 1 → 파티션 1
userId=A → hash(A) % 3 = 0 → 파티션 0 (항상 같은 파티션)
```

같은 키의 메시지는 순서가 보장된다. 파티션 내에서는 append-only로 쌓이기 때문이다.

**키가 없는 경우 — 라운드로빈 (기본)**

키를 지정하지 않으면 파티션에 순서대로 돌아가며 분배한다. 파티션 간 부하가 고르게 분산되지만 순서는 보장되지 않는다.

**커스텀 파티셔너**

직접 파티셔너를 구현해서 비즈니스 로직에 맞게 분배할 수도 있다. 예를 들어 VIP 고객 메시지는 파티션 0에만 넣는 식.

## 실무에서 주의할 점

**파티션 쏠림**

키 분포가 고르지 않으면 특정 파티션에 메시지가 몰린다. userId가 키인데 특정 사용자가 트래픽의 90%를 만들면 해당 파티션만 과부하가 생긴다.

**파티션 수 변경 시 키 해싱이 바뀐다**

파티션 수를 늘리면 `hash(key) % 파티션 수` 결과가 달라진다. 같은 키가 다른 파티션으로 들어가게 돼서 순서 보장이 깨질 수 있다. 파티션 수는 처음부터 넉넉하게 잡는 게 일반적이다.

**순서 보장은 파티션 내에서만**

Kafka는 토픽 전체의 순서를 보장하지 않는다. 같은 키를 쓰면 같은 파티션에 들어가므로 그 키에 대한 순서는 보장된다. 순서가 중요한 도메인이라면 키 설계가 핵심이다.
