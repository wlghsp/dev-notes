# iceberg-compaction (아이스버그 컴팩션)

**"많은 수의 작은 데이터 파일을 적은 수의 큰 파일로 합쳐서 읽기 성능을 회복하는 작업"**

CDC나 스트리밍으로 데이터를 계속 흘려보내면 한 번에 쓰는 양이 적어서 작은 Parquet 파일이 계속 쌓인다. 이 상태를 작은 파일 문제(small file problem)라 부른다.

---

## 왜 문제가 되는가

쿼리 엔진이 파일을 하나 열 때마다 메타데이터 읽기, 커넥션 수립 같은 고정 비용이 든다. 파일이 잘게 쪼개져 있으면 실제로 읽어야 할 데이터양은 같아도 이 고정 비용이 파일 수만큼 반복된다.

```mermaid
flowchart LR
    subgraph 작은 파일 다수
        F1[1MB] 
        F2[1MB]
        F3[1MB]
        F4["... 수백 개"]
    end
    subgraph compaction 후
        G1[128MB 파일 1개]
    end
    작은 파일 다수 -->|compaction| compaction 후
```

manifest에 파일별 통계가 있어 프루닝은 여전히 되지만, 프루닝을 통과한 파일이 많으면 결국 그만큼 파일을 여는 오버헤드가 쌓인다. 참고: iceberg-manifest.md

## 동작 방식 — 새 스냅샷으로 파일 교체

compaction은 기존 작은 파일들을 읽어서 큰 파일 하나(또는 몇 개)로 다시 쓰고, 그 결과를 새 스냅샷으로 커밋한다. 기존 스냅샷의 작은 파일들은 새 스냅샷에서 더 이상 참조되지 않을 뿐, 즉시 삭제되지는 않는다. 참고: iceberg-snapshot.md

읽기 쿼리는 compaction이 진행되는 동안에도 이전 스냅샷(작은 파일들)이나 완료된 새 스냅샷(큰 파일) 중 하나를 일관되게 본다. 스냅샷 교체가 원자적이기 때문에 절반만 합쳐진 상태를 볼 일이 없다.

## CDC 파이프라인에서 특히 중요한 이유

CDC는 변경 이벤트가 발생할 때마다 소량씩 커밋되는 경우가 많아서, 배치로 적재하는 경우보다 작은 파일이 훨씬 빨리 쌓인다. 그래서 CDC 기반으로 Iceberg 테이블을 운영할 때는 compaction을 주기적으로 도는 별도 작업(scheduled job)으로 반드시 함께 설계해야 한다.

---

## 한 줄 요약

> compaction = 스트리밍/CDC로 쌓인 작은 파일들을 큰 파일로 합쳐 새 스냅샷으로 교체하는 작업. 파일 오픈 오버헤드를 줄여 읽기 성능을 회복하며, CDC 파이프라인에서는 필수 운영 작업이다.
