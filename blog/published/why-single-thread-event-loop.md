# I/O 집약 vs CPU 집약 — 이벤트루프와 멀티스레드의 트레이드오프

> "자바에서 멀티스레드 잘 쓰냐"는 질문을 받았다.
>
> 생각해보니, Spring을 쓰는 것 자체가 이미 멀티스레딩이었다. 요청마다 스레드를 할당하고, 스레드풀로 관리하고 — 그걸 프레임워크가 다 해주니까 의식하지 못했을 뿐이다.
>
> 그런데 왜 멀티스레드인지, 싱글스레드 방식과 어떻게 다른지는 한 번도 제대로 들여다본 적이 없었다. 그래서 파고들었다.

---

## 웹 서버는 뭘 하며 시간을 보내는가

일반적인 API 요청 하나를 뜯어보면:

```
1. HTTP 요청 파싱          → CPU (빠름, 수 μs)
2. DB에서 유저 조회        → 기다리기 (느림, 수십 ms)
3. 외부 결제 API 호출      → 기다리기 (느림, 수백 ms)
4. 결과 DB에 저장          → 기다리기 (느림, 수십 ms)
5. JSON 직렬화해서 응답    → CPU (빠름, 수 μs)
```

CPU가 일하는 시간은 전체의 **1% 미만**이다. 나머지는 전부 기다리는 시간이다.

이 "기다리는 작업"이 바로 I/O다.

---

## I/O란 무엇인가

Input/Output — CPU가 직접 하지 않고 **외부 장치에 요청하는 모든 작업**이다.

```
CPU (빠름)
    ↕ 기다림
외부 장치 (느림)
    ├── 디스크 (파일 읽기/쓰기)
    ├── 네트워크 (DB 쿼리, 외부 API, 소켓)
    └── 입력장치 (키보드, 마우스 — 서버에선 해당 없음)
```

CPU 입장에서는 **"내가 처리하는 게 아니라 다른 곳에 시켜놓고 기다리는 것"** 이 전부 I/O다.

### 속도 차이가 핵심

```
CPU 연산:          1 ns
RAM 접근:        100 ns     (CPU보다 100배 느림)
SSD 읽기:    100,000 ns     (CPU보다 10만배 느림)
DB 쿼리:  50,000,000 ns     (CPU보다 5천만배 느림)
외부 API: 200,000,000 ns    (CPU보다 2억배 느림)
```

DB 쿼리 한 번 기다리는 동안 CPU는 수천만 번 연산을 할 수 있다. 그 시간을 낭비하느냐, 다른 요청에 쓰느냐 — 이게 이벤트루프와 멀티스레드 논쟁의 출발점이다.

---

## 멀티스레드는 이 문제를 어떻게 보는가

"기다리는 동안 낭비잖아" → **"그럼 스레드를 여러 개 두면 되잖아"**

```
스레드 1: DB 기다리는 중... (멈춰 있음)
스레드 2: 다른 요청 처리 중
스레드 3: 또 다른 요청 처리 중
...
스레드 200: 대기 중
```

스레드가 I/O를 기다리는 동안 그냥 블로킹된다. 대신 다른 스레드가 다른 요청을 처리한다. 코드는 위에서 아래로 읽히는 직관적인 구조다.

그런데 이 방식에는 비용이 따른다.

### 스레드 자체가 비싸다

스레드 하나를 만들면 OS가 Stack 메모리를 미리 할당한다 (JVM 기본 512KB~1MB).

```
동시 접속 10,000명 → 스레드 10,000개
→ Stack 메모리만 5~10GB
→ 대부분의 스레드는 I/O 기다리며 멍하니 대기 중
```

대기 중인 스레드도 메모리를 차지한다.

### Context Switching 비용

OS가 스레드를 번갈아 실행할 때마다 레지스터, 스택 포인터 등 상태를 저장/복원한다.

```
스레드가 많을수록 → Context Switching 빈도 증가
→ CPU가 실제 작업보다 스레드 전환에 시간 소비
```

### 동기화 복잡도

Heap을 공유하므로 `synchronized`, `Lock` 등 동기화 코드가 필요하다. 잘못 짜면 Deadlock, Race Condition 발생.

즉, 멀티스레드는 "기다리는 동안 다른 스레드가 대신 일한다"는 구조인데, 기다리는 스레드 자체가 비용이다. 기다리는 시간이 길수록 이 낭비가 커진다.

---

## I/O 집약 vs CPU 집약

이 지점에서 작업의 성격을 나눠볼 필요가 있다.

### 요리사 비유

**CPU 집약 = 요리사가 직접 손을 써야 하는 일**

```
채소 다듬기, 반죽하기, 고기 썰기...
→ 요리사가 계속 손을 움직여야 함
→ 자리를 비울 수 없음
→ 요리사가 많을수록 유리 (멀티스레드)
```

**I/O 집약 = 기다리는 일**

```
물 끓을 때까지 대기, 오븐에서 구워질 때까지 대기...
→ 요리사가 냄비 앞에 서서 멍하니 기다림
→ 그 시간에 다른 요리를 시작할 수 있음
→ 요리사 1명이 여러 냄비를 관리하는 게 효율적 (이벤트루프)
```

![비동기(싱글 요리사, 여러 냄비) vs 멀티스레드(여러 요리사, 여러 작업)](./chef_asyc_multithreading.png)

### 실제 서버로 보면

**I/O 집약 — 일반 웹 API**

```
클라이언트 요청
    → DB 쿼리 날림 (기다리는 중... 50ms)
    → 외부 API 호출 (기다리는 중... 200ms)
    → 응답 반환

스레드가 하는 일: 실제 코드 실행 5ms + 기다리기 245ms
```

기다리는 동안 스레드가 할 일이 없다. 싱글스레드가 그 시간에 다른 요청을 처리하면 된다.

**CPU 집약 — 연산이 많은 작업**

```
이미지 업로드
    → 1920×1080 이미지를 여러 사이즈로 리사이즈
    → 픽셀 수백만 개를 직접 계산
    → 저장

스레드가 하는 일: CPU 계산 2000ms + 기다리기 0ms
```

기다리는 시간이 없다. CPU를 계속 써야 한다. 코어가 여러 개면 동시에 여러 이미지를 병렬 처리할 수 있다.

### 정리

| | I/O 집약 | CPU 집약 |
|---|---|---|
| 시간을 어디서 쓰는가 | 기다리기 (DB, 네트워크) | 계산하기 (CPU) |
| 예시 | 일반 CRUD API, 채팅 | 이미지 처리, 암호화, ML |
| 유리한 모델 | 싱글스레드 이벤트루프 | 멀티스레드 |
| 이유 | 기다리는 동안 다른 일 처리 | 코어 여러 개로 병렬 계산 |

대부분의 웹 서비스는 I/O 집약이다. DB 조회, 외부 API 호출, 파일 읽기 — 전부 기다리는 일이다.

그럼 실제 서버 프레임워크는 이 문제를 어떻게 푸는가.

---

## 실제로 어떻게 구현되는가 — Spring MVC vs Node.js

같은 문제(I/O 집약적 웹 서버)를 두 생태계가 정반대 방식으로 푼다.

### 잠깐 — Spring이랑 Spring MVC가 다른 건가?

헷갈리는 사람이 많다. 관계를 한 줄로 정리하면:

```
Spring Framework  ←  큰 틀 (IoC 컨테이너, DI, AOP 등 핵심 기능)
    ├── Spring MVC      ←  웹 요청 처리 (Servlet 기반, 블로킹)
    └── Spring WebFlux  ←  웹 요청 처리 (리액티브 기반, 논블로킹)

Spring Boot  ←  설정 자동화 래퍼 (Spring MVC, WebFlux 모두에 적용 가능)
```

**Spring**은 자바 생태계 전반의 프레임워크다. **Spring MVC**는 그 안에서 HTTP 요청을 처리하는 모듈이고, Servlet 기반으로 동작한다. **Spring Boot**는 Spring MVC(또는 WebFlux) 위에 올라타서 설정을 자동화해주는 것이다.

"Spring 쓴다"고 하면 보통 Spring Boot + Spring MVC 조합을 말한다. 이 글에서 Spring MVC라고 부르는 건 이 블로킹 방식의 웹 처리 모델을 가리킨다.

### Spring MVC: 스레드를 여러 개

Spring MVC는 Tomcat의 스레드풀을 이용한다. 요청이 들어오면 풀에서 스레드 하나를 꺼내 그 요청 전체를 처리하고, 응답을 보내면 스레드를 풀에 반납한다.

```
HTTP 요청 들어옴
    → Tomcat이 스레드풀에서 스레드 하나 꺼냄
    → 그 스레드가 Controller → Service → Repository 끝까지 처리
    → DB 기다리는 동안에도 그 스레드가 묶여 있음
    → 응답 완료 → 스레드 풀에 반납
```

개발자가 멀티스레드를 직접 다루지 않아도 되는 이유가 여기 있다. `@RestController`, `@Service` 같은 애노테이션을 붙이면 Tomcat과 Spring이 스레드 할당부터 반납까지 알아서 처리한다.

```java
@RestController
public class UserController {

    @GetMapping("/users/{id}")
    public ResponseEntity<UserResponse> getUser(@PathVariable Long id) {
        // 이 메서드 전체가 하나의 스레드 위에서 실행된다
        User user = userRepository.findById(id);       // 스레드가 여기서 블로킹
        List<Order> orders = orderService.getList(id); // 스레드가 여기서도 블로킹
        return ResponseEntity.ok(new UserResponse(user, orders));
    }
}
```

개발자 입장에서는 그냥 위에서 아래로 읽히는 코드를 짜면 된다. 멀티스레드인지 신경 쓸 필요가 없다. 단, 그 대가로 스레드가 I/O를 기다리는 동안 계속 묶여 있다.

Tomcat의 스레드풀 기본값은 200개다. 동시 요청이 200개를 넘으면 나머지는 큐에서 대기하거나 거절된다.

```
동시 요청 200개   → 스레드 200개 모두 사용 중
동시 요청 201번째 → 스레드 없음 → 대기 또는 거절
```

비효율적이지만 하드웨어가 싸지고 메모리가 늘면서 충분히 감당 가능했다. Spring MVC가 설계된 **2000년대 초반** 기준으로는 최선의 선택이었다.

### Node.js: 기다리는 동안 다른 일 처리

Node.js의 **이벤트루프는 싱글스레드**다. 그 대신 I/O를 **비동기**로 처리한다.

```
이벤트루프 (스레드 1개):
  요청 A → DB 쿼리 날림 → (기다리지 않고) 다음으로
  요청 B → 외부 API 호출 → (기다리지 않고) 다음으로
  요청 C → 처리 시작
  ...
  DB 응답 옴 → 요청 A 이어서 처리
  API 응답 옴 → 요청 B 이어서 처리
```

I/O를 날려놓고 응답이 올 때까지 다른 요청을 처리한다. 이벤트루프 스레드 하나로 수천 개의 동시 요청을 처리할 수 있다.

**단, 정확히는 "완전한 싱글스레드"가 아니다.** Node.js 내부의 libuv 라이브러리는 파일 I/O 같은 일부 작업을 처리하기 위해 백그라운드 스레드풀(기본 4개)을 따로 운영한다.

```
Node.js 구조:
  이벤트루프 (스레드 1개) ← 자바스크립트 실행, 요청 흐름 제어
      ↕ I/O 위임
  libuv 스레드풀 (기본 4개) ← 파일 읽기/쓰기 등 블로킹 I/O 처리
```

이벤트루프가 직접 기다리지 않는 것이지, 스레드가 전혀 없는 게 아니다. 소켓 기반 네트워크 I/O(DB 쿼리, HTTP 요청 등)는 OS의 비동기 I/O(epoll/kqueue)로 처리하고, 스레드풀은 그것으로 처리하기 어려운 파일 I/O 등에만 쓰인다. **핵심은 스레드 수가 요청 수에 비례하지 않는다는 점**이다.

코드로 보면:

```javascript
// async/await 방식
const user = await userRepository.findById(id);    // 기다리는 동안 다른 요청 처리
const orders = await orderService.getList(id);     // 기다리는 동안 다른 요청 처리
res.json({ user, orders });
```

`await`이 있는 동안 이벤트루프는 다른 요청을 처리하고, 응답이 오면 돌아온다.

### 비교

| | Spring MVC | Node.js |
|---|---|---|
| 스레드 수 | 요청당 1개 (보통 200개 풀) | 이벤트루프 1개 + libuv 스레드풀 소수 |
| I/O 처리 | 블로킹 (스레드가 기다림) | 논블로킹 (이벤트루프가 다른 일 처리) |
| 동시 접속 한계 | 스레드 수 = 메모리 한계 | 메모리 훨씬 여유로움 |
| 코드 스타일 | 절차적, 직관적 | 비동기, async/await |
| 약점 | 높은 동시 접속 시 메모리/Context Switching | CPU 집약 작업 시 싱글스레드 병목 |

## 그럼 Spring MVC는 두 마리 토끼를 잡는 선택인가

"I/O에 최적화된 건 아니지만, CPU 집약 작업도 소화하니 어떻게 보면 더 범용적인 선택 아닌가?"

맞다. 단, "둘 다 최적"이 아니라 "둘 다 어느 정도 된다"는 의미에서.

### CPU 집약에서는 실제로 유리하다

```
CPU 집약 작업 (이미지 처리, 암호화, ML 추론...)
→ 스레드가 CPU 코어를 계속 점유
→ 멀티스레드 = 코어 여러 개 동시 활용
→ Node.js 싱글스레드보다 명확히 유리
```

Node.js에서 CPU 집약 작업이 들어오면 이벤트루프 자체가 막힌다. 그 순간 다른 모든 요청이 멈춘다. Spring MVC는 스레드가 여러 개라 그 문제가 없다.

### 하지만 I/O 집약에서 치르는 대가가 있다

"어느 정도 된다"지 "최적화됐다"고는 못 한다.

```
동시 접속 200명    →  Spring MVC 충분
동시 접속 10,000명 →  스레드 수천 개, 메모리/Context Switching 부담 시작
동시 접속 100,000명 →  한계. 서버를 늘리거나 구조를 바꿔야 함
```

Node.js나 WebFlux는 스레드 수십 개로 100,000명을 처리한다. Spring MVC는 그 규모에서 하드웨어를 더 투입하거나 서버를 수평 확장해야 한다.

### 세 가지 선택지의 실제 포지션

| | Spring MVC | Node.js | Spring WebFlux |
|---|---|---|---|
| I/O 집약 | 무난 | 최적 | 최적 |
| CPU 집약 | 최적 | 취약 | 무난 |
| 코드 복잡도 | 낮음 | 중간 | 높음 |

어느 쪽이 낫다는 게 아니다. **서비스의 성격에 맞게 고르면 된다.**

MSA 환경에서는 이 선택이 더 자유롭다. I/O 집약적인 API 서버는 Node.js로, 연산이 많은 작업은 Java나 Go 서버로 분리하면 그만이다. 하나의 프레임워크가 모든 걸 감당할 필요가 없다.

---

## TL;DR

| | 멀티스레드 (Spring MVC) | 싱글스레드 (Node.js) |
|---|---|---|
| I/O 대기 중 | 스레드가 묶여 있음 | 다른 요청 처리 |
| CPU 집약 | 코어 여러 개 활용 | 이벤트루프 전체가 막힘 |
| 스레드 수 | 요청 수에 비례 | 요청 수와 무관 |

Spring을 쓴다는 건 이미 멀티스레딩을 쓰는 것이다. 프레임워크가 스레드 관리를 대신 해줄 뿐이다.
