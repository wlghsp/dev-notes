# [강의 노트] 4강: 싱글 스레드의 한계를 넘다: 콜 스택, libuv, 이벤트 큐, 그리고 이벤트 루프 6단계 심층 해부 (1/2)

## 1. 개요 및 배경 (Overview & Background)

본 강의는 자바스크립트 엔진(V8)과 Node.js의 심장인 libuv가 어떻게 협력하여 거대한 시스템을 굴러가게 만드는지, 메모리와 스레드 레벨에서 벌어지는 실제 동작 원리를 낱낱이 파헤칩니다. 거대한 고층 빌딩 건축 현장의 비유를 통해, 단일 스레드(Single Thread)의 한계를 극복하는 핵심 부품인 콜 스택(Call Stack), 립 유브이(libuv), 이벤트 큐(Event Queue), 이벤트 루프(Event Loop)의 역할을 완벽하게 이해합니다.

> 💡 **[CS 및 실무 적용 Point: 백엔드 병목 지점의 정확한 진단]**
> 현업에서 API 응답 지연이나 CPU 100% 스파이크 현상이 발생했을 때, 이것이 콜 스택이 막힌 것(동기 블로킹)인지, 스레드 풀이 고갈된 것(libuv 병목)인지, 아니면 마이크로태스크 큐가 폭주하여 기아 현상(Starvation)이 발생한 것인지 정확히 진단하려면 이 아키텍처 구조를 머릿속에 완벽히 그리고 있어야 합니다. 이 뼈대를 이해하는 엔지니어만이 시스템의 진짜 원인을 치료할 수 있습니다.

> 🌱 **[직관적 비유]**
> Node.js라는 거대한 프로그램은 하나의 고층 빌딩 건축 현장입니다. 수많은 하청업체와 자재들이 얽혀 있지만, 이 모든 것을 지휘하고 승인하는 사람은 오직 단 한 명, 총괄 현장 소장님(메인 스레드)뿐입니다. 이 현장이 소장님 단 한 명만으로도 어떻게 수만 명의 인부가 있는 것처럼 완벽하게 돌아가는지 그 톱니바퀴들을 하나씩 뜯어보겠습니다.

## 2. 현장을 굴러가게 만드는 4가지 핵심 부품

### 2.1 첫 번째 부품: 콜 스택 (Call Stack) - 단 하나의 작업 공간

자바스크립트 엔진(V8) 내부에는 변수가 저장되는 창고(Memory Heap)와 실제로 코드가 실행되는 단 하나의 책상(Call Stack)이 존재합니다. 코드가 실행된다는 것은 이 책상 위에 서류가 올라왔다는 뜻입니다.

- **후입선출 (LIFO, Last In First Out)**: 콜 스택은 나중에 들어온 서류가 책상 맨 위에 쌓이고, 그것부터 먼저 처리되어 나가는 구조입니다.
- **블로킹(Blocking)의 발생**: 메인 스레드가 오직 1개이므로, 이 스택에 용량이 큰 파일 읽기(fs.readFileSync)가 올라가면 소장님이 그것을 끝낼 때까지 현장 전체가 멈춰버립니다.

> 💡 **[CS 실무 Point: Call Stack Size Exceeded]**
> 재귀 함수(Recursive Function)를 잘못 작성하여 탈출 조건을 주지 않으면, 함수가 콜 스택에 무한히 쌓이다가 결국 운영체제가 할당한 메모리 한계치를 넘어 폭발하는 Maximum call stack size exceeded 에러가 발생하며 서버가 크래시(Crash)됩니다.

> 🌱 **[직관적 비유]**
> 콜 스택은 총괄 현장 소장님의 '책상'입니다. 소장님은 서류를 차곡차곡 쌓아두고 위에서부터 처리합니다. 만약 10GB짜리 도면을 직접 처음부터 끝까지 다 읽고 있다면(동기식 블로킹), 다른 서류는 만지지도 못하고 현장이 마비됩니다.

**[시각화] 동기식 작업 시 콜 스택의 블로킹 상태**

```javascript
const 도면 = fs.readFileSync('10GB_도면.txt');
console.log('완료');
```

```
[ Call Stack (소장님 책상) ]
  |                                   |
  | fs.readFileSync('10GB_도면.txt') | <-- 여기서 몇 분 동안 멈춤! (블로킹)
  | 메인 실행 컨텍스트                |
  -------------------------------------
  * 결과: 책상이 막혀 그 아래의 console.log는 아예 책상에 올라오지도 못함.
```

### 2.2 두 번째 부품: 립 유브이 (libuv) - 대형 하청업체와 스레드 풀

고독한 소장님을 돕기 위해 Node.js가 외부에서 고용한 C 언어 기반의 강력한 하청업체입니다.

- **스레드 풀 (Thread Pool)**: libuv 내부에 존재하는 여러 명의 백그라운드 일꾼(스레드)들입니다. 파일 입출력, 암호화 등 무거운 작업을 병렬로 처리합니다.
- **하이브리드 시스템**: 개발자가 코드를 짜는 환경은 싱글 스레드이지만, 시스템 밑바탕에서는 libuv가 멀티 스레드로 동작합니다.

> 💡 **[CS 실무 Point: 스레드 풀 크기 튜닝]**
> 기본적으로 libuv의 스레드 풀은 4개의 스레드만 갖습니다. 이미지 리사이징 요청이 동시에 10개가 들어오면 6개는 대기하게 되어 지연이 발생합니다. 시니어 엔지니어는 서버의 코어 수에 맞춰 UV_THREADPOOL_SIZE를 튜닝하여 병목을 해소합니다.

> 🌱 **[직관적 비유]**
> libuv는 든든한 '대형 하청업체 시공반'입니다. 소장님이 무거운 철근을 옮기라는 지시를 발견하면, 직접 하지 않고 리버브(libuv)에게 서류를 넘깁니다. 알아서 일꾼들이 땀 흘려 일하는 동안 소장님은 즉시 다음 설계도를 봅니다.

### 2.3 세 번째 부품: 이벤트 큐 (Event Queue) - 작업 완료 보고서 대기함

libuv에서 비동기 작업을 마친 후, "소장님, 작업 끝났습니다!"라고 보고하는 '콜백 함수(Callback)'들이 차례대로 대기하는 공간입니다.

- **선입선출 (FIFO, First In First Out)**: 책상(콜 스택)의 규칙과 반대로, 대기함은 줄서기 규칙을 따릅니다. 먼저 들어온 콜백이 먼저 나갑니다.

> 💡 **[CS 실무 Point: 분업화된 대기함]**
> 이 대기함은 사실 거대한 하나의 통이 아닙니다. 알람 보고서 전용, 파일 읽기 보고서 전용 등 작업의 성격에 따라 총 6개의 전용 대기함으로 세분화되어 있으며, 이는 04-event-loop-phases-and-microtask.md에서 다룰 6단계 정거장의 비밀과 연결됩니다.

### 2.4 네 번째 부품: 이벤트 루프 (Event Loop) - 깐깐한 순찰 반장

대기함에 쌓인 보고서들을 언제 소장님 책상으로 올려보낼지 결정하는 무한 회전 감시 시스템입니다.

- **작동 규칙**: 이벤트 루프는 소장님의 콜 스택이 완전히 텅 비었을 때만 움직입니다. 메인 스레드가 찰나의 휴식을 취할 때, 대기함에서 콜백을 하나 꺼내 소장님 책상으로 밀어 올립니다.

**[시각화] 비동기 작업의 유기적 흐름 (Call Stack -> libuv -> Queue)**

```javascript
fs.readFile('도면.txt', (err, data) => console.log('다 읽음!'));
```

```
1. 지시 즉시 전달 (소장님은 바로 책상을 비움)
[ Call Stack ] : (텅 빔 - 다음 코드로 즉시 넘어감)
      ⬇️ (작업 위임)

2. 백그라운드 작업 (하청업체가 대신 일함)
[ libuv 스레드 풀 ] : [ 일꾼1: 도면.txt 읽는 중... ]
      ⬇️ (작업 완료)

3. 보고서 대기 (완성 순서대로 줄서기)
[ 이벤트 큐 ] : [ 콜백: console.log('다 읽음!') ] 대기 중!
      ⬇️ (순찰 반장: 콜 스택이 비어있는지 확인 후 밀어 올림)

4. 최종 처리
[ Call Stack ] : 콜백 함수 실행 -> 화면에 '다 읽음!' 출력
```

이어지는 내용(이벤트 루프 6단계 페이즈, VIP 우선순위, 사고 실험)은 04-event-loop-phases-and-microtask.md에서 다룹니다.
