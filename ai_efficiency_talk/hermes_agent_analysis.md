# Hermes Agent 분석 — AI 효율 활용 관점

## 개요

`https://github.com/NousResearch/hermes-agent.git` — Nous Research가 만든 독립 실행형 AI 에이전트. Claude Code 플러그인이 아니라 완전히 별개의 CLI/게이트웨이 프로그램(자체 터미널 UI, Telegram/Discord/Slack 등 메시징 연동, cron, MCP 서버, Docker/SSH/Modal/Daytona 등 다중 백엔드 지원). 750KB 넘는 `cli.py`를 포함한 대규모 프로젝트로, VFF(output-style 텍스트 몇 개짜리)와는 규모와 성격이 다름.

설치는 하지 않고 문서(`website/docs/user-guide/features/memory.md`, `skills.md`)와 README만 읽고 구조 분석함. "AI 효율적 사용"에 참고할 만한 아이디어는 아래 2가지 메커니즘.

## 1. Bounded, Curated Memory (경계 있는 메모리)

**구조**: `MEMORY.md`(에이전트 개인 노트, 2,200자 상한)와 `USER.md`(사용자 프로필, 1,375자 상한) 두 파일. 세션 시작 시 시스템 프롬프트에 "얼려진 스냅샷"으로 주입되고, 세션 중 추가된 내용은 디스크엔 바로 반영되지만 시스템 프롬프트엔 다음 세션부터 반영됨(프롬프트 캐시 보존 목적).

**핵심 아이디어 — 한도 초과 시 자동 압축이 아니라 에러**: 한도를 넘는 write는 자동으로 잘리거나 요약되지 않고, 도구가 에러를 반환하며 "지금 있는 엔트리를 통합하거나 지워서 공간을 만든 뒤 다시 시도하라"고 요구함. 즉 압축 판단을 시스템이 조용히 하지 않고 에이전트가 명시적으로 하게 강제함.

**저장 기준이 텍스트로 명시됨**: "저장할 것"(사용자 선호, 환경 사실, 정정 사항, 완료된 작업, 명시적 요청)과 "건너뛸 것"(너무 사소한 것, 쉽게 재검색 가능한 것, 원본 데이터 덤프, 세션 한정 정보)을 구체적 예시와 함께 문서화. "나쁜 예"로 "User has a project"(너무 모호함)와 "On January 5th... user asked me to look at..."(너무 장황함)를 나란히 제시하는 방식이 기준을 구체적으로 만듦.

**dev-notes의 auto memory와 비교**: 현재 우리 memory 시스템(`/Users/jihochoi/.claude/projects/.../memory/`)은 파일 개수·글자 수 상한이 없고 MEMORY.md는 "인덱스"라서 본문이 아닌 한 줄 포인터만 담음. Hermes 방식은 저장 총량 자체를 강제로 작게 유지해서(약 800+500 토큰) 매 세션 프롬프트 비용을 고정시키는 접근이고, 우리 방식은 본문을 개별 파일에 무제한으로 쌓되 인덱스만 짧게 유지하는 접근. 목적이 다름 — Hermes는 "항상 켜져 있는 시스템 프롬프트 비용"을 억제하는 데 초점, 우리는 "필요할 때만 읽는 참조 파일"에 초점. 다만 **한도 초과 시 조용히 자르지 않고 에이전트에게 통합/삭제를 강제한다는 원칙**은, 향후 인덱스(MEMORY.md)가 200줄 넘게 길어지는 시점에 참고할 만한 패턴.

## 2. 자가개선 스킬 시스템 (Progressive Disclosure + 자동 스킬 생성)

**Progressive Disclosure 3단계**: `skills_list()`로 이름/설명만 먼저 로드(약 3k 토큰), 실제 필요할 때 `skill_view(name)`으로 전체 내용 로드, 더 깊은 참조가 필요하면 `skill_view(name, path)`로 특정 파일만 로드. 모든 스킬을 항상 시스템 프롬프트에 욱여넣지 않고 필요한 만큼만 점진적으로 읽어들이는 구조.

**에이전트가 스스로 스킬을 만드는 조건이 명시됨**: (1) 복잡한 작업(5회 이상 도구 호출)을 성공적으로 마쳤을 때, (2) 에러나 막다른 길을 겪은 뒤 작동하는 경로를 찾았을 때, (3) 사용자가 접근 방식을 정정했을 때, (4) 비trivial한 워크플로우를 발견했을 때. 즉 "성공 경험"과 "실패 후 교정"을 모두 스킬화 대상으로 삼음.

**쓰기 승인 게이트(`write_approval`)**: 기본은 자유 쓰기지만, 켜면 모든 메모리/스킬 쓰기가 승인 대기(`pending`) 상태로 스테이징되고 `approve`/`reject`로 사람이 검수. "에이전트가 나에 대해 잘못된 가정을 저장했다"는 문제에 대한 답으로 명시적으로 제시됨.

**패치 우선(`patch` vs `edit`)**: 스킬 수정 시 전체 재작성(`edit`)보다 부분 교체(`patch`, `old_string`/`new_string`)를 권장 — 토큰 비용 관점에서 변경분만 도구 호출에 실리는 게 더 싸다는 이유.

## dev-notes/Claude Code 워크플로에 참고할 점

- **저장 기준을 "좋은 예/나쁜 예" 쌍으로 명시하는 방식**은 우리 auto memory 규칙에도 이미 있지만(user/feedback/project/reference 타입 구분), Hermes는 한 걸음 더 나아가 매 저장 시도마다 도구가 기준 위반을 기계적으로 체크(글자수 초과, 중복 등)하는 게 차이. 우리는 순전히 판단(Claude)에 의존.
- **"승인 대기 스테이징" 개념**은 우리가 "커밋/푸시는 사용자 승인 후에만" 규칙과 원리가 같음 — 되돌리기 어렵거나 사용자 신뢰에 영향 주는 쓰기는 기본으로 막고 명시적 승인을 받는 패턴이 이 프로젝트에도 이미 있음(CLAUDE.md 커밋 규칙).
- Progressive disclosure(레벨0 이름만 → 레벨1 전체 내용)는 Claude Code의 Skill 도구가 이미 쓰는 것과 동일한 패턴(스킬 이름/설명만 먼저 보고, 필요 시 전체 로드) — Hermes가 이를 사용자 문서에 명시적으로 이름 붙여 설명한 것이 참고할 만함.

## 결론

VFF처럼 "설치해서 바로 쓸 수 있는 도구"가 아니라, **메모리/스킬 관리에 대한 설계 아이디어 참고용 레포**. 실제로 Claude Code에 이식 가능한 것은 없고(별개 CLI 프로그램이라 플러그인 형태로 가져올 수 없음), 위 두 원칙(한도 초과 시 강제 통합, 성공/실패 모두를 스킬화 트리거로 삼는 것)만 개념적으로 참고 가치가 있음.

## 한계

- 코드 레벨 검증(실제 메모리 압축 로직, 보안 스캐너 동작)은 하지 않았고 문서(`website/docs/`)만 읽음.
- 설치/실행 테스트는 하지 않음 — 이 레포는 규모가 크고(uv, Python 3.11, Node.js 등 별도 런타임 요구) Claude Code와 통합되는 게 아니라 완전히 독립된 시스템이라 실사용 검증은 범위 밖으로 판단.
