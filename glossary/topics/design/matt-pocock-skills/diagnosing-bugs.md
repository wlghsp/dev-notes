# /diagnosing-bugs — 버그 진단 6단계

## 한 줄 요약

피드백 루프 없으면 가설 금지. 재현 명령어 하나 없으면 코드 읽지 마라.

---

## 언제 쓰나

- "이게 왜 안 되지?"가 30분째 해결 안 될 때
- 버그가 간헐적으로 발생할 때
- 성능 회귀(regression)를 잡을 때
- 에이전트에게 "이 버그 고쳐줘"를 시켜야 할 때

---

## 6단계 프로세스

### 1단계: 피드백 루프 구축 (이게 전부)

이 단계가 핵심이다. 빨간 신호를 줄 수 있는 명령어 하나 없으면 2단계로 가지 않는다.
"코드를 읽고 가설을 세우는" 행동은 이 명령어가 생기기 전까지 금지다.

피드백 루프 구축 수단 (이 순서로 시도):

1. 실패하는 테스트 — 가장 이상적
2. curl/HTTP 스크립트 — 서버에 요청 보내서 응답 확인
3. CLI 호출 + 스냅샷 비교 — 출력을 알려진 결과와 비교
4. 헤드리스 브라우저 스크립트 — Playwright/Puppeteer로 UI 조작
5. 캡처된 트레이스 재생 — 네트워크 요청/이벤트 로그를 저장해서 재실행
6. 일회용 하네스 — 최소 시스템 서브셋으로 코드 경로 재현
7. 속성/퍼즈 루프 — 출력이 "가끔 틀림"이면 랜덤 입력 1000개로 실패 패턴 찾기
8. 이분 탐색 하네스 — 두 상태(커밋, 데이터셋) 사이에서 자동 이분 탐색
9. 차분 루프 — 같은 입력을 구버전/신버전으로 실행해서 출력 비교
10. HITL bash 스크립트 — 사람이 직접 눌러야 하는 경우 최후 수단

완료 기준: 이미 한 번 실행해봤고, 이 특정 버그를 잡을 수 있고, 결정론적이고, 빠르고, 에이전트 혼자 실행 가능.

---

### 2단계: 재현 + 최소화

루프 실행해서 빨간 신호 확인.
그다음 재현 시나리오를 최대한 작게 만든다.
요소를 하나씩 제거하면서 루프 돌리기. 제거해도 여전히 빨간 신호면 불필요한 것.
모든 남은 요소가 필수일 때까지 반복.

---

### 3단계: 가설 3-5개 생성

하나만 만들면 첫 번째 아이디어에 고착된다.
반드시 3-5개를 만들고 순위를 매긴다.

각 가설은 반증 가능해야 한다:
- "X가 원인이면, Y를 바꾸면 버그가 사라진다"
- "X가 원인이면, Z를 바꾸면 버그가 더 심해진다"

이 형식으로 쓸 수 없으면 그건 가설이 아니라 느낌이다. 버린다.

---

### 4단계: 계측

가설당 프로브 하나. 한 번에 변수 하나만 바꾼다.

도구 우선순위:
1. 디버거/REPL — 브레이크포인트 하나가 로그 열 개보다 낫다
2. 가설을 구분하는 경계 지점에 타겟 로그
3. "전체 로깅"은 절대 쓰지 않는다

디버그 로그는 반드시 고유 접두사 붙인다:
`[DEBUG-a4f2] userId=123 state=pending`
나중에 `grep DEBUG-a4f2` 한 번으로 전부 찾아서 삭제한다.

---

### 5단계: 수정 + 회귀 테스트

올바른 이음새(seam)가 있으면 수정 전에 테스트 먼저:
1. 최소화된 재현을 실패하는 테스트로 만든다
2. 실패 확인
3. 수정 적용
4. 통과 확인
5. 1단계 피드백 루프를 원래 시나리오로 재실행

---

### 6단계: 정리 + 사후 분석

필수 체크리스트:
- 원래 재현 시나리오가 더 이상 재현되지 않는다
- 회귀 테스트 통과
- [DEBUG-...] 로그 전부 제거 (grep으로 확인)
- 일회용 프로토타입 삭제

그리고 반드시 물어본다: 이 버그를 예방할 수 있었던 설계 변화가 있었나?
있다면 /improve-codebase-architecture에 넘긴다.

---

## 핵심 습관

코드를 읽기 전에 재현 명령어부터.
피드백 루프가 없으면 코드를 아무리 읽어도 확신이 없다.
재현 명령어 하나가 있으면 버그의 90%는 이미 해결된 것이다.
