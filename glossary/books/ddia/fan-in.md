# fan-in
참고: fan-out.md

---

여러 소스에서 들어오는 데이터나 작업을 하나로 모으는 구조다. fan-out의 반대 방향이다.

fan-out이 하나의 이벤트가 여러 곳으로 퍼지는 것이라면, fan-in은 여러 곳에서 발생한 것들이 하나의 처리 지점으로 수렴하는 것이다.

대표적인 사례는 스트림 처리다. 카프카 파티션이 여러 개로 나뉘어 있어도, 하나의 컨슈머 그룹이 모든 파티션의 메시지를 받아서 집계한다. 파티션 수가 늘어날수록 단일 처리 지점의 부하가 커지는 것이 fan-in의 병목이다.

API 게이트웨이 패턴도 fan-in이다. 클라이언트 요청 하나에 대해 내부적으로 여러 마이크로서비스를 호출하고, 그 응답들을 하나로 합쳐서 반환한다. 이 경우 가장 느린 서비스의 응답 시간이 전체 응답 시간을 결정한다.

fan-out과 fan-in은 함께 등장하는 경우가 많다. 하나의 요청을 여러 워커에 분산(fan-out)해서 병렬 처리한 뒤, 결과를 다시 모아서(fan-in) 반환하는 구조가 그 예다. MapReduce가 이 패턴을 따른다. Map 단계가 fan-out, Reduce 단계가 fan-in이다.
