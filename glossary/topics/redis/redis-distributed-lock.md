# Redis 분산 락 (Distributed Lock)

여러 프로세스나 서버가 동시에 접근하면 안 되는 자원을, Redis를 이용해 하나의 프로세스만 점유하도록 만드는 락.

단일 서버 안의 락(예: Java의 synchronized)은 같은 프로세스 안에서만 유효하다. 서버가 여러 대로 늘어나면 프로세스 간 상호 배제가 안 되므로, 모든 서버가 공유하는 Redis를 락 저장소로 쓴다.

## 락을 거는 방법

`SET key value NX EX ttl` 한 번으로 건다.

NX는 키가 없을 때만 설정된다는 뜻이다. 이미 다른 프로세스가 락을 잡고 있으면(키가 이미 존재하면) 이 명령은 실패하고, 그것이 곧 "락을 못 잡았다"는 신호가 된다.

EX로 TTL(만료 시간)을 반드시 같이 설정해야 한다. 락을 잡은 프로세스가 죽어서 해제를 못 하면, TTL이 없는 락은 영원히 풀리지 않고 다른 프로세스는 계속 대기하게 된다.

## 락을 푸는 방법이 왜 까다로운가

단순히 `DEL key`로 지우면 안 된다. 내가 건 락인지 확인하지 않고 지우면, 다음과 같은 순서로 문제가 생긴다.

1. 프로세스 A가 락을 건다
2. A의 TTL이 만료돼 락이 자동으로 풀린다
3. 프로세스 B가 새로 락을 건다
4. A가 뒤늦게 작업을 마치고 DEL을 호출한다 — 이때 지워지는 것은 B의 락이다

그래서 해제는 "이 락의 value가 내가 설정한 값과 같은지 확인한 뒤에만 지운다"는 GET-then-DEL 순서가 필요하다. 이 두 단계 사이에 다른 프로세스가 끼어들면 안 되므로, redis-lua-script.md에서 설명한 원자적 실행이 여기서 필요해진다.

## 왜 Lua로 묶는가

GET과 DEL을 개별 명령으로 보내면, 확인(GET)과 삭제(DEL) 사이의 짧은 시간에 다른 프로세스가 새로 락을 잡을 수 있다. 그러면 방금 확인한 값은 이미 낡은 값이고, DEL은 남의 락을 지우게 된다.

Lua 스크립트로 "GET해서 값이 같으면 DEL한다"를 하나의 원자적 연산으로 묶으면, 확인과 삭제 사이에 끼어들 여지가 없어진다.

## TTL만으로는 완전하지 않다

TTL은 "락을 잡은 프로세스가 죽었을 때 영원히 안 풀리는 문제"를 막아주지만, 다른 문제를 만든다. 락을 잡은 프로세스가 예상보다 오래 작업하면, TTL이 만료돼 락이 풀리고 다른 프로세스가 같은 자원에 동시에 접근하게 된다.

이 문제를 다루는 방법(락 갱신, Redlock 알고리즘 등)은 별도로 다룰 만큼 크므로 여기서는 다루지 않는다.
