# 용어 정의 — I/O 집약 vs CPU 집약 발표 대비

---

## 스레드 (Thread)

프로세스 안에서 실제로 코드를 실행하는 단위. CPU가 작업을 처리하는 최소 흐름이다.

- 같은 프로세스 안의 스레드들은 Heap 메모리를 공유하고, Stack은 각자 따로 가진다.
- OS가 스레드를 스케줄링해서 CPU에 순서대로 올린다.
- JVM 기준으로 스레드 하나당 Stack 메모리 512KB~1MB가 기본 할당된다.

> **Q. 프로세스랑 스레드 차이?**
> 프로세스는 실행 중인 프로그램 자체 (메모리 공간 독립). 스레드는 그 프로세스 안에서 실행되는 흐름 (메모리 공유). 프로세스 하나에 스레드 여러 개가 있을 수 있다.

---

## 멀티스레드 (Multi-thread)

스레드를 여러 개 만들어 동시에 여러 작업을 처리하는 방식.

- 코어가 여러 개면 진짜 병렬 실행이 된다.
- I/O 대기 중인 스레드가 있어도 다른 스레드가 계속 실행된다.
- 단점: 스레드 수가 늘면 메모리 사용량 증가 + Context Switching 비용 증가 + 동기화 복잡도 증가.

---

## 싱글스레드 (Single-thread)

스레드가 하나뿐인 실행 모델. 한 번에 하나의 작업만 처리한다.

- Node.js 이벤트루프가 대표적인 싱글스레드 구조다.
- CPU 집약 작업이 들어오면 그 작업이 끝날 때까지 다른 요청을 처리하지 못한다.
- I/O 집약 환경에서는 비동기 처리와 결합하면 높은 처리량을 낼 수 있다.

---

## I/O (Input/Output)

CPU가 직접 연산하지 않고 **외부 장치에 요청하는 모든 작업**.

- 디스크 I/O: 파일 읽기/쓰기
- 네트워크 I/O: DB 쿼리, 외부 API 호출, 소켓 통신
- CPU 입장에서는 "내가 처리하는 게 아니라 시켜놓고 기다리는 것"이 전부 I/O다.

> **Q. RAM 접근도 I/O인가?**
> 넓은 의미에서는 맞다. 다만 일반적으로 I/O라고 하면 CPU 외부의 느린 장치(디스크, 네트워크)를 가리킨다. RAM은 CPU 캐시보다 느리지만, 디스크/네트워크에 비하면 수천~수억 배 빠르기 때문에 보통 별도로 언급하지 않는다.

---

## 블로킹 / 논블로킹 / 동기 / 비동기

네 개념이 자주 혼용되는데, 각각이 답하는 질문이 다르다.

### 먼저 비유로

카페에서 커피를 주문했다고 하자.

```
블로킹    — 카운터 앞에 서서 커피가 나올 때까지 꼼짝 않고 기다린다.
논블로킹  — 주문만 하고 자리로 돌아가서 다른 일을 한다.
동기      — 커피가 다 됐는지 내가 직접 가서 확인한다.
비동기    — 커피가 되면 직원이 나에게 알려준다 (진동벨, 호출).
```

### 각각이 답하는 질문

| | 질문 | 핵심 |
|---|---|---|
| 블로킹 | 호출한 쪽이 기다리는가? | 기다림 (다른 일 못 함) |
| 논블로킹 | 호출한 쪽이 기다리는가? | 안 기다림 (바로 반환) |
| 동기 | 결과를 언제, 누가 확인하는가? | 호출한 쪽이 직접 확인 |
| 비동기 | 결과를 언제, 누가 확인하는가? | 완료되면 알림을 받음 |

블로킹/논블로킹은 **제어권** 문제고, 동기/비동기는 **결과 통보** 방식의 문제다.

### 조합하면 4가지

```
동기  + 블로킹   → 가장 흔한 형태. 요청하고 결과 올 때까지 기다림.
                  예: Spring MVC에서 DB 쿼리 (스레드가 멈춤)

동기  + 논블로킹 → 요청 후 바로 돌아오지만, 완료됐는지 내가 계속 확인(폴링).
                  예: while(isDone()) 체크하는 루프

비동기 + 블로킹  → 잘 안 쓰는 조합. 알림을 기다리긴 하는데 그동안 막혀 있음.
                  예: select() 시스템 콜 (실무에서 거의 안 씀)

비동기 + 논블로킹 → 요청하고 바로 돌아가서 다른 일 하다가 완료 알림 받음.
                   예: Node.js 이벤트루프, async/await
```

실무에서 "비동기"라고 하면 보통 **비동기 + 논블로킹** 조합을 가리킨다.

### 코드로 보면

```javascript
// 동기 + 블로킹 (Java Spring MVC 스타일)
User user = userRepository.findById(id);  // 여기서 스레드 멈춤
// user가 올 때까지 다음 줄 실행 안 됨

// 비동기 + 논블로킹 (Node.js async/await)
const user = await userRepository.findById(id);  // await 동안 이벤트루프는 다른 요청 처리
// DB 응답 오면 이 줄부터 재개
```

> **Q. async/await은 동기처럼 생겼는데 비동기인가?**
> 맞다. async/await은 비동기 코드를 동기처럼 **읽히게** 해주는 문법 설탕(syntactic sugar)이다. `await` 키워드가 있는 동안 해당 함수는 일시 중단되고, 이벤트루프는 다른 작업을 처리한다. 코드는 순서대로 읽히지만, 실행은 논블로킹으로 동작한다.

## 블로킹 (Blocking) — 요약

I/O 작업을 요청한 후 **응답이 올 때까지 스레드가 멈춰서 기다리는** 방식.

```
스레드: DB 쿼리 요청 → ......(멈춤)...... → 응답 받음 → 다음 코드 실행
```

- 코드 흐름이 직관적이다 (위에서 아래로).
- 기다리는 동안 스레드는 아무것도 하지 못하고 메모리만 차지한다.
- Spring MVC(Servlet 기반)의 기본 동작 방식이다.

---

## 논블로킹 (Non-blocking) — 요약

I/O 작업을 요청한 후 **응답을 기다리지 않고 다음 코드로 바로 넘어가는** 방식.

```
이벤트루프: DB 쿼리 요청 → (기다리지 않고) 다음 요청 처리 → DB 응답 옴 → 이어서 처리
```

- 응답이 오면 콜백/이벤트로 알림을 받는다.
- 스레드 하나로 여러 I/O를 동시에 관리할 수 있다.
- Node.js 이벤트루프, Spring WebFlux의 동작 방식이다.

---

## 이벤트루프 (Event Loop)

논블로킹 I/O를 구현하는 핵심 메커니즘. 하나의 스레드가 루프를 돌며 완료된 I/O 이벤트를 감지하고 처리한다.

```
루프:
  1. I/O 요청 큐에서 작업 꺼내서 실행
  2. 완료된 I/O 이벤트 확인
  3. 완료된 것 있으면 콜백 실행
  4. 1번으로 돌아감
```

- Node.js에서 자바스크립트 코드를 실행하는 스레드가 이벤트루프다.
- 이벤트루프 자체가 블로킹되면(CPU 집약 작업 등) 모든 요청이 멈춘다.

---

## 스레드풀 (Thread Pool)

스레드를 미리 만들어놓고 재사용하는 방식. 요청마다 스레드를 새로 생성/소멸하는 비용을 줄인다.

- Spring MVC는 보통 Tomcat 스레드풀 (기본 200개)을 사용한다.
- Node.js의 libuv도 내부적으로 스레드풀(기본 4개)을 사용해 블로킹 파일 I/O를 처리한다.

> **Q. 스레드풀 크기는 어떻게 결정하는가?**
> I/O 집약 서비스에서는 스레드 수를 늘려도 CPU 코어 수 이상으로는 병렬 처리가 안 된다. 대기 시간이 많은 경우 스레드 수를 늘려서 대기 중에 다른 스레드가 일하도록 하는 것이지만, 너무 많으면 Context Switching 비용이 커진다. 일반적으로 CPU 코어 수 × 2 정도를 시작점으로 잡고 부하 테스트로 튜닝한다.

---

## Context Switching

OS가 CPU에서 실행 중인 스레드를 교체할 때 발생하는 작업. 현재 스레드의 레지스터, 스택 포인터 등 상태를 저장하고, 다음 스레드의 상태를 복원한다.

- 스레드 수가 많을수록 전환 빈도가 높아진다.
- 전환 자체에 수 μs~수십 μs의 CPU 시간이 소비된다.
- 스레드가 너무 많으면 실제 작업보다 Context Switching에 시간을 더 쓰는 상황이 생긴다.

---

## 동기화 (Synchronization)

멀티스레드 환경에서 여러 스레드가 공유 자원에 동시에 접근할 때 발생하는 문제를 방지하는 것.

- `synchronized`, `Lock`, `volatile` 등의 메커니즘을 사용한다.
- 잘못 구현하면 Deadlock(서로 기다리며 영원히 진행 안 됨)이나 Race Condition(실행 순서에 따라 결과가 달라짐)이 발생한다.
- 싱글스레드 이벤트루프는 공유 자원 접근이 없으므로 이 문제가 없다.

---

## 비동기 (Async)

작업을 요청한 후 **결과를 나중에 받는** 프로그래밍 패턴. 논블로킹 I/O를 코드로 표현하는 방식이다.

```javascript
// 비동기 — await 동안 이벤트루프는 다른 요청 처리
const user = await userRepository.findById(id);
```

- 콜백(callback), Promise, async/await 등 여러 표현 방식이 있다.
- async/await은 비동기 코드를 동기 코드처럼 읽히게 해주는 문법 설탕(syntactic sugar)이다.

---

## libuv

Node.js가 사용하는 C 라이브러리. 크로스플랫폼 비동기 I/O를 제공한다.

- 이벤트루프 구현체가 여기 있다.
- 네트워크 I/O(소켓)는 OS의 epoll(Linux), kqueue(macOS)를 통해 진짜 비동기로 처리한다.
- 파일 I/O처럼 OS 수준에서 비동기가 어려운 작업은 내부 스레드풀(기본 4개)로 처리한다.

> **Q. 그러면 Node.js가 진짜 싱글스레드는 아닌가?**
> 자바스크립트 코드를 실행하는 스레드는 하나다. 그게 이벤트루프다. libuv 스레드풀은 Node.js 내부에서 쓰는 것이고, 자바스크립트 코드가 이 스레드들에 직접 접근하거나 공유 상태를 동기화할 필요가 없다. 그래서 "싱글스레드"라고 부르는 것이다.

---

## epoll / kqueue

OS가 제공하는 비동기 I/O 알림 메커니즘.

- **epoll**: Linux의 구현체
- **kqueue**: macOS/BSD의 구현체
- 수천 개의 소켓을 하나의 스레드에서 감시하다가 데이터가 오면 알려준다.
- 이 덕분에 이벤트루프가 스레드 하나로 수천 개의 네트워크 연결을 처리할 수 있다.

---

## Servlet

Java에서 HTTP 요청을 처리하는 표준 인터페이스. Spring MVC의 기반이다.

- 요청 하나당 스레드 하나를 할당하는 블로킹 모델로 설계됐다.
- Tomcat 같은 Servlet 컨테이너가 스레드풀을 관리하고 요청을 스레드에 배분한다.

---

## Spring MVC vs Spring WebFlux

두 모듈 모두 Spring Framework 위에서 HTTP 요청을 처리하지만 방식이 다르다.

| | Spring MVC | Spring WebFlux |
|---|---|---|
| 기반 | Servlet (블로킹) | Reactor (논블로킹) |
| 스레드 모델 | 요청당 스레드 1개 | 이벤트루프 + 소수 스레드 |
| 코드 스타일 | 절차적, 직관적 | 리액티브 (Mono, Flux) |
| 학습 곡선 | 낮음 | 높음 |
| I/O 집약 성능 | 무난 (규모 한계 있음) | 최적 |

> **Q. 그럼 WebFlux가 항상 낫지 않은가?**
> 성능만 보면 I/O 집약에서는 WebFlux가 낫다. 하지만 리액티브 프로그래밍(Mono, Flux, 연산자 체이닝)은 코드 복잡도가 높고 디버깅이 어렵다. 팀이 익숙하지 않으면 버그와 유지보수 비용이 오히려 커진다. 동시 접속이 수천 명 수준이면 Spring MVC로 충분하고, 그 이상이면 WebFlux나 수평 확장을 고려한다.

---

## I/O 집약 (I/O-bound)

작업 시간의 대부분을 I/O 대기에 쓰는 작업 유형.

- 대표 예: DB 조회, 외부 API 호출, 파일 읽기, 소켓 통신
- 일반적인 웹 API 서버가 여기 해당한다.
- 싱글스레드 이벤트루프가 유리하다 — 기다리는 동안 다른 요청을 처리할 수 있기 때문이다.

---

## CPU 집약 (CPU-bound)

작업 시간의 대부분을 CPU 연산에 쓰는 작업 유형.

- 대표 예: 이미지 리사이즈, 동영상 인코딩, 암호화/복호화, ML 추론
- 기다리는 시간이 없고 CPU를 계속 점유한다.
- 멀티스레드가 유리하다 — 코어 여러 개를 동시에 활용할 수 있기 때문이다.
- Node.js 이벤트루프에서 이런 작업이 실행되면 루프 전체가 막힌다.
