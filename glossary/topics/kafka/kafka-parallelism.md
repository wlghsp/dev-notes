# kafka-parallelism (카프카 병렬 처리)
참고: offset.md, partition.md

---

카프카에서 병렬 처리 성능을 결정하는 공식은 하나다.

```
실제 병렬 처리 수 = min(파티션 수, 컨슈머 인스턴스 수)
```

파티션을 늘리는 건 병렬 처리 가능성의 상한을 높이는 것이고, 실제로 병렬로 처리하려면 컨슈머 인스턴스도 같이 늘려야 한다.

## 토픽 / 파티션 / 컨슈머 그룹 관계

토픽은 메시지의 카테고리다. 파티션은 토픽을 물리적으로 쪼갠 단위로, 각각 독립적인 append-only 로그다.

핵심 규칙: 파티션 하나는 같은 그룹 내에서 컨슈머 하나만 읽는다.

```
토픽 (파티션 3개)
├── 파티션 0 ──→ 컨슈머 A (그룹 1)
├── 파티션 1 ──→ 컨슈머 B (그룹 1)
└── 파티션 2 ──→ 컨슈머 C (그룹 1)
```

컨슈머가 파티션보다 많으면 남는 컨슈머는 놀고, 적으면 하나가 여러 파티션을 담당한다. 그룹이 다르면 같은 파티션을 독립적으로 읽고 offset도 그룹별로 따로 관리된다.

## 컨슈머 인스턴스 수 = 프로세스 수가 아니다

"프로세스 몇 개"가 아니라 KafkaConsumer 인스턴스가 몇 개냐를 봐야 한다.

- **Logstash** — `consumer_threads: 3` 이면 KafkaConsumer 인스턴스가 3개. 스레드 하나당 컨슈머 하나다.
- **Spring Kafka** — `concurrency: 3` 이면 컨슈머 인스턴스 3개. `concurrency: 1`이면 파티션이 10개여도 혼자 다 처리한다.

실제 컨슈머 인스턴스 수를 확인하려면 브로커에서 직접 조회한다.

```bash
kafka-consumer-groups.sh --describe --group 그룹ID
```

CONSUMER-ID 컬럼에 실제 인스턴스 수와 담당 파티션이 나온다.

## 파티션 수 늘리는 것만으로는 부족하다

파티션을 10개로 늘려도 컨슈머 인스턴스가 1개면 병렬 효과 없다. 처리량을 높이려면 파티션 수와 컨슈머 인스턴스 수를 함께 맞춰야 한다.
