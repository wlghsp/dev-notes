# 트래픽 기본기 — RED/USE, 동시 사용자 vs TPS, 용량 산정

percentile-and-tps.md를 먼저 읽고 오는 걸 전제로 한다. 거기서 p95/p99/TPS를 배웠다면, 여기서는 그걸 **어떻게 조합해서 보고, 용량 얘기를 어떻게 하는가**를 다룬다.
---

## 1. 왜 필요했나

지표를 알아도 "대시보드를 열면 뭘 먼저 보지?", "사용자 1000명이면 서버 몇 대 필요하지?"에서 막힌다. 이 문서는 그 두 질문에 답하는 틀이다.

## 2. 뭘 볼지 정하는 틀 — RED, USE, Golden Signals

### RED (서비스 관점, 요청을 처리하는 쪽)

| 글자 | 뜻 | 지표 |
|---|---|---|
| R | Rate | TPS |
| E | Errors | 5xx 비율 |
| D | Duration | p95, p99 |

API 서버를 볼 때는 이 셋이면 시작할 수 있다. 앞 문서에서 배운 게 정확히 이것이다.

### USE (자원 관점, 처리하는 도구 쪽)

| 글자 | 뜻 | 예 |
|---|---|---|
| U | Utilization | CPU 사용률, 스레드 풀 사용률 |
| S | Saturation | 큐에 쌓인 대기 수, 커넥션 풀 대기 |
| E | Errors | 디스크 에러, 커넥션 거부 |

CPU, 스레드 풀, 커넥션 풀, 디스크 같은 **자원마다** 적용한다.

### Golden Signals (구글 SRE)

Latency, Traffic, Errors, **Saturation**. RED에 포화를 더한 것이다.

### 같이 쓰는 순서
1. **RED로 증상을 확인한다.** "p99가 올랐다", "5xx가 늘었다"
2. **USE로 원인 자원을 찾는다.** "스레드 풀이 꽉 찼다", "DB 커넥션 대기가 쌓인다"

RED는 "무슨 일이 일어났나", USE는 "어디가 막혔나"다.

### 책에서 확인한 것

**Golden Signals 네 가지의 정확한 정의 (SRE 북 6장 p.60)**

| 신호 | 책의 설명 |
|---|---|
| Latency | 요청을 처리하는 데 걸리는 시간. **성공 요청과 실패 요청의 지연을 구분**해야 한다. DB 연결 끊김으로 나는 500은 아주 빠를 수 있어서, 섞으면 계산이 오해를 부른다. 한편 **느린 에러는 빠른 에러보다 더 나쁘다.** |
| Traffic | 시스템에 가해지는 수요. 웹 서비스는 보통 초당 HTTP 요청 수이고, 정적/동적 같은 요청 성격별로 나눠 볼 수 있다 |
| Errors | 실패한 요청의 비율. **명시적**(HTTP 500), **암묵적**(200인데 내용이 틀림), **정책상**(1초 약속을 어긴 요청)을 모두 포함한다 |
| Saturation | 서비스가 얼마나 "찼는가". 가장 제약된 자원에 초점을 둔다. **많은 시스템이 사용률 100%가 되기 전에 성능이 떨어지므로 사용률 목표를 두는 것이 필수**다 |

책은 이 네 가지를 모두 재고, 하나라도 문제(포화는 문제 직전)면 사람을 호출하면 서비스가 "최소한 어느 정도는" 모니터링으로 덮인다고 말한다. 또 **지연 증가는 종종 포화의 선행 지표**이며, 작은 윈도우(예: 1분)의 p99를 재면 포화의 아주 이른 신호를 얻을 수 있다 (p.60~61).

**USE 방법론의 원문 (Sys Perf 2장 p.42~47)**

한 문장 요약: **"모든 자원에 대해 사용률, 포화, 에러를 확인하라."**

| 용어 | 책의 정의 |
|---|---|
| Utilization | 정해진 시간 간격 동안 자원이 **일을 하느라 바빴던 시간의 비율**. 바쁜 중에도 더 받을 수 있으면 포화는 아니다 |
| Saturation | 자원이 **처리하지 못하고 대기열에 쌓아 둔 일의 정도** |
| Errors | 에러 이벤트의 횟수 |

표현 방식도 정해져 있다.
- 사용률: 시간 간격에 대한 퍼센트 ("CPU 하나가 90%로 돌고 있다")
- 포화: **대기열 길이** ("CPU의 평균 run-queue 길이가 4")
- 에러: 보고된 에러 수

책의 예시 표(Table 2.5)는 이렇게 나눈다.

| 자원 | 사용률 | 포화 |
|---|---|---|
| CPU | CPU 사용률 | run-queue 길이 |
| 메모리 | 남은 여유 메모리 | 스와핑, OOM 이벤트 |
| 디스크 I/O | 장치 바쁨 비율 | 대기열 길이 |

몇 가지 책의 주의점:
- **에러부터 확인한다.** 순서도에서 에러를 사용률/포화보다 먼저 놓는다. 에러는 빠르고 해석하기 쉬워서 먼저 배제하는 편이 시간 효율이 좋기 때문이다 (p.44).
- **재시도되는 실패도 에러다.** 복구 가능한 실패는 눈에 띄지 않으면서 성능을 깎는다.
- 소프트웨어 자원도 "지표가 말이 되면" 같은 방식으로 볼 수 있다 (p.42). 그래서 스레드 풀·커넥션 풀의 대기가 USE의 포화에 해당한다.
- **캐시는 대상이 아니다.** USE는 사용률/포화가 높을수록 성능이 나빠지는 자원에 효과적이고, 캐시는 오히려 높은 사용률에서 성능을 개선한다 (p.46).
- 처음 발견한 문제가 "문제의 전부"가 아닐 수 있어서 계속 반복한다.
- 목적은 **시스템적 병목을 일찍 찾는 것**이고, 아무것도 안 나오면 다른 방법론으로 넘어간다.

**사용률은 간격에 따라 거짓말을 한다 (Sys Perf p.44~45).** 5분 평균 사용률은 짧은 순간의 100%(= 포화)를 가린다. 요금소 비유: 하루 평균 40% 사용률이어도 러시아워에는 줄이 서 있었을 수 있다. 그러니 USE에서 사용률만 보지 말고 **포화(대기열)** 를 같이 봐야 하는 것이다.

## 3. 동시 사용자 ≠ TPS

요구사항에서 가장 많이 틀어지는 부분.

사용자는 요청을 보내고 나서 화면을 보며 **쉰다(think time).** 그래서 동시 접속자 수가 곧 TPS가 아니다.

```
TPS = 동시 사용자 수 / (응답시간 + think time)
```

(이 식은 가진 책에서 확인한 것이 아니라 Little's Law를 사용자 쪽에서 쓴 제 정리다.)

예: 동시 사용자 1000명, 응답시간 1초, think time 9초

```
TPS = 1000 / (1 + 9) = 100
```

1000명이 붙어 있어도 서버는 초당 100건만 받는다. think time이 1초면 TPS는 500이 된다.

대화에서는 이렇게 되묻는다.
- "동시 접속자 기준인가요, 동시 요청 기준인가요?"
- "TPS로 환산하면 얼마로 보시나요?" (사용자가 얼마나 자주 요청하는지가 핵심)

앞 문서의 Little's Law와 같은 식이다. 시스템 안에서 **처리 중인 요청 수 = TPS × 응답시간**, 사용자 쪽에서 보면 **TPS = 사용자 수 / (응답시간 + think time)**.

## 4. 평균이 아니라 피크로 잡는다

용량은 한가한 평균이 아니라 **몰리는 순간**에 맞춘다.

| 항목 | 값 |
|---|---|
| 일 평균 TPS | 100 |
| 피크 배수 (점심, 이벤트 등) | 5배 → 500 |
| 여유율 | 1.5배 → 750 |
| 파드 1대 처리량 (부하 테스트로 측정) | 100 |
| 필요한 파드 수 | 750 / 100 = 7.5 → **8대** |

여기서 틀리기 쉬운 지점:
- **파드 1대 처리량**은 추측하지 말고 부하 테스트로 잰다. 앞 문서 11장처럼 "p99가 꺾이기 직전"을 한계로 본다.
- 한계 처리량의 100%로 운영하지 않는다. 얼마를 상한으로 잡을지는 정해진 숫자가 없고, 부하 테스트에서 **지연이 꺾이는 지점(knee point)** 을 보고 정한다. 책 근거: SRE 북 6장(p.60)은 많은 시스템이 100%에 이르기 전에 성능이 떨어지므로 사용률 목표가 필수라고 하고, Sys Perf 2장(p.64)의 단순 모델에서는 사용률 60%부터 평균 응답시간이 약 2배, 80%에서 3배가 된다. 그 모델에서 p90/p99는 60%를 넘으면 훨씬 빠르게 나빠진다. 이 문서의 이전 판에 있던 "70~80% 상한"은 책 근거가 있는 숫자가 아니라 어림값이었다.
- 파드 하나가 죽어도 버티는지(N+1)도 본다. 8대가 필요하면 9대를 둔다.

피크 배수는 과거 지표로 구한다. 예를 들면 `max_over_time`으로 최근 30일의 최대 TPS를 본다.

```promql
max_over_time(
  sum(rate(http_server_requests_seconds_count{service="sns-app"}[2m]))[30d:5m]
)
```

## 5. 에러를 구분해서 본다

| 종류 | 대체로 의미 | 알람 |
|---|---|---|
| 4xx | 클라이언트 잘못 (잘못된 요청, 인증 실패) | 보통 안 건다. 급증하면 확인 |
| 5xx | 서버 잘못 | **여기에 건다** |
| 타임아웃 | 응답이 아예 없음 | 별도로 본다 |

책의 관점 (SRE 북 6장 p.60): 에러는 HTTP 5xx만이 아니다. **200인데 내용이 틀린 응답**(암묵적 실패)과 **약속한 시간을 넘긴 요청**(정책상 실패)도 에러로 센다. 5xx는 로드밸런서에서 잡으면 완전히 실패한 요청은 꽤 잡히지만, 잘못된 내용을 주는 경우는 종단 간 테스트로만 발견된다고 한다. 또 에러 요청의 지연은 성공 요청과 **분리해서** 추적한다.

주의: **타임아웃은 지연 지표에 안 잡힐 수 있다.** 응답이 끝나야 기록되기 때문에, 응답 없이 끊긴 요청은 p99에 반영되지 않는다. 그래서 지연과 에러율을 같이 봐야 한다.

## 6. 포화 상태에서 쓰는 방어 패턴

한계를 넘는 트래픽이 오면 시스템이 죽지 않고 **일부를 포기하는 쪽**으로 설계한다.

| 패턴 | 하는 일 |
|---|---|
| 레이트 리밋 | 클라이언트별로 초당 요청 수를 제한 |
| 로드 셰딩 | 과부하일 때 일부 요청을 일찍 거절(503) |
| 백프레셔 | 처리 못 하면 상류에 "천천히 보내라"고 알림 |
| 서킷 브레이커 | 하류가 계속 실패하면 호출 자체를 끊어 보호 |
| 타임아웃 | 너무 오래 걸리는 호출은 포기하고 자원 반환 |

### 재시도의 함정 (retry storm)

서버가 느려지면 클라이언트가 타임아웃 → 재시도를 한다. 클라이언트가 최대 3회 재시도하면 서버가 받는 요청은 최대 **4배** 가 된다. 이미 힘든 서버에 부하를 더 얹어 완전히 무너뜨린다.

방어: **지수 백오프**(재시도 간격을 1초, 2초, 4초로 늘림) + **지터**(간격에 랜덤을 섞어 동시에 몰리지 않게) + 재시도 횟수 상한.

## 7. 캐시와 트래픽

앱 TPS가 같아도 **캐시 히트율**이 떨어지면 DB로 가는 요청이 늘어난다.

- 히트율 95%, 앱 TPS 1000 → DB 약 50
- 히트율 80%, 앱 TPS 1000 → DB 약 200 (4배)

그래서 "앱 TPS는 그대로인데 DB가 힘들어한다"면 캐시 히트율, 캐시 만료 시점(한꺼번에 만료되는 경우)을 본다.

## 8. 대화에서 쓰는 말

| 이렇게 말하면 | 뜻 |
|---|---|
| "RED부터 보죠" | TPS, 에러율, 지연으로 증상 확인 |
| "USE로 내려가 보죠" | CPU, 스레드, 커넥션 풀 등 자원 포화 확인 |
| "동시 접속자예요, 동시 요청이에요?" | think time을 감안해 TPS로 환산하려는 질문 |
| "피크 기준으로 잡았습니다" | 평균이 아니라 몰리는 순간 기준 용량 |
| "여유율 1.5배 봤어요" | 한계 직전이 아니라 여유를 둔 설계 |
| "재시도가 부하를 증폭하고 있어요" | retry storm |
| "히트율이 떨어져서 DB로 넘어갔어요" | 캐시 미스 증가로 하류 부하 증가 |

### 스스로 점검

1. RED와 USE는 각각 무엇을 알려주고, 어떤 순서로 쓰는가?
2. 동시 사용자 500명, 응답시간 0.5초, think time 4.5초면 TPS는? (답: 500 / 5 = 100)
3. 일 평균 200TPS, 피크 4배, 여유율 1.5배, 파드 1대 한계 150TPS면 몇 대인가? (답: 200×4×1.5=1200, 1200/150=8대, N+1이면 9대)
4. 타임아웃이 p99에 안 잡힐 수 있는 이유는?
5. 클라이언트가 3회 재시도하면 서버 부하는 왜 최대 4배가 되는가?

## Recap

RED(TPS, 에러율, 지연)로 증상을 확인하고 USE(사용률, 포화, 에러)로 막힌 자원을 찾는 두 단계로 대시보드를 읽는다. 사용자는 요청 사이에 쉬기 때문에 동시 접속자 수는 TPS가 아니며 `TPS = 사용자 수 / (응답시간 + think time)`으로 환산한다. 용량은 평균이 아니라 피크에 여유율을 곱해 잡고, 파드 1대 처리량은 부하 테스트로 재며, 한계의 70~80%와 N+1을 기준으로 운영한다. 에러는 4xx와 5xx, 타임아웃을 구분하고 알람은 5xx 중심으로 건다. 한계를 넘는 트래픽에는 레이트 리밋, 로드 셰딩, 서킷 브레이커로 일부를 포기하며, 재시도는 지수 백오프와 지터 없이는 부하를 증폭시킨다. 캐시 히트율이 떨어지면 앱 TPS가 같아도 DB 부하는 몇 배로 늘어난다.
