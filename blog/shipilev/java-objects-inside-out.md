# 자바 객체는 메모리에서 실제로 어떻게 생겼는가

원문: "Java Objects Inside Out" — Aleksey Shipilëv (shipilev.net)

## Why

자바에서 객체 하나를 만들면 메모리에 정확히 몇 바이트가 잡히는지 평소에 신경 쓸 일이 없다. 하지만 대량의 객체를 다루는 상황에서는 이 크기가 실제 메모리 사용량과 GC 부담을 결정한다. 이 글은 HotSpot JVM이 객체를 메모리에 배치하는 방식을 다룬다.

## 객체 헤더 구조

모든 자바 객체는 헤더로 시작하고, 헤더는 Mark Word와 Class Word 두 부분으로 나뉜다.

- **Mark Word**: GC 메타데이터(forwarding pointer, 객체 나이), identity hash code, 락(lock) 정보 등 여러 용도로 쓰인다. 64비트 시스템에서는 8바이트, 32비트에서는 4바이트를 차지하는데, GC가 압축되지 않은 참조를 다뤄야 하기 때문에 이 정도 크기가 필요하다.
- **Class Word**: 객체의 타입 메타데이터(Klass*)를 가리키는 포인터. 64비트 VM에서 힙이 작으면 압축되어 4바이트지만, 힙이 64GB 이상으로 커지면 압축이 불가능해져 8바이트로 늘어난다. 이때는 필드가 하나도 없는 객체조차 크기가 커진다.

## 기본 타입의 크기

압축 참조는 4바이트, boolean과 byte는 1바이트, char와 short는 2바이트, int와 float는 4바이트, long과 double은 8바이트를 차지한다. `boolean`은 1비트만 있으면 충분한데도, 원자적 접근과 메모리 주소 지정 제약 때문에 1바이트 전체를 차지한다.

## 배열과 헤더

배열은 일반 객체 헤더에 배열 길이를 담는 4바이트 필드가 추가된다. 여기서 중요한 점은 배열 데이터의 시작 위치가 머신 워드 크기에 맞춰 정렬된다는 것이다. 그 결과 배열 데이터가 16바이트가 아니라 24바이트 지점부터 시작하게 되어, 정렬을 맞추느라 낭비되는 공간이 생길 수 있다.

## 필드 순서와 패킹

필드를 선언한 순서와 실제 메모리에 배치되는 순서는 다르다. JVM은 패딩을 최소화하기 위해 큰 필드부터 배치한다(long/double → int/float → char/short → byte/boolean 순).

각 필드는 자신의 크기에 맞는 경계에 정렬되어야 한다. 예를 들어 8바이트 `long`은 8바이트 경계에 정렬된다. 이 과정에서 생기는 정렬 공백은 더 작은 필드가 채워 넣을 수 있다.

## 객체 정렬

객체 전체도 8바이트 단위로 정렬된다(`-XX:ObjectAlignmentInBytes=16` 옵션으로 16바이트로 바꿀 수도 있다). 그래서 객체의 실제 필요 크기가 20바이트라면 24바이트로 반올림되고, 4바이트가 남는다.

이렇게 남는 공간을 "정렬 그림자(alignment shadow)"라고 부른다. 여기에 작은 필드를 끼워 넣으면 겉보기 객체 크기를 늘리지 않고도 필드를 추가할 수 있다.

## 실제 크기 예시

압축 참조를 쓰는 64비트 환경에서 아무 필드도 없는 `java.lang.Object`는 16바이트(Mark Word 8 + Class Word 4 + 패딩 4)를 차지한다. 32비트 시스템에서는 같은 객체가 8바이트(Mark Word 4 + Class Word 4)면 충분하다.

`int` 필드 하나를 가진 `java.lang.Integer`는 압축 모드에서 16바이트, 비압축 모드에서는 24바이트가 된다. 압축 여부 하나가 객체 크기를 이만큼 바꿔놓는다.

## 상속 관계에서의 필드 배치

JDK 15 이전에는 부모 클래스의 필드가 항상 먼저 배치됐지만, 부모 클래스에서 생긴 정렬 공백을 자식 클래스의 필드가 재사용하지 못했다. 예를 들어 boolean 하나짜리 필드를 가진 클래스를 계속 상속하면, 상속 단계마다 8바이트 이상의 패딩이 추가로 쌓였다.

JDK 15부터는 자식 클래스의 필드가 부모 클래스의 공백을 채울 수 있도록 개선되었다.

## 압축 참조의 영향

압축 참조는 참조 필드를 8바이트에서 4바이트로, Class Word도 8바이트에서 4바이트로 줄여준다.

다만 힙이 약 32GB를 넘으면 압축이 불가능해진다. 이 시점부터 Class Word와 모든 참조 필드가 즉시 확장되면서, 애플리케이션 전체의 객체 크기가 한꺼번에 크게 늘어난다.
