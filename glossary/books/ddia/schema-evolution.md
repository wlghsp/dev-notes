# schema-evolution (스키마 진화)

참고: encoding.md, backward-forward-compatibility.md, protobuf-thrift-avro.md

---

애플리케이션은 시간이 지나면서 계속 변한다. 기능이 추가되거나 수정되면 보통 저장하는 데이터 형식도 바뀐다. 새 필드가 추가되거나, 기존 데이터를 다른 방식으로 표현해야 하는 식이다. 이렇게 스키마(또는 데이터 형식)가 바뀌는 것, 그리고 그 변화에 시스템이 적응하는 것 전체를 스키마 진화라고 부른다.

## 왜 문제가 되는가

코드 변경은 순식간에 일어나지 않는다.

- 서버 애플리케이션은 보통 rolling upgrade(staged rollout)로 배포한다. 몇 대씩 순차적으로 새 버전을 올리기 때문에, 배포 도중에는 신버전과 구버전 코드가 동시에 돌아간다.
- 클라이언트 애플리케이션은 사용자가 업데이트를 언제 설치할지 통제할 수 없다.

결과적으로 신버전/구버전 코드와 신버전/구버전 데이터 형식이 시스템 안에 동시에 공존할 수 있다. 시스템이 계속 정상 동작하려면 backward-forward-compatibility.md 양쪽을 유지해야 한다.

## 관계형 모델 vs schema-on-read

이 문제에 대응하는 방식은 데이터 모델마다 다르다. 관계형 DB는 한 시점에 정확히 하나의 스키마만 강제한다(ALTER로 바꿀 수는 있음). schema-on-read(스키마리스) 문서 DB는 스키마를 강제하지 않아서, DB 안에 서로 다른 시점에 쓰인 신/구 데이터 형식이 섞여 있을 수 있다. 참고: schema-on-write-vs-read.md

## 실제 인코딩 포맷에서의 구현

encoding.md에서 다룬 각 포맷은 스키마 진화를 지원하는 방식이 다르다. 필드 태그 번호를 쓰는 Protocol Buffers/Thrift, 필드 이름 매칭을 쓰는 Avro가 대표적이며 구체적인 규칙은 protobuf-thrift-avro.md에 정리했다.

핵심 원칙은 공통적이다.

1. 필드를 추가할 때는 기본값이 있거나 optional이어야 backward compatibility가 유지된다.
2. 필드를 제거할 때는 반대로 forward compatibility가 걸린다.
3. 필드의 식별자(태그 번호 또는 이름)는 절대 재사용하면 안 된다. 과거에 쓰인 데이터가 여전히 그 식별자를 참조하고 있을 수 있기 때문이다.

## data outlives code

DB는 5년 전에 쓰인 값과 5초 전에 쓰인 값이 같은 테이블에 공존할 수 있다. 애플리케이션 코드는 배포 한 번으로 몇 분 안에 완전히 교체할 수 있지만, DB에 쓰인 옛날 데이터는 명시적으로 다시 쓰지 않는 한 원래 인코딩 그대로 남아있다. 이 관찰을 "데이터가 코드보다 오래 산다"고 표현한다. 대부분의 관계형 DB는 컬럼을 추가하는 정도의 스키마 변경은 기존 데이터를 다시 쓰지 않고도 처리한다(누락된 컬럼은 null로 채움). 결과적으로 스키마 진화는 DB 전체가 마치 하나의 스키마로 인코딩된 것처럼 보이게 해주지만, 실제 저장소에는 여러 세대의 스키마로 인코딩된 레코드가 섞여 있을 수 있다.
