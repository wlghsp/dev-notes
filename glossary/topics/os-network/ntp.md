# NTP (Network Time Protocol)

여러 서버(VM)의 시스템 시각을 하나의 기준 시각에 맞춰 동기화하는 프로토콜. 각 VM은 자체 하드웨어 클럭(RTC)을 갖고 있는데, 이 클럭은 서버마다 미세하게 다른 속도로 흘러간다(clock drift). NTP는 이 오차를 주기적으로 보정해서 여러 서버가 "같은 시간"을 보게 만든다.

---

## 왜 클럭이 서버마다 달라지는가

모든 컴퓨터의 하드웨어 클럭은 수정 발진자(crystal oscillator)의 진동을 세어 시간을 계산한다. 이 발진자는 온도, 전압, 제조 편차에 따라 진동 주파수가 미세하게 달라진다. 그 결과 VM A는 하루에 몇 밀리초 빨라지고, VM B는 몇 밀리초 느려지는 식으로 시간이 서서히 어긋난다(drift). 하이퍼바이저 위에서 도는 VM은 이 문제가 더 심하다. 호스트가 다른 프로세스에 CPU를 뺏기면 VM의 가상 클럭도 같이 멈췄다 가는 경우가 있어서, 물리 서버보다 drift가 크게 나타날 수 있다.

## Stratum 계층 구조

NTP는 시각 정보를 트리 형태로 전파한다. 각 층을 stratum이라 부른다.

```
Stratum 0: 원자시계, GPS 수신기 (기준 시각 소스, 네트워크에 직접 연결 안 됨)
Stratum 1: Stratum 0에 직접 연결된 서버 (national time server 등)
Stratum 2: Stratum 1 서버를 참조하는 서버
Stratum 3: Stratum 2 서버를 참조하는 서버
...
```

숫자가 낮을수록 원본 기준 시각에 가깝고 정확도가 높다. 사내/클러스터 내부에서는 보통 외부 Stratum 1~2 서버(예: pool.ntp.org)를 참조하는 자체 NTP 서버 한 대를 Stratum 3 정도로 두고, 클러스터의 나머지 VM들은 이 내부 서버 하나만 바라보게 구성하는 경우가 많다. 모든 VM이 외부로 직접 나가게 하는 것보다 관리가 쉽고, 외부 네트워크 문제에 덜 취약하기 때문이다.

## Offset과 Drift

NTP가 다루는 오차는 두 가지 종류다.

- **Offset** — 현재 시점에 내 클럭이 기준 시각과 얼마나 벌어져 있는지의 차이값. NTP 동기화는 이 offset을 측정해서 클럭을 조정한다.
- **Drift** — 내 클럭이 시간이 지날수록 얼마나 빨리/느리게 어긋나는 경향인지의 비율(예: 초당 몇 ppm). NTP 데몬은 이 drift율을 추정해서 다음 동기화 때까지 미리 보정치를 적용한다.

동기화 방식도 오차 크기에 따라 다르다. 오차가 작으면(수백 ms 이내) 클럭 속도를 미세 조정해서 서서히 맞춘다(slewing). 오차가 크면(초 단위 이상) 클럭을 즉시 강제로 덮어쓴다(stepping). slewing은 시간이 뒤로 가지 않는다는 장점이 있어 서비스 운영 중에는 이 방식이 선호된다 — 시각이 갑자기 과거로 튀면 로그 순서가 뒤바뀌거나 타임아웃 계산이 꼬일 수 있다.

## k8s 클러스터에서 NTP가 중요한 이유

k8s는 여러 VM(master, worker, ingress)이 협업하는 분산 시스템이다. 이 VM들의 시각이 어긋나면 겉보기엔 멀쩡해 보이던 클러스터가 미묘하게 실패하기 시작한다.

**etcd 합의(consensus)가 깨질 수 있다.** master 노드의 두뇌인 etcd는 Raft 합의 알고리즘으로 리더를 선출하고 로그를 복제하는데, 이 과정에서 각 노드가 발급하는 타임스탬프와 타임아웃 계산이 시간 동기화를 전제로 한다. 노드 간 시각차가 크면 리더 선출이 불안정해지거나, 정상 노드가 응답 지연으로 오판되어 클러스터에서 축출되는 현상이 생길 수 있다.

**인증서(TLS) 검증이 실패한다.** k8s의 모든 컴포넌트 간 통신(kubelet ↔ API server, Istio의 mTLS 등)은 TLS 인증서로 이뤄진다. 인증서는 `notBefore`/`notAfter`라는 유효기간을 갖는데, 어느 한 VM의 시계가 이 범위를 벗어나면(너무 빠르거나 너무 느리면) 그 VM은 인증서가 "아직 유효하지 않다" 또는 "이미 만료됐다"고 판단해서 연결을 거부한다. 앞서 정리한 istio-ingressgateway나 istiod의 Citadel이 발급하는 인증서도 마찬가지다 — 시각이 어긋난 노드는 정상 인증서도 거부할 수 있다.

**로그/트레이싱 상관관계가 무너진다.** 여러 노드에 흩어진 로그를 시간순으로 이어붙여 장애를 추적하거나, Jaeger 같은 분산 추적 시스템으로 요청 흐름을 재구성할 때 각 이벤트의 타임스탬프가 기준이 된다. 노드 간 시각이 어긋나 있으면 실제로는 A → B → C 순서로 일어난 요청이 로그상으로는 B → A → C처럼 뒤바뀌어 보여서, 원인 분석이 왜곡된다.

**스케줄링/리스(lease) 판단이 흔들린다.** k8s는 노드의 생존 여부를 주기적인 heartbeat(lease 갱신)로 판단한다. 이 판단에는 "마지막 갱신 후 얼마나 지났는가"라는 시간 계산이 들어가는데, 노드 시계가 실제보다 느리면 아직 살아있는 노드가 죽은 것으로 오판되어 Pod가 불필요하게 재스케줄링될 수 있다.

## VM 여러 대를 맞출 때의 실무 포인트

- 클러스터 내부에 NTP 서버(chrony 또는 ntpd)를 한 대 두고, master/worker/ingress 노드 전부가 이 내부 서버 하나를 참조하게 구성하는 것이 일반적이다. 각 VM이 제각각 외부 NTP 서버를 바라보면 외부 서버마다 응답 지연이 달라 오히려 노드 간 시각차가 더 벌어질 수 있다.
- 최초 설정 시점에 시각차가 이미 크게 벌어져 있으면(수 분 이상) slewing으로는 수렴이 느리므로, 클러스터를 띄우기 전에 한 번 stepping으로 강제 동기화한 뒤 그 이후부터 NTP 데몬이 slewing으로 유지하게 하는 순서가 안전하다.
- 동기화 여부는 각 VM에서 확인할 수 있다. chrony 기준으로는 아래 명령으로 offset과 stratum을 볼 수 있다.

```bash
chronyc tracking      # 현재 offset, 참조 서버, stratum 확인
chronyc sources -v    # 참조 중인 NTP 서버 목록과 상태
```
