# compilation-pipeline

소스 코드가 실행 가능한 바이너리가 되기까지 거치는 4단계 변환 과정.

```
hello.c
  → [Preprocessor]  → hello.i   (전처리된 소스)
  → [Compiler]      → hello.s   (어셈블리 코드)
  → [Assembler]     → hello.o   (기계어 오브젝트 파일)
  → [Linker]        → hello     (실행 가능한 바이너리)
```

## 각 단계

1. **Preprocessor** — `#include`, `#define` 같은 전처리 지시문을 처리한다. 헤더 파일을 인라인으로 삽입하고 매크로를 치환한다. 결과는 순수한 C 소스.

2. **Compiler** — C 소스를 해당 아키텍처의 어셈블리 코드로 변환한다. 이 단계에서 최적화(-O2, -O3)가 일어난다.

3. **Assembler** — 어셈블리 코드를 기계어로 변환해 오브젝트 파일(.o)을 만든다. 이 시점에서는 외부 심볼(다른 파일의 함수, 변수)에 대한 주소가 아직 비어 있다.

4. **Linker** — 여러 오브젝트 파일과 라이브러리를 합쳐 주소를 확정하고 실행 파일을 만든다. 미해결 심볼을 해소하는 게 링커의 핵심 역할이다.

## 왜 4단계로 나뉘는가

각 단계가 독립적이기 때문에 변경된 파일만 재컴파일할 수 있다. `hello.c`만 수정하면 `hello.c`만 컴파일하고 링크만 다시 하면 된다. 전체를 처음부터 다시 번역할 필요가 없다.

## 컴파일 시스템을 이해해야 하는 이유

**성능 최적화** — 컴파일러가 C 코드를 어떻게 기계어로 번역하는지 알면 더 효율적인 코드를 작성할 수 있다. switch가 if-else보다 빠른지, 포인터 참조와 배열 인덱스 중 무엇이 더 빠른지 같은 판단이 가능해진다.

**링크 오류 이해** — 링커 오류는 가장 이해하기 어려운 오류 중 하나다. "심볼을 찾을 수 없다"는 오류가 왜 발생하는지, 정적 라이브러리와 동적 라이브러리의 차이가 무엇인지 알려면 링커를 이해해야 한다.

**보안 취약점 회피** — 버퍼 오버플로우 취약점은 스택에 데이터와 제어 정보가 함께 저장되는 방식을 이해해야 막을 수 있다. 이는 컴파일러와 링커가 메모리를 어떻게 배치하는지와 직결된다.
