# 모듈별 Spring IoC 컨테이너 분리

모듈러 모놀리스에서 모든 모듈이 하나의 Spring IoC 컨테이너(ApplicationContext)를 공유하는 대신, 모듈마다 독립된 컨테이너를 두고 공통 인프라(DataSource, TransactionManager 등)만 별도의 인프라 컨테이너에서 공유하는 구성이다.

## 왜 필요한가

기본적으로 Spring Boot 애플리케이션은 하나의 ApplicationContext 안에 모든 Bean을 등록한다.
이 상태에서는 `order` 모듈의 Bean이 `catalog` 모듈의 Bean을 주입받으려고 시도해도 Spring이 이를 막을 방법이 없다.
컨테이너 자체가 하나이기 때문에, 모듈 경계를 지키는 일이 전적으로 개발자의 규율(코드 리뷰, `verify()` 테스트 등)에 의존하게 된다.
이건 spring-modulith.md에서 다룬 Bean 이름 충돌 문제(bean-name-collision.md)와도 같은 뿌리를 가진 문제다 — 여러 모듈이 하나의 컨테이너를 공유하기 때문에 생기는 부작용이라는 점에서 같다.

## 구성 방식

`DataSource`, `TransactionManager`처럼 여러 모듈이 공통으로 필요로 하는 인프라 Bean은 별도의 인프라 컨테이너에 등록한다.
그리고 `User`, `Catalog`, `Order`, `Brew` 같은 각 모듈은 자신만의 독립된 컨테이너를 갖고, 필요한 경우에만 인프라 컨테이너를 참조한다.
이렇게 하면 한 모듈의 컨테이너 안에는 그 모듈이 실제로 필요로 하는 Bean만 존재하게 되어, 다른 모듈의 Bean을 실수로 주입받는 일이 애초에 구조적으로 불가능해진다.

## 대가

이 구성은 강력한 격리를 제공하지만 구현 복잡도가 높다.
Spring의 기본 동작(하나의 ApplicationContext)을 벗어나는 방식이라 컨테이너 계층 구조를 직접 설계하고 관리해야 하고, 컨테이너 간에 어떤 Bean을 공유할지도 명시적으로 결정해야 한다.
그래서 실무에서는 이 정도로 엄격한 격리까지 가지 않고, `verify()` 테스트나 패키지 가시성 정도로 모듈 경계를 지키는 경우가 더 흔하다.
이 구성은 모듈 독립성을 극단까지 밀어붙였을 때 어떤 모습이 되는지 보여주는 사례로 이해하면 된다.
