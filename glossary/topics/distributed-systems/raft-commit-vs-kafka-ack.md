# Raft commit과 Kafka ack의 차이

참고: raft.md, kafka-isr.md, kafka-acks.md

---

Raft의 "과반수가 확인하면 커밋한다"와 Kafka의 acks를 같은 개념으로 묶어서 이해하면 헷갈린다. 둘 다 "다수의 확인을 받으면 확정한다"는 형태는 비슷하지만, 확정 기준과 안전성 보장이 다르다.

## Raft: 왜 과반수만으로 커밋해도 안전한가

Raft는 전체 노드가 항상 100% 동기화된 상태를 요구하지 않는다. 목표는 장애가 나도 이미 합의된 데이터가 유실되지 않는 것이다.

과반수(quorum)가 로그를 저장했다는 것은, 이후 리더가 죽고 새 리더 선출이 일어나도 그 데이터를 가진 노드가 반드시 새 투표에 포함된다는 뜻이다. 5대 중 3대가 저장을 확인하고 커밋했다면, 나머지 2대가 동시에 죽어도 3대 중 최소 1대는 살아남아 새 리더 후보에 포함되므로 데이터는 보존된다.

"전원 저장"이 아니라 "과반수 저장"이 안전의 최소 조건이다. 이 덕분에 매 쓰기마다 전체 노드 응답을 기다리지 않아도 되어 가용성과 지연시간이 개선된다. 커밋에 참여하지 못한 소수 노드는 이후 리더가 강제로 자신의 로그를 복제해 맞춘다.

## Kafka: acks는 다수결이 아니라 ISR 전체

Kafka의 acks는 Raft의 quorum(과반수) 방식과 다르다. `acks=all`은 "과반수"가 아니라 "ISR(In-Sync Replica) 전체"가 받아야 성공으로 본다. ISR이 3개면 3개 전체, 2개로 줄었으면 2개 전체가 기준이다. 과반수라는 고정 비율이 아니라, 그때그때 동기화 상태를 유지 중인 복제본 집합 전체를 기준으로 삼는 점이 다르다. 상세는 kafka-isr.md, kafka-acks.md 참고.

## 계층이 다르다

Raft의 "커밋"은 합의 알고리즘 내부에서 리더가 "이 로그 엔트리는 이제 확정됐다"고 판단하는 시점이다. Kafka의 acks는 프로듀서가 브로커로부터 받는 응답 확인 수준을 프로듀서가 설정하는 값이다. 하나는 시스템 내부의 확정 기준이고, 하나는 클라이언트가 요구하는 응답 대기 수준이라는 점에서 계층이 다르다.

Kafka의 일반 토픽 파티션 replication은 Raft가 아니라 ISR 기반의 자체 프로토콜을 쓴다. 진짜 Raft의 commit 개념이 등장하는 곳은 KRaft 모드의 메타데이터 복제(브로커 목록, 파티션 리더 정보 등)뿐이다. 일반 데이터 replication과 KRaft 메타데이터 replication을 같은 "커밋"으로 묶어서 이해하면 혼동이 생긴다.
