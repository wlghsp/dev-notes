# nginx

고성능 웹 서버이자 리버스 프록시. 적은 메모리로 대량의 동시 연결을 처리하도록 설계되었다.

## 왜 만들어졌나

Apache(Apache HTTP Server)는 요청마다 프로세스(또는 스레드)를 하나 만들어 처리한다. 동시 연결이 수천 개를 넘어가면 프로세스/스레드 생성 비용과 메모리 사용량이 폭발적으로 늘어난다. 이를 C10K 문제라고 한다(동시에 1만 개의 연결을 처리하는 문제).

여기서 말하는 Apache는 Apache Tomcat과는 다른 프로젝트다. 둘 다 Apache Software Foundation 소속이라 이름이 겹칠 뿐, Apache HTTP Server는 C로 작성된 범용 웹 서버이고 Tomcat은 Java Servlet 컨테이너다.

NGINX는 이 문제를 해결하기 위해 이벤트 기반 비동기 아키텍처로 설계되었다.

## 프로세스 구조

NGINX는 두 종류의 프로세스로 동작한다.

1. master process — 설정 파일을 읽고 worker 프로세스를 생성·관리한다. 요청을 직접 처리하지 않는다.
2. worker process — 실제 요청을 처리한다. 기본적으로 CPU 코어 수만큼 생성된다.

worker 프로세스는 prefork 방식으로 시작 시 미리 만들어진다. 각 worker는 독립된 프로세스이므로 하나가 죽어도 다른 worker에 영향이 없다.

## 이벤트 루프

각 worker 프로세스는 단일 스레드로 동작하면서 이벤트 루프를 실행한다. 수천 개의 연결을 하나의 스레드에서 처리한다.

동작 방식:
1. 연결 요청이 들어오면 소켓을 열고 등록한다
2. I/O가 준비될 때까지 블로킹하지 않고 다른 연결을 처리한다
3. OS가 I/O 준비 완료 이벤트를 알려주면(epoll/kqueue) 해당 연결을 이어서 처리한다

스레드를 쓰지 않기 때문에 컨텍스트 스위치 비용이 없다. 연결 수가 늘어도 메모리 사용량이 거의 늘지 않는다.

## Apache와의 차이

Apache(HTTP Server) prefork: 요청 1개 → 프로세스 1개. 동시 연결 1000개 = 프로세스 1000개.

NGINX: 요청 수천 개 → worker 프로세스 N개(코어 수). 각 worker가 이벤트 루프로 수천 연결을 처리.

정적 파일 서빙, 리버스 프록시처럼 I/O 대기가 많은 작업에서 NGINX가 유리하다. CPU 연산이 많은 동적 처리는 차이가 줄어든다.

## 주요 역할

1. 웹 서버 — 정적 파일(HTML, CSS, 이미지)을 직접 서빙
2. 리버스 프록시 — 클라이언트 요청을 받아 백엔드 서버(Spring, Django 등)로 전달하고 응답을 돌려준다
3. 로드 밸런서 — 여러 백엔드 서버에 요청을 분산한다
4. SSL 종료 — HTTPS 처리를 NGINX에서 끝내고 백엔드에는 HTTP로 전달한다
