# 1주차: 기준 프로젝트에서 문제 상황을 만들고 수치화 패턴으로 쓰기

## 과제

- [필수] 기준 프로젝트를 docker compose로 띄우고 GET /api/studies 목록 조회처럼 자주 불리는 기능 1개를 골라 정상 동작을 확인합니다. 강의 1주차의 "문제를 만들어야 합니다"를 따라 그 기능에서 사용자가 늘면 무엇이 먼저 깨질지 예측합니다.
- [필수] 고른 기능의 현재 응답 시간을 같은 입력으로 3회 이상 측정해 resume/resume.md의 근거 범위에 기록합니다. 강의 1주차 "성능이란 & 성능측정"의 정의를 그대로 씁니다.
- [필수] 강의 1주차 "수치화 패턴"에 맞춰 이력서 문장 1개를 작성하고, 그 문장의 각 수치가 어디서 나왔는지 저장소 안 경로로 연결합니다. 아직 측정하지 못한 값은 확인 불가로 표시합니다.
- [필수] src/test/ 아래에 그 기능의 회귀 테스트 1개를 추가해 이후 주차의 개선이 기능을 깨지 않는지 확인할 수 있게 만듭니다.
- [선택 확장] 문제 상황 후보를 3개까지 늘려 우선순위와 근거를 함께 적습니다.

아래 근거형 질문에 본인 코드·실험·검증 결과를 인용해 답합니다.

1. 이 기능에서 사용자가 늘면 가장 먼저 무엇이 병목이 될 것 같고, 그 근거는 무엇인가요?
2. 측정한 응답 시간이 실제 사용 패턴을 얼마나 대표하며 어떤 한계가 있나요?
3. 작성한 이력서 문장에서 팀의 성과와 본인의 기여를 어떤 증거로 구분할 수 있나요?
4. 현재 문장에서 아직 검증할 수 없는 주장과 이를 보완할 계획은 무엇인가요?

## 제출 증거

- 고른 API 경로와 docker compose 실행·응답 확인 기록
- 같은 입력 3회 이상 측정한 응답 시간과 측정 조건
- resume/resume.md의 수치화 패턴 문장 1개와 각 수치의 저장소 안 근거
- src/test/ 회귀 테스트 1개와 통과 출력
- 질문 1~4 답변
- 선택 근거와 근거형 질문 답변
- 리뷰 지적과 같은 PR에서 반영한 내용

## 완료 기준

- 기준 프로젝트가 실제로 실행되고 고른 API의 응답이 확인된 기록이 있다.
- 측정이 같은 입력으로 반복되었고 조건(표본 수, 환경)이 함께 적혀 있어 다른 사람이 재현할 수 있다.
- 이력서 문장의 수치가 저장소 안 경로로 연결되고, 측정하지 못한 값은 추정치가 아니라 확인 불가로 표시되어 있다.
- src/test/ 회귀 테스트가 고른 기능의 동작을 실제로 검사한다.
- 리뷰에서 지적한 공백을 같은 PR에서 보완하고 변경 내용을 기록한다.
