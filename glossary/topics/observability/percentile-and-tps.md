# 평균, p95/p99, TPS — 직접 쳐보면서 익히기

대화에서 "p99가 튀었어요", "TPS 얼마 나와요?"를 알아듣고 말할 수 있는 수준이 목표.
아래 코드는 전부 직접 타이핑해서 돌려본다. (python3만 있으면 됨. 난수 쓰는 숫자는 환경에 따라 조금 다를 수 있음)

## 1. 왜 필요했나 — 평균은 거짓말을 한다

응답시간 10건: 9건은 0.1초, 1건은 10초.

```python
times = [0.1]*9 + [10.0]
print("평균", sum(times)/len(times))
```

평균 1.09초. "대충 1초쯤 걸리네"로 보이지만 실제로는 9명은 0.1초, 1명은 10초를 겪었다.
평균에는 이 사람이 안 보인다. 그래서 **"전체 중 몇 %가 이 시간 안에 끝나는가"** 로 말한다. 이게 백분위수(percentile)다.

### 책에서도 같은 말을 한다
- SRE 북 4장(p.42): 평균 지연을 쓰는 것은 매력적으로 보이지만, **대부분은 빠른데 긴 꼬리가 훨씬 느린 상황**을 가린다. 책의 그림 4-1은 보통 요청이 약 50ms인데 5%는 20배 느린 시스템이다. 평균만 보면 하루 종일 변화가 없어 보이지만, 꼬리(맨 위 선)는 크게 변하고 있다.
- Sys Perf 2장(p.74): 평균을 성능 지표로 볼 때마다 **"분포가 어떻게 생겼는가?"** 를 물으라고 한다. 인용구도 같이 실려 있다: "평균 깊이가 6인치인 개울을 건너다 익사한 사람."
- SRE 북 4장(p.42~43): 지표는 평균보다 **분포**로 생각하는 게 낫다. 컴퓨터 시스템의 데이터는 치우쳐 있다. 응답이 0ms보다 빠를 수 없고, 1000ms 타임아웃이 있으면 그보다 느린 성공 응답도 없다. 그래서 **평균과 중앙값이 같거나 비슷하다고 가정하면 안 된다.**

## 2. 백분위수(percentile) — 줄 세우고 N번째 보기

방법은 이게 전부다.

1. 응답시간을 **빠른 순으로 정렬**
2. 전체의 N% 위치에 있는 값을 읽는다

| 이름 | 읽는 법 |
|---|---|
| p50 | 100명 중 50번째. 중앙값. "보통 사용자" |
| p95 | 100명 중 95번째. "느린 편 5%의 입구" |
| p99 | 100명 중 99번째. "최악 1%의 입구" |

**p95 = 0.3초** 의 뜻: 요청의 95%는 0.3초 이하로 끝났고, 5%는 그보다 오래 걸렸다.

책의 설명 (SRE 북 4장 p.42): p99나 p99.9 같은 높은 백분위수는 **그럴듯한 최악의 경우**를 보여주고, p50(중앙값)은 **보통의 경험**을 보여준다. 응답시간의 편차가 클수록 보통 사용자의 경험도 꼬리의 영향을 받고, 부하가 높을수록 큐잉 때문에 이 효과가 심해진다. 그래서 일부 SRE 팀은 높은 백분위수만 본다. p99.9가 좋으면 보통 경험은 당연히 좋기 때문이다.

Sys Perf 2장(p.73)도 p90, p95, p99, p99.9를 요청 지연 모니터링에서 "가장 느린 쪽을 수치화"하는 데 쓰고, SLA에서 "대부분의 사용자에게 성능이 허용 범위인가"를 재는 기준으로 쓴다고 설명한다.

### 직접 쳐보기

```python
import math

def pct(sorted_times, p):
    return sorted_times[math.ceil(p/100*len(sorted_times)) - 1]

times = [0.1]*9 + [10.0]
s = sorted(times)
print("p50", pct(s,50), "p90", pct(s,90), "p95", pct(s,95), "p99", pct(s,99))
```

결과: p50 0.1, p90 0.1, p95 10.0, p99 10.0

10건뿐이라 p95부터 10초가 잡힌다. 샘플이 적으면 p99가 사실상 "최댓값"이 된다는 것도 같이 보인다.

### 100건으로 감 잡기

```python
import random
random.seed(1)
t = [random.uniform(0.05, 0.3) for _ in range(98)] + [4.0, 9.0]
s = sorted(t)
print("avg %.3f p50 %.3f p95 %.3f p99 %.3f max %.1f" % (sum(t)/len(t), pct(s,50), pct(s,95), pct(s,99), s[-1]))
```

결과: avg 0.305, p50 0.178, p95 0.289, p99 4.000, max 9.0

- 평균 0.3초, p95 0.29초 → 멀쩡해 보임
- p99 4초 → 100명 중 1~2명은 4초 이상 기다림

**p95는 괜찮은데 p99만 튀면** "대부분은 정상, 극소수가 아주 느림"이다. 보통 GC, 락 대기, 특정 쿼리, 특정 파드 문제를 의심하는 신호.

## 3. TPS — 초당 몇 건 처리하나

TPS(Transactions Per Second) = **1초 동안 처리한 요청 수**. 웹 서버에서는 RPS(Requests Per Second)와 거의 같은 뜻으로 쓴다.

Prometheus의 요청 카운트(`..._count`)는 **계속 늘어나기만 하는 누적 숫자(counter)** 다. 그래서 "지금 몇 TPS"를 보려면 일정 시간 동안 **얼마나 늘었나 ÷ 몇 초**를 계산해야 한다. 이게 `rate()`다.

```python
counter = {0: 0, 10: 500, 20: 1100, 30: 1700}   # 시각(초): 누적 요청 수
ts = sorted(counter)
for a, b in zip(ts, ts[1:]):
    print(f"{a}~{b}초 TPS = {(counter[b]-counter[a])/(b-a)}")
```

결과: 50.0 → 60.0 → 60.0

누적 값 1700 자체는 의미가 없다. **증가량 ÷ 시간** 이 TPS다.

### TPS와 지연시간은 같이 본다
- TPS는 "얼마나 많이 오나", p95/p99는 "얼마나 느리게 처리하나"
- 보통 TPS가 올라가다 어느 지점부터 p99가 먼저 튀고, 더 올라가면 에러가 난다. 그 지점이 시스템 한계의 힌트.
- 한쪽만 보면 반쪽짜리: TPS가 낮아도 p99가 높을 수 있고, TPS가 높아도 p99는 괜찮을 수 있다.

## 4. 히스토그램 — 값을 다 저장 못 하니까 구간 개수만 센다

요청이 초당 수천 건이면 응답시간을 전부 저장해서 정렬할 수 없다. 그래서 Prometheus는 **구간(bucket)별 누적 개수** 만 저장한다.

- `le` = "less than or equal", 이 시간 **이하**로 끝난 요청의 누적 개수
- 마지막 `le="+Inf"` = 전체 개수

```python
import random
random.seed(1)
times = ([random.uniform(0.05, 0.3) for _ in range(9800)]
       + [random.uniform(0.5, 1.0) for _ in range(150)]
       + [random.uniform(2, 8) for _ in range(50)])

les = [0.1, 0.25, 0.5, 1.0, 2.5, 5.0, float("inf")]
buckets = {le: sum(1 for t in times if t <= le) for le in les}
for le, c in buckets.items():
    print(le, c)
```

결과:

```
0.1   2004
0.25  7809
0.5   9800
1.0   9950
2.5   9957
5.0   9976
inf   10000
```

주의: **누적**이다. `le=0.5`의 9800에는 `le=0.25`의 7809가 이미 포함돼 있다.

### 책에서 확인한 것 (SRE 북 6장 p.61)
평균이 느린 건지 꼬리가 아주 느린 건지 구분하는 가장 간단한 방법은, 실제 지연시간 대신 **지연시간 구간별 요청 수** 를 모으는 것이다. 책의 예는 0~10ms, 10~30ms, 30~100ms, 100~300ms처럼 구간을 나누고, **구간 경계를 대략 지수적으로(약 3배씩)** 잡으면 분포를 보기 쉽다는 것이다.

- 평균 100ms인 서비스가 초당 1000건을 받을 때, 요청의 1%가 5초 걸리는 일은 쉽게 일어난다 (같은 쪽 설명). 분포를 재지 않고 "대부분은 평균 근처일 것"이라고 믿는 것은 희망사항이라는 각주도 있다.
- 이것이 5장에서 bucket 경계를 신경 써야 하는 이유와 연결된다. 경계가 성글면 꼬리를 못 본다.

Sys Perf 2장(p.74)은 한 가지를 더 경고한다. 평균, 표준편차, 백분위수는 **봉우리가 하나인 분포** 를 전제로 한다. 실제 시스템은 캐시 히트일 때 빠르고 미스일 때 느린 식으로 **봉우리가 둘 이상**일 수 있고, 그러면 평균이 오히려 "대표값과 반대"가 될 수 있다. 책의 예에서는 디스크 I/O 지연이 1ms 미만과 약 7ms 근처로 갈렸는데 평균 3.3ms는 어느 쪽도 대표하지 않았다. 이럴 때는 **히스토그램으로 분포 전체**를 봐야 한다.

## 5. histogram_quantile — bucket에서 p95를 추정

원본 값이 없으니 정확한 p95는 못 구하고 **추정**한다.

1. 목표 순번 = 분위수 × 전체. p95면 0.95 × 10000 = 9500번째
2. 누적 개수가 9500을 처음 넘는 bucket을 찾는다 → `le=0.5` (9800)
3. 그 구간(0.25~0.5) 안에서는 요청이 **고르게 퍼져 있다고 가정** 하고 비율로 계산

### 직접 구현

```python
def hq(q, buckets):
    les = sorted(buckets)
    target = q * buckets[les[-1]]
    prev_le, prev_c = 0.0, 0
    for le in les:
        c = buckets[le]
        if c >= target:
            if le == float("inf"):
                return prev_le
            return prev_le + (le - prev_le) * (target - prev_c) / (c - prev_c)
        prev_le, prev_c = le, c

for q in (0.5, 0.95, 0.99):
    real = sorted(times)[int(q * len(times)) - 1]
    print(q, "추정 %.3f" % hq(q, buckets), "실제 %.3f" % real)
```

결과:

```
0.5   추정 0.177  실제 0.177
0.95  추정 0.462  실제 0.293
0.99  추정 0.833  실제 0.816
```

**p95 추정(0.462)이 실제(0.293)보다 크게 나왔다.** 이유는 0.25~0.5 구간이 넓어서 "고르게 퍼져 있다"는 가정이 틀렸기 때문이다. 실제 요청은 0.25 근처에 몰려 있었다.

→ 이게 히스토그램의 한계다. **bucket 경계가 내가 보고 싶은 값 근처에 촘촘해야 정확하다.** 실무에서 "대시보드 p95 숫자는 근사치"라고 하는 이유.

한 가지 더: 마지막 유한 bucket(5.0)을 넘어서는 값은 `+Inf`에 들어가서 구분이 안 된다. 코드의 `return prev_le`가 그것. 30초 걸려도 5초로 보일 수 있다.

## 6. 실제 PromQL로 옮기기

처음 질문했던 쿼리가 이제 읽힌다.

```promql
sum(rate(http_server_requests_seconds_bucket{namespace="sns", service="sns-app", uri!~"/actuator.*"}[2m])) by (le)
```

- `_bucket` → 4번 구간별 누적 개수
- `rate(...[2m])` → 3번처럼 증가량 ÷ 시간 (최근 2분 기준)
- `sum(...) by (le)` → 파드, URI 등은 합치고 구간(le)만 남김

여기에 5번을 씌우면 p95:

```promql
histogram_quantile(0.95,
  sum(rate(http_server_requests_seconds_bucket{namespace="sns", service="sns-app", uri!~"/actuator.*"}[2m])) by (le)
)
```

TPS는 `_count`(전체 요청 누적 수)에 `rate`만 쓰면 된다.

```promql
sum(rate(http_server_requests_seconds_count{namespace="sns", service="sns-app", uri!~"/actuator.*"}[2m]))
```

에러율까지 보려면 5xx만 걸러서 나눈다.

```promql
sum(rate(http_server_requests_seconds_count{service="sns-app", status=~"5.."}[2m]))
/
sum(rate(http_server_requests_seconds_count{service="sns-app"}[2m]))
```

## 7. 대화에서 쓰는 말

| 이렇게 말하면 | 뜻 |
|---|---|
| "p95 300ms예요" | 요청의 95%가 0.3초 안에 끝남 |
| "p99가 튀어요" | 극소수 요청이 매우 느려짐. 평균은 멀쩡할 수 있음 |
| "평균은 괜찮은데 p99가 안 좋아요" | 꼬리 지연(tail latency) 문제 |
| "TPS 500 나와요" | 초당 500건 처리 중 |
| "TPS는 그대로인데 p95가 올랐어요" | 같은 부하인데 느려짐. 서버나 DB 쪽 이상 의심 |
| "부하 올리니 p99부터 무너져요" | 한계 지점이 가까워지는 신호 |
| "p95는 히스토그램 근사치예요" | bucket 경계 때문에 오차가 있음 |

# 여기부터 전문가 구간

## 8. 백분위수는 평균내면 안 된다

가장 흔한 실수. 아래는 전부 틀린 계산이다.

- 파드 3개의 p95를 평균내서 "서비스 p95"로 쓰기
- 1분 단위 p99 10개를 평균내서 "10분 p99"로 쓰기

백분위수는 **합치거나 평균낼 수 없다.** 파드 A는 요청 10건, 파드 B는 요청 10000건이면 B가 사실상 전체를 결정하는데, 단순 평균은 둘을 똑같이 취급한다.

올바른 방법은 **원본(또는 bucket 개수)을 먼저 합치고 나서 분위수를 구하는 것**이다. 그래서 쿼리가 `histogram_quantile(sum(rate(bucket)) by (le))` 순서인 것이다. 이 순서를 설명할 수 있으면 대화에서 신뢰를 얻는다.

반대로 **bucket 개수와 `_count`, `_sum`은 합쳐도 된다.** 합산 가능한 원재료를 저장하고 분위수는 마지막에 계산하는 것이 히스토그램의 설계 이유다.

### 책에서 비슷한 예: 샘플링 (Obs Eng, p.210)
이벤트를 샘플링해서 저장할 때, 각 이벤트가 대표하는 개수를 무시하고 단순 계산하면 틀린다. 책의 예: 값과 샘플 비율의 쌍이 `[{1,5}, {3,2}, {7,9}]`일 때, 비율을 무시하고 중앙값을 구하면 3이다. 하지만 비율대로 펼치면 `[1,1,1,1,1,3,3,7,7,7,7,7,7,7,7,7]`이고 중앙값은 **7** 이다.

원리는 이 장과 같다. **분위수는 "무엇을 몇 개로 세었는가"에 의존한다.** 개수 정보를 먼저 정확히 합친 뒤에 분위수를 구해야 하고, 이미 계산된 분위수끼리는 합치지 못한다. 책은 또 고정 비율 샘플링에서는 p99나 중앙값이 샘플링 때문에 왜곡되지 않는다고 말한다 (같은 쪽). 단, 비율이 달라지면 가중치를 반영해야 한다.

## 9. 꼬리 지연은 증폭된다 (왜 p99가 중요한가)

"1%만 느린데 뭐가 문제냐"에 대한 답.

한 화면을 그리려고 백엔드 호출이 N번 일어나고, 각 호출의 p99가 1초라고 하자. 하나라도 느리면 화면이 느리다.

```python
for n in (1, 10, 50, 100):
    print(n, "개 호출 중 하나라도 p99를 넘을 확률 = %.1f%%" % ((1 - 0.99**n) * 100))
```

결과: 1개 1.0%, 10개 9.6%, 50개 39.5%, 100개 63.4%

마이크로서비스처럼 호출이 많이 겹치는 구조에서는 **개별 서비스의 p99가 사용자 입장의 "보통 경험"** 이 된다. 그래서 대규모 시스템은 평균이 아니라 p99, p99.9를 본다.

SRE 북 6장(p.61)이 같은 말을 한다: 사용자가 이런 웹 서비스 여러 개에 의존해 한 페이지를 그리면, **한 백엔드의 99번째 백분위수가 프론트엔드의 중앙값이 될 수 있다.**

## 10. Little's Law — TPS와 지연시간을 잇는 공식

```
동시에 처리 중인 요청 수 = TPS × 평균 응답시간(초)
```

- TPS 500, 평균 0.2초 → 항상 약 100개 요청이 처리 중
- 스레드 풀이 200개(Tomcat 기본값)면 여유는 절반
- 지연이 0.2초 → 0.4초로 늘면 같은 TPS에서도 동시 처리 수가 200이 되어 **스레드가 꽉 찬다**

이 공식 하나로 설명되는 현상:
- "TPS는 그대로인데 지연이 느려지니 갑자기 타임아웃이 쏟아진다"
- "DB가 조금 느려졌을 뿐인데 앱 전체가 멈췄다" (스레드가 DB 응답을 기다리며 쌓임)
- 커넥션 풀, 스레드 풀 크기를 정할 때의 근거: **필요한 풀 크기 ≈ 목표 TPS × 응답시간**

## 11. 부하가 올라갈 때 곡선의 모양

TPS를 천천히 올리면 지연은 선형으로 오르지 않는다.

```
지연 ▲                     ╱  ← 한계 근처에서 급증 (하키 스틱)
     │                   ╱
     │             ____╱
     │ ___________╱
     └──────────────────────▶ TPS
```

- 초반에는 거의 평평하다 (여유 구간)
- 자원 사용률이 높아지면 요청이 **큐에서 대기** 하기 시작하고 지연이 급증한다
- p99가 먼저 꺾인다. 아래 책 근거 참고.
- 그 뒤에 p95, 평균, 마지막에 에러(타임아웃, 5xx) 순으로 무너지는 경우가 많다. (이 순서는 책이 아니라 제 경험칙 정리다.)

### 책에서 확인한 것

**사용률과 응답시간 (Sys Perf 2장 p.64).** 큐잉 이론의 단순 모델(M/D/1)에서 평균 응답시간은 서비스시간 s와 사용률 U로 이렇게 나온다.

```
r = s × (2 - U) / (2 × (1 - U))
```

서비스시간이 1이라면 (직접 계산한 값):

| 사용률 U | 평균 응답시간 (s의 배수) |
|---|---|
| 50% | 1.5배 |
| 60% | 1.75배 |
| 70% | 2.17배 |
| 80% | 3.0배 |
| 90% | 5.5배 |
| 95% | 10.5배 |

책은 "60%를 넘으면 평균 응답시간이 약 두 배, 80%에서는 세 배"라고 정리한다. 그리고 이것은 **가장 좋은 경우의 모델**이다. 서비스시간에 편차가 있으면 더 높아지고, 응답시간에는 분포가 있어서 **90번째와 99번째 백분위수는 60%를 넘으면 훨씬 빠르게 나빠진다.** 이것이 "100%가 되기 한참 전부터 문제가 시작된다"는 말의 근거다.

**포화의 선행 지표 (SRE 북 6장 p.60~61).** "많은 시스템은 사용률이 100%에 이르기 전에 성능이 저하되므로 사용률 목표를 두는 것이 필수"이고, **지연 증가는 종종 포화의 선행 지표**다. 작은 윈도우(예: 1분)에서 99번째 백분위수 응답시간을 재면 포화의 **아주 이른 신호**를 얻을 수 있다고 한다. 이 문서의 "p99가 먼저 꺾인다"는 문장의 출처가 이것이다.

**Knee point (Sys Perf 2장 p.25).** 부하를 올릴 때 처리량은 처음에는 선형으로 늘다가 어느 지점부터 자원 경합 때문에 선형에서 벗어나고, 결국에는 경합 오버헤드가 커져 **처리량이 오히려 줄어든다.** 이 꺾이는 지점을 knee point라고 부른다. 부하 테스트에서 찾고자 하는 것이 이 지점이다.

부하 테스트 결과를 말할 때: "TPS 800까지는 p95 200ms로 평평했고, 900부터 p99가 먼저 튀면서 1000에서 에러가 났다. 그래서 안전 용량은 약 700~800으로 본다."

## 12. 실무에서 말할 때 정확해야 하는 것들

**수치는 항상 세 가지를 같이 말한다.**
"p95가 300ms" ✗ → "최근 5분, 전체 API 기준 p95 300ms" ✓ (분위수 + 기간 + 범위)

**에러 요청의 지연은 따로 본다 (SRE 북 6장 p.60)**
- DB 연결을 잃어 나는 HTTP 500은 아주 빨리 응답할 수 있다. 이 요청을 지연 통계에 섞으면 **계산이 오해를 부른다.**
- 반대로 **느린 에러는 빠른 에러보다 나쁘다.** 그래서 에러를 지연에서 빼 버리지 말고, 에러 요청의 지연을 따로 추적하라고 한다.
- 이 책의 에러 정의도 넓다. 500뿐 아니라 **200이지만 내용이 틀린 응답**, 그리고 **정책상의 에러**(1초 이내를 약속했다면 1초를 넘긴 요청은 에러)까지 포함한다.

**측정 해상도 (SRE 북 6장 p.62)**
- 1분 단위로 보는 CPU 부하는 꼬리 지연을 일으키는 **짧은 스파이크**를 드러내지 못한다.
- 같은 맥락으로 Sys Perf 2장(p.44~45)은 5분 평균 사용률이 순간적인 100% 구간(포화)을 가릴 수 있다고 경고한다. 요금소 비유: 하루 평균 사용률이 40%여도 러시아워에는 줄이 섰을 수 있다.

**SLO를 정할 때 (SRE 북 4장 p.43)**
- "측정하기 쉬운 것"이 아니라 **"사용자가 무엇을 신경 쓰는가"** 에서 출발한다. 쉬운 것에서 시작하면 덜 유용한 SLO가 된다.
- 지표(SLI)의 정의를 표준화한다: 집계 간격, 집계 범위, 측정 빈도, 포함할 요청, 데이터 획득 방법 등을 매번 새로 따지지 않고 템플릿으로 둔다.

**SLO 표현**
- SLI: 측정하는 지표 (예: p99 응답시간, 성공률)
- SLO: 목표 (예: "p99 < 500ms를 월 99.9% 시간 동안 만족")
- SLA: 고객과의 계약 (어기면 보상)

**rate의 윈도우**
- `[2m]`은 스크레이프 간격의 4배 이상으로 잡는다. 너무 짧으면 그래프가 들쭉날쭉, 너무 길면 순간 급등이 뭉개진다.
- `irate`는 마지막 두 점만 봐서 순간값에 민감하다. 알람과 대시보드에는 `rate`가 무난하다.

**히스토그램 정확도**
- p95 근처에 bucket 경계가 없으면 오차가 크다 (5장에서 확인). SLO가 500ms라면 500ms에 bucket 경계가 있어야 "500ms 이하 비율"을 정확히 셀 수 있다.
- Spring Boot(Micrometer)는 `management.metrics.distribution.percentiles-histogram.http.server.requests=true`를 켜야 bucket이 나온다.
- SLO 경계를 직접 지정하려면 `management.metrics.distribution.slo.http.server.requests=100ms,250ms,500ms,1s`처럼 쓴다.

**부하 테스트 주의 (coordinated omission, 이 항목은 가진 책에서 확인하지 못한 제 지식)**
- 서버가 멈춘 동안 부하 도구도 요청을 못 보내서, 그 구간의 느린 요청이 아예 측정에서 빠지는 현상. p99가 실제보다 좋게 나온다.
- 일정 간격으로 요청을 쏘는 도구(wrk2, k6의 arrival-rate 모드 등)를 써야 이를 피할 수 있다.

## 13. 상황별 진단 대화 (연습용)

| 상황 | 해석 | 다음에 볼 것 |
|---|---|---|
| TPS 그대로, p95 상승 | 같은 부하인데 느려짐 | DB 쿼리, 외부 호출, GC, CPU |
| p99만 튐, p95 정상 | 일부 요청만 느림 | 특정 URI, 특정 파드, GC pause, 락 |
| 전부 느림 + TPS 감소 | 처리 능력 포화 | 스레드/커넥션 풀 고갈, 큐 대기 |
| TPS 급감 + 에러 증가 | 요청이 실패하거나 못 들어옴 | 5xx 비율, LB/프록시, 파드 재시작 |
| TPS 급증 + p95 같이 상승 | 부하 증가로 한계 접근 | 오토스케일, 용량 한계, 유입 원인 |
| 평균 정상, p99 비정상 | 꼬리 지연 | 9장처럼 호출이 많은 구조라면 영향 큼 |

### 스스로 점검 (답을 말로 설명해 보기)

1. 파드 3개의 p95를 평균내면 안 되는 이유는?
2. TPS 300, 평균 응답시간 0.5초면 동시에 처리 중인 요청은 몇 개이고, 스레드 풀이 100이면 어떻게 되나?
3. p95는 정상인데 p99만 나쁘면 무엇을 의심하고 어디부터 보나?
4. 대시보드의 p95가 실제와 다를 수 있는 이유는?
5. 호출이 50번 겹치는 화면에서 개별 서비스 p99가 중요한 이유는?

(답: 1번은 8장, 2번은 10장에서 150개이므로 풀이 부족으로 대기·지연, 3번은 13장 표, 4번은 5장, 5번은 9장)

## Recap

평균은 느린 소수를 숨기기 때문에, 응답시간은 줄 세워서 N% 위치를 읽는 **백분위수(p50/p95/p99)** 로 말한다. p95는 "95%가 이 시간 안에 끝남", p99는 "최악 1%의 입구"이고, p95는 정상인데 p99만 튀면 소수 요청만 느린 상황이다. **TPS** 는 초당 처리 건수이며, Prometheus 카운터는 누적값이라 `rate()`로 증가량 ÷ 시간을 구해야 한다. 요청이 많아 원본을 못 저장하니 **히스토그램** 은 `le` 구간별 누적 개수만 저장하고, `histogram_quantile`이 그 구간 안을 고르게 퍼졌다고 가정해 분위수를 **추정** 한다. 그래서 bucket이 성글면 오차가 생기고, 여러 파드를 합칠 때는 `sum(rate(bucket)) by (le)`를 먼저 한 뒤 `histogram_quantile`을 씌운다. 백분위수는 평균내거나 합칠 수 없고, 호출이 겹치는 구조에서는 꼬리 지연이 증폭되며, Little's Law(동시 처리 수 = TPS × 응답시간)로 TPS·지연·풀 크기가 하나로 이어진다. 부하가 한계에 다가가면 p99가 가장 먼저 꺾이고 에러가 마지막에 나타난다.
