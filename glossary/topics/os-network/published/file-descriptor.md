# File Descriptor (파일 디스크립터)

OS가 "열린 것"을 관리하는 번호표다. 프로세스가 파일, 소켓, 파이프 등을 열면 OS가 정수 하나를 돌려준다. 프로세스는 이 번호로 해당 자원을 읽고 쓴다.

## 기본 번호

프로세스가 시작될 때 기본으로 3개가 열려 있다.

- 0 — 표준 입력 (키보드)
- 1 — 표준 출력 (터미널 화면)
- 2 — 표준 에러

그 이후로 파일이나 소켓을 열면 3, 4, 5... 순서로 번호가 붙는다.

## 왜 번호로 다루냐

유닉스의 "모든 것이 파일" 철학 때문이다. OS 입장에서 파일이든 소켓이든 파이프든 전부 "열린 자원"으로 동일하게 취급한다.

프로세스는 fd에 `read(fd, ...)` / `write(fd, ...)` 하면 되고, 그게 디스크로 가는지 네트워크로 가는지는 OS 커널이 처리한다. 프로세스는 신경 안 써도 된다.

```c
// 파일이든 소켓이든 열면 순서대로 번호가 붙는다
int fd1 = open("file.txt", O_RDONLY);        // fd1 = 3
int fd2 = socket(AF_INET, SOCK_STREAM, 0);   // fd2 = 4

// 종류가 달라도 번호 체계는 동일하다
```

## fd가 핵심인 이유 — 프로세스는 대상을 몰라도 된다

fd의 진짜 가치는 추상화에 있다. 프로세스는 fd에 읽고 쓴다는 동작만 알면 되고, 그 fd가 파일인지 소켓인지 파이프인지 신경 안 써도 된다. 커널이 fd 뒤에서 실제 목적지를 처리한다.

```
프로세스
  ↓ read(fd) / write(fd)  ← 항상 동일한 동작
  fd (그냥 번호)
  ↓
커널이 알아서 처리
  ├── 파일이면 → 디스크 I/O
  ├── 소켓이면 → 네트워크 I/O
  ├── 파이프면 → 다른 프로세스로
  └── 터미널이면 → 화면 출력
```

이게 없었으면 파일 읽는 코드, 소켓 읽는 코드, 파이프 읽는 코드를 전부 따로 짜야 했다. fd라는 추상화 층 하나가 그 복잡함을 커널 아래로 숨긴다.

```bash
cat file.txt              # fd(파일) → fd(터미널)
cat file.txt > out.txt    # fd(파일) → fd(파일)
cat file.txt | nc host 80 # fd(파일) → fd(소켓)
```

`cat`은 소켓이 뭔지 몰라도 된다. 그냥 fd에 쓰면 커널이 알아서 네트워크로 내보낸다. 유닉스의 "모든 것은 파일이다" 철학을 실제로 구현한 메커니즘이 fd다.

---

## 실용적인 의미

`cat`, `echo` 같은 명령어가 파일에도, 소켓에도, 터미널에도 동일하게 동작하는 게 이 덕분이다. 다 fd로 동일하게 다루니까.

fd를 닫지 않으면 자원이 해제되지 않는다. 서버 프로세스에서 연결을 받을 때마다 소켓 fd가 생기는데, 닫지 않고 쌓이면 fd가 고갈된다. 이게 "too many open files" 에러의 원인이다.
