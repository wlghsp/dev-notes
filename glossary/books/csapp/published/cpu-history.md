# CPU / 메모리 관리 진화 역사

지금 당연하게 쓰는 구조들은 전부 누군가의 문제 해결이었다. 한 사람의 천재가 설계한 게 아니라 수십 년간 수천 명의 엔지니어가 문제를 하나씩 해결하면서 쌓인 결과물이다.

## 1950~60년대 — 물리 주소 직접 사용

프로그램이 물리 주소를 직접 썼다. 한 번에 프로그램 하나만 실행했기 때문에 문제가 없었다. 메모리 보호 개념 자체가 없었다.

## 1960~70년대 — 멀티프로그래밍 시작, 세그멘테이션 등장

여러 프로그램을 동시에 돌리려니 서로 메모리를 침범하는 문제가 생겼다. 프로그램A가 프로그램B 메모리를 덮어쓰면 시스템 전체가 죽었다.

해결책으로 세그멘테이션이 등장했다. 메모리를 역할별로 나눠서 각 세그먼트에 권한을 부여했다. 코드 영역은 읽기 전용, 데이터 영역은 읽기/쓰기 식으로.

문제는 세그먼트 크기가 제각각이라 메모리 단편화가 심했다. 세그먼트를 할당하고 해제하다 보면 중간에 쓸 수 없는 구멍이 생겼다.

## 1970~80년대 — 페이징 등장

단편화 문제를 해결하기 위해 페이징이 등장했다. 메모리를 고정 크기(4KB)로 자르면 단편화가 줄고, 물리적으로 흩어진 페이지들을 가상 주소에서 연속된 것처럼 매핑할 수 있었다.

이때 가상 주소 개념도 같이 등장했다. 프로그램이 물리 주소를 직접 쓰는 대신 가상 주소를 쓰고, 페이지 테이블이 가상 → 물리 주소로 변환하는 구조다. 덕분에 각 프로세스는 자기만의 독립된 주소 공간을 가지게 됐고, 서로 메모리를 침범할 수 없게 됐다.

근데 소프트웨어로 주소 변환을 하니 너무 느렸다. 메모리 접근마다 OS가 개입해서 변환하면 모든 연산이 2배로 느려졌다.

## 1980년대 — MMU 탄생

소프트웨어로 처리하던 주소 변환을 하드웨어로 옮겼다. MMU가 CPU 안에 내장됐다. Intel 80286에 처음 내장된 MMU가 주소 변환을 하드웨어로 처리하면서 오버헤드가 사라졌다.

OS가 페이지 테이블(규칙)을 만들고, MMU가 그 규칙대로 변환을 실행하는 지금의 구조가 이때 자리잡았다.

## 1990년대 — TLB 추가

MMU가 있어도 페이지 테이블이 메모리에 있으니까 조회할 때마다 메모리 접근이 발생했다. 메모리 접근은 수백 클럭으로 느렸다.

TLB를 MMU 안에 추가해서 최근 변환 결과를 캐싱했다. TLB 히트면 메모리 접근 없이 바로 물리 주소를 얻을 수 있게 됐다.

## 2000년대 — 64비트 전환

RAM 가격이 떨어지면서 4GB를 넘기 시작했다. 32비트 주소로는 4GB 이상을 가리킬 수 없었다. 64비트로 전환하면서 사실상 무한대의 주소 공간을 쓸 수 있게 됐다.

64비트 주소 공간은 너무 커서 페이지 테이블 항목 수가 폭발적으로 늘어났다. 가상 주소 전체를 한 테이블에 담으면 테이블 자체가 수 TB를 차지하는 문제가 생겼다. 실제로 쓰는 주소만 테이블에 올리는 다단계 페이지 테이블로 해결했다.

## 2000년대 중반 — 멀티코어

클럭을 올리면 발열이 심해지는 한계에 부딪혔다. 하나의 코어를 빠르게 만드는 대신 코어를 여러 개 넣는 방향으로 바뀌었다. 지금 CPU가 4코어, 8코어, 16코어인 이유다.

## 2010년대 — 보안 취약점 발견 (Spectre / Meltdown)

CPU가 성능을 위해 "예측해서 미리 실행(투기적 실행)"하는 최적화를 수십 년간 써왔는데, 이게 보안 구멍이 된다는 게 밝혀졌다. 최적화가 너무 정교해진 나머지 다른 프로세스 메모리를 훔쳐볼 수 있었다.

수십 년간 쌓아온 최적화가 보안과 충돌한 사건이었다.

## 2020년대 — Apple Silicon

ARM 기반으로 CPU, GPU, 메모리를 하나의 칩(SoC)에 통합했다. Unified Memory Architecture로 CPU와 GPU가 메모리를 공유하면서 복사 오버헤드를 없앴다. 저전력 고성능의 새로운 방향을 제시했다.
