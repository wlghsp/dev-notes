## 3. TTL과 무효화 전략

- `popular` 결과가 실제로 바뀌는 시점은 언제인가? (`EnrollmentService.enroll()`이 `study.enroll()`을 호출해 `enrolledCount`를 갱신하는 순간 — 이 갱신이 정렬 순위에 영향을 줄 수 있다)

:

- TTL(만료 시간)만으로 충분한가, 능동적 무효화(신청 발생 시 캐시 삭제/갱신)도 필요한가? 그 판단 기준은 무엇인가? (TTL이 짧으면 캐시 효과가 줄고, 길면 신청이 몰리는 인기 스터디 순위가 실제와 오래 어긋날 수 있다)

:

- TTL을 정한다면 몇 초/분으로 정할 것이며, 그 근거는 무엇인가? (인기 스터디 목록이 몇 초 단위로 갱신돼야 사용자가 이상함을 못 느끈다고 판단하는가)

:

- 능동적 무효화를 택한다면, `EnrollmentService.enroll()`의 어느 지점에서 캐시를 지워야 하는가? (트랜잭션 커밋 전에 지우면 롤백 시 문제가 될 수 있다는 점을 고려한다)

:

## 4. 캐시 문제 사례 방지

- cache penetration(존재하지 않는 키를 계속 조회해 캐시를 우회하고 DB를 계속 때리는 것)이 `popular` API에서 발생할 여지가 있는가? (고정된 키 하나만 쓰는 캐시라면 이 문제와 무관할 수 있다 — 왜 그런지 설명해본다)

:

- cache avalanche(대량의 캐시가 동시에 만료되며 DB에 요청이 몰리는 것)는 이 API에서 발생할 수 있는가? (캐시 키가 하나뿐이라면 "동시 만료"라는 말이 이 상황에 어떻게 적용되는가 — TTL에 jitter를 주는 이유가 무엇인가)

:

- Hot Key(특정 키에 요청이 몰려 그 키를 처리하는 Redis 노드나 애플리케이션 스레드가 병목이 되는 것)는 `popular`처럼 캐시 키가 하나뿐인 경우 왜 특히 취약한가?

:

- 셋 중 이 프로젝트 상황(단일 Redis 인스턴스, 단일 캐시 키)에 가장 해당하는 것은 무엇이고, 어떤 방지 장치를 적용할 것인가?

:
