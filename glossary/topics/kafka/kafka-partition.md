# Kafka Partition

토픽을 물리적으로 나눈 단위. Kafka가 수평 확장과 병렬 처리를 할 수 있는 핵심 구조다.

## 구조

토픽 하나는 하나 이상의 파티션으로 구성된다. 각 파티션은 메시지가 순서대로 쌓이는 append-only 로그 파일이다. 새 메시지는 항상 맨 뒤에 붙고, 한번 쓰인 메시지는 수정되지 않는다.

```
토픽: orders
  partition-0: [msg0] [msg1] [msg2] [msg3] ...
  partition-1: [msg0] [msg1] [msg2] ...
  partition-2: [msg0] [msg1] ...
```

각 파티션 내에서 메시지는 offset으로 식별된다. offset은 파티션 내에서만 유일하다. 파티션 0의 offset 3과 파티션 1의 offset 3은 다른 메시지다.

## 왜 파티션으로 나누는가

**병렬 처리**
파티션이 여러 개면 consumer도 여러 개가 동시에 읽을 수 있다. consumer group 내에서 파티션 하나는 consumer 하나에게 배정된다. 파티션이 3개면 최대 3개의 consumer가 동시에 처리한다.

**수평 확장**
파티션은 브로커 여러 대에 분산 저장된다. 처리량이 부족하면 파티션을 늘리고 브로커를 추가하면 된다. 브로커 한 대에 부하가 몰리지 않는다.

## 순서 보장 범위

파티션 내에서는 순서가 보장된다. 같은 파티션에 들어간 메시지는 항상 넣은 순서대로 읽힌다.

파티션 간에는 순서가 보장되지 않는다. 토픽 전체에서 발행 순서를 보장하려면 파티션을 1개로만 써야 하는데, 그러면 병렬 처리를 포기해야 한다.

같은 key를 가진 메시지는 항상 같은 파티션으로 보내진다. 예를 들어 user_id를 key로 쓰면, 같은 사용자의 이벤트는 항상 같은 파티션에 순서대로 쌓인다. 사용자 단위 순서 보장이 필요할 때 쓰는 패턴이다.

## 파티션 수 결정

파티션은 한번 늘리면 줄이기 어렵다. 줄이는 공식 방법이 없고, 데이터를 재배치해야 한다.

파티션 수는 처리량 목표와 consumer 수를 기준으로 정한다. consumer를 10개 띄울 계획이라면 파티션도 최소 10개는 있어야 한다. consumer보다 파티션이 적으면 남는 consumer는 아무것도 읽지 못한다.
