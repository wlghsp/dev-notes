# cache (캐시)

자주 접근하거나 비용이 큰 응답 결과를 메모리에 임시 저장해두고 이후 요청에 빠르게 응답하는 임시 저장소.

## 캐시 티어

웹 서버와 DB 사이에 독립적인 캐시 계층을 둔다. DB보다 훨씬 빠르고 DB 부하를 줄이며 캐시 티어를 독립적으로 확장할 수 있다.

## Read-Through 전략

웹 서버가 데이터를 요청하면 캐시를 먼저 확인한다.

1. 캐시에 데이터가 있으면 → 캐시에서 바로 반환 (Cache Hit)
2. 캐시에 없으면 → DB에서 조회 → 캐시에 저장 → 클라이언트에 반환 (Cache Miss)

## 사용 시 고려사항

**언제 캐시를 쓸까** — 데이터를 자주 읽고 드물게 수정할 때 적합하다. 캐시 데이터는 휘발성 메모리에 저장되므로 중요 데이터는 영구 저장소에도 보관해야 한다.

**만료 정책(Expiration)** — 만료 시간이 너무 짧으면 DB를 너무 자주 읽고, 너무 길면 데이터가 stale해진다.

**일관성(Consistency)** — DB와 캐시의 데이터를 동기화 상태로 유지하기 어렵다. 멀티 리전 확장 시 특히 어렵다.

**SPOF(Single Point of Failure)** — 캐시 서버가 한 대면 전체 장애로 이어진다. 여러 데이터센터에 캐시 서버를 분산하고 메모리를 여유 있게 확보하는 게 권장된다.

> 📷 Figure 1-8 (책 p.14) — SPOF 예시 다이어그램

**캐시 축출 정책(Eviction Policy)** — 캐시가 가득 차면 기존 항목을 제거해야 한다. LRU(Least Recently Used)가 가장 많이 쓰인다. LFU, FIFO도 상황에 따라 사용한다.
