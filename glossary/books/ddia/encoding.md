# encoding (인코딩)

참고: schema-evolution.md, protobuf-thrift-avro.md

---

인메모리 객체(구조체, 리스트, 해시맵 등)를 파일에 쓰거나 네트워크로 보낼 수 있는 바이트 시퀀스로 변환하는 것이다. 인메모리 표현은 포인터를 써서 CPU가 접근하기 좋게 최적화되어 있지만, 포인터는 다른 프로세스에서 아무 의미가 없기 때문에 자기 완결적인(self-contained) 바이트 시퀀스로 바꿔야 한다.

인코딩은 serialization, marshalling이라고도 부른다. 반대 방향(바이트 시퀀스 → 인메모리 객체)은 디코딩, parsing, deserialization, unmarshalling이라고 부른다.

주의: 트랜잭션 맥락에서도 serialization이라는 단어가 쓰이는데(transaction.md의 serializability), 완전히 다른 의미다. 이 둘을 혼동하지 않아야 한다.

## 언어 전용 인코딩의 문제

Java의 java.io.Serializable, Python의 pickle처럼 프로그래밍 언어가 기본 제공하는 인코딩은 편리하지만 몇 가지 근본적인 문제가 있다.

1. 특정 언어에 종속된다. 다른 언어로 작성된 프로세스와 데이터를 주고받기 어렵다.
2. 디코딩 과정에서 임의의 클래스를 인스턴스화할 수 있어야 하는데, 이게 보안 문제로 이어진다. 공격자가 임의의 바이트 시퀀스를 디코딩시킬 수 있으면 임의 코드 실행으로 이어질 수 있다.
3. 버전 관리(schema-evolution.md)가 후순위로 밀려 있는 경우가 많다.
4. 인코딩/디코딩 효율이 나쁜 경우가 많다(Java 기본 직렬화가 대표적).

이런 이유로 언어 전용 인코딩은 일시적인 용도 외에는 쓰지 않는 게 좋다.

## 텍스트 기반 포맷의 한계

JSON, XML, CSV는 여러 언어에서 공통으로 쓸 수 있어 널리 쓰이지만 몇 가지 애매함이 있다.

- 숫자 인코딩이 모호하다. XML/CSV는 숫자와 숫자처럼 생긴 문자열을 구분 못 한다. JSON은 문자열과 숫자는 구분하지만 정수/부동소수점을 구분하지 않고 정밀도를 명시하지 않는다. 2^53보다 큰 정수는 JavaScript 같은 언어에서 부정확해질 수 있다.
- 바이너리 문자열을 기본 지원하지 않는다. Base64로 우회하는데 데이터 크기가 33% 늘어난다.
- 스키마가 선택적이다. 스키마 없이 쓰는 경우가 많아서 인코딩/디코딩 로직을 애플리케이션이 직접 하드코딩해야 한다.

이런 단점에도 불구하고 조직 간 데이터 교환처럼 "포맷에 대한 합의"가 중요한 상황에서는 여전히 JSON/XML/CSV가 실용적이다.

## 바이너리 인코딩

조직 내부에서만 쓰는 데이터라면 더 컴팩트하고 빠른 바이너리 포맷을 선택할 수 있다. MessagePack, BSON 같은 것들이 JSON 데이터 모델은 유지하면서 바이너리로 인코딩한 예시다. 다만 스키마를 강제하지 않는 한 필드 이름을 인코딩된 데이터 안에 계속 포함시켜야 해서 절감 폭이 크지 않다. 스키마 기반으로 필드 이름 대신 태그 번호만 쓰는 방식(protobuf-thrift-avro.md)이 이 문제를 해결한다.
