# 실시간 협업 편집 시스템 아키텍처

구글시트, 구글독스, Figma, Notion처럼 여러 사람이 동시에 같은 문서를 편집하는 시스템을 만들 때 필요한 구성 요소.

WebSocket은 이 시스템의 일부(전송 계층)일 뿐이고, 진짜 어려운 문제는 동시에 들어온 서로 다른 편집을 어떻게 병합해도 모두가 같은 결과를 보게 만드는가이다.

## 왜 단순 브로드캐스트로는 안 되는가

각 클라이언트의 편집을 그대로 다른 클라이언트에 전달하기만 하면, 동시에 발생한 편집끼리 순서가 뒤섞여 클라이언트마다 최종 문서 상태가 달라질 수 있다. 이 문제를 해결하는 게 이 아키텍처의 핵심이다. 풀이법은 크게 두 계열로 나뉜다 (operational-transformation.md, crdt.md 참고).

**OT**는 중앙 서버가 연산 순서를 조정하는 방식이다. 오프라인 편집에는 상대적으로 약하고, 서버 없이 P2P로 병합하기는 어렵다. 대신 메타데이터 오버헤드가 적다. 대표 사례는 구글독스 계열(알려진 바로는).

**CRDT**는 데이터 구조 자체가 병합을 보장하는 방식이다. 오프라인 편집에 강하고, 서버 없이 P2P 병합도 가능하다. 대신 tombstone 등으로 메타데이터 오버헤드가 크다. 대표 사례는 Figma, Notion, Yjs 기반 서비스.

## 시스템 구성 요소

**1. 전송 계층 — WebSocket**
각 클라이언트가 서버(또는 서로)와 지속 연결을 유지하며 편집 연산을 실시간으로 주고받는다. HTTP 폴링과 달리 서버가 능동적으로 변경을 push할 수 있다. 이 계층 자체는 충돌 해결과 무관하다 — 그냥 메시지를 빠르게 전달하는 파이프다.

**2. 로컬 낙관적 반영 (Optimistic UI)**
사용자가 타이핑할 때마다 서버 응답을 기다리면 입력이 버벅인다. 클라이언트는 자신의 편집을 즉시 로컬 화면에 반영하고, 서버로는 비동기로 전송한다. 나중에 서버에서 확정된 상태와 다르면 재조정(reconciliation)한다.

**3. 충돌 해결 — OT 또는 CRDT**
동시에 들어온 편집을 병합하는 핵심 로직. OT는 서버가 transform을 수행하며 순서를 중재하고, CRDT는 데이터 구조 자체가 병합을 보장한다.

**4. 영속화 (Persistence)**
편집 연산 스트림을 계속 재생하는 것만으로는 비효율적이므로, 주기적으로 스냅샷을 저장한다. 재접속한 클라이언트는 최신 스냅샷 + 이후 연산만 받아서 따라잡는다.

**5. 프레즌스 (Presence)**
누가 지금 접속해 있는지, 커서가 어디 있는지 같은 정보. 문서 상태와는 별개로, 휘발성이 강하고 최신 값만 중요하므로 별도의 가벼운 채널로 처리하는 경우가 많다.

**6. 재연결 및 동기화**
네트워크가 끊겼다가 복구되면, 클라이언트는 마지막으로 알고 있던 상태 버전을 서버에 보내고 그 이후의 diff만 받아온다. 전체 문서를 매번 다시 받지 않는다.

## 정리

WebSocket = 실시간 메시지 파이프 (전송 계층)
OT/CRDT = 동시 편집을 병합하는 알고리즘 (충돌 해결 계층)

이 둘은 서로 다른 계층의 문제이고, 실시간 협업 시스템을 만든다는 건 사실상 후자를 어떻게 설계하느냐의 문제다.
