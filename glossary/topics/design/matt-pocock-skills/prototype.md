# /prototype — 버리는 코드로 설계 검증

## 한 줄 요약

프로토타입은 질문에 답하기 위한 버리는 코드다. 질문이 뭔지가 형태를 결정한다.

---

## 언제 쓰나

- "이 상태 모델이 맞는 건지" 종이에서는 알 수 없을 때
- "이 페이지가 어떻게 보여야 하지" 머릿속에 여러 안이 있을 때
- API 설계 전에 인터페이스를 손으로 느껴보고 싶을 때
- 에지케이스가 실제로 어떻게 동작하는지 확인하고 싶을 때

---

## 두 가지 형태

질문이 뭔지에 따라 갈린다.

### 형태 A: 로직 프로토타입

질문: "이 상태 머신/비즈니스 로직이 맞게 느껴지나?"

결과물: 터미널 앱. 키보드로 상태를 직접 조작해서 결과를 확인한다.

구조:
- 순수한 로직 모듈 (입출력만, 터미널 코드 없음) — 나중에 실제 코드에 붙일 수 있음
- 얇은 TUI 셸 — 화면 지우고 상태 렌더링, 키보드 입력 받기, 다시 렌더링

렌더링 형식:
```
현재 상태 (굵게):
  userId: 123
  status: pending
  items: [...]

[a] 아이템 추가   [d] 삭제   [c] 체크아웃   [q] 종료
```

핵심 원칙:
- 로직 모듈과 TUI를 분리한다. 로직에 console.log가 들어가면 안 된다.
- TUI는 버리지만 로직 모듈은 실제 코드에 붙일 수 있다.

---

### 형태 B: UI 프로토타입

질문: "이 페이지가 어떻게 보여야 하나?"

결과물: 브라우저에서 플로팅 바로 변형(variant)을 전환할 수 있는 페이지.

구조:
- 기존 페이지에 `?variant=A/B/C` 파라미터로 다른 렌더링 (가능하면 이 방식)
- 기존 페이지가 없으면 새 임시 라우트 생성 (최후 수단)

플로팅 바:
- 화면 하단 중앙에 고정
- 왼쪽/오른쪽 화살표로 변형 전환
- 키보드 방향키도 지원
- 프로덕션 빌드에서 숨김 (NODE_ENV 체크)

변형 규칙:
- 3개가 기본. 5개 이상은 노이즈.
- 색만 다르면 안 된다. 레이아웃, 정보 계층, 주요 행동 유도 요소가 구조적으로 달라야 한다.

---

## 두 형태 공통 원칙

1. 버리는 코드임을 파일명에 표시한다. 이름에 "prototype"을 넣는다.

2. 명령어 하나로 실행한다. `pnpm prototype:order-flow` 같은 형태.

3. 영속성 없음. 상태는 메모리에만. DB가 필요하면 "PROTOTYPE - wipe me" 이름 붙인 스크래치 파일.

4. 폴리시 없음. 테스트 없음. 에러 핸들링 최소. 추상화 없음. 빨리 배우는 게 목적.

5. 사용 후 반드시 질문의 답을 기록한다. 커밋 메시지, ADR, NOTES.md 중 하나에.
   그다음 삭제하거나 실제 코드에 흡수시킨다. 썩도록 내버려 두지 않는다.

---

## 실제 활용 시나리오

```
나: /prototype 주문 상태 머신 설계 검토하고 싶어
    결제 완료 → 배송 준비 → 배송 중 → 배송 완료 흐름인데
    취소/환불이 어느 단계에서 가능한지 헷갈려

에이전트: 로직 프로토타입 만들게요.
         [상태 머신 TUI 생성]
         pnpm run prototype:order-flow 로 실행하세요.
         키보드로 직접 상태 전환해보세요.

나: (직접 조작)
    오, 배송 중에 취소하면 환불 상태가 빠졌네.
    여기 transition 하나 추가해야겠다.
```

---

## 안티패턴

- 프로토타입에 테스트 추가하기 — 프로토타입이 아님
- 실제 DB에 연결하기 — 질문이 DB가 아닌 이상 금지
- "나중에 쓸 수도 있으니" 일반화하기 — 하나의 질문에만 답한다
- 로직과 TUI 섞기 — 로직 모듈에 터미널 코드 들어가면 재사용 불가
- 프로토타입을 프로덕션에 그대로 올리기 — 반드시 다시 쓴다
