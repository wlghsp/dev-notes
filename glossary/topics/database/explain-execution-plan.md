# EXPLAIN과 실행 계획

쿼리를 실제로 실행하기 전에, DB 옵티마이저가 이 쿼리를 어떤 방식으로 처리할지 미리 보여주는 도구다. MySQL 콘솔에서 쿼리 앞에 `EXPLAIN`만 붙이면 실제 데이터를 읽지 않고 계획만 뽑아준다.

Hibernate/JPA를 쓰는 프로젝트라면, SQL 로그로 찍힌 실제 쿼리를 그대로 복사해서 MySQL 콘솔에 붙여넣고 `EXPLAIN`을 붙이면 된다 — 애플리케이션 코드를 거치지 않고도 그 쿼리가 인덱스를 타는지 바로 확인 가능하다.

## 풀 스캔인지 아닌지 판단하는 세 가지 컬럼

**`type`** — 이 쿼리가 테이블을 어떤 방식으로 접근하는지 나타낸다. `ALL`이면 테이블 전체를 처음부터 끝까지 훑는 풀 스캔이라는 �지. `ref`, `range`, `const` 등은 인덱스를 활용해서 필요한 행만 골라 읽는다는 뜻이라 `ALL`보다 낫다.

**`key`** — 실제로 사용된 인덱스 이름. `NULL`이면 옵티마이저가 어떤 인덱스도 고르지 않았다는 뜻이고, 이건 곧 풀 스캔으로 이어진다.

**`rows`** — 이 쿼리를 처리하기 위해 옵티마이저가 예상하는 스캔 행 수. 이 값이 테이블 전체 행 수에 가까우면(예: 전체 100만 건인데 rows도 90만대) 인덱스가 조건을 제대로 좁혀주지 못하고 있다는 신호다.

세 값을 같이 봐야 한다 — `key`가 `NULL`인데 `rows`가 테이블 전체 크기와 비슷하면 사실상 확정적으로 풀 스캔이다. 반대로 `key`가 특정 인덱스를 가리키더라도 `rows`가 여전히 크면, 인덱스는 타고 있지만 그 인덱스가 조건을 충분히 좁히지 못하고 있다는 뜻이라 인덱스 컬럼 순서(참고: composite-index-leftmost-prefix.md)를 다시 봐야 한다.

## 개선 전/후를 비교할 때 고정해야 하는 것

인덱스를 새로 걸기 전과 건 후의 EXPLAIN을 나란히 비교해서 효과를 증명하려면, 다음이 같아야 "같은 조건에서 비교했다"고 말할 수 있다.

- 같은 데이터 규모(시드 데이터 건수가 다르면 옵티마이저의 판단 자체가 달라진다)
- 같은 쿼리 파라미터(기간, 상태값, 최소 금액 등 조건 값)
- 같은 워밍업 상태(캐시가 덥혀진 상태인지 아닌지)

이 중 하나라도 다르면, `rows`나 `type`이 개선된 것처럼 보여도 그게 인덱스 덕분인지 조건이 달라진 결과인지 구분할 수 없다.
